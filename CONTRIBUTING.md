# Как участвовать в разработке kacho-iam

Спасибо за интерес к проекту. Этот документ описывает, как сообщить о проблеме,
подготовить изменение и провести его через ревью.

## Сообщить об ошибке или предложить улучшение

Все задачи ведутся в **GitHub Issues**:
`https://github.com/PRO-Robotech/kacho/issues`.

- **Баг** — приложите версию, шаги воспроизведения, ожидаемое и фактическое
  поведение, релевантные логи. Метка `bug`.
- **Улучшение / фича** — опишите задачу и зачем она нужна (какую проблему решает),
  до обсуждения дизайна. Метка `enhancement`.
- Перед заведением проверьте, нет ли уже похожего issue.

Об уязвимостях сообщайте приватно (GitHub Security Advisories), не через публичные Issues.

## Окружение

- Go 1.26+, Postgres 16+, Docker (для integration-тестов на testcontainers).
- Сборка и проверки:

```bash
make build          # bin/kacho-iam
make build-migrator # bin/kacho-migrator
make test-short     # быстрые тесты (моки)
make test           # полный прогон с integration (нужен Docker)
make vet
make lint
```

## Поток изменения

1. Заведите (или возьмите) issue и опишите в нем, что собираетесь делать.
2. Отведите ветку от актуального состояния основной ветки.
3. Внесите изменение **вместе с тестами** (см. ниже) и обновите документацию,
   если меняется поведение или контракт.
4. Подпишите коммиты (`git commit -s`) — это подтверждение соглашения о
   вкладе, см. раздел ниже. Коммит без подписи CI не пропустит.
5. Откройте Pull Request: в описании — что и зачем, ссылка на issue
   (`Closes #<n>`), как проверяли.
6. Пройдите ревью; CI (сборка, vet, lint, тесты) должен быть зеленым.

Сообщения коммитов — в формате **Conventional Commits**
(`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:` / `ci:`).

## Стандарты кода

- **Чистая архитектура.** Поток зависимостей: `handler → use-case → domain`;
  `repo` — адаптер, реализующий порты use-case'ов. Domain зависит только от stdlib
  и proto-типов. Бизнес-логика — в use-case'ах, не в handler'ах.
- **Без ORM.** Доступ к БД — handwritten pgx.
- **Инварианты — на уровне БД.** Ссылочная целостность и уникальность выражаются
  через FK / UNIQUE / CHECK, а не software-проверками «прочитал → проверил → записал».
- **AuthN/AuthZ везде.** Каждый RPC обоих листенеров (public `9090` и internal `9091`)
  проходит per-RPC авторизацию; internal-листенер не освобожден.
- **Ошибки** — стабильный контракт: корректные gRPC-коды и фиксированные тексты,
  без утечки внутренних деталей БД наружу.
- **Каждый файл** с исходным кодом, схемой, конфигом или скриптом начинается с
  хедера лицензии:

  ```
  Copyright (c) PRO-Robotech
  SPDX-License-Identifier: AGPL-3.0-or-later
  ```

- **Комментарии** объясняют, какую задачу решает код и как он работает, — кратко и
  по делу; форматирование — `gofmt`.

## Тесты

Изменение не принимается без тестов в том же PR:

- **unit** — use-case'ы и handler через mock-порты (`internal/.../*_test.go`), домен, конфиг;
- **integration** — для нового SQL/инварианта: testcontainers Postgres, включая
  конкурентные сценарии для FK/UNIQUE (`internal/repo/kacho/pg/*_integration_test.go` —
  файла с таким именем без префикса ресурса в каталоге нет, проб там больше сотни).

Тестируйте поведение, а не реализацию. Тесты, проверяющие отсутствие уже удаленного
поведения, в кодовой базе не держим.

## Соглашение о вкладе — подтверждается одной командой

Продукт распространяется под [AGPL-3.0-or-later](LICENSE). Отправляя изменение,
вы принимаете [соглашение о вкладе](CLA.md): авторские права остаются вашими, а
правообладатель получает право выдавать ваш вклад в том числе на условиях,
отличных от AGPL.

Подтверждается подписью коммита:

```bash
git commit -s          # добавляет строку Signed-off-by
git commit --amend -s  # если коммит уже сделан
```

Строка `Signed-off-by: Имя <адрес>` означает «я прочитал CLA.md и принимаю его
условия». Адрес в подписи обязан совпадать с адресом автора коммита: подписаться
за другого нельзя. Соавторы (`Co-authored-by`) подтверждают каждый за себя.

Проверить до отправки:

```bash
make -C services/iam cla-check
```

Если подпись коммита неприменима — например, соглашение подписывает юридическое
лицо, — личность вносится в `cla-ledger.yaml` с указанием, чем и когда оно
принято; см. [CLA.md](CLA.md) §5.
