# 33. Production Runbook

## Назначение

Реакция на типичные инциденты в production kaname. Каждая запись
включает: симптом → быстрая диагностика → действия → escalation.

Карта listener'ов (чтобы быстро ориентироваться в портах):

| Порт | Назначение |
|------|------------|
| `:9090` | публичный gRPC (tenant-facing, TLS/JWT) |
| `:9091` | internal gRPC (service→service, mTLS): `InternalIAMService.Check`, fgaproxy `RegisterResource`, cluster-admin, session-revocations |
| `:9095` | диагностика (cluster-internal): Prometheus `/metrics`, `/healthz`, `/readyz` |
| `:9096` | поверхность выдачи (внешняя): `/iam/token` докерного контура, токен-эндпоинт `/iam/v1/token`, `/iam/v1/authorize`, `/.well-known/oauth-authorization-server` |
| `:9097` | cluster-internal: публикатор набора ключей проверки (`authn.token-signing.key-set-path`) и авторитет отзыва |
| `:9100` | полоса входа (адрес объявляет профиль): взаимный TLS, вызывающий — только край |
| `:9098` / `:9099` | собственные REST-фронты, публичный и внутренний (адрес объявляет посадка; не объявлен — фронт не поднят) |

Готовность и живость — HTTP-пробы `/readyz` и `/healthz` на `:9095`; `/readyz` отражает
коннект к базе, версию схемы и поднятый LRO-worker.

Команды к `:9095` ниже записаны для production-профиля: слушатель поднят по TLS
(односторонний режим), поэтому `https` и `--no-check-certificate` — запрос не покидает под,
а корня внутреннего УЦ в хранилище образа нет. В образе службы есть `wget`, `curl` нет. На
стенде без транспорта слушателя — `http://127.0.0.1:9095`.

## P1 — Авторизация полностью не работает

**Симптомы:**
- API calls (через api-gateway) возвращают `UNAVAILABLE`/`PERMISSION_DENIED` массово.
- Postgres `kaname` недоступен или деградирует.

**Быстрая диагностика:**

```bash
# Pod alive?
kubectl -n kacho get pod -l app=kaname

# DB reachable? (от корня репозитория)
make -C deploy psql SVC=iam   # либо nc -zv <db-host> 5432

# fga_outbox: глубина журнала и его голова. «Непринятых» строк у него НЕ БЫВАЕТ:
# журнал читает триггер, складывающий прямой факт в той же транзакции, что и вставку.
kubectl -n kacho exec deploy/postgres -- \
  psql -c "SELECT count(*) AS rows, max(created_at) AS last FROM kaname.fga_outbox;"

# Логи последние 5min.
kubectl -n kacho logs -l app=kaname --since=5m | grep -E "ERROR|FATAL|authz|verdict"
```

**Действия:**

1. **DB down** → escalate DBA. Это **полный отказ авторизации**: вердикт
   складывается той же базой, поэтому недоступность `kaname` означает
   fail-closed по всем доменам, а не только по мутациям iam. Разбор и цена —
   [`../architecture/failure-domains.md`](../architecture/failure-domains.md).
2. **Реплика для чтения отстаёт** → вердикт читает master; проверить, не
   переключён ли пул на реплику.
3. **kaname OOM/crash** → `kubectl rollout restart deploy/kaname`;
   проверить memory limits.
4. **subject_change_outbox — НЕ очередь, и «backlog» по ней не считается.** Это
   журнал с курсором: строки не помечаются доставленными, поэтому «pending» по
   ним не определён. Отставание живёт **у читателя** (края), а не в таблице —
   см. раздел ниже.

   Строки при этом **снимаются** фоновой уборкой: журнал удерживается ровно
   столько, сколько читателю позволено отставать. Поэтому `count(*)` выходит на
   полку, а не растёт монотонно, и падение этого числа — норма, а не потеря.
   Величина удержания объявлена один раз, у самого читателя
   (`pkg/subjectchange`, `JournalRetention`); уборка идёт общей петлёй сервиса и
   печатает снятое по каждому предмету отдельно (`retention sweep removed rows`,
   `subject=subject_change_outbox`).

   **Что означает `subject-change position is no longer resumable` в журнале
   края.** Читатель отстал дальше удержания и ответил fail-closed: погасил кэш
   решений целиком и закрыл все открытые потоки. Отзыв при этом применён ШИРЕ
   нужного, а не потерян. В штатной работе такого не бывает — срок молчания,
   который край объявляет рабочим, обязан укладываться в удержание, и посадка,
   объявившая иначе, **не поднимается**. Значит запись означает одно из двух:
   читатель действительно отсутствовал дольше удержания (сеть, перекат владельца
   прав) либо удержание опустили. Ищите первое.

**Escalation:** SRE on-call → IAM team.

## P2 — выдача есть, доступа нет

> [!note] До стадии S6 этот раздел назывался «дренаж журнала отстаёт» — предмета нет
> Прежняя редакция описывала отставание вывоза строк журнала во внешний движок:
> «грант уже в базе iam, но кортеж ещё не записан в движок». Ни движка, ни вывоза
> не существует — прямой факт складывается **той же транзакцией**, что и выдача,
> поэтому состояние «выдано, но не применено» невыразимо by construction.
>
> Симптом при этом остался и приходит теперь из двух других мест. Раздел переписан
> под них.

**Симптом:** пользователь получил выдачу, а вызов по-прежнему отвергается.

### Причина 1 — отстал кэш края (частая, самоисправляющаяся)

api-gateway кэширует срез прав субъекта и **гасит этот кэш сам**: каждая его реплика
читает `kaname.subject_change_outbox` курсором по возрастанию `id` через
`InternalIAMService.PollSubjectChanges` с интервалом
`KACHO_API_GATEWAY_SUBJECT_CHANGE_POLL_INTERVAL` (умолчание `2s`). Пока опрос не
прошёл, край отвечает по старому срезу.

> [!important] Отставание живёт У ЧИТАТЕЛЯ, и в этой таблице его НЕ ВИДНО
> `subject_change_outbox` — журнал с курсором, а не очередь с доставкой: iam ничего
> в него не «отправляет». Колонок `sent_at` / `attempt_count` / `last_error` /
> `notified_at` в схеме **больше нет** — сняты миграцией
> `20260829181500_subject_change_journal_drops_the_delivery_columns.sql` (задача #1396)
> после того, как писателей не осталось. Выборка идёт по `id > since_id`.
>
> Это меняет и то, чем оканчивается ошибка процедуры. Прежняя редакция раздела
> предлагала считать отставание запросом `WHERE sent_at IS NULL` — при живой колонке он
> возвращал **весь журнал целиком** и показывал «растущее отставание» на совершенно
> исправной службе. Сегодня тот же запрос отвергается базой («колонки нет»), то есть
> ошибка процедуры стала видимой вместо того, чтобы давать правдоподобное число.
>
> Курсор каждая реплика края держит **в своей памяти**, поэтому со стороны iam
> «докуда дочитали» не видно вовсе. Отставание диагностируется на крае, а не здесь.

```bash
# Глубина журнала и его голова — это НЕ отставание, а точка отсчёта курсора.
kubectl -n kacho exec deploy/postgres -- psql -c "
SELECT count(*) AS rows_total, max(id) AS head_id, max(created_at) AS last_row
FROM kaname.subject_change_outbox;
"

# Строки по конкретному субъекту: намерение вообще записалось?
kubectl -n kacho exec deploy/postgres -- psql -c "
SELECT id, op, event_type, created_at
FROM kaname.subject_change_outbox
WHERE subject_id = '<subject_id>'
ORDER BY id DESC LIMIT 10;
"
```

**Действия:**

1. **Проверить, что дело в кэше** — спросить iam напрямую, минуя край:
   `AuthorizeService.Check` по внутреннему слушателю. Отвечает `allowed=true` —
   значит право есть и отстал именно кэш.
2. **Проверить, что строка записалась** — запрос по `subject_id` выше. Строки нет ⇒
   предмет не в сбросе кэша, а в производителе (use-case выдачи); идти в Причину 2.
3. **Строка есть, край не сходится дольше пары интервалов** — предмет на **крае**,
   не в iam. Смотреть там: доходит ли опрос до iam и не заклинил ли он.
   ```bash
   kubectl -n kacho logs -l app=api-gateway --since=10m | grep -iE "subject.?change|poll"
   ```
   Ребро открывает край; будить его со стороны iam **нечем и не нужно** — iam о
   крае не знает.
4. **Крайняя мера — перекатить край**, а не iam: `kubectl rollout restart
   deploy/api-gateway`. Реплика поднимется, возьмёт курсор по `head_id` и продолжит
   с головы журнала.

### Причина 2 — намерение не стало фактом (редкая, не самоисправляющаяся)

Право не появляется и при обращении мимо кэша. Тогда сверяются журнал и его
проекция:

```bash
kubectl -n kacho exec deploy/postgres -- psql -c "
-- намерение записано?
SELECT id, event_type, payload, created_at
  FROM kaname.fga_outbox
 WHERE payload::text LIKE '%<subject_id>%'
 ORDER BY id DESC LIMIT 10;
-- факт сложился?
SELECT * FROM kaname.relation_fact
 WHERE subject = 'user:<subject_id>' LIMIT 20;
"
```

| Что видно | Что это значит | Что делать |
|---|---|---|
| строки нет ни в журнале, ни в проекции | намерение не эмитировано | чинить производителя (use-case выдачи), не проекцию |
| строка в журнале есть, в проекции нет | дефект триггера проекции | escalate IAM team; предмет — миграция `0098_relation_fact_follows_the_journal.sql` |
| обе строки есть, доступа нет | вопрос не к факту: смотреть выдачу роли, метки, членство | разбор — `AuthorizeService.ExpandRelations` на этом ресурсе |

`ExpandRelations` отвечает **плоским перечнем оснований** — из чего право
складывается сейчас. Пустой перечень при живой выдаче означает, что план вывода
не связал роль с глаголом: сверять `role_verb` и модель прав.


## P2 — новый пользователь вошёл, но не видит свой Account/Project

Личные ресурсы человека — Account, Project и собственническую привязку — заводит сама служба,
и момент зависит от того, нёс ли адрес приглашение:

- адрес без приглашения — регистрация на полосе входа заводит личность (`ACTIVE`) и личные
  ресурсы одной транзакцией;
- адрес с приглашением — регистрация оставляет строку `PENDING`, а личность, личные ресурсы и
  членства в пригласивших аккаунтах активирует подтверждение адреса кодом из письма.

Пока адрес не подтверждён, сессия действует только для экранов подтверждения: прочие вызовы
отвергаются `EMAIL_NOT_VERIFIED`, и ни одно право человека не действует.

**Симптомы:**
- Человек вошёл, а консоль не показывает ни одного Account/Project либо вызовы отвергаются
  `EMAIL_NOT_VERIFIED`.
- Приглашённый подтвердил адрес, а аккаунта пригласившего у него нет.

**Диагностика:**

```bash
# Состояние личности: активна ли, подтверждён ли адрес, не истекло ли приглашение.
kubectl -n kacho exec deploy/postgres -- psql -c "
SELECT id, invite_status, email_verified_at IS NOT NULL AS verified, invite_expires_at, account_id
FROM kaname.users WHERE lower(email) = lower('<адрес>');
"

# Членства человека по аккаунтам.
kubectl -n kacho exec deploy/postgres -- psql -c "
SELECT account_id, state, invited_by, created_at FROM kaname.memberships
WHERE user_id = '<usr_id>' ORDER BY created_at;
"

# Исходы регистрации и подтверждения адреса.
kubectl -n kacho exec deploy/kaname -- wget -qO- --no-check-certificate https://127.0.0.1:9095/metrics \
  | grep -E 'kaname_(registration|address_verification)_outcomes_total'

# Пост-коммитная материализация собственнической привязки.
kubectl -n kacho logs -l app=kaname --since=30m | grep 'owner-binding reconcile failed'
```

**Действия:**

1. **`verified = false`, приглашения нет либо оно живо** → адрес не подтверждён, и это
   ожидаемое положение, а не сбой: человек запрашивает письмо с кодом и предъявляет код на
   полосе входа. Письмо не приходит —
   смотреть исходы `letter-queued` / `letter-paced` ряда
   `kaname_address_verification_outcomes_total`: `letter-paced` значит, что интервал либо
   предел писем за окно ещё не истёк.
2. **`invite_status = PENDING` и `invite_expires_at` в прошлом** либо исход `invite-not-valid`
   → приглашение истекло или снято до подтверждения: верный код отвергается
   `INVITE_NOT_VALID`, исход откатывается, и участником человек не становится. Лечится новым
   приглашением (`UserService.Invite` либо `MembershipService.Create`).
3. **Личность `ACTIVE`, членство есть, а прав нет** → в журнале `owner-binding reconcile
   failed (sweep will retry)`: материализация привязки после коммита не прошла. Исход
   регистрации и подтверждения она не гейтит — намерение лежит в очереди сверки той же
   транзакцией, и его доберёт фоновая сверка (страховка — периодический обход,
   `KANAME_RECONCILE_SWEEP_INTERVAL_MS`, умолчание 30 с). Не сошлось — раздел «P2 — выдача
   есть, доступа нет» выше.
4. **Строк человека нет вовсе** → регистрация не прошла: смотреть исход в
   `kaname_registration_outcomes_total` (`refused-occupied`, `refused-invite-expired`,
   `refused-rate`, `refused-source`, `store-failed`).

## P2 — 401 / `unknown kid` на всех JWT

**Издатель один — сама служба, и набор ключей проверки один.** Слушатель `:9097` отдаёт ровно
одну запись — набор ключницы iam по пути `authn.token-signing.key-set-path` (умолчание
`/.well-known/kaname/jwks.json`). Вторую запись публикатор отвергает при старте: набор другого
издателя рядом с нашим проверял бы токен, объявляющий другого.

Прежнее хранилище подписных ключей снято миграцией и не возвращается: приватную
половину не читал обратно никто, а запись в него удавалась — поэтому оно
выглядело исправным всю свою жизнь. Его отсутствие — норма, НЕ причина инцидента.
Отчёт о состоянии ключей снят с обслуживания вместе с ним (он отдавал пустой
набор и никем не звался).

**Симптомы:**
- api-gateway отдаёт 401 на все JWT; в логах валидации — `unknown kid` / signature mismatch.

**Диагностика:**

```bash
# 1. Что публикует iam (:9097)? Путь — значение authn.token-signing.key-set-path.
kubectl -n kacho exec deploy/kaname -- \
  wget -qO- --no-check-certificate https://127.0.0.1:9097/.well-known/kaname/jwks.json | jq '.keys[].kid'

# 2. Каким ключом подписан отвергнутый токен? kid — в заголовке самого токена.
printf '%s' "$TOKEN" | jq -rR 'split(".")[0] | gsub("-";"+") | gsub("_";"/") | @base64d | fromjson | .kid'

# 3. Отказ публикатора называет себя в журнале службы.
kubectl -n kacho logs -l app=kaname --since=30m | grep -E 'jwks: our key'
```

**Действия:**

1. **kid токена есть в наборе п.1, а gateway всё равно 401** → gateway кеширует
   JWKS; рестартнуть gateway-pod, чтобы сбросить кеш.
2. **Публикатор отвечает отказом (`502`)** → это fail-closed, и исходов два, намеренно
   различимых: `jwks: our key-set record could not be served` (`jwks_keyset_unavailable`) —
   источник не ответил, повтор осмыслен; `jwks: our key set is empty` (`jwks_keyset_empty`) —
   ключей нет вовсе, повтор не поможет, нужен ключ. Публикация идёт целиком либо никак:
   частичного набора не бывает, потому что набор с пропущенным ключом отвергает
   живые токены, ничем себя не выдавая.
3. **kid токена в наборе нет** → токен подписан ключом, которого набор уже либо ещё не
   публикует: снятым после компрометации (снимается немедленно), выведенным после отсрочки
   либо не нашим вовсе — издатель (`iss`) виден в самом токене. Для только что
   повернувшегося ключа — п.4.
4. **Токен нашего издателя отвергнут сразу после ротации** → проверить ПОРЯДОК:
   ключ обязан попасть в набор РАНЬШЕ, чем им подписан первый токен. Обратный
   порядок даёт громкий и мгновенный отказ у каждого потребителя. Тихое зеркало
   той же ошибки — снятие ключа, пока живы подписанные им токены: отказ приходит
   не сразу, а когда у потребителя истечёт кэш набора, то есть у разных
   потребителей в разное время и уже без связи с действием. Отсрочка снятия для
   того и вычисляется из срока токена и потолка чужого кэша, а не выбирается.
   Отказ токенам НОВОГО ключа в первые секунды после ротации (журнал `signing
   handed over to a new key`) — окно перезапроса набора, а не дефект порядка:
   потребитель, увидев неизвестный `kid`, перезапрашивает набор не чаще своего
   минимального интервала — kaname 1 с, gateway 3 с, registry 30 с
   (`tokenpolicy.UnknownKeyIDRefetchInterval`). Поэтому после каждой ротации —
   по сроку и командой — токены нового ключа могут отвергаться до 30 с; дольше —
   уже дефект.
5. **Ключ подписи утёк либо подлежит выводу** → команда оператора тем же
   образом и с той же настройкой, что служба (например, `kubectl exec` в под
   службы):

   ```bash
   kaname signing-key compromise -kid=<kid> -decided-by=<кто решил>   # утечка
   kaname signing-key retire     -kid=<kid> -decided-by=<кто решил>   # вывод
   ```

   `compromise` снимает ключ из набора НЕМЕДЛЕННО — подписанные им токены
   отвергаются, — и, если он подписывал, передаёт подпись новому ключу.
   `retire` передаёт подпись новому ключу, а выведенный оставляет в наборе на
   отсрочку. Исход печатается строкой `outcome=…` вместе с `replacement=<kid>`,
   когда подпись перешла в этом вызове — в том числе на повторе. Коды: `0`
   сделано (повтор — `already-done`), `1` отказ по существу, `3` вердикта нет.
   Когда замена, заводимая `compromise`, не легла, команда перечитывает
   подписывающего и отвечает по прочитанному. Подписывающий есть (его успела
   поставить реплика на старте либо второй оператор, или запись самой команды
   легла, хотя фиксация отказала) — исход без отказа, код `0`, и строка
   называет его `signer=<kid>`: служба подписывает этим ключом.
   `outcome=partial` у `compromise` значит: ключ снят, замена не заведена и
   подписывающего нет — это прочитано после отказа замены, служба не
   подписывает — повторите команду, повтор довершает замену и называет её.
   `outcome=signer-unknown` (код `3`) значит: ключ снят, а подписывает ли
   служба, не установлено (чтение подписывающего отказало либо истёк предел
   посреди замены) — повторите команду. Вся команда
   идёт под своим пределом в минуту: зависшая база даёт код `3` с причиной
   `предел команды … истёк` — вердикта нет, повтор безопасен (сделанное он
   называет `already-done`).
6. **Звонит `KanameSigningKeySweeperSilent`** → проходы обслуживания ключницы не
   завершаются: выведенные ключи стоят в наборе дольше отсрочки, а ротация до
   срока подписывающего (запас — четыре интервала прохода) тоже не идёт. Причина
   — в журнале процесса: `signing key sweep failed` / `signing key rotation
   failed`.
7. **В журнале `signing key generated for a hand-over that did not happen could
   not be retired`** → передачу подписи оборвал конец вызова (предел прохода,
   предел команды, остановка процесса), и вывести порождённый для неё ключ не
   удалось даже под его собственным пределом в 10 с. Ключ не подписывает, но
   стоит в наборе опубликованным. Действий не нужно: сметатель выводит
   опубликованный ключ старше `stranded_after` (4 мин — дважды предел передачи
   в 2 мин) первым же проходом после этого — журнал `signing key stranded before
   its hand-over retired by the sweeper`, — а снимает через отсрочку, как всякий
   выведенный. Тот же сметатель доделывает передачу, до которой процесс не
   дожил вовсе. Чинить — только если звонит `KanameSigningKeySweeperSilent`.

## P3 — Миграции не применились / pod не стартует

Схема — `kaname`, миграции — goose, прогоняются отдельным бинарем
`cmd/migrator` (`bin/kaname-migrator up`). Если схема отстает от кода — pod
падает на старте или RPC отдают неожиданные ошибки.

**Первым делом — КОД ВЫХОДА накатчика: он называет класс сам.**

```bash
kubectl -n kacho get pod -l app=kaname \
  -o jsonpath='{.items[*].status.initContainerStatuses[*].lastState.terminated.exitCode}{"\n"}'
```

| код | что это значит | что делать |
|---:|---|---|
| `0` | цепочка применена | ничего |
| `75` | базы на месте НЕТ (сеть, порт, сервер ещё стартует) — о миграциях не известно ничего | чинить базу, накат перезапустится сам |
| прочий ненулевой | накат отвергнут ПО СУЩЕСТВУ: адрес базы, негодный пароль, отсутствующая база, отказ миграции | читать последнюю строку журнала, она называет причину |

Различие не косметическое: `75` означает, что вердикта о схеме не существует, а
любой другой ненулевой — что вердикт есть и он отрицательный. Ждать `75` осмысленно,
ждать прочих — нет.

**Диагностика:**

```bash
# Лог старта — ошибки миграции/схемы.
kubectl -n kacho logs -l app=kaname --tail=200 | grep -iE "migrat|goose|schema|relation .* does not exist"

# Текущая версия goose.
kubectl -n kacho exec deploy/postgres -- \
  psql -c "SELECT version_id, is_applied, tstamp FROM kaname.goose_db_version ORDER BY id DESC LIMIT 5;"
```

**Действия:**

1. **Миграция упала на полпути** → разобрать причину по логам migrator; чинить
   **только новой** миграцией — применную миграцию не редактировать.
2. **Pod опередил миграцию** (rollout раньше migrator-job) → дождаться/перезапустить
   migrator-job, затем pod.
3. **Адрес базы не задан** (`database address "…" names no host`) → ожидание не
   сойдётся никогда: задать `db.host` в values, `--dsn` или `KACHO_MIGRATOR_DSN`.
   Накат отвечает на это ненулевым кодом, НЕ равным `75`, — то есть находкой.
4. Локально вне kind: `KANAME_DB_PASSWORD=<...> bin/kaname-migrator up`.

## Cluster-admin grants

Cluster-admin-привязки выдаются через internal-only `InternalClusterService`
(`:9091`, mTLS) — на публичном TLS их нет (запрет #6). Хранятся в
`kaname.cluster_admin_grants`: `granted_until IS NULL` — постоянный grant,
непустой `granted_until` — с истечением.

**Инвентаризация:**

```bash
# Текущие активные cluster-admin (denormalized snapshot).
grpcurl -d '{}' <mTLS-flags> kaname-internal:9091 \
  kaname.cloud.iam.v1.InternalClusterService/ListAdmins

# Либо напрямую в БД.
kubectl -n kacho exec deploy/postgres -- psql -c "
SELECT id, subject_id, granted_by, granted_at, granted_until
FROM kaname.cluster_admin_grants
ORDER BY granted_at DESC;
"
```

**Действия:**

1. Выдать cluster-admin → `InternalClusterService/GrantAdmin`
   (`subject_type=USER`, `subject_id=usr_...`). Возвращает `Operation` (async).
2. Отозвать → `InternalClusterService/RevokeAdmin`. Self-revoke и revoke
   последнего админа отвергаются (`FailedPrecondition`) — это защита от
   полной потери cluster-admin.
3. Все вызовы требуют verified client-cert (mTLS) и проходят in-handler
   проверка отношения + acr-floor; «достучаться без сертификата» по `:9091` нельзя.

## P3 — audit_outbox растёт: журнал аудита не вывозится

**Симптомы:**
- `kaname.audit_outbox` копит строки со `status='pending'`;
- `outbox_oldest_pending_age_seconds{table="kaname.audit_outbox"}` растёт по
  стенным часам вместо того, чтобы держаться ограниченным сверху.

**Что это значит.** Журнал аудита вывозится в поток структурных записей службы
(`pkg/audit`, вывоз поднят в композиционном корне). Растущий возраст головы
означает, что поток записей НЕ ПРИНИМАЕТ строки, а не что доставки не
предусмотрено.

**Действия:**

1. Прочитать причину прямо из строки: `SELECT last_error, attempts FROM
   kaname.audit_outbox WHERE status = 'pending' ORDER BY next_attempt_at
   LIMIT 5;` — вывоз записывает туда ответ приёмника.
2. Самая частая причина — **уровень потока службы поднят выше Info**: тогда
   приёмник отказывает с прямым текстом об этом. Лечится настройкой уровня и
   перекатом; строки дождутся, их не теряют.
3. Убедиться, что вывоз вообще поднят: в журнале службы есть записи компонента
   `audit_shipper`. Их отсутствие при растущей очереди — отказ старта, а не
   отсутствие механизма.
4. Подрезка вывезенных строк (`DELETE WHERE status='sent' AND created_at <
   now() - interval '30d'`) — операция обслуживания, а не починка: недоставленные
   строки не трогать.

## Утилитарные команды

```bash
# psql (от корня репозитория).
make -C deploy psql SVC=iam

# Tail logs.
kubectl -n kacho logs -l app=kaname -f --tail=200

# Состояние очередей. ВНИМАНИЕ: во второй колонке РАЗНЫЕ величины. У audit это
# непринятые строки; у fga и subject_change — ВЕСЬ УДЕРЖАННЫЙ журнал (пометки доставки
# у обоих нет: fga читает триггер в той же транзакции, subject_change читают курсором,
# «pending» по ним не определён, а строки снимает фоновая уборка по сроку — число
# выходит на полку, а не растёт монотонно).
kubectl -n kacho exec deploy/postgres -- psql -c "
SELECT 'fga (УДЕРЖАНО, журнал)'   AS q, count(*)                              AS n, max(created_at) AS last FROM kaname.fga_outbox
UNION ALL SELECT 'subject_change (УДЕРЖАНО, журнал)', count(*),                          max(created_at)       FROM kaname.subject_change_outbox
UNION ALL SELECT 'resource_reconcile (всего)',     count(*),                          max(created_at)       FROM kaname.resource_reconcile_outbox
UNION ALL SELECT 'audit (pending)',   count(*) FILTER (WHERE status='pending'),        max(created_at)       FROM kaname.audit_outbox;
"

# LRO in-flight (метрика на :9095).
kubectl -n kacho exec deploy/kaname -- wget -qO- --no-check-certificate https://127.0.0.1:9095/metrics | grep kaname_lro_inflight

# Решения authz (rate/итог) — деградация видна по росту deny.
kubectl -n kacho exec deploy/kaname -- wget -qO- --no-check-certificate https://127.0.0.1:9095/metrics | grep kaname_authz_check_decisions_total

# Graceful restart Deployment.
kubectl rollout restart deploy/kaname -n kacho
kubectl rollout status  deploy/kaname -n kacho --timeout=120s
```

## Запреты в инцидентах

- **НЕ delete'ить `operations` rows вручную** — потеря LRO/audit-следа.
- **НЕ редактировать примененную миграцию** — только новая миграция.
- **НЕ менять `permissions` system-роли** — id пересчитается, все
  AccessBinding'и со ссылкой на роль сломаются.
- **НЕ трогать `relation_fact` руками** — это проекция журнала, а не источник:
  правка переживёт до первой же перезаписи и разойдётся с журналом молча.
- **НЕ публиковать `Internal*`-сервисы на external endpoint** — cluster-admin /
  session-revocations / fgaproxy живут только на `:9091`.
