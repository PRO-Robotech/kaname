## Обзор и граница прежнего контракта

`GrantDelegationService.Update` добавляет разрешённые роли, типы целей и типы субъектов в уже действующее делегирование одного модуля. Существующие выдачи сохраняют свои идентификаторы, происхождение, содержимое и действующий доступ. Новая возможность сама ничего не выдаёт.

Это отдельная дельта к [приёмке #986](delegated-grants-stay-within-the-delegation.md), редакция 3, SHA-256 `7512fd96c7aeb85f352fd55954cfb881fa7c8610169574adb2291155bb690fe6`. Её §2 п.3, Р1 «Update нет» и В5 описывают прежний контракт; **после отдельного одобрения и реализации #1032** три оси-набора становятся только расширяемыми. Аккаунт и остальные неизменяемые свойства остаются фиксированы. Прежнее одобрение #986 не является одобрением Update. История и отпечаток прежней приёмки не переписываются.

Основание дельты — решение В5 от 26 октября, переданное в #1032: расширение в том же модуле, запрет удаления значений любой оси, сохранение прежних выдач. Настоящий документ не утверждает наличие реализации Update в исходной версии.

## Что НЕ входит

- Kachō, Terraform, actual svc-registry, оператор, установка потребителя, выдача его ключей и вызов его API. Слово `registry` ниже — уже существующий тестовый модуль Kaname.
- Новый механизм rolebind/escalate, правка правил ролей, перенос аккаунта или делегата, смена автора, права переделегировать, `Delete`, TTL/`expiresAt`, подписка.
- Атомарный перенос выдач между разными делегированиями, сохранение их ID при замене делегирования или обещание замены без перерыва доступа.
- Изменение `Create`, `Revoke` и обычных ограничений делегированной выдачи, кроме необходимых комментариев о появлении Update. Применённые миграции не редактируются.

## Контракт Update

### Вход, ответ и неизменяемые свойства

Метод: `kaname.cloud.iam.v1.GrantDelegationService.Update`; REST: `PATCH /iam/v1/grantDelegations/{grantDelegationId}`; тело `*`.

| Поле запроса (JSON) | Смысл |
|---|---|
| `grantDelegationId` (`grant_delegation_id`) | Обязательный ID существующего делегирования; адрес запроса, не новое значение ID |
| `roleIds` (`role_ids`) | Полный желаемый набор ролей выбранной оси, 1..16 |
| `targetTypes` (`target_types`) | Полный желаемый набор точечных типов выбранной оси, 1..16 |
| `subjectTypes` (`subject_types`) | Полный желаемый набор типов субъектов выбранной оси, 1..4 |
| `updateMask` (`update_mask`, `google.protobuf.FieldMask`) | Выбор осей; на JSON — строка, например `"roleIds,targetTypes"`; на gRPC paths — `role_ids`, `target_types`, `subject_types` |

У непустой маски применяются только названные оси; остальные остаются прежними. Названная ось без значения, `[]` или JSON `null` означает пустой набор и отвергается; это не сигнал «оставить как было». Пустая или отсутствующая маска означает полный PATCH всех трёх осей: отсутствие любой из них также отвергается. Маска не является дельтой добавлений. `*`, неизвестные поля, вложенные пути и поля вне трёх осей не дают дополнительного режима обновления.

Допустимы snake_case и camelCase написания известных путей маски; перед выбором осей они имеют одно каноническое значение. Повтор одного пути маски не меняет результат. Значения вне явно заданной маски не применяются. У выбранного набора порядок незначим, дубликаты отвергаются, а не молча удаляются. `Get`, `List`, `Operation.response` возвращают наборы в прежнем порядке #986: роли и цели по строке, субъекты по имени enum.

В запросе не вводятся поля `id`, `accountId`, `delegate`, `module`, `status`, `delegatedBy`, `createdAt`, `revokedAt`, `revokedBy`, `expiresAt`, etag/revision или requestId. Известные неизменяемые поля ресурса, названные в маске, отвергаются отдельно от неизвестного поля. Ни пустая маска, ни тело запроса не могут изменить их. Неизвестные ключи JSON не являются поддержанным входом Update; сервер не должен превращать их в изменение ресурса.

Успех возвращает `Operation` с непустым `id`, метаданными `UpdateGrantDelegationMetadata{grantDelegationId,accountId}`. Полл `OperationService.Get` до `done=true`: `error` отсутствует, `response` — `GrantDelegation` с тем же ID. `done` означает фиксацию ресурса; новых ожиданий материализации как условия завершения операции нет. Последующий `Get` и `List` согласны с результатом, если между ними не было другой разрешённой мутации.

### Полномочия и жизненный цикл

Мутация требует тот же уровень входа и то же право выдавать на аккаунте, что `Create`/`Revoke`: владелец аккаунта, администратор этого аккаунта либо администратор облака; `required_acr_min="2"`, `HANDLER_DECIDES`. Делегирование само по себе не даёт права на Update, даже собственного. Иной субъект с самостоятельным правом выдавать пользуется этим правом, а не делегированным путём.

`delegatedBy` остаётся первоначальным автором. Полномочия вызывающего Update не подменяют автора последующих выдач: каждая новая выдача по-прежнему проверяет актуальное право первоначального автора по Д3 #986. Потеря автором права не отзывает прежние выдачи и не превращает ACTIVE в новый статус. Для Update дополнительно требуется актуальное право первоначального автора: тот же существующий вопрос «вправе выдавать на аккаунте», без нового требования владеть каждой ролью или её действиями. Если вызывающий вправе править, но первоначальный автор потерял право, Update (включая no-op) отвергается как невыполненная предпосылка. Отказ в праве вызывающего остаётся PERMISSION_DENIED и предшествует этой проверке. Update не оживляет делегирование с неэффективным происхождением полномочий. Дополнительный общий проект rolebind/escalate для этого не вводится.

Обновляется только ACTIVE. REVOKED — конечное состояние; даже точный повтор осей не оживляет его. У делегирования нет срока и EXPIRED; истечение срока отдельной AccessBinding сохраняет прежнюю семантику, Update её не продлевает и не оживляет.

### Монотонность, атомарность и повтор

Для каждой выбранной оси `C` — текущий зафиксированный набор, `N` — полный набор запроса. Требуется `C ⊆ N`; равенство разрешено. Для неназванных осей итог равен текущему `C`. Все выбранные оси принимаются либо отвергаются вместе. Состав проверяется по тем же правилам, что Create: роли объявлены манифестом исходного модуля, все их правила относятся к нему, цели — живые точечные типы того же модуля, `iam` запрещён. Проверяется весь результирующий набор, не только разность; ранее выбывший из каталога тип не легализуется повтором.

Повтор уже применённого полного набора при неизменном состоянии успешен как no-op: результат тот же, выдачи не создаются и не меняются. Новый ID операции допустим; тождество операций не обещается. Для перестановки значений действует тот же no-op. Аудит изменения нужен только при фактическом расширении; повтор/no-op не создаёт второго события расширения. Отказ не оставляет успешного события расширения. Обычный журнал запроса и завершившаяся с ошибкой Operation допустимы.

Конкурирующие запросы оцениваются относительно состояния в точке собственной фиксации. Нельзя вернуть успех и потерять расширение успешно завершившегося запроса. У двух запросов по одной оси, основанных на одном старом наборе и добавляющих разные элементы, один фиксирует расширение, второй получает отказ сужения, если не содержит первый элемент. После чтения нового состояния клиент может послать объединение и получить успех. Маски на непересекающихся осях сохраняют оба расширения; одинаковые запросы оба успешны, второе применение — no-op. Конкретный внутренний механизм синхронизации приёмкой не задаётся.

Сбой до фиксации не оставляет частичных осей, новых/отозванных выдач или успешного аудита. Потеря ответа после фиксации разрешается `Get` и повтором: это не обещание отката уже зафиксированной операции. При гонке с Revoke возможен только порядок Update→Revoke либо Revoke→отказ Update; после успешного Revoke ни операция Update, ни её повтор не оживляют запись и выдачи.

### Коды и порядок отказов

После аутентификации: форма ID/маски/выбранных наборов → загрузка записи с прежним сокрытием существования → право вызывающего → ACTIVE → актуальное право первоначального автора → состав и монотонность. Проверки зависящего от состояния результата действуют также при фиксации. У авторизованного вызова дефект, известный до создания операции, возвращается синхронно; изменение состояния после приёма запроса возвращается в `Operation.error` с тем же кодом и текстом. Сценарии гонок ниже явно различают эти два момента.

| Условие | gRPC / REST | Текст / details |
|---|---|---|
| Пустой ID | `INVALID_ARGUMENT` / 400, code 3 | `grant_delegation_id: required`; BadRequest.field_violations: поле `grant_delegation_id`, description равна message |
| Неверная форма ID `bad` | `INVALID_ARGUMENT` / 400, code 3 | `invalid grant delegation id 'bad'`; без BadRequest, как #986 |
| Пустая выбранная ось F | `INVALID_ARGUMENT` / 400, code 3 | `F: required`; BadRequest.field_violations[0].field=F |
| Дубликаты/предел/неизвестный тип | `INVALID_ARGUMENT` / 400, code 3 | Дословные тексты Create из Р6 #986, с соответствующим snake_case полем; description=message |
| Маска неизвестного X | `INVALID_ARGUMENT` / 400, code 3 | `Illegal argument update_mask field "X"`; field=X |
| Маска неизменяемого X | `INVALID_ARGUMENT` / 400, code 3 | `<camelCase X> is immutable after GrantDelegation.Create`; field=написание X в маске |
| Нет записи либо нет права | `PERMISSION_DENIED` / 403, code 7 | `permission denied`, без BadRequest; тела побайтово одинаковы |
| Хранилище прав недоступно | `UNAVAILABLE` / 503, code 14 | `authz backend unavailable`; отказ закрытый |
| Первоначальный автор потерял право при уполномоченном вызывающем | `FAILED_PRECONDITION` / 400, code 9 | **Новый текст:** `grant delegation <id>: delegator no longer has grant authority`; без BadRequest |
| REVOKED | `FAILED_PRECONDITION` / 400, code 9 | `grant delegation <id> is already revoked` |
| Удалено значение выбранной оси F | `FAILED_PRECONDITION` / 400, code 9 | **Новый текст:** `grant delegation <id>: <F> may only expand`; без BadRequest |
| Роль не существует/не модульная/роли и цели разных модулей | `FAILED_PRECONDITION` / 400, code 9 | Тексты Create из Р6 #986: `Role <id> not found`; `role <id> is not declared by a module manifest`; `role_ids and target_types must belong to one module; found <модули по возрастанию>` |
| Итог целиком на ином модуле при попытке заменить оси | `FAILED_PRECONDITION` / 400, code 9 | **Новый текст:** `grant delegation <id>: module is immutable after GrantDelegation.Create` |

При нескольких одновременно неверных осях первым называется `role_ids`, затем `target_types`, затем `subject_types`; весь запрос отвергнут. При валидной форме, но одновременно неверном составе и сужении, сначала проверяется принадлежность исходному модулю, затем монотонность. Синхронный отказ не отдаёт ID операции. Наличие строки делегирования нельзя узнать по разнице отсутствия и отказа права. Неполадка проверки прав не заменяется PERMISSION_DENIED. Отказы нижнего слоя используют существующий маппинг Kaname; новый произвольный код для конфликта не вводится.

## Мир проб и обозначения

Каждый независимый сценарий получает свою чистую копию мира `newGDWorld`; это существующий мир интеграционных проб Kaname, а не действующий потребитель. Из него берутся реальные выданные ID:

- `A` — acc-A, `U` — владелец A, `E` — администратор A, `C` — администратор облака; `O` — человек без права выдавать в A.
- `D` — обычная служебная учётка-делегат без самостоятельного права выдавать; `S` — отличная от D учётка в A; `S2` — отдельная учётка `svaA2` мира GD в A, без B0 и иных путей доступа к Y; `M` — отличная от S/S2/D учётка `svaA3` мира GD в A. `G` — отдельная новая группа A с единственным участником M, без D, заведённая обычными Group.Create и Group.AddMember от U до выдач. `P` — проект A. У M нет иных путей доступа к X/Y. Состав G прочитан обратно; отсутствие доступа S2/M подтверждено effective Check, а не только отсутствием прямого binding.
- `r1`, `r2`, `r3` — ID доставленных `registry.puller`, `registry.pusher`, `registry.admin`; `t1="registry.registries"`, `t2="registry.repositories"`.
- `X` — зарегистрированный реестр в P; `Y` — его зарегистрированный репозиторий. `rX` и `tX="vpc.addressPool"` — существующие роль и тип другого тестового модуля.
- `s1="SUBJECT_TYPE_SERVICE_ACCOUNT"`, `s2="SUBJECT_TYPE_GROUP"`, `s3="SUBJECT_TYPE_USER"`, `s4="SUBJECT_TYPE_SYSTEM_CLASS"`.
- `D0` создаётся через Create от U: `accountId=A, delegate={type:s1,id:D}, roleIds=[r1], targetTypes=[t1], subjectTypes=[s1]`; ID результата — `d`.
- `B0` создаётся от D через AccessBinding.Create: `subjects=[{type:s1,id:S}], roleId=r1, scopeType="iam.project", scopeId=P, target={resources:{resources:[{type:t1,id:X}]}}`. Дождаться успешной операции, проверить `delegationId=d`, затем фактическое `v_get(S,X)=true`. Перед этим у S на X должно быть false; альтернативных путей доступа для S нет.

`PATCH(d, mask, ...)` ниже всегда означает указанный полный RPC/REST Update, `grantDelegationId=d`, `updateMask=mask` и перечисленные поля. Символы заменяются **ID из посева**, не именами или псевдо-ID. Каждый успешный PATCH включает полл Operation и чтение Get/List по контракту выше.

**Инвариант сохранения I:** поля D0 вне применяемых осей побайтово/по protobuf равны снимку до запроса; все старые AccessBinding сохраняют ID, роль, субъектов, scope, target, delegationId, status, сроки, защиту и атрибуцию; фактический доступ S к X остаётся true после запроса и после прохода штатного согласования. Наличие строки само по себе I не доказывает. У отказа все три оси также равны снимку; новых выдач и событий успешного расширения нет. Сравнение дат и отзыва не включает независимые специально вызванные в сценарии изменения.

## Сценарии

### GDU-01 — расширение одной оси, три независимые пары

**Given** D0, B0 и I; U аутентифицирован на уровне 2; каждая строка исполняется на отдельной копии мира. Тела выдач ниже — полные `AccessBindingService.Create` от D, идентификаторы взяты из посева; отрицательный и положительный вызовы используют **побайтово одно тело**:

| Ветка | Полное тело выдачи | Отличимый эффективный результат |
|---|---|---|
| a, новая роль | `subjects=[{type:s1,id:S}], roleId=r2, scopeType="iam.project", scopeId=P, target={resources:{resources:[{type:t1,id:X}]}}` | `v_update(S,Y)`: r1 даёт дочернему Y только get/list, r2 дополнительно update |
| b, новый тип цели | `subjects=[{type:s1,id:S2}], roleId=r1, scopeType="iam.project", scopeId=P, target={resources:{resources:[{type:t2,id:Y}]}}` | `v_get(S2,Y)`: S2 не получал B0 и не имеет альтернативного доступа |
| c, новый тип субъекта | `subjects=[{type:s2,id:G}], roleId=r1, scopeType="iam.project", scopeId=P, target={resources:{resources:[{type:t1,id:X}]}}` | `v_get(M,X)`: проверяется реальный единственный член G без альтернативного доступа |

**When** до PATCH выполняется соответствующий effective Check, затем D отправляет указанное тело выдачи.
**Then** Check=false; Create синхронно PERMISSION_DENIED `permission denied`, без новой выдачи: нарушена только выбранная ось — соответственно r2, t2 или s2; прочие оси, принадлежность, состав и полномочия удовлетворены.
**When** U вызывает соответственно (a) `PATCH(d,"roleIds",roleIds=[r1,r2])`; (b) `PATCH(d,"targetTypes",targetTypes=[t1,t2])`; (c) `PATCH(d,"subjectTypes",subjectTypes=[s1,s2])`.
**Then** каждая операция успешна, расширена ровно выбранная ось, I выполняется. **До новой выдачи** тот же effective Check всё ещё false: PATCH сам прав не выдал.
**When** D повторяет точное тело выдачи соответствующей строки, операция успешна и штатное согласование завершено.
**Then** тот же effective Check становится true; новая AccessBinding несёт delegationId=d. Для b предъявитель Check — S2, не S/U/C; для c — M, не группа как абстрактный субъект и не администратор. Отдельно S/B0 всё время сохраняют `v_get(S,X)=true` и I до PATCH, после PATCH, после новой выдачи и согласования.
**Близнец** каждого отказа Create — тот же запрос после PATCH; изменилось только наличие r2/t2/s2 в соответствующей оси. Чтение Y исходным S не доказывает ветку b: оно уже могло прийти через B0 на родительский X.

### GDU-02 — три оси в одном запросе и независимость границ

**Given** D0, B0, U.
**When** `PATCH(d,"roleIds,targetTypes,subjectTypes",roleIds=[r1,r2],targetTypes=[t1,t2],subjectTypes=[s1,s2])`.
**Then** успех, Get/List содержат именно эти три набора, I выполняется; D выдаёт r2 на Y группе G. До PATCH и после PATCH до выдачи `v_update(M,Y)=false`; после успешной выдачи и согласования `v_update(M,Y)=true`, предъявитель M — реальный член G без иных прав.
**And** на трёх отдельных копиях перед запросом выдачи отсутствует ровно одно из значений r2/t2/s2: соответственно выдача запрещена `PERMISSION_DENIED`, `permission denied`; её положительный близнец — полная тройка. Другие ограничения Д3–Д7 #986 действуют.

### GDU-03 — удаление и смешанное добавление/удаление

**Given** D0 предварительно расширено до `[r1,r2]`, `[t1,t2]`, `[s1,s2]`; B0 действует.
**When** на отдельных копиях: `PATCH(d,"roleIds",roleIds=[r2])`; `PATCH(d,"targetTypes",targetTypes=[t2])`; `PATCH(d,"subjectTypes",subjectTypes=[s2])`; `PATCH(d,"roleIds",roleIds=[r2,r3])`; смешанный запрос `PATCH(d,"roleIds,subjectTypes",roleIds=[r1,r2,r3],subjectTypes=[s2])`.
**Then** синхронно FAILED_PRECONDITION с текстом расширения соответствующей оси; в последней строке `subject_types`. Ни одна ось не меняется, I выполняется.
**Близнецы:** добавить обратно единственное пропущенное r1/t1/s1 в соответствующем запросе — успех (включая no-op); последняя строка с `[s1,s2]` успешно добавляет r3.

### GDU-04 — пустое, отсутствие и полная маска

**Given** D0 и B0.
**When** для каждой оси F: выбранная F равна `[]`, `null` либо отсутствует; отдельно маска отсутствует/пуста и в полном теле отсутствует ровно F; отдельно запрос без маски и без трёх осей.
**Then** INVALID_ARGUMENT, `F: required`, соответствующее поле BadRequest; без мутации, I. У последнего запроса F=`role_ids`.
**Близнец** каждой строки — вернуть текущий непустой набор F (в последней — все три): успешный no-op. Полный запрос без маски с тремя надмножествами успешен как GDU-02. Непустая маска одной оси с отсутствием двух остальных успешна как GDU-01.

### GDU-05 — повторы, порядок и границы наборов

**Given** D0 расширено до трёх ролей и трёх типов субъектов; B0 действует.
**When** посланы те же множества с переставленными ≥3 элементами и повторены дословно.
**Then** успешный no-op, I; Get/List/response нормализованы, число событий расширения не увеличилось.
**When** на отдельных копиях в выбранной оси повторён один элемент.
**Then** INVALID_ARGUMENT с текстом Create о повторе и соответствующим полем; I. **Близнец:** убрать только второй экземпляр — успешный no-op.
**And** отдельно для ролей и целей посевом доставлены 17 разных значений одного тестового модуля: набор из 16 принимается, тот же набор плюс 17-е отвергается `at most 16 roles/types`. Для субъектов все четыре значения принимаются; UNSPECIFIED/неизвестное enum-значение вместо одного из четырёх отвергается. Пятый различный допустимый тип невозможен и не выдумывается.

### GDU-06 — неизвестные значения, wildcard и состав модуля

**Given** D0, B0 и U; каждый вариант — отдельная копия.
**When** к roleIds добавлено: (a) отсутствующее значение `rol00000000000000000`, (b) существующая немодульная роль, (c) rX. Либо к targetTypes добавлено (d) `registry.*`, (e) `registry.missing`, (f) снятый с живого каталога тип, (g) tX. Либо к subjectTypes добавлено (h) UNSPECIFIED/неизвестное enum-число.
**Then** (a,b,c,g) FAILED_PRECONDITION по таблице, (d,e,f,h) INVALID_ARGUMENT по Create; весь запрос без изменений, I. Существование rX/tX предварительно подтверждено посевом, поэтому cross-module не подменяется отсутствием.
**Близнецы:** в каждой строке заменить только неверное добавляемое значение соответственно r2/t2/s2 — успех GDU-01. `"*"` как добавляемый roleId — отсутствующая роль, FAILED_PRECONDITION `Role * not found`, а не wildcard. Пробелы/регистр в значении не нормализуются в другой каталоговый ключ.
**And** no-op выбранной оси с ранее живым, теперь снятым типом отвергается тем же INVALID_ARGUMENT; положительный близнец — тип снова жив при неизменном запросе. Отдельная строка: в сохранённом targetTypes есть ранее живой t2, теперь снятый из живого каталога, а запрос выбирает **только** `PATCH(d,"roleIds",roleIds=[r1,r2])`. Результат INVALID_ARGUMENT с прежним текстом Create о неживом `target_types[] "registry.repositories"` и field=`target_types`; roleIds и остальные поля не меняются. Контроль меняет только живость t2 на true, тело PATCH неизменно — успех. Проверки доступа сравниваются со снимком **после** изменения каталога: сам Update не отвечает за независимые последствия снятия типа.
**And** попытка целиком заменить роли/цели на согласованные значения другого модуля отвергается ошибкой неизменяемого module; близнец — полные наборы исходного модуля. Добавление роли `iam` отвергается как иной модуль. При проверке составной роли каждое её правило также принадлежит исходному модулю. Отдельный тест двойника порта роли с чужим правилом держит этот предикат; такой объект не объявляется достижимым через обычный загрузчик манифеста и не подменяет интеграционную пару существующих r2/rX.

### GDU-07 — маска не меняет идентичность и автора

**Given** D0, B0.
**When** маска называет по отдельности `id`, `account_id/accountId`, `delegate`, `module`, `status`, `delegated_by/delegatedBy`, `created_at/createdAt`, `revoked_at/revokedAt`, `revoked_by/revokedBy`; либо неизвестное `expiresAt`, `bogus`, `*`, `roleIds.child`.
**Then** INVALID_ARGUMENT с точным текстом таблицы, I. **Близнец:** сменить только путь маски на `roleIds` с `[r1,r2]` — успех.
**And** `role_ids` и `roleIds` в gRPC paths дают один результат; JSON `updateMask="roleIds"` даёт тот же результат. Повтор пути в gRPC не дублирует изменение. Значение другой оси в теле вне маски не меняет эту ось; отдельный контроль с включением этой оси в маску меняет её.

### GDU-08 — право вызывающего и сокрытие существования

**Given** D0, B0; исходный автор U держит право.
**When** одинаковый PATCH из GDU-01a по отдельности отправляют U, E и C.
**Then** каждый успешен, I; `delegatedBy` во всех случаях остаётся U.
**When** тот же запрос отправляет O либо D без самостоятельного права.
**Then** PERMISSION_DENIED `permission denied`, I. **Близнец** — тот же субъект с отдельно полученным правом администратора A; появляется ровно право, запрос успешен.
**And** отдельная матрица при авторе E: actor O без права + E без права → PERMISSION_DENIED `permission denied`; O без права + E с правом → тот же PERMISSION_DENIED; O с отдельным правом admin + E без права → FAILED_PRECONDITION `grant delegation <d>: delegator no longer has grant authority`; оба с правом → успех. Между соседними контролями меняется только право указанного субъекта. Так отрицание actor не раскрывает creator-precondition; положительные пары actor и creator используют соответственно сохранённое право E и сохранённое право O.
**When** U отправляет тот же запрос с синтаксически годным отсутствующим ID `gdl00000000000000000`.
**Then** PERMISSION_DENIED `permission denied`, тело побайтово как отказ O; существующий d — положительный близнец.

### GDU-09 — личность, уровень входа и неверный ID

**Given** успешный вызов U уровня 2, D0, B0.
**When** тот же запрос проходит собственную дверь Kaname без аутентификации либо с уровнем 1 вместо 2.
**Then** на собственном публичном пути без удостоверения — UNAUTHENTICATED / HTTP 401, code 16, `no credential presented; authenticate with authorization: Bearer <token>`; проверенное человеческое удостоверение уровня 1 — UNAUTHENTICATED / HTTP 401, code 16, `authentication level is insufficient: step up with a second factor, or present a credential of another kind`. Для уровня 1 заголовок WWW-Authenticate: `Bearer error="insufficient_user_authentication", error_description="Required ACR 2 for this resource; presented ACR 1", acr_values="2"`; на gRPC тот же challenge в `kaname-step-up-challenge`. Обработчик не изменяет ресурс, I; положительный близнец — тот же человек уровня 2. Существующее освобождение проверенного машинного принципала от интерактивного ACR сохраняется: оно не заменяет право на Update. Прямой вызов use-case без принципала отдельно даёт прежний PERMISSION_DENIED `permission denied`; это другая полоса, не альтернативный статус публичного запроса.
**When** аутентифицированный U подаёт пустой grantDelegationId либо `bad`.
**Then** точные INVALID_ARGUMENT из таблицы, без операции; близнец d успешен. Форма судится и у субъекта без права, до сокрытия существования.

### GDU-10 — первоначальный автор потерял право

**Given** D0 создал E; B0 уже дал S чтение X; право E отозвано штатным Revoke выдачи admin, факт утраты подтверждён; U остаётся владельцем A.
**When** U пытается расширить roleIds до `[r1,r2]`.
**Then** синхронно FAILED_PRECONDITION `grant delegation <d>: delegator no longer has grant authority`; `delegatedBy=E`, все оси и B0 с его действующим доступом сохранены. No-op получает тот же отказ. D не может создать новую выдачу r1: PERMISSION_DENIED `permission denied`.
**Близнец:** E вновь получил то же самостоятельное право admin; тот же PATCH U успешен, delegatedBy остаётся E, и новая выдача r2 от D успешна. Если проверку права автора невозможно выполнить, ответ UNAVAILABLE `authz backend unavailable`, а не FAILED_PRECONDITION; контроль — восстановлена только доступность проверки. При потере права автором после приёма, до фиксации Update, повторная проверка завершает Operation.error тем же FAILED_PRECONDITION без изменения осей. Update не заменяет проверку автора на каждой последующей выдаче и не переносит её на U.

### GDU-11 — отозванная запись и истёкшие выдачи

**Given** D0 и B0; на одной копии Revoke(d) завершён, на другой D0 ACTIVE, но отдельная выдача Bexp уже истекла и перестала давать доступ.
**When** одинаковый PATCH из GDU-01a.
**Then** REVOKED: FAILED_PRECONDITION `grant delegation <d> is already revoked`; та же ошибка на no-op; ничего не оживает. **Близнец** — до отзыва D0, PATCH успешен.
**And** ACTIVE с Bexp: успех; Bexp сохраняет срок/состояние отзыва и по-прежнему не даёт доступ. **Близнец** Bexp — тот же исходный срок ещё не достигнут, доступ до/после PATCH разрешён. Проход срока строится существующим ExpireBinding по образцу URG-34: после штатного Create изолированный посев ставит срок в прошлое, затем вызывает штатное истечение; близнецу ставится будущий срок. Нет ожидания настенных секунд.

### GDU-12 — недоступная зависимость и атомарный отказ

**Given** D0, B0 и успешный многомерный запрос GDU-02.
**When** (a) вопрос права нельзя выполнить, либо (b) запись расширения не может завершиться до фиксации.
**Then** (a) UNAVAILABLE `authz backend unavailable`, синхронно; (b) Operation завершается ошибкой штатного маппинга Kaname; ни одной частично новой оси, новой/отозванной выдачи или успешного события расширения; I. Производитель испытания заранее выбирает конкретный отказ (для недоступной записи — UNAVAILABLE `service unavailable`), не принимает произвольный набор кодов.
**Близнец:** убрана только управляемая неисправность, тот же запрос успешен. Потеря ответа после успешной фиксации отдельно проверяется чтением и безопасным повтором GDU-05.

### GDU-13 — конкурирующие изменения одной оси

**Given** D0, B0; два принятых запроса от U основаны на `[r1]`: A=`[r1,r2]`, B=`[r1,r3]`, маска `roleIds`; фиксация A управляемо предшествует B.
**When** исполняются обе операции.
**Then** A успешна; B завершается Operation.error FAILED_PRECONDITION `grant delegation <d>: role_ids may only expand`; Get содержит `[r1,r2]`, не `[r1,r3]`; I. **Близнец B:** единственная правка его тела на `[r1,r2,r3]` даёт успех, оба добавления сохранены. Симметричная постановка с первым B проверяет другой порядок.
**And** запрос B, поступивший уже после завершения A, получает тот же отказ синхронно. Слепое объединение сужающего входа в успех недопустимо.

### GDU-14 — независимые оси и одинаковые повторы конкурентно

**Given** D0, B0.
**When** конкурентно отправлены roleIds=`[r1,r2]` с маской roleIds и targetTypes=`[t1,t2]` с маской targetTypes.
**Then** обе операции успешны, Get сохраняет обе оси; I. При третьем запросе subjectTypes=`[s1,s2]` сохраняются все три. Это положительный близнец GDU-13 по факту пересечения изменяемых осей.
**When** на чистой копии два одинаковых запроса GDU-02 конкурируют.
**Then** оба успешны, конечные наборы как GDU-02, одно событие фактического расширения, ни одной новой выдачи.

### GDU-15 — Update одновременно с выдачей и отзывом

**Given** D0, B0 и принимаемый PATCH GDU-01a.
**When** выдача по старой разрешённой комбинации проходит до либо после фиксации PATCH.
**Then** выдача допустима в обоих порядках; доступ B0 не теряется. Новая роль r2 до фиксации ещё не разрешена, после фиксации разрешена; запросы различаются только порядком относительно фиксации.
**When** Revoke(d) фиксируется первым после приёма PATCH, но до его фиксации.
**Then** PATCH завершается Operation.error FAILED_PRECONDITION с текстом REVOKED; делегирование и все его выдачи остаются отозванными. **Близнец:** сначала успешный PATCH, затем Revoke — обе операции успешны, конечный результат тот же REVOKED, доступа нет. Повтор PATCH после Revoke синхронно отвергается.

### GDU-16 — аудит расширения и отсутствие выдачи по инициативе Update

**Given** D0, B0; U расширяет все оси как GDU-02.
**When** операция завершена.
**Then** одно событие `iam.grant_delegation.updated`: actor=вызывающий U, delegation_id=d, account_id=A, tenant_account_id=A, before/after содержат нормализованные три набора; первоначальный delegatedBy ресурса не меняется. Событие относится к той же успешной фиксации. События выдачи или отзыва AccessBinding от самого Update отсутствуют.
**Близнецы:** GDU-05 no-op и GDU-03 отказ не оставляют такого события; успешное расширение единственного значения оставляет ровно одно. Проверка внутреннего аудита — интеграционная: публичный RPC чтения аудита не добавляется.

### GDU-17 — сужение через замену: порядок без нового API переноса

**Given** D0 расширено до `[r1,r2]`, `[t1,t2]`, `[s1,s2]`; есть выдачи r1 и r2, включая защищённую от удаления. Требуется оставить только r1/t1/s1 той же паре аккаунт–делегат.
**When** уполномоченный U сохраняет список желаемых повторных выдач, завершает Revoke(d), убеждается в отказе старого доступа; затем Create для той же пары с `[r1]`, `[t1]`, `[s1]`, затем D создаёт разрешённые повторные выдачи по новой записи.
**Then** новая запись и повторные выдачи имеют новые ID; у каждой повторной выдачи delegationId равен новому ID, старые ссылки не переписаны. Старые выдачи REVOKED с DELEGATION_REVOKED, непустым revokedAt и остаются для аудита; разрешённый доступ возвращается только после новых выдач. Запрещённая комбинация r2 не переносится. Защита старой выдачи отзыву делегирования не мешает.
**Близнец порядка:** Create новой ACTIVE-записи той же пары до Revoke получает ALREADY_EXISTS в Operation.error по #986; после Revoke тот же Create успешен. Удалять старые REVOKED-выдачи перед повторной выдачей не требуется: после завершения Revoke они освобождают слот уникальности. Старые строки после Create новой записи остаются REVOKED и не оживают. Перенос означает повторную выдачу разрешённого набора, без автоматического обхода ограничений и без обещания непрерывного доступа.

## План собственного края и DoD

Стадия одна — общий Update Kaname вместе с приёмкой; потребитель не является стадией.

1. До продуктового кода — отдельное ревью этого отпечатка; актуальное внешнее событие ревью записывается отдельно. Старое одобрение #986 не переносится.
2. Proto/regen, обработчик, права, запись и атомарность реализуют все GDU-01…17. Прежние публичные комментарии об отсутствии Update согласованы с новой дельтой; история приёмки #986 не переписана. Миграция добавляется лишь при необходимости инварианта, старые не правятся.
3. Интеграционные пробы GDU-01…17 и их параметризованные близнецы: до кода зафиксирован RED по отсутствующему предмету, после кода GREEN на одной ревизии; выполнено ровно объявленное число подслучаев. Отдельно проверяются фактический доступ и согласование, а не только строки.
4. В существующем `tests/newman/cases/iam-grant-delegation.py` добавляются пары `IAM-GDU-EXPAND-ROLE-ALLOWED` / `IAM-GDU-NARROW-ROLE-DENIED`, `IAM-GDU-EXPAND-TARGET-ALLOWED` / `IAM-GDU-CROSS-MODULE-TARGET-DENIED`, `IAM-GDU-EXPAND-SUBJECT-ALLOWED` / `IAM-GDU-EMPTY-SUBJECT-DENIED`, `IAM-GDU-OWNER-UPDATE-ALLOWED` / `IAM-GDU-DELEGATE-UPDATE-DENIED`; отдельные `IAM-GDU-REPEAT-UNCHANGED` и `IAM-GDU-REVOKED-UPDATE-DENIED` с ACTIVE-контролем. Поля, маска и ожидания — GDU-01/03/04/06/08/11. `IAM-GDU-EXPAND-TARGET-ALLOWED` использует S2 и точное тело GDU-01b: false до PATCH, отказ выдачи, false после PATCH до выдачи, true после повторной выдачи. `IAM-GDU-EXPAND-ROLE-ALLOWED` доказывает v_update(S,Y); `IAM-GDU-EXPAND-SUBJECT-ALLOWED` — v_get(M,X) от реального члена G; у всех отдельный S/B0 держит I. После успешного PATCH обязательно читается старая выдача, затем **собственный** доступ её субъекта через API Kaname, не actual svc-registry. Край утверждает и HTTP, и gRPC code, ошибки и результат Operation, Get/List.
5. Пара «до обновления право было / после обновления осталось» не подменяется только Get AccessBinding: эффективный путь должен читать выдачу и полный механизм решения. Край использует существующий `POST /iam/v1/authorize:check`: предъявитель S, `subject="service_account:<S>", resource={type:"registry_registry",id:X}, action="registry.registries.get", requiredRelation="v_get"`; HTTP 200 и allowed=true до/после Update, allowed=false до создания B0. Для GDU-01b — предъявитель S2, `subject="service_account:<S2>", resource={type:"registry_repository",id:Y}, action="registry.repositories.get", requiredRelation="v_get"`. Для GDU-01a — предъявитель S, тот же Y, `action="registry.repositories.update", requiredRelation="v_update"`; для GDU-01c — предъявитель M, `subject="service_account:<M>"`, X и v_get. В GDU-02 M спрашивает v_update на Y. Все проверки возвращают HTTP 200 и точный allowed=false/true по сценарию, код ошибки не считается отрицательным effective verdict. Служебные удостоверения S/S2/M выдаются существующим посевом собственного стенда; токен U/C или другого субъекта вместо требуемого S/S2/M не считается самопроверкой доступа. Тип ResourceRef здесь словарь модели, в AccessBinding.target — точечный словарь каталога. Никакой новый наружный Check не нужен.
6. Весь затронутый набор домена доступа, включая старые GD-01…70 и GD-E1…E5/групповые близнецы #1011, выполняется с обеими сторонами на одном точном SHA. Именованный реальный маршрут края — `tests/newman/scripts/run.sh` → `iam-grant-delegation`; интеграционный дом — указанный пакет access_binding. Запись «access-domain suite» означает этот затронутый домен, не выдуманный исполняемый target.
7. Доказательства same-SHA, число исполненных/проваленных/неисполненных сценариев, сырые отчёты собственного края и CI прикладываются последующей полосой реализации. Этот draft не является runtime/CI/DoD-proof.
