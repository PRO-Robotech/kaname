# Приёмка #1045. Регистрация потомка по праву пользователя на родителе

**Статус DRAFT для ревью R2. Приоритет разработки подтверждён владельцем.**
**Основание приёмки** — [#1045](https://github.com/PRO-Robotech/kaname/issues/1045), решение владельца от 26 октября 2026 года и [уточнение об неизменяемости родителя](https://github.com/PRO-Robotech/kaname/issues/1045#issuecomment-6419339486).
**База сверки** — `e225cc5957d8a66a9a3e8c750555a7a08f4c10fa`. Коммиты вывода родителя `adc3087cc` и каскада `42fad14e7` входят в эту историю. [#982](https://github.com/PRO-Robotech/kaname/issues/982), [#1002](https://github.com/PRO-Robotech/kaname/issues/1002) и [#969](https://github.com/PRO-Robotech/kaname/issues/969) закрыты.
**Граница поставки** — пользовательская операция и сквозная приёмка Kaname. Пример вызывающего модуля работает в автономной фикстуре Kaname.

## Контракт

1. Манифест модуля включает механизм для конкретного типа потомка, типа родителя и отдельного глагола создания потомка на родителе. Выдача этого глагола использует действующий механизм ролей.
2. Kaname из канонического идентификатора потомка получает ключ родителя. Затем проверяет право аутентифицированного пользователя на этом ключе. Ветвления по существованию, состоянию или ёмкости родителя следуют после проверки права.
3. Из записи родителя Kaname выводит цепь и область по действующему контракту #982. Сохранённая связь потомка с родителем неизменяема. Закрытие родителя, решение о допуске и запись потомка согласованы при параллельных операциях.
4. Успешная регистрация создаёт только отношение `parent`. Kaname назначает версию записи. Аудит связывает создание с аутентифицированным пользователем. Право пользователя на открытый механизм распространяется на регистрацию. Снятие регистрации остаётся операцией с действующими полномочиями модуля.
5. Kaname проверяет грамматику имени, лимит числа потомков, темп создания и состояние родителя. Манифест задаёт границу идентификатора родителя, предел числа живых потомков и параметры темпа. Закрытие относится к текущей регистрации родителя и фиксируется в Kaname. Для всех отказов по правилам регистрации ожидается один публичный ответ с одинаковыми кодом, сообщением и деталями. Аудит различает внутренние причины отказов.
6. Снятие регистрации родителя использует существующий каскад. Версия записи защищает новый объект от запоздалого снятия по прежней версии.

Для параллельных случаев используются управляемые барьеры и наблюдаемые транзакционные исходы.

## Предлагаемый контракт для первой реализации

- Запрос содержит каталожный тип и канонический ID потомка. Грамматика включается явно для конкретного типа. ID состоит из непустых сегментов, разделённых символом `/`. Число сегментов родительского ключа фиксирует политика типа. Сегмент содержит строчную латиницу, цифры, точку, подчёркивание и дефис, начинается и заканчивается буквой или цифрой. Полный ключ каждого объекта в модели прав занимает не более 512 байт. Декодирование и нормализация пути не выполняются. Используемый ранее модульный вход сохраняет собственные правила ID, включая прежние формы с косой чертой.
- Ключ родителя вычисляется до чтения сведений о его зарегистрированности. После последнего ожидания блокировок право подтверждается по действующей модели, а родитель сверяется с той же регистрацией. Регистрация, закрытие и снятие родителя используют общее ограждение. Закрытие хранится как состояние текущей регистрации в Kaname.
- Модуль-владелец вызывает внутренний `CloseChildParent` с типом, ID и точной версией регистрации родителя. Допуск требует действующей установки модуля и права `fga_writer` в сохранённой области. Повтор для той же версии возвращает исходное `closed_at`. Несовпадение версии и отсутствие регистрации дают одинаковый отказ. Для удаления модуль отдельно вызывает штатный `UnregisterResource`.
- Ёмкость включает живых потомков того же типа, зарегистрированных обоими путями. Расход темпа относится к успешным новым созданиям данного типа под конкретной версией родителя. Предел и продолжительность окна задаются явной политикой. Отсчёт использует время решения PostgreSQL; при откате новые записи и расход откатываются вместе.
- Повтор допустимого запроса для уже созданного этим механизмом объекта с тем же родителем возвращает сохранённую версию после текущей проверки права и состояния родителя. Расход и аудит создания не удваиваются. Исчерпание ёмкости или темпа не меняет результат такого повтора. Наличие объекта, зарегистрированного внешним писателем, не разрешает перенос его родителя или смену владельца версии.
- Предметные отказы возвращают `PermissionDenied` с сообщением `permission denied` и без деталей. Причина сохраняется во внутреннем аудите. В ответе успешной операции нужна назначенная сервером версия.

## Доказательства для закрытия #1045

Утверждённый R2, точный SHA реализации и фактические результаты перечисленных сценариев в Kaname. Проверяются сквозной вход, транзакционная согласованность, версии, аудит, состояние до и после, включая оба порядка гонки с закрытием. Штатный хук и CI выполняются на указанной голове, после вливания подтверждается `main`. Результат публикуется в `DoD-proof @<sha>`.
