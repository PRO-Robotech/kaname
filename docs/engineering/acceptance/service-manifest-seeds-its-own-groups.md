## §0 Обзор

Право «писать кортежи владения через службу» — поверхность **самой службы**
(`RegisterResource` / `UnregisterResource`). Аудиторию этой возможности сегодня объявляет не
владелец возможности, а **свод**: группу `module-relation-writers`, её выдачу `fga_writer` на
кластере и пятерых её членов заводит применённая миграция `0001_initial.sql`. Манифест службы
раздела посева не имеет вовсе, а пять манифестов модулей платформы лишь **вступают** в группу
и в своих шапках утверждают, что «эти группы заводит платформа», — чего не делает никто.

Документ закрепляет семь вещей.

1. **Группу и её выдачу объявляет манифест службы** — тот же раздел `seed`, что у модулей, та
   же форма, тот же применитель, тот же валидатор связности.
2. **Манифест службы приезжает применителю ВСТРОЕННЫМ В ОБРАЗ, а не доставкой — и механизм
   назван вместе с его держателем.** Доставка собирается обходом дерева платформы, где службы
   больше нет ни одним файлом (§1.1), а копия её манифеста в чужом репозитории запрещена
   решением владельца (ban #20). Встраивание делается **второй копией в каталоге пакета**, и её
   побайтовое согласие с манифестом дерева держит цель сборки — та же цена и тот же приём, что
   у канона модели прав в этом же дереве (§2.6, Р2). Встроенность даёт и порядок: своё
   применяется **раньше** доставленного, поэтому вступление модуля находит группу заведённой.
3. **Манифест службы получает ОДИН потребитель из пяти, и по каждому названо почему.** Перечень
   доставки на пути старта читают пятеро (§2.7); подмешанный в него манифест достался бы всем
   разом — вплоть до второго писателя семи строк каталога и до раздела `roles:`, чей исход уже
   решён соседней APPROVED-приёмкой. Поэтому манифест едет применителю посева **отдельным
   доводом** (Р3).
4. **Форму субъекта FGA у получателя-ГРУППЫ применитель берёт У КАНОНА.** Получателем выдачи
   впервые становится группа, и канон принимает её только формой членства; писатель строк посева
   сегодня строит субъекта встроенным выражением, которое на группе с каноном расходится
   (§2.5). Форма берётся вызовом объявленного источника, а не третьей копией (Р1а).
5. **Идемпотентность выдачи держит ЕСТЕСТВЕННЫЙ КЛЮЧ живой строки, а не совпадение
   выведенного идентификатора.** Это измеренное опровержение предиката задачи: идентификатор
   живой строки `fga_writer` выведен тем же выражением, но при **прежнем написании якоря**, а
   якорь с тех пор переименован миграцией — и переименование идентификатора не касается. Значит
   выражение применителя даёт **другое** значение на каждой установке, включая чистую; вторая
   строка не «ложится поверх», а **отвергается** частичным уникальным индексом — применение
   обрывается и служба не поднимается (§2.2).
6. **`module-quota-readers` снимается целиком** — вступления из пяти манифестов платформы,
   строка группы из базы службы и её членства, **сколько их записал применитель** по `joins`
   доставленных манифестов (из свода после миграций их **ноль**, §1.3), кортежи членства через
   журнал прав, со следом аудита. Её выдачу `quota_reader` отозвала миграция `20260914091500`;
   группа осталась пустой и ничего не открывает. У снимающей миграции есть **откатная половина**,
   и её контракт — решение документа, а не исполнителя: `Down` возвращает строку группы свода,
   членств не возвращает, повторный накат сходится (§6 S2б, MRW-25).
7. **Сверка паритета относит живую группу к модулю, ЧЕЙ МАНИФЕСТ ЕЁ ОБЪЯВЛЯЕТ.** Сегодня
   владелец выводится из имени вида `kacho-<служба>`; `module-relation-writers` такому имени не
   отвечает, поэтому объявление её манифестом службы дало бы **ложную находку** «группа
   ОБЪЯВЛЕНА и не живёт» (§1.5).

Чего документ **не** делает: не меняет модель прав, не трогает ни одного глагола, не расширяет
и не сужает круг тех, кто пишет кортежи. Состав получателей права `fga_writer` до и после —
те же пять служебных записей модулей платформы. Предмет здесь один: **кто объявляет**, а не
**кому дано**.

## §1 Перепись производителей — ДО сценариев

Класс, отвергавший работу этой линии больше двух раз, — «Тогда» без производителя. Поэтому
раздел стоит первым, а не последним: по каждому утверждению документа ниже назван либо
**живой производитель координатой**, либо **стадия с открытой задачей**.

### §1.1 Как манифест службы применяется сегодня — НИКАК

Три независимых предиката, и все три дают ноль.

```sh
# 1. раздела посева у манифеста службы нет
git grep -c '^seed:' -- manifest.yaml | wc -l               # → 0

# 2. встроенного в образ читателя своего манифеста нет
#    ОБЛАСТЬ СУЖЕНА ДО КОДА НАМЕРЕННО: без `-- '*.go'` предикат находит СОБСТВЕННУЮ
#    строку этого документа (и строку записи круга 1), то есть считает своё
#    объяснение — `testing.md` §«Гейт на класс», п. 4. Существо не меняется:
#    директив `go:embed` в прод-коде девять, ни одна не про манифест.
git grep -n 'go:embed manifest.yaml' -- '*.go' ':!*_test.go'   # → пусто
git grep -n 'go:embed.*manifest'     -- '*.go'                 # → пусто

# 3. чарт службы своего манифеста никуда не монтирует
git grep -n 'manifests' -- 'deploy/*.yaml'                 # → пусто
```

Четвёртый предикат — в чужом дереве, и он объясняет, **почему** доставка его не привозит:
производитель ConfigMap доставки обходит `services/*/manifest.yaml` **дерева платформы**, а
каталога службы там больше нет ни одним файлом.

Предикаты чужого дерева записаны ИСПОЛНИМОЙ формой — `git -C <копия платформы>` с прибитой
ревизией, — а не приставкой `PRO-Robotech/kacho:`: приставка объявлена соглашением шапки и
читается однозначно, но прогнать её как записано нельзя, и читатель переводит её сам.

```sh
K=45d1719fe8dd76728847f45e901bc5ded7ea993d   # ревизия платформы, объявленная шапкой

# каталог службы в дереве платформы — снят вынесением (kacho#2598)
git -C <копия платформы> ls-tree -r $K --name-only | grep -c '^services/iam/'      # → 0

# манифесты, которые доставка собирает
git -C <копия платформы> ls-tree -r $K --name-only \
  | grep -E '^services/[^/]+/manifest\.yaml$'                                      # → 5:
#   compute · nlb · registry · storage · vpc
```

Каталог обхода объявлен константой `servicesDir` в фундаменте
(`PRO-Robotech/corelib@v1.8.0:modulemanifest/producer/producer.go`, строки 55–58 и 247–260), и
ключ ConfigMap выводится из имени каталога службы.

**Следствие, несущее для §3:** сегодня у манифеста службы нет читателя **ни на одном** пути —
ни доставки, ни встроенности, ни монтирования. Значит раздел `seed`, дописанный в него без
второй половины работы, был бы объявлением без производителя — ровно тот класс, который
`api-conventions.md` §«Принято-и-проигнорировано» называет запрещённым.


членство, ради которого группа существует.

Все десять вступлений называют аккаунт группы **прежним** написанием (предикат: тот же

значение, и оно — `Previous` окна написаний, не `Declared`; §2.14). Применитель резолвит его

`seed-identity-names-its-own-service.md`, не этого документа (§7). Манифест **службы** прежнего
написания не несёт (Р1).

Шапки этих же пяти манифестов несут утверждение, которое станет ложным правой половиной
работы и верным — левой: «`module-quota-readers` и `module-relation-writers` заводит
платформа». Предикат —
`for m in compute nlb registry storage vpc; do git -C <копия платформы> show $K:services/$m/manifest.yaml | grep -c 'заводит платформа'; done`
→ **1** в каждом из пяти.

внутри `applyOne` **своего** модуля, а вступление `compute` — внутри своего; между модулями
порядка нет никакого, кроме имени. Отказ был бы назван
(`groupID`: «группа %s/%s не резолвится»), но это всё равно отказ старта.

верном дереве, снимают первой.

**не исполняется ни разу**. Дефект формы поэтому не красный и не зелёный: он невидим, пока
группа не станет получателем, — а получателем её делает ровно этот документ.

**О7 — исходов встроенности ТРИ, и у каждого своя цена.** Прежняя редакция называла исход
(«встроен в образ») и не называла механизма, тогда как оба механизма требуют того, чего
документ не объявлял: копии внутри каталога пакета с держателем её согласия — либо пути в
образе со стражем старта. Разбор — §2.6, решение — Р2.

### §2.1 Посылки о кругах — обе перемерены, и ответ у них РАЗНЫЙ

Здесь две посылки двух разных заданий, и смешивать их нельзя: первая была опровергнута и

> это третий экземпляр одного класса в одном разделе
> Здесь стоял перечень каталогов записей ревью, когда-либо заведённых

### §2.2 Посылка задачи «применитель кладёт объявленное поверх живой строки, не меняя идентификатора» — ВЕРНА ДЛЯ ГРУППЫ И ЛОЖНА ДЛЯ ЕЁ ВЫДАЧИ

Предикат снятия 1 задачи утверждает это про обе строки разом. Замер разводит их.

**Для группы — верно** (П4). Конфликт разрешается по ограничению уникальности `(account_id,
name)`, идентификатор стоит только в списке значений вставки и на живую строку не переносится.
Это сказано и в шапке писателя: «У группы такой производной нет: живые группы несут случайные
идентификаторы. Поэтому её идемпотентность держит ограничение уникальности `(account_id,
name)`, а не совпадение идентификатора».

**Для выдачи — ложно, и ПРИЧИНА не та, которую называла прежняя редакция.** Идентификатор
выдачи применитель **выводит** выражением
(`internal/repo/kaname/pg/module_seed_writer.go`, раздел «Идентификатор выдачи ВЫВОДИТСЯ тем же
выражением, каким его вывела платформа»), и конфликт объявляет по `(id)`. Замер разводит **два**
входа этого выражения — форму субъекта и написание якоря:

```sh
python3 - <<'PY'
import hashlib
def acb(user, form, kind, anchor):
    return 'acb' + hashlib.md5(f'system-grant:{user}:{form}:{kind}:{anchor}'.encode()).hexdigest()[:17]
for user in ('group:grp258e6bbe9bbe45568', 'group:grp258e6bbe9bbe45568#member'):
    for anchor in ('cluster_root', 'cluster_kacho_root'):
        print(f'{user:42} @{anchor:18} -> {acb(user, "fga_writer", "cluster", anchor)}')
print('живая строка свода', ' ' * 41, '-> acb9e920fb038c7e4f74')
PY
#   group:grp258e6bbe9bbe45568                 @cluster_root       -> acbbcb7bb3d70aa9cc4b
#   group:grp258e6bbe9bbe45568                 @cluster_kacho_root -> acb7a84798bb6bfc448b
#   group:grp258e6bbe9bbe45568#member          @cluster_root       -> acbc5d31947bd0d570e8
#   group:grp258e6bbe9bbe45568#member          @cluster_kacho_root -> acb9e920fb038c7e4f74
#   живая строка свода                                             -> acb9e920fb038c7e4f74
```

**Живой идентификатор ВЫВЕДЕН, а не отчеканен рукой: он равен выражению на форме с сигилом
членства при ПРЕЖНЕМ написании якоря.** Совпадение точное и случайным быть не может —
семнадцать шестнадцатеричных знаков.

> [!warning] Прежняя редакция этого раздела утверждала обратное, и её ОПЫТ БЫЛ СЛЕП ровно по §2.5
> Здесь стояло: «ни одно из двух написаний якоря не даёт живого идентификатора — расхождение не
> следствие переименования якоря, а следствие того, что свод чеканил идентификаторы рукой».
> Опыт подавал выражению **голый объект группы** — ту самую форму, которой канон не принимает, —
> и потому не мог получить живого значения **ни при каком** якоре. Замер с формой канона даёт
> его с первой попытки.
>
> Это не отдельная небрежность, а **второй экземпляр одного класса**: там, где форма субъекта
> строится не вызовом объявленного источника (Р1а), ошибается не только продукт, но и тот, кто
> его измеряет. Свою ошибку называю прямо: форма была построена руками, число получилось верным
> для другого входа, и из него выведена неверная причина — при верном следствии.

**Причина расхождения — ПЕРЕИМЕНОВАНИЕ ЯКОРЯ, и она названа самим писателем заранее.** Якорь
переехал `cluster_kacho_root` → `cluster_root` миграцией
`20260906214500_cluster_anchor_moves_to_its_declared_spelling.sql`; переписчик правит **значение
якоря** во всех местах схемы и требует нулевого остатка прежнего написания, но идентификатор
выдачи непрозрачен и переписи не подлежит. Шапка писателя ровно это и оговаривает: «якорь входит
в выражение своим ЖИВЫМ написанием. Установка, пережившая переименование якоря, получит на этой
выдаче другой идентификатор».

**Следствие СИЛЬНЕЕ прежнего, а не слабее.** Расхождение не принадлежит «старым установкам»:
свод сеет строку прежним написанием, а миграция переименования применяется **следом и везде**,
включая чистую установку. Значит несовпадение выведенного идентификатора с живым
**универсально и постоянно**, и решение Р4 (естественный ключ вместо совпадения идентификатора)
требуется не от случая, а by construction.

Выражение, помимо применителя, применяет лишь миграция `20260909202745` и лишь к выдачам
`system_viewer` служебным записям
(`sed -n '299,302p' internal/migrations/20260909202745_module_identities_leave_the_baseline.sql`),
и там оно подставляет **форму субъекта FGA** — довод, на который опирается Р1а.

**Что произойдёт на живой установке — не «вторая строка», а ОТКАЗ.** Вставка с другим
идентификатором наталкивается на частичный уникальный индекс по естественному ключу, которого
`ON CONFLICT (id)` не покрывает:

```sh
git grep -n 'access_bindings_active_relation_grant_uniq' -- internal/migrations
#   0001_initial.sql:4450  CREATE UNIQUE INDEX … (subject_type, subject_id, granted_relation,
#                          resource_type, resource_id) WHERE granted_relation <> '' AND revoked_at IS NULL
```

Индекс жив: снимающей его миграции в дереве нет ни одной (та же команда даёт единственное
объявление). Значит применение отвергается кодом `23505`, транзакция модуля откатывается,
`ApplyAll` прекращает работу и служба **не поднимается**. Предикат задачи «кортежи уже живых
установок не рвутся» выполняется случайно и по худшей причине: до кортежей дело не доходит.

**Замечание в пользу самого предиката.** Для двух живых выдач посева (`system_viewer` у `vpc`
и `compute`) он верен буквально: их идентификаторы **выведены** тем же выражением, конфликт по
`(id)` срабатывает, изменений ноль. Форм выдачи две; живых строк роль-формы в разделах `seed`
сегодня **ноль** —
`for m in compute nlb registry storage vpc; do git -C <копия платформы> show $K:services/$m/manifest.yaml | grep -c 'roleId:'; done`
даёт 0 в каждом из пяти, и это состояние без предмета, а не исключение.

### §2.5 Находка «применитель строит форму субъекта FGA БЕЗ сигила членства» — ПОДТВЕРЖДЕНА опытом

Посылка проверена, и она верна. Форму субъекта объявляет **одно** место (П9); писатель строк
посева его не зовёт и строит форму встроенным выражением.

```sh
git grep -c 'FGASubjectRef' -- internal/repo/kaname/pg/     # → 0 файлов
git grep -n  'fgaUser :='   -- internal/repo/kaname/pg/module_seed_writer.go
#   :283  fgaUser := subjectType + ":" + subjectID
```

**Опыт — одно-фактный, прогнан во временном пакете дерева и снят за собой.** Сравниваются две
формы одного субъекта: канон и встроенное выражение применителя; различается только вид
получателя.

```
group            канон=group:<id>#member            применитель=group:<id>            совпали=false
service_account  канон=service_account:<id>         применитель=service_account:<id>  совпали=true
user             канон=user:<id>                    применитель=user:<id>             совпали=true
```

Расхождение — ровно на группе, то есть на том единственном виде получателя, который вводит Р1.
Служебная запись и человек — **законные близнецы**: на них формы совпадают, и проба, написанная
только на них, зеленела бы при любой реализации.

**Канон голый объект группы субъектом НЕ принимает** (П5):
`proto/kaname/cloud/iam/v1/fga_model.fga:294` — `define fga_writer: [service_account,
group#member]`. Правильную форму показывают живые строки **этой же выдачи**, заведённые сводом:
`0001_initial.sql:3162` (ведомость эмитированного), запись **24** журнала прав и прямой факт
отношения — все три несут `group:<id>#member`.

**Радиус — три места из ОДНОГО выражения**, и это надо сказать числом: `fgaUser` участвует в
производной идентификатора выдачи, в ведомости эмитированного и в полезной нагрузке журнала
прав (`git grep -n 'fgaUser' -- internal/repo/kaname/pg/module_seed_writer.go` → **4** строки:
объявление и три потребителя). Значит неверная форма расходится по трём предметам сразу, а не
по одному.

**Почему это не ловится сегодня ничем.** Получателей-групп в разделах `seed` манифестов
платформы **ноль**, и предикат обязан идти ПОМОДУЛЬНО:

```sh
K=45d1719fe8dd76728847f45e901bc5ded7ea993d
for m in compute nlb registry storage vpc; do
  printf -- '-- %s\n' "$m"
  git -C <копия платформы> show $K:services/$m/manifest.yaml \
    | awk '/accessBindings:/{f=1} f&&/type:/'
done
#   -- compute:  - {type: serviceAccount, name: kacho-compute}
#   -- nlb:      (пусто)
#   -- registry: (пусто)
#   -- storage:  (пусто)
#   -- vpc:      - {type: serviceAccount, name: kacho-vpc}
```

Итого **две** строки, обе `{type: serviceAccount, …}`. Ветвь получателя-группы **не исполняется
ни разу**, поэтому её дефект не красный и не зелёный — он невидим.

> [!note] Прежняя запись этого предиката подавала пять манифестов ОДНИМ ПОТОКОМ и давала ТРИ
> строки, третья — не о получателе
> Флаг `f` в `awk` не сбрасывается на границе файлов, а границы в склеенном потоке нет: после
> `compute` он остаётся взведённым и печатает `- {name: parent, type: registry_registry}` из
> `registry` — строку каталога ресурсов, к получателям выдачи отношения не имеющую. Существо
> утверждения от этого не менялось (получателей-групп ноль), неверным было объявленное число.
> Помодульный прогон границу файла имеет by construction.

**Что из этого следует для документа.** Ни одно «Тогда» прежней редакции не утверждало о
**форме** записываемого субъекта, поэтому MRW-01 и MRW-03 были зелены при неверной форме: оба
судят наличие строки выдачи и её идентификатор, а не то, что уезжает в журнал прав. Решение —
Р1а, сценарии — MRW-20 и MRW-21, ведомость — §8, держатель — §9.

### §2.6 Находка «Р2 объявляет ИСХОД, а не МЕХАНИЗМ» — ПОДТВЕРЖДЕНА замером

Прежняя редакция говорила «манифест встроен в образ» и механизма не называла. Оба механизма
требуют того, чего документ не объявлял, и третий исход не рассматривался вовсе.

**Встраивание директивой требует ВТОРОЙ копии внутри каталога пакета.** Пакета в корне дерева
нет (`ls *.go` в корне — «No such file or directory»), а директива встраивания родительского
каталога не принимает. Опыт (временный пакет, снят за собой):

```

```

**Файла в образе тоже нет.** Вторая ступень сборки наполняется двумя двоичными, сертификатами и
файлом провенанса; `grep -n 'manifest' Dockerfile` не даёт **ни одной** строки.

**Прецедент встраивания в этом же дереве показывает недостающую половину, и состоит он из
ПАРЫ артефактов РАЗНОГО РОДА.** Канон модели прав лежит **двумя** копиями —
`proto/kaname/cloud/iam/v1/fga_model.fga` и `internal/authzmodel/fga_model.fga`, — их отпечатки
совпадают (`md5sum proto/kaname/cloud/iam/v1/fga_model.fga internal/authzmodel/fga_model.fga` →
одно значение на обе), вторая встроена директивой (`internal/authzmodel/authzmodel.go:67`).

| **держит** равенство | `internal/authzmodel` `TestEmbeddedModelIsByteIdenticalToCanonical` (`identity_test.go:24`) | сверяет ДВЕ копии побайтово и роняет прогон на расхождении |

То же говорит сам Makefile: «Равенство держит гейт `internal/authzmodel`
TestEmbeddedModelIsByteIdenticalToCanonical» (`sed -n '710,713p' Makefile`); и третье место
дерева — `internal/authzmap/fga_model_drift_test.go:19–23`.

> [!warning] Прежняя редакция называла держателем `make model-canon-check` — у этой цели ДРУГОЙ
> ПРЕДМЕТ, и подмена ломала бы признак готовности S1
> Шапка цели говорит о себе сама (`sed -n '349,352p' Makefile`): «блоки модели доступов
> сверяются с манифестами модулей ПОБАЙТОВО (задача #1089). Цель обходит закрытый набор
> модулей, **порождает блоки типов из манифеста каждого** и сравнивает их с каноном …,
> прочитанным ИЗ ДЕРЕВА». То есть она сверяет ПОРОЖДЁННОЕ из манифестов с каноном, а второго

> tools/model-canon-check.sh` → пусто.
>
> **Цена подмены измерима, а не теоретична.** Признак готовности S1 требует: «правка
> `manifest.yaml` без пересборки копии роняет цель». У цели, построенной «по образцу
> `model-canon-check`», такого свойства нет **by construction** — она порождает одну сторону из

> бы молча, и расхождение проявилось бы первым стартом.

> TestEmbeddedModelIsByteIdenticalToCanonical ./internal/authzmodel/` → `ok`.

Ровно этой пары — порождающей цели И держащей пробы — у прежней редакции не было ни в §6, ни

### §2.7 Находка «судьба манифеста решена для ОДНОГО потребителя из пяти» — ПОДТВЕРЖДЕНА замером

На пути старта перечень манифестов читают **пять** потребителей, а прежняя редакция решала

Манифест службы при этом **не пуст**: `python3 -c "import yaml,sys; d=yaml.safe_load(open('manifest.yaml'));

**Исход по каждому — в Р3.** Три из пяти измерены опытом (временный пакет, снят за собой):
композиция модели с манифестом службы в перечне даёт `manifests=1 resources=7 canon=32

сверх образа; применитель каталога стал бы **вторым** писателем семи строк, которые сеет
миграция (П11).

**У раздела `roles:` исход уже решён соседней приёмкой, и его надо ЦИТИРОВАТЬ, а не решать
заново.** `docs/engineering/acceptance/roles-come-as-data-not-migrations.md` (APPROVED)
классифицирует роли по владельцу имени и говорит про `iam` прямо: «такой же модуль, а не
исключение… переезжают к применителю на общих основаниях, когда появится манифест `iam`». Тот же
исход держит **живой** гейт (П10): его перепись называет манифест `iam` найденным, а девятнадцать
вставок роли в применённых миграциях — историческим остатком, чей «переезд к применителю есть
**отдельный предмет**». Значит эта работа раздел `roles:` не трогает, и так сказано в Р3.

### §2.8 Находка «у оси „живая строка есть / строки нет“ названа одна сторона» — ПОДТВЕРЖДЕНА замером

Все четыре сценария формы **отношения** прежней редакции (MRW-01, 02, 03, 05) описывают мир, где
строка выдачи в базе уже есть, и §5 говорит это дословно: строку заводит `0001_initial.sql:3196`
на **каждой** установке, включая чистую. Снимающей её миграции в дереве нет ни одной:
`git grep -ln 'fga_writer' -- 'internal/migrations/*.sql'` → **один** файл, `0001_initial.sql`.

Следствие: **пишущая ветвь применителя, ради которой Р1 и заводится, не утверждалась ни одним
«Тогда»**. Для формы **роли** документ требование выполнял (MRW-14 называет обе стороны), для
формы отношения — нет. Тот же пробел делал невидимой и находку §2.5: форма записываемого
субъекта не проверялась, потому что **записи** не требовал ни один сценарий.

Мир «строки нет» конструируем тем же приёмом, каким документ уже пользуется в MRW-12: строка
удаляется из базы до применения. Сценарий — MRW-19, дом и дельта — §5.

### §2.9 Что в РЕДАКЦИИ 1 было МОИМ промахом — названо прямо

Раздел о **редакции 1** (`d66107b2`) и о находках, снятых редакцией 2; промахи редакции 2,
названные кругом 1, разобраны отдельно — §11; промахи **редакции 3**, названные оппонентом уже
после круга 1, — §2.10…§2.13 и §12. Все четыре находки подтверждены замером, ни одна
не опровергнута, и это надо сказать первым.
Разночтением не была ни одна: три — пропуск одного рода, четвёртая — неверная причина при верном
следствии.

**Три пропуска одного рода: документ называл ИСХОД там, где обязан был назвать МЕХАНИЗМ и его
радиус.** Р2 объявляла встроенность, не называя, чем она делается и чем держится (§2.6); Р2/Р3
решали судьбу манифеста для одного потребителя, не измерив, что их пять (§2.7); §4 не требовала
**записи** ни одним «Тогда», отчего форма записываемого не проверялась ничем (§2.8).

**Четвёртая — неверная ПРИЧИНА при верном следствии, и она же экземпляр того класса, который
сама и обнажает.** §2.2 утверждала, что идентификатор живой выдачи отчеканен рукой; замер
показывает, что он **выведен** тем же выражением при прежнем написании якоря. Ошибиться удалось
потому, что опыт строил форму субъекта **руками** — ровно как это делает применитель, — и потому
не мог попасть в живое значение ни при каком якоре. Следствие §2.2 (конфликт по идентификатору
не срабатывает, применение отвергается) от этого не изменилось и стало сильнее: расхождение
универсально, а не свойственно старым установкам.

**Урок, который дороже трёх пропусков:** форма, построенная руками вместо вызова объявленного
источника, ошибается **дважды** — в продукте и в том, кто продукт измеряет. Это и есть довод в
пользу Р1а, полученный на себе.

Отдельно — число в §8. Прежняя редакция писала «живых производителей 7 из 18» и **единицы счёта
не называла**, поэтому проверить его читатель не мог. В настоящей редакции число сопровождается
перечнем строк, к которым относится.

### §2.10 Находка «пишущая ветвь применителя для ГРУППЫ не утверждается ни одним „Тогда“» — ПОДТВЕРЖДЕНА замером

### §2.12 Находка «два APPROVED-соседа не названы ни разу» — ПОДТВЕРЖДЕНА замером

Оба соседа — APPROVED, оба **резервируют предмет**, которого касаются решения этого документа,

**Сосед 1 — `module-manifest-relation-grant.md` (APPROVED, круг 1, 2026-09-03).** Его §5 говорит

именам строк, а не по разности чисел.

**Сосед 2 — `module-manifest-seed-contract.md` (APPROVED).** Его §4 выносит за скобки «порядок

**≥2**, и хотя бы один объявляет группу, в которую вступает другой». Преемника называет

(`gh issue view 1088 -R PRO-Robotech/kacho --json state` → `CLOSED`).

**Предикат заведения наступает вместе с Р1 — и Р3 отвечает на него, а не откладывает.** Замер
популяции сегодня:

```sh

K=45d1719fe8dd76728847f45e901bc5ded7ea993d
git -C <копия платформы> ls-tree -r $K --name-only | grep -cE '(^|/)manifest\.yaml$'   # → 5
for m in compute nlb registry storage vpc; do

#   → «0 2» во всех пяти: ни один доставленный манифест не объявляет НИ ОДНОЙ группы
```

в дереве службы даёт **0**: манифест лежит в корне и слэша в пути не имеет. Считать надо то, что
видит применитель, а это **1 свой + 5 доставленных = 6**.

**Следствие, несущее для Р3.** Группу объявляет **ровно один** манифест — свой; все вступления
идут в неё. Значит порядок, выводимый из `joins`, для существующей популяции сводится к одному
правилу «своё раньше доставленного», и его Р3 **решает**, а не откладывает. Порядок **между
доставленными** остаётся нерешённым, и его популяция — **ноль** объявленных групп на пять
манифестов: это состояние без предмета, а не отсрочка. Предикат возврата предмета назван в §7.

### §2.13 Находка «„Дано“ MRW-04 не строится домом §5» — ПОДТВЕРЖДЕНА замером

«Дано» MRW-04 просит «базу, в которой этой группы ещё нет». Дом §5 редакции 3 — «база + манифест
Р1 + каталог доставки с одним манифестом модуля», дельта «доставка есть». Снятия строки в доме
нет, а на базе, которую дом строит, группа **жива из свода** (§2.10) — значит `groupID` резолвит
её при любом порядке обхода, и «Тогда» MRW-04 («вступление `compute` записано, отказа „группа не
резолвится“ нет») выполняется **независимо от Р3**. Единственный сценарий решения Р3 о порядке
оставался без различающего мира.

**Исход — правка ДОМА, а не «Дано»** (первая из двух ветвей, названных находкой): дом MRW-04 и
его близнеца MRW-05 получает снятие строки группы вместе с её выдачей, дельта между ними
остаётся **одна** — «доставка есть / доставки нет». Побочно это чинит и MRW-05: на снятой строке
его «Тогда» («группа и её выдача заведены») перестаёт быть утверждением о своде и становится
утверждением о применителе.

### §2.14 Блокирующие круга 2 «факт о БАЗЕ взят из СВОДА» — ПОДТВЕРЖДЕНЫ замером, все три

## §3 Решения

### Р1. Группу и её выдачу объявляет манифест службы

Манифест службы (`manifest.yaml`, `module: iam`) получает раздел `seed` с двумя подразделами:

- `groups` — одна запись: `module-relation-writers` с `account: system` — написанием,
  объявленным `domain.SystemAccountName` (`internal/domain/seed_identity_window.go:53`) и
  решённым APPROVED-соседом `seed-identity-names-its-own-service.md` §2.3 (класс C: имя
  называет **установку**, а не продукт), — с назначением, взятым **дословно** у живой строки
  свода;
- `accessBindings` — одна запись: получатель `{type: group, name: module-relation-writers}`,
  `grantedRelation: fga_writer`, `scopeType: iam.cluster`, `scopeId: cluster_root`,
  `target: allInScope`.

Подразделов `serviceAccounts` и `joins` у него нет: своей служебной записи у службы доступа
не бывает, и вступать ей некуда. Это сказано **словом** в шапке манифеста, а не оставлено
умолчанием.

**Почему выдача обязана быть.** Её требует валидатор связности (П6): заведённая манифестом
группа, которую он же не одаривает, — объявление без следствия. Требование здесь не помеха, а
ровно то, что делает решение владельца исполнимым: аудиторию и выдачу объявляет один документ.

**Почему `system`, а НЕ `kacho-system` — написание здесь НЕСУЩЕЕ, а не вкус.** Аккаунт в базе
называется `system`: его перевела применённая миграция `20260913144108`
(`UPDATE kaname.accounts SET name = 'system'`, `sed -n '5p;100,101p'
internal/migrations/20260913144108_seed_identity_leaves_the_platform_brand.sql`).
`kacho-system` — **прежнее** написание, и его продолжает принимать только **окно написаний**
(`seed_identity_window.go:80–83`, `Previous: "kacho-system"`), заведённое ради непереведённых
манифестов чужого продукта (§1.4: пять `joins` платформы называют аккаунт так). Читает окно
**один** писатель посева (`resolveBySpellings`, `module_seed_writer.go:122`), поэтому
применителю годятся оба написания и MRW-01…05 зелены при любом. Различает их **сверка
паритета**: она сравнивает написания **сырыми** (Р5) и окна не знает, — с `kacho-system`
объявленная группа не нашла бы живой пары `(system, module-relation-writers)`, и MRW-11 был бы
красен на верном продукте. Сверх того литерал прежнего написания в разделе `seed` уехал бы в
ведро «манифесты» переписи соседа, чьё §7-П2 требует от живого написания дойти до нуля
(`python3 docs/engineering/acceptance/seed-identity-names-its-own-service.py`, классификатор
`bucket`, `.py:222–234` на стволе `a69c79d6`: путь `manifest.yaml` и не-комментарий →
«манифесты»; текст приёмок и записи ревью изъяты из вёдер границей `is_acceptance_text`,
`.py:210–219`, — #159). Схема от прежнего написания
**не удерживает** — её перечисление несёт оба (§2.14), — значит удерживает этот документ, и
проба формы обязана подавать `account: system` буквально.

### Р1а. Форму субъекта FGA применитель БЕРЁТ У КАНОНА, а не строит третьей копией

Получателем выдачи Р1 впервые становится **группа**, и с этим в контракт входит форма, которой
прежде не было ни у одной живой выдачи посева: субъектом кортежа выступает не объект группы, а
её **членство**. Канон принимает только эту форму (П5), а живые строки этой же выдачи, заведённые
сводом, её и несут (§2.5).

**Решение.** Писатель строк посева строит субъект FGA **вызовом** объявленного источника формы
(П9) — того же, которым её строят проекция выдачи и реконсайлер, — и своего выражения не держит.
Наблюдаемо: у получателя-**группы** ведомость эмитированного и журнал прав получают субъекта с
сигилом членства; у получателя-**служебной записи** форма остаётся прежней побайтово.

**Почему вызов, а не «дописать сигил на месте».** Третья копия формы разошлась бы с первыми
двумя молча и ровно там, где расхождение дороже всего: субъект выдачи и субъект отзыва стали бы
разными, то есть отзыв не снял бы того, что выдача завела. Это сказано в godoc самого источника
требованием побайтовой симметрии — и здесь оно не пересказывается, а исполняется.

**Радиус решения — три предмета из одного выражения, а не один** (§2.5): производная
идентификатора выдачи, ведомость эмитированного, полезная нагрузка журнала прав. Значит проба
обязана утверждать **все три**, а не только последнюю: идентификатор, выведенный из неверной
формы, не совпал бы с идентификатором, выведенным из верной, и Р4 разрешал бы его естественным
ключом молча.

**Производная идентификатора берёт ИМЕННО эту форму, и это не выбор документа, а живой
прецедент.** Выражение, которое применитель повторяет, объявлено применённой миграцией, и её
довод — форма субъекта FGA: `sed -n '299,302p'
internal/migrations/20260909202745_module_identities_leave_the_baseline.sql` — там подставлено
`'system-grant:service_account:' || sa_id`. На служебной записи форма субъекта FGA и пара
«тип:идентификатор» совпадают, поэтому прецедент не различает их **by construction**; различает
их ровно получатель-группа, и различие решается в пользу формы FGA — той, которую принимает
канон.

**Чего решение НЕ делает.** Оно не меняет формы для служебной записи и человека — там канон и
выражение применителя совпадают уже сегодня (§2.5), и это законный близнец всякой пробы на эту
ось, а не «заодно исправленное».

### Р2. Манифест службы приезжает применителю ВСТРОЕННЫМ В ОБРАЗ

Исходов **три**, и каждый отвергнут или принят по названной цене, а не по вкусу. Прежняя
редакция называла исход и не называла механизма — разбор этого промаха в §2.6.

| исход | механизм | цена |
|---|---|---|
| **встроен в образ ВТОРОЙ КОПИЕЙ в каталоге пакета-носителя** (принят) | копия `manifest.yaml` в каталоге пакета-носителя плюс директива встраивания; копию **порождает цель сборки**, а побайтовое равенство её с манифестом дерева **держит проба** — два артефакта разного рода, по образцу пары `make fga-model-embed` + `TestEmbeddedModelIsByteIdenticalToCanonical` (§2.6) | вторая копия в дереве — и она **не** копия чужого репозитория (ban #20 про чужого владельца, а владелец здесь свой). Цена копии — держатель: без него две копии разойдутся молча |
| файлом в образе (отвергнут) | копирование `manifest.yaml` во вторую ступень сборки плюс ручка пути плюс отказ старта при её незаданности | цена выше при том же результате: заводит **ручку посадки** там, где величина не имеет законного разброса, и страж, который обязан отличать «путь не задан» от «файл не читается». Копия в дереве при этом всё равно не нужна — но и согласие держать нечем: сравнивать в образе не с чем |
| свой чарт монтирует свой манифест в каталог доставки (отвергнут) | `deploy/templates/configmap.yaml` кладёт манифест службы в тот же каталог, откуда читается доставка | копии в чужом репозитории не требует, и **доводом ban #20 не отвергается** — отвергается двумя другими. Первая: манифест попадает в **перечень доставки**, то есть ко всем пяти потребителям сразу (§2.7, Р3), а решение Р3 требует обратного. Вторая: условие «группа заведена» становится условием **посадки** — установка, чей оператор каталог не объявил, поднимется без группы, и это тот же пробел, что у доставки платформой |
| доставкой платформы (отвергнут) | ConfigMap зонтичного чарта платформы | требует копии манифеста службы в дереве платформы — **запрещено** решением владельца 2026-09-13 (ban #20: файл, чей владелец — другой репозиторий, в этом дереве не лежит). Сверх того делает существование группы условием установки платформы, тогда как право принадлежит поверхности самой службы, и ломает порядок (О2) |

**Почему директива, а не путь в образе.** Директива даёт величину, у которой нет незаданного
состояния: манифест либо встроен и собран вместе с двоичным, либо сборка не состоялась. Путь в
образе — это ручка, а всякая ручка требует стража старта и различения «не задана» от «не
читается»; за то же самое платится дважды.

**Цена принятого исхода названа, а не умолчана: копий становится ДВЕ.** Ровно та же цена уже
принята в этом дереве у канона модели прав — две побайтово равные копии, вторая встроена
директивой (§2.6). Поэтому и здесь **держателей обязательно ДВА, и они разного рода**:

- **порождает** копию — цель сборки, по образцу `make fga-model-embed` (`Makefile:718`): она
  копирует `manifest.yaml` в каталог пакета-носителя и тут же сверяет `cmp`. Цель **не
  является** держателем равенства: она его восстанавливает;
- **держит** равенство — **проба**, сверяющая обе копии побайтово и роняющая прогон на
  расхождении, по образцу `TestEmbeddedModelIsByteIdenticalToCanonical`
  (`internal/authzmodel/identity_test.go:24`). Признак готовности S1 («правка `manifest.yaml`
  без пересборки копии роняет») исполняет **она**, а не цель.

`make model-canon-check` держателем этой пары **не является и в образец не годится** — у него
другой предмет: он порождает блоки типов из манифестов модулей и сверяет их с каноном, а
встроенную копию не читает вовсе (разбор и предикаты — §2.6). Строки держателей — §9, пункт
S1 — §6.

**Пакет-носитель назван, потому что имя определяет ЧИТАТЕЛЯ, а не раскладку.** Копия лежит в
каталоге **своего** пакета `internal/` — отдельного носителя манифеста службы, а не внутри
применителя посева (`internal/apps/kaname/moduleseed`). Два довода, и оба из устройства
дерева:

- директива встраивания привязывает копию к каталогу пакета и родительского каталога не
  принимает (§2.6, опыт), поэтому «копия рядом с читателем» означает **каталог конкретного
  пакета**, и он обязан быть назван;
- применитель посева — слой use-case, и файлов он не читает: манифест ему приходит **готовым
  доводом** (Р3). Носителем поэтому служит пакет, который импортирует **композиционный
  корень** (`cmd/kaname/serve.go`), — ровно так устроен и прецедент: `internal/authzmodel`
  несёт копию и отдаёт её потребителям, сам ничьим потребителем не будучи.


**Что из этого следует для самостоятельной установки.** Служба без платформы поднимается с
заведённой группой и выданным ей правом; членов у группы нет, и это верное состояние, а не
пробел: модулей нет — писать кортежи некому. Пустая группа не даёт никому ничего (тот же
довод, которым две применённые миграции оставили пустыми обе группы).

### Р3. Свой манифест применяется ПЕРВЫМ, и порядок объявлен, а не получен случайно

Применитель получает манифест службы **отдельным доводом**, а не подмешанным в перечень
доставки, и применяет его до перебора доставленных. Два следствия, и оба обязательны:

- вступление модуля всегда встречает группу заведённой — независимо от имени модуля и от
  порядка обхода каталога доставки;
- перепись применения различает «свой» и «доставленные» **числом**: «манифестов доставлено N ·
  свой применён да/нет». Одно число на оба разряда скрыло бы ровно тот случай, ради которого
  разделение и делается.

**«Отдельным доводом» — не деталь провязки, а ГРАНИЦА РАДИУСА.** Перечень доставки читают
**пять** потребителей (§2.7), и подмешанный в него манифест службы достался бы всем пятерым
разом. Отдельный довод делает получателем **одного** — и это решение, за которое отвечает
таблица ниже.

#### Исход по КАЖДОМУ из пяти потребителей перечня

Порядок строк — порядок вызовов на пути старта (`grep -n 'deliveredManifests'
cmd/kaname/serve.go`).

| потребитель | получает ли манифест службы в S1 | почему именно так |
|---|---|---|
| опора паритета каталога (`:309`) | **нет** | безвреден и бесполезен: опыт даёт `added:[]` — ни одной строки сверх образа (§2.7). Ребро, ничего не меняющее, — это ребро, которое некому проверить: его зелёное неотличимо от его отсутствия |
| композиция модели прав (`:335`) | **нет** | опыт даёт `composed=[] reaffirmed=[7 типов]` — ни одного **нового** типа: свои семь служба и так берёт из встроенного канона образа (§7). Ребро добавило бы второй источник тех же типов, не добавив ни одного |
| применитель каталога (`:359`) | **нет** | завёл бы **второго писателя** семи строк `catalog_resource` модуля `iam`, которые сеет миграция (П11). Два места об одном предмете расходятся молча — ровно тот класс, который называет шапка гейта ролей |
| применитель ролей модуля (`:441`) | **нет** | предмет **адъюдицирован переписью живого гейта** (П10) как исторический остаток применённых миграций, правке не подлежащий (ban #5); классификацию держит APPROVED-сосед `roles-come-as-data-not-migrations.md` §3.4. Открытой задачи у него нет, и это сказано словом ниже — вместе с предикатом, по которому он перестанет быть остатком |
| применитель посева (`:457`) | **ДА** | единственный получатель: предмет работы — раздел `seed`, и он читается только здесь |

**Что это НЕ откладывает, и здесь ПРЕЖНИЙ ДОВОД БЫЛ ЛОЖЕН — опровергнут замером круга 1.**
Прежняя редакция снимала с четвёртой строки ban #11 словами «предмет принадлежит названной
чужой работе, **и она открыта**». Открытой работы нет ни в одном из двух трекеров:

```sh
gh issue list -R PRO-Robotech/kaname --state open --limit 200 --json number,title,body \

gh issue list -R PRO-Robotech/kacho  --state open --limit 500 --json number,title,body \
  -q '.[]|select((.title+" "+.body)|test("применител(ю|ь|я) ролей|19 ролей|roles-come-as-data"))|.number'
#   первая → пусто (открытых осмотрено 48); вторая → одна задача #1896 о координатах в
#   приёмках (открытых осмотрено 235). Предмета нет. Прежняя запись вывода называла ещё #111
#   — её тело образцу больше не отвечает (правлено до редакции 4), вывод перемерен 2026-09-16

```

Довод переписан **третьим** из исходов, названных кругом 1, и слова «открыта» в нём больше нет:

- **предмет адъюдицирован**, а не отложен: перепись живого гейта `TestMODRD23` называет
  девятнадцать вставок роли `iam` в **уже применённых** миграциях историческим остатком,
  правке не подлежащим (ban #5 — применённую миграцию не правят). Адъюдикация — исход, а не
  отсрочка: «решим потом» здесь нет ни одной строкой;
- **предикат прекращения остатка назван и он МАШИННЫЙ, а не «когда дойдут руки»**: остаток
  перестаёт быть остатком ровно тогда, когда перепись гейта печатает по нему **ноль**, —

  ```sh
  go test -count=1 -short -run TestMODRD23 -v ./internal/check/ \
    | grep 'исторический остаток'
  #   сегодня: «… вставок роли модуля с манифестом в УЖЕ ПРИМЕНЁННЫХ миграциях 19 —
  #   правке не подлежат (ban #5), их переезд к применителю есть отдельный предмет»
  ```

  Ноль он напечатает не раньше, чем СОЙДУТСЯ ДВЕ вещи: новая миграция снимет эти строки **и**
  у раздела `roles:` появится читатель. Ни того, ни другого эта работа не делает и не обещает;
- **условие соседней APPROVED-приёмки при этом УЖЕ НАСТУПИЛО, и это надо сказать прямо**:
  `roles-come-as-data-not-migrations.md` §3.4 говорит «переезжают к применителю на общих
  основаниях, когда появится манифест `iam`», а манифест в дереве есть (П10). Наступившее
  условие **не превращает** остаток в отсрочку этой работы: приёмка-сосед объявляет **правило
  классификации**, а не срок, и её собственный держатель — тот же гейт, который остаток и
  считает. Работу, которую это условие открывает, заводит её владелец своим изменением; здесь
  она не заказывается и не обещается.

Остальные три строки «нет» не откладывают ничего по другой причине: у них исход — «ребра не
заводим», и ребра, которого нет, откладывать нечего.

**Порядок, который Р3 решает, — и порядок, который зарезервирован соседом.** APPROVED-приёмка
`module-manifest-seed-contract.md` §4 вынесла за скобки «порядок установки модулей, выводимый из
`joins`» как гейт на нулевой популяции и назвала предикат заведения преемника: «манифестов ≥2, и
хотя бы один объявляет группу, в которую вступает другой». Р1 создаёт именно это состояние, и
Р3 на него **отвечает**, а не откладывает: единственный манифест, объявляющий группу, — свой, все
пять доставленных лишь вступают (`0 2` у каждого, §2.12), поэтому «своё раньше доставленного» и
есть весь порядок, выводимый из `joins` сегодня. Порядок **между доставленными** Р3 не решает —
там популяция ноль, и предикат возврата предмета назван в §7. Преемник, за которым сосед
оставлял предмет, — `#1088` — закрыт; довод «работа открыта» здесь не используется (тот же
класс, что Б5 круга 1).

**Свой манифест на пути старта читается ТЕМ ЖЕ загрузчиком и БЕЗ оракула модели — как и
доставленные, и это решение, а не умолчание.** Загрузчик судит существование отношения и вид
получателя только с внесённой моделью — без неё «о существовании отношения не утверждаем
ничего»: `if oracle == nil { return nil }` (`internal/manifest/relationgrant.go:161–163`); на
пути старта её не вносит никто (`cmd/kaname/module_manifests.go:70` —
`manifest.LoadDelivered(cfg.Dir)` без опций), и довод записан у самого порта: модель ещё
собирается из доставленного, «спрашивать её здесь значит спрашивать у ответа»
(`internal/manifest/relationoracle.go:100–118`). Второй загрузчик — с каноном образа — для
своего манифеста здесь **не заводится**: у него был бы другой вердикт на том же документе, чем у
оснастки дерева, и два судьи одного документа разошлись бы молча. Отношение и вид получателя
своего манифеста судит **оснастка дерева** (`internal/manifestcheckrun`, `make
module-manifest-check`; в конвейере — шаг «манифесты модулей — форму судит один загрузчик»,
`.github/workflows/ci.yml:561–570`), и свой манифест **уже в её обходе**: «манифестов прочитано
1 · находок 0 · прочитан: manifest.yaml» (§14.1); встроенная копия побайтово равна ему (Р2),
поэтому до старта доезжает документ, который оснастка судила. Следствие для сценариев: MRW-09 и
MRW-10 держит оснастка дерева, а не старт службы (§5, §8); MRW-07 — положительный близнец
MRW-06, а не их.

**Признак нарушения этого решения — механический:** манифест службы оказался в перечне,
который читают пятеро. Проверяется тем, что довод применителя посева отличен от перечня
доставки, а не тем, что кто-то помнит про это правило.

### Р4. Идемпотентность выдачи держит ЕСТЕСТВЕННЫЙ КЛЮЧ живой строки

Применитель, встретив живую выдачу **того же субъекта** того же **отношения** на том же
**якоре**, не заводит второй строки, не отказывает и не трогает кортеж — независимо от того,
каким идентификатором эта строка заведена. Наблюдаемо: применение проходит, перепись выдач
показывает «записано 0», журнал прав не получает ни одной строки, идентификатор живой строки
не меняется.

Исходы, рассмотренные и отвергнутые, с их ценой:

| исход | почему отвергнут |
|---|---|
| миграция **переклеивает** живую строку на выведенный идентификатор | невыразимо: внешний ключ `access_binding_emitted_tuples_binding_id_fkey` объявлен **без** `ON UPDATE CASCADE` (`git grep -n 'access_binding_emitted_tuples_binding_id_fkey' -- internal/migrations` → `0001_initial.sql:5354`), поэтому `UPDATE … SET id` отвергается ссылкой ребёнка. У соседнего ключа `access_binding_subjects_scope_fk` каскад обновления **есть** (`:5362`) — то есть половина детей переехала бы, а половина отвергла бы переезд |
| миграция **снимает и заводит заново** | выразимо и дорого: уносит ведомость эмитированного каскадом удаления, эмитирует пару «снятие + запись» в журнал прав на **каждой** установке и заводит окно, в котором право отсутствует. Платится это ради совпадения идентификатора, которого снаружи никто не адресует: выдача системная и защищена от удаления |
| применитель **молча пропускает** выдачу, если хоть какая-то строка у субъекта есть | отвергнут: «выдача уже есть» и «выдача есть, но другая» стали бы неразличимы, а второе — настоящая находка |

Решение действует **для формы отношения**. Для формы роли живых строк посева сегодня ноль
(§2.2), и её естественный ключ — другой индекс (`access_bindings_active_grant_uniq`,
`0001_initial.sql:4443`); требование к ней названо в §4 отдельным сценарием, чтобы тот же
класс не пришлось находить второй раз.

### Р5. Живая группа относится к модулю, ЧЕЙ МАНИФЕСТ ЕЁ ОБЪЯВЛЯЕТ

Правило владельца для групп меняется: имя вида `kacho-<служба>` остаётся правилом для
**служебных записей**, а группа относится к модулю **по объявлению**. Группа, которую не
объявляет ни один прочитанный манифест, владельца не имеет, вердикту не подлежит и считается
переписью отдельно — тем же разрядом «без модуля-владельца», что и сегодня.

**Почему не «по имени с приставкой `module-`».** Приставка не называет владельца: обе
сегодняшние группы её несут, а объявлять их будет один манифест из шести. Правило по имени
пришлось бы менять снова с первой же группой, заведённой другим модулем.

**КЛЮЧ атрибуции — УЗКАЯ пара (аккаунт, имя); ключ сравнения остаётся ТРОЙКОЙ с назначением.**
Это не деталь реализации, а несущее различие, и без него обе стороны вердикта гаснут разом.
Ключ сравнения объявлен сегодня: `keysOfGroup` (`internal/moduleseedparity/parity.go:301`)
склеивает `Account \x00 Name \x00 Description`. Если тем же тройным ключом относить живую
строку к модулю, то группа, чьё живое назначение разошлось с объявленным, ни одному модулю не
достанется — уйдёт в разряд «без модуля-владельца», и **обе** стороны подраздела промолчат:
«ЖИВЁТ и не объявлена» не сработает (строки нет у модуля), «ОБЪЯВЛЕНА и не живёт» — тоже
(живой у модуля нет, но и находка о ней адресована бы никому). Перепись при этом напечатала бы
«с владельцем 0», и это выглядело бы исправной работой, потому что MRW-13 ровно такое состояние
объявляет законным. Поэтому: **относим по паре, сравниваем по тройке** — тогда дрейф назначения
даёт находку, а не молчание.

**Правило по объявлению распространяется и на ВЫДАЧУ, чей субъект — эта группа.** Это второе
следствие Р5, и без него MRW-11 («находок ноль») недостижим **by construction**: сегодня
владелец живой выдачи выводится из ИМЕНИ её субъекта тем же правилом `kacho-<служба>`, а имя
`module-relation-writers` ему не отвечает. Замер (временный опыт в пакете проб, снят за собой):

```
ownerOfSeededName("module-relation-writers")                        -> owner="" ok=false
ownerOfSeededName("kacho-vpc")                                      -> owner="vpc" ok=true
ownerOfBindingSubject("group", "", "module-relation-writers")       -> owner="" ok=false
ownerOfBindingSubject("service_account", "kacho-vpc", "")           -> owner="vpc" ok=true
```

То есть живая выдача `fga_writer` группе сегодня принадлежит **никому** (разряд «без
модуля-владельца»). Объяви её манифест `iam` — и у объявленной выдачи не окажется живой пары:
сверка выдаст **ложную** находку «выдача ОБЪЯВЛЕНА и не живёт» на верном дереве. Это ровно то,
чего опасается О4, но в подразделе **выдач**, а не групп, и прежняя редакция этого не называла.
Решение: выдача, чей субъект — группа, относится к модулю по **объявлению этой группы** —
той же паре (аккаунт, имя). Служебная запись как субъект правила не меняет: там имя
`kacho-<служба>` остаётся и работает.

**Довод godoc против второго правила назван и ОТВЕДЁН, а не обойдён молчанием.** Шапка
`ownerOfSeededName` (`internal/moduleseedparity/parity_test.go:392–397`) говорит: «Правило ОДНО
на служебную запись и на группу … Второе правило для второго предмета разошлось бы с первым
молча». Довод верен для того, о чём он написан, — и здесь не о том. Расходиться молча могут
**два правила об ОДНОМ предмете**: тогда у одной строки два ответа, и какой из них действует,
не решал никто. Здесь предметы **разные**: служебная запись относится к модулю по своему имени
(его назначает сам модуль, `kacho-<служба>`), группа — по тому, **кто её объявил**. У одной
строки по-прежнему **ровно один** ответ, и вопрос «какое правило применить» решается видом
строки, а не совпадением. Разойтись им не на чем by construction — а вот **одно** правило на
два предмета уже расходится с деревом: имя `module-relation-writers` его не удовлетворяет, и
владельцем группы сегодня не является никто.

**Что это делает с классификацией APPROVED-соседа — сказано, а не умолчано.**
`module-manifest-relation-grant.md` §5 и §3.7 относят обе живые группы и шесть живых выдач к
разряду «без модуля-владельца» и объявляют их предмет открытым отдельно — с посылкой «у них
нет модуля, чей манифест мог бы их объявить». Р5 эту классификацию **не отменяет**: она
**истекает** для двух строк вместе с Р1, потому что Р1 заводит ровно тот манифест, которого
посылка не видела. Группа `module-relation-writers` и её выдача `fga_writer` получают владельца
`iam`; остальные строки разряда остаются его предметом — исход и числа в §7, замер в §2.12.

**Сверка сравнивает написания СЫРЫМИ, и окно написаний в неё НЕ заводится.** Ключ пары
склеивается из `g.Account` как есть (`keysOfGroup`, `parity.go:301`), живая сторона читает
`a.name` из базы (`readLiveGroups`, `parity_test.go:453–470`), а окна
`domain.SeedIdentitySpellings` в пакете сверки нет ни одного вызова (§2.14). Следствие для
манифеста службы: **объявленное написание обязано совпадать с живым** — `account: system` (Р1).
Второй читатель окна здесь не заводится намеренно: окно существует ради **непереведённых чужих**
манифестов и истекает с их переводом (сосед, §7-П2); научив ему сверку, документ завёл бы
читателя, который переживёт предмет окна и сделает его снятие невидимым. Свой манифест
переведён с первой строки — ему окно не нужно.

**Что это НЕ ослабляет.** Обе стороны вердикта остаются: «группа ОБЪЯВЛЕНА и не живёт»
срабатывает, если объявленной строки в базе нет (MRW-12); «группа ЖИВЁТ и не объявлена»
срабатывает, если живая строка объявлена **этим** модулем с другим назначением (MRW-22).
Появление у группы владельца **сужает** разряд «без владельца», а не переносит строки в
молчание: обе величины печатаются рядом (`Subsection`, `parity.go:176–179` — «объявлено · живых
· без модуля-владельца · с владельцем»).

### Р6. `module-quota-readers` снимается ДВУМЯ стадиями в разных репозиториях, и порядок несущий

Сначала вступления уходят из манифестов платформы (S2а), потом строки — миграцией службы
(S2б). Обратный порядок ломает установку: применитель, встретив вступление в снятую группу,
отказывает (`groupID`: «группа %s/%s не резолвится»), и служба не поднимается.

Между стадиями живёт состояние «группа есть, вступлений в манифестах нет», в котором не
ломается ничто ни при какой комбинации версий: применитель не снимает строк, а пустая группа
ничего не открывает. **Членства в этом состоянии — от применителя, не от свода** (§1.3): на
установке, получившей доставку до S2а, они лежат в базе, сколько их записал `JoinGroup` по
`joins`, и применитель после S2а их **не снимает**; на самостоятельной установке их ноль — и
было ноль всегда, потому что членства свода сняла `20260909202745`. Обе формы этого состояния —
дома MRW-16 и MRW-24 (§5), и снимает их одна миграция S2б.

**И здесь надо сказать точно, чем это держится, потому что соблазн назвать соседний гейт
велик.** «Применитель не снимает строк» у посева держится **шапкой пакета**
(`sed -n '28,31p' internal/apps/kaname/moduleseed/apply.go`), и машинного держателя у него
нет: гейт `TestMODRD15ApplierNeverDeletesARoleRow` судит применитель **ролей**
(`internal/apps/kaname/moduleroles`) и о посеве не утверждает ничего — предмет назван первой
же строкой его разбора (`sed -n '4,14p' internal/check/applier_never_deletes.go`). Перенос
того же разбора на посев — выразимая работа, и она **здесь не заказывается**: предмет у неё
свой.

**След S2б — РЕШЕНИЕ, а не выбор исполнителя: одна запись аудита на ГРУППУ, ни одной на
членство, строка снятия кортежа на КАЖДОЕ членство.** Форма взята у штатных производителей, а
не придумана, — и у штатных производителей со-коммитов **четыре**, а не два; по каждому
сказано, повторяется он или беспредметен:

| со-коммит штатного производителя | координата | в S2б |
|---|---|---|
| снятие группы → запись аудита `iam.group.deleted` с арендатором | `internal/apps/kaname/api/group/audit.go:12`, эмиссия в writer-tx — `delete.go:92–101` | **повторяется**: одна запись на группу |
| снятие группы → событие реконсайла `ReconcileEventDelete` для `iam.group` — отзыв пообъектного кортежа владельца, материализованного при создании через API | `delete.go:89` | **беспредметен**: группу завёл свод, и ни кортежа владельца, ни зеркальной строки у неё нет — `grep -c 'iam_group:grp1ed8897b56bb9106f' internal/migrations/*.sql` → **0** в каждом файле, `grep -c "INSERT INTO kaname.resource_mirror" internal/migrations/0001_initial.sql` → **0**; отзывать реконсайлеру нечего, и ни одна применённая миграция в `resource_reconcile_outbox` не пишет (`grep -n 'INSERT INTO kaname.resource_reconcile_outbox' internal/migrations/*.sql` → пусто) |
| снятие члена → строка снятия кортежа `group:<группа>#member@service_account:<личность>` | `remove_member.go:104` | **повторяется**: по одной на каждое снятое членство, **безусловно** — штатный производитель состояния очереди не читает (ниже) |
| снятие члена → событие смены субъекта `group_member_change` — гашение кэша вердиктов края у члена | `remove_member.go:116` | **беспредметен**: гасить нечего — через эту группу член ничего не получает уже с `20260914091500` (выдача `quota_reader` снята, `:195`; выдач с субъектом-группой после цепочки **0**), а миграции дома в `subject_change_outbox` не пишут ни одна, включая ту, что снимала саму выдачу (`grep -n 'INSERT INTO kaname.subject_change_outbox' internal/migrations/*.sql` → пусто) |

Записи аудита на членство штатное снятие члена **не пишет** — и миграция не пишет. Форма
журнала — `fga_outbox_event_type_check` (`0001_initial.sql:1951`); прецедент строк снятия в
применённой миграции — `0001_initial.sql:3447`, `:3461–3464`; прецедент записи аудита с
`tenant_account_id` — `20260909202745:172`, `20260914091500:130`. Проекция журнала снимает
прямой факт сама: триггер `relation_fact_follows_journal` (`0001_initial.sql:5234`) читает
всякую строку снятия. В мире без членств (MRW-24) журнал не получает **ничего**, а запись
аудита остаётся одна — снимается группа.

**Состояние очереди — НЕ развилка формы, и почему обе миграции-прецедента здесь не образец.**
`20260914091500` различает два состояния очереди (`:160–186`): кортеж, чья запись уже
отправлена, — строка снятия; кортеж, чья запись **ещё в очереди**, — убирается сама строка
записи. Довод назван её пробой (`limit_reader_grant_revoked_integration_test.go:104–113`):
строку про отношение, которого **в модели больше нет**, дренаж отвергнет, и партиция встанет.
`20260909202745` снимает членства без строк снятия вовсе, чистя очередь и факты прямо
(`:210–221`), и её довод — «журнальные строки этих личностей уходят следом»: личности снимались
вместе с членствами. Здесь не действует **ни один**: отношение `group#member` в модели остаётся,
личности-члены остаются (они принадлежат доставленным манифестам, S2б их не трогает), а строка
снятия за строкой записи того же кортежа лежит в **той же партиции** очереди — `(user, object)`
(`internal/repo/kaname/pg/fga_outbox/emitter.go:204–216`), — и дренаж применяет их в порядке
идентификаторов: запись, потом снятие. Это ровно форма штатного `RemoveMember`, который
состояния очереди не читает. Поэтому «Дано» MRW-16 называет состояние очереди **фактом дома**
(строки записи ещё в очереди — дренажа в пробе нет), а «Тогда» требует N строк снятия **позже**
записей, а не «N либо ноль».

**Цена состояния названа, а не умолчана:** в посадке, где читаются манифесты платформы, сверка
паритета между S2а и S2б даёт находку «вступление ЖИВЁТ и не объявлено» — по одной на каждый
из пяти модулей. В посадке самостоятельного клона её нет: чужие модули там **считаются**, а не
судятся (`sed -n '207,238p' internal/moduleseedparity/parity_test.go`), и это измеренное
свойство, а не надежда.

### Р7. Свод перестаёт быть источником истины, но `0001` не правится

Применённую миграцию не правят (ban #5). Из этого следует по каждой строке §1.3:

| строка свода | что с ней делает эта работа |
|---|---|
| группа `module-relation-writers` | **усыновляется**: применитель кладёт объявленное поверх неё по ограничению уникальности (П4), идентификатор не меняется |
| выдача `fga_writer` | **усыновляется** естественным ключом (Р4); новой миграции для неё не требуется |
| группа `module-quota-readers` и её членства — **сколько их применил применитель**, из свода после `20260909202745` их ноль | **снимаются** новой миграцией (S2б); число снятых членств печатается переписью, а не предполагается равным пяти |
| выдача `quota_reader` | уже снята миграцией `20260914091500`; эта работа её не касается |
| членства в `module-relation-writers` | из свода их **нет** — сняты `20260909202745` вместе с личностями; живые заводит применитель по `joins` доставленных манифестов, и эта работа их не трогает |

## §4 Сценарии

Идентификаторы `MRW-01…MRW-25` трассируются в имена проб. Все «Дано» строятся домом,
названным в §5. Сценарии `MRW-19…MRW-21` и `MRW-23` стоят в конце стадии S1, к которой
принадлежат, `MRW-22` — рядом со своим близнецом `MRW-13`, потому что его предмет — сверка, а
`MRW-24` — между `MRW-16` и `MRW-17`, потому что он их разделяет по одному факту, а `MRW-25` —
после `MRW-17`, рядом со своим близнецом `MRW-24`: номер здесь трассировочный якорь, а не
порядок чтения. «Системный аккаунт» в сценариях означает аккаунт с
именем `system` (Р1).

### S1 — манифест службы объявляет свою группу

**MRW-01 · чистая установка: группа и выдача заведены объявлением**

- **Дано** установка службы, чья база поднята применением всех миграций дерева, и манифест
  службы объявляет раздел `seed` по Р1
- **И** доставки манифестов платформы нет (`manifests.dir` не объявлен посадкой)
- **Когда** служба стартует
- **Тогда** в базе есть **ровно одна** группа с именем `module-relation-writers` в аккаунте
  `system` (Р1), и её назначение равно объявленному манифестом
- **И** у неё есть **ровно одна** активная выдача отношения `fga_writer` на объекте
  `cluster:cluster_root`, с признаком системной и защитой от удаления
- **И** членов у группы **ноль** — членства свода сняла применённая `20260909202745`, а доставки
  здесь нет (§1.3); это верное состояние, а не пробел
- **И** служба принимает трафик (стадия применения посева не отказала)

**MRW-02 · повторный старт ничего не меняет**

- **Дано** установка MRW-01 после успешного старта
- **Когда** служба перезапускается без единой правки манифеста
- **Тогда** перепись применения своего манифеста печатает «групп 0/1 · выдач 0/1»
  (записано/объявлено)
- **И** идентификатор строки группы и идентификатор строки выдачи те же, что до перезапуска
- **И** в журнал прав не добавлено ни одной строки

**MRW-03 · идентификатор, выведенный при ПРЕЖНЕМ якоре, усыновляется, а не отвергается**
*(положительный близнец MRW-02; отличается ОДНИМ фактом — идентификатор живой строки выведен при
написании якоря `cluster_kacho_root`, тогда как выражение применителя берёт якорь живой,
`cluster_root`, и даёт другое значение)*

- **Дано** установка, чья база несёт живые строки свода §1.3 — две группы и выдачу `fga_writer`
  с идентификатором `acb9e920fb038c7e4f74`; членств у групп после цепочки миграций **нет**, и
  этот сценарий о них не утверждает
- **Когда** служба с манифестом Р1 стартует впервые
- **Тогда** применение посева **проходит** — отказа с кодом нарушения уникальности нет
- **И** строк активной выдачи отношения `fga_writer` группе на кластере в базе **одна**, и её
  идентификатор по-прежнему `acb9e920fb038c7e4f74`
- **И** ведомость эмитированного этой выдачи не изменилась, и в журнал прав не добавлено ни
  одной строки — то есть кортеж не перезаписан и не снят

**MRW-04 · своё применяется раньше доставленного**

- **Дано** установка, из базы которой **снята** строка группы `module-relation-writers` —
  вместе с её выдачей, потому что иного порядка схема не допускает (§5), — и чья доставка несёт
  манифест `compute` со вступлением в эту группу (в пробе службы — **синтетический**, положенный
  пробой в каталог доставки; строитель — §5)
- **Когда** служба стартует
- **Тогда** вступление `compute` записано, отказа «группа не резолвится» нет
- **И** перепись называет **раздельно**: свой манифест применён, доставленных манифестов —
  число

> Снятие строки здесь **несущее**, а не аккуратность: на базе миграций дерева группа жива из
> свода (§2.10), и `groupID` резолвит её при любом порядке обхода — «Тогда» выполнялось бы
> **независимо от Р3**, то есть сценарий не мог бы упасть на неверном порядке.

**MRW-05 · самостоятельная установка без платформы**
*(отрицательный близнец MRW-04 по ОДНОЙ оси — доставки нет вовсе)*

- **Дано** та же база, что у MRW-04 — со снятой строкой группы и её выдачей, — и установка,
  чья посадка не объявляет каталог доставки
- **Когда** служба стартует
- **Тогда** группа и её выдача заведены **применителем**: строк по одной, назначение и якорь
  равны объявленным манифестом
- **И** членов у группы ноль, и это не отказ: перепись печатает «доставленных манифестов 0».
  Ноль здесь — **от отсутствия доставки**, а не от снятия строки: их не было бы и на нетронутой
  базе миграций (§1.3, `20260909202745`)

**MRW-06 · группа без выдачи отвергается формой**

- **Дано** манифест службы, объявляющий группу `module-relation-writers` и **не** называющий
  её ни в одной выдаче
- **Когда** манифест разбирается судьёй формы
- **Тогда** разбор даёт находку рода `ErrGroupNeverGranted`, называющую путь `seed.groups[0]` и
  номер строки документа
- **И** служба с таким манифестом не стартует

**MRW-07 · положительный близнец MRW-06**
*(отличается ОДНИМ фактом — выдача названа)*

- **Дано** тот же манифест, дополненный выдачей `fga_writer` этой группе на кластере
- **Когда** манифест разбирается тем же судьёй
- **Тогда** находок ноль, и служба стартует

**MRW-08 · якорь вне кластерного singleton'а отвергается**

- **Дано** манифест службы, чья выдача объявлена с `scopeType: iam.account`
- **Когда** манифест разбирается судьёй формы
- **Тогда** находка рода `ErrBindingAnchor` с путём `seed.accessBindings[0]`
- **И** та же выдача с `scopeType: iam.cluster` находок не даёт *(обе стороны оси названы)*

**MRW-09 · отношение вне канона отвергается**

- **Дано** манифест службы, чья выдача называет отношение, которого канон у типа `cluster` не
  объявляет
- **Когда** манифест разбирается судьёй формы **с внесённым каноном** — так его зовёт оснастка
  дерева (`make module-manifest-check`, шаг конвейера; §5)
- **Тогда** находка рода `ErrRelationNotDeclared`
- **И** та же выдача с `fga_writer` находок не даёт *(обе стороны названы)*
- **И** на пути старта тот же документ оракула не получает, и этот отказ там **не производится**
  (Р3): сценарий держит оснастка дерева, а не старт службы

**MRW-10 · получатель, которого отношение не принимает, отвергается**

- **Дано** манифест службы, объявляющий получателем **группу** на отношении `system_viewer`
  кластера — канон принимает у него `user` и `service_account`, но не членство группы
- **Когда** манифест разбирается судьёй формы **с внесённым каноном** — оснасткой дерева (§5)
- **Тогда** находка рода `ErrRelationRecipientKind`, и текст называет **принимаемые** виды
- **И** та же группа на `fga_writer` принимается *(обе стороны названы: отношение, принимающее
  членство, и отношение, его не принимающее)*
- **И** на пути старта этот отказ не производится — как у MRW-09 (Р3)

**MRW-11 · сверка паритета зелена на объявленной группе**

- **Дано** база, поднятая миграциями и приведённая применителем к манифесту Р1
- **Когда** прогоняется сверка посева
- **Тогда** находок ноль
- **И** перепись по подразделу групп печатает четыре величины, и «с владельцем» **не** ноль:
  живая `module-relation-writers` отнесена к модулю `iam`
- **И** перепись по подразделу **выдач** печатает те же четыре величины, и «с владельцем»
  **не** ноль: живая выдача `fga_writer` группе отнесена к модулю `iam` **по объявлению её
  группы** — той же паре `(system, module-relation-writers)` (Р5, второе следствие). Это
  положительная сторона оси, чью отрицательную несёт MRW-12 в подразделе выдач; без неё
  реализация, отбрасывающая выдачи с субъектом-группой из сравнения, была бы зелена по обоим

**MRW-12 · объявленной группы нет в базе — находка остаётся**
*(отрицательный близнец MRW-11, ОДНО отличие мира: объявленной строки группы в базе нет)*

- **Дано** та же база, из которой строка группы снята — **вместе с её выдачей**, потому что
  иного порядка схема не допускает: снятие строки группы, пока она числится субъектом выдачи,
  отвергается триггером `groups_subject_ref_before_delete_trg` кодом `23503`
  (`0001_initial.sql:5171`, функция `principal_not_referenced_as_subject`, `:1302–1319`).
  Зависимое снятие — **не второй факт мира**, а порядок, который схема диктует для одного
- **Когда** прогоняется та же сверка
- **Тогда** находка «группа ОБЪЯВЛЕНА и не живёт», называющая модуль `iam` и файл манифеста
- **И** находок по подразделу групп ровно **одна** — вторая сторона («ЖИВЁТ и не объявлена») не
  срабатывает: живой строки нет вовсе
- **И** рядом приходит находка подраздела **выдач** — «выдача ОБЪЯВЛЕНА и не живёт»: живой
  выдачи не стало вместе с группой. Её ждут **вместе** с первой; сценарий, требующий ровно
  одной находки на весь прогон, был бы красным на верном поведении

**MRW-13 · живая группа, которую не объявляет никто, владельца не получает**

- **Дано** база, в которой есть группа с именем, не объявленным ни одним прочитанным
  манифестом
- **Когда** прогоняется сверка
- **Тогда** находок по ней нет
- **И** перепись считает её в разряде «без модуля-владельца», и это число печатается
- **И** её выдача, если она есть, считается в **том же** разряде подраздела выдач и находки не
  даёт: владелец выдачи выводится из объявления её группы, а группу не объявил никто (Р5)

**MRW-22 · живая группа объявлена этим модулем с ДРУГИМ назначением — находка остаётся**
*(отрицательный близнец MRW-11, ОДИН факт отличия — назначение живой строки разошлось с
объявленным; MRW-12 отличается от MRW-11 другим фактом — отсутствием живой строки, поэтому это
не он)*

- **Дано** база MRW-11 — приведённая применителем к манифесту Р1, — в которой назначение живой
  строки группы `module-relation-writers` изменено и с объявленным манифестом не совпадает
- **Когда** прогоняется та же сверка
- **Тогда** находок по подразделу групп **две**, и обе называют модуль `iam` и файл манифеста:
  «группа ЖИВЁТ и не объявлена» — с ЖИВЫМ назначением, «группа ОБЪЯВЛЕНА и не живёт» — с
  ОБЪЯВЛЕННЫМ
- **И** перепись по подразделу групп печатает «с владельцем» **не ноль**: живая строка отнесена
  к модулю `iam` **по паре (аккаунт, имя)**, а не по тройке с назначением — иначе она ушла бы в
  разряд «без модуля-владельца» и обе находки погасли бы разом (Р5)
- **И** на той же базе **без** правки назначения (MRW-11) находок ноль *(обе стороны оси
  «назначение сошлось / разошлось» названы)*

**MRW-14 · выдача роли усыновляется своим естественным ключом**

- **Дано** манифест, объявляющий выдачу **ролью** субъекту, у которого такая активная выдача в
  базе уже есть с другим идентификатором
- **Когда** применяется посев
- **Тогда** применение проходит, строк выдачи остаётся одна, изменений ноль
- **И** та же выдача, которой в базе нет, заводится, и перепись считает её записанной
  *(обе стороны оси «строка есть / строки нет» названы)*

**MRW-19 · выдачи отношением в базе НЕТ — применитель её ЗАВОДИТ**
*(близнец MRW-03 по ОДНОЙ оси «строка есть / строки нет»; отличается одним фактом — строка
выдачи удалена из базы до применения)*

- **Дано** установка, чья база поднята миграциями дерева и из которой **удалена** строка активной
  выдачи отношения `fga_writer` группе `module-relation-writers` на `cluster:cluster_root`
  вместе с её дочерним субъектом и ведомостью эмитированного
- **И** строка самой группы на месте
- **Когда** служба с манифестом Р1 стартует
- **Тогда** применение проходит, и в базе есть **ровно одна** активная выдача отношения
  `fga_writer` этой группе на `cluster:cluster_root`
- **И** перепись выдач печатает «записано **1**» — то есть строку завёл применитель, а не
  миграция
- **И** журнал прав получил **ровно одну НОВУЮ** строку записи кортежа (строки, оставшиеся от
  свода, не считаются: они старше применения), а ведомость эмитированного — ровно одну строку
- **И** на той же базе **без** удаления строки (MRW-03) та же перепись печатает «записано **0**»,
  и журнал не получает ничего *(обе стороны оси названы)*

**MRW-20 · форма субъекта у получателя-ГРУППЫ несёт СИГИЛ ЧЛЕНСТВА**

- **Дано** мир MRW-19 — строки выдачи в базе нет, применитель её заводит
- **Когда** служба с манифестом Р1 стартует
- **Тогда** субъект FGA, записанный в ведомость эмитированного, равен субъекту, который отдаёт
  объявленный источник формы (П9) для пары (`group`, идентификатор группы), — то есть несёт
  сигил членства, а не голый объект группы
- **И** полезная нагрузка строки журнала прав несёт **того же** субъекта побайтово
- **И** идентификатор заведённой выдачи выведен из **этой же** формы: он равен идентификатору,
  который даёт выражение применителя на субъекте с сигилом, и **не равен** тому, что оно даёт на
  голом объекте группы
- **И** записанный субъект совпадает **дословно** с тем, что свод пишет для этой же выдачи
  своим литералом (`0001_initial.sql:3162` и запись **24** журнала прав) — то есть применитель и
  свод адресуют одного субъекта, а не двух

**MRW-21 · положительный близнец MRW-20 на служебной записи**
*(отличается ОДНИМ фактом — вид получателя: служебная запись вместо группы)*

- **Дано** доставленный манифест модуля, чья выдача посева адресована **служебной записи**
  (в пробе службы — синтетический, по прецеденту `seedProbeManifest`, §5), и база, в которой
  этой выдачи нет
- **Когда** применяется посев
- **Тогда** субъект FGA, записанный в ведомость эмитированного и в журнал прав, равен
  `service_account:<идентификатор>` — **без** сигила членства
- **И** он совпадает с тем, что отдаёт объявленный источник формы для той же пары *(обе стороны
  оси «вид получателя» названы: на группе формы расходились, на служебной записи совпадают)*

**MRW-23 · строки ГРУППЫ в базе НЕТ — применитель её ЗАВОДИТ**

  **не факт дома**: миграция каталога доставки не читает (§6, предикат допуска S2б внешний), а
  членства, записанные применителем, остаются в базе при любом её состоянии — применитель строк
  не снимает (Р6); что будет со следующим стартом при отставшей доставке — MRW-18

**Чем каждый дом строится.** Состояния базы — поднимаемой в пробе базой службы, к которой
применяются миграции дерева; состояния манифеста — документом, поданным судье формы, без
файла в дереве, причём для MRW-09/10 судья получает **канон образа как оракул** (ниже);
состояния доставки — каталогом во временном каталоге пробы, куда она кладёт **синтетические**
манифесты (ниже). Ни одно «Дано» не требует
состояния, которого схема не допускает: все строки, о которых идёт речь, схема уже держит
(группа, выдача формы отношения на кластере, членство). **Живые экземпляры после цепочки
миграций есть у двух видов из трёх:** обе группы и выдача `fga_writer` живы из свода, а членств
**нет ни одного** — их сняла `20260909202745` (§1.3, вторая таблица). Поэтому дом, которому
нужны членства (MRW-16), строится **не миграциями дерева**, а применителем с доставленными
манифестами: `JoinGroup` пишет строку `group_members` на каждый `join` (`module_seed_writer.go:203`),
и число их равно числу доставленных манифестов со вступлением. Дом «группа есть, членств ноль»
(MRW-24) — это и есть база миграций дерева как она есть.

**Дом MRW-16 обязателен и обязателен именно ПОСЕВОМ, а не перечислением.** Прежние редакции
называли строителем «базу миграций дерева» и число «5» — из свода; на такой базе проба либо
падала бы на «Дано» («членств 5 ожидалось, есть 0» — красное на верном дереве), либо зеленела
вакуумно: «на каждое снятое членство журнал получил строку» истинно при нуле снятых, и миграция,
не пишущая в журнал вовсе, проходила бы MRW-16. Различает стороны только посев членств
применителем — и близнец с нулём членств (MRW-24), который вакуумную реализацию **не** ловит
by construction и потому стоит рядом, а не вместо.

**Доставку в пробе службы строит СИНТЕТИЧЕСКИЙ манифест, и это единственный годный
строитель.** Манифестов платформы в дереве службы нет и быть не может: `git ls-files | grep -cE
'(^|/)manifest\.yaml$'` → **1** (свой), а пакет проб говорит это словом — «манифесты СОСЕДЕЙ
доезжают ДОСТАВКОЙ в рантайме … заводить здесь их копию значило бы завести второе место об одном
предмете» (`internal/testsupport/modulemanifests/modulemanifests.go:37–41`; ban #20). Строителей
два, годен один:

| строитель | что даёт | почему |
|---|---|---|
| **синтетический манифест внутри пробы** (принят) | документ в памяти пробы: `module` из закрытого набора, раздел `seed` с личностью и вступлением в группу, положенный файлом во временный каталог доставки | прецедент в этом же дереве: `seedProbeManifest` (`internal/repo/kaname/pg/module_seed_writer_integration_test.go:38–66` — `module: vpc`, личность, выдача, вступление в **живую** `module-quota-readers`) и каталог доставки, собираемый пробой (`internal/manifest/delivery_test.go:33,54`). Строится в любой посадке |
| чтение соседнего дерева платформы (`platformtree.Require`, `internal/testsupport/platformtree/platformtree.go:118`) | манифесты пяти модулей на ревизии K | в самостоятельном клоне и **в конвейере** проба **пропускается** (образец — `internal/check/quota_reader_grant_test.go:13`), то есть у MRW-04/16/18/21 не было бы производителя ровно там, где вердикт нужен |

Следствие для чисел: **N в MRW-16 — число синтетических вступлений (≥ 1), а не пять.** «На
ревизии K — пять» (§1.4) — утверждение о посадке платформы, и о ней оно остаётся верным; о доме
пробы оно не говорит ничего. Синтетические манифесты называют аккаунт группы написанием
`system`, не `kacho-system` (§6 S1 п. 7: литерал прежнего написания в `_test.go` двигал бы ведро
«живой» соседа).

**Дом MRW-09 и MRW-10 несёт ОРАКУЛ КАНОНА как факт дома, а не как умолчание судьи.** Судья
формы производит `ErrRelationNotDeclared` и `ErrRelationRecipientKind` только с внесённой
моделью: без неё он «о существовании отношения не утверждает ничего» — `if oracle == nil {
return nil }` (`internal/manifest/relationgrant.go:161–163`), и это решение, а не пробел
(`internal/manifest/relationoracle.go:100–118`: на пути старта модель ещё собирается из
доставленного). Вносит оракул **оснастка дерева**: `internal/manifestcheckrun/run.go:100,238`
(`manifest.WithRelationOracle(…)` с `manifestoracle.Canon()`,
`internal/manifestoracle/manifestoracle.go:60`), которую зовут `make module-manifest-check`
(`Makefile:299–302`, `tools/modulemanifestcheck`) и `iamctl validate` (`cmd/iamctl/main.go:87`);
в конвейере — шаг «манифесты модулей — форму судит один загрузчик»
(`.github/workflows/ci.yml:561–570`). Единственный прод-вызов `WithRelationOracle` — в этой
оснастке: `git grep -n WithRelationOracle -- cmd internal ':!*_test.go'` → `run.go:100`,
`run.go:238`. На пути старта свой манифест читается **без** оракула (Р3), поэтому MRW-09/10
держит оснастка дерева, а MRW-07 — положительный близнец MRW-06, не их: обе стороны каждой из их
осей названы **внутри** MRW-09 и MRW-10. Замер §14.1: `make module-manifest-check` на дереве
этой редакции → код 0, «манифестов прочитано 1 · находок 0 · прочитан: manifest.yaml» — свой
манифест уже в обходе.

**Дом MRW-17 строится ДО прямого хода, а не «повторным применением», и снятие строки группы
выразимо.** «Та же миграция применяется повторно» у `goose` не существует: применённая версия
второй раз не исполняется, а откат восстанавливает группу (`Down`, §6 S2б) — тогда прямой ход
находит её снова (MRW-25). Мир «группы нет к моменту прямого хода» строится тем же приёмом, что
`limit_drop_refusal_integration_test.go:75`: `goose.UpTo(db, ".", <версия S2б> − 1)`, прямое
`DELETE FROM kaname.groups WHERE id = 'grp1ed8897b56bb9106f'`, затем `goose.Up`. Снятию ничто
не мешает: после `20260914091500` строка не числится субъектом ни одной выдачи (`:195` снимает
выдачу, субъекты уходят каскадом `access_binding_subjects_scope_fk`, `0001_initial.sql:5362`),
членств у неё ноль (§1.3), триггер журнала ресурса только пишет строку
(`20260914090000:338`, функция `:192–227` — `INSERT` без `RAISE`), а триггеру
`groups_subject_ref_before_delete_trg` не на чем сработать.

**Дом MRW-25 — форма прецедента дословно:** `goose.Up` до конца, затем `goose.Down` в цикле,
пока версия базы не станет ниже версии S2б, затем `goose.Up` снова
(`limit_reader_grant_revoked_integration_test.go:148–184`); откат идёт «ДО СВОЕЙ версии, а не
„на один шаг“» — иначе проба утверждала бы, что её предмет — последняя миграция дерева, и
ломалась бы от следующей (там же, `:148–150`). Прецедент прогнан на дереве этой редакции:
PASS, «откат: миграций снято 2 (до версии ниже 20260914091500)» (§14.1).

**Дом MRW-19 строится СНЯТИЕМ, и снятие выразимо.** Мир «строки выдачи нет» получается тем же
приёмом, каким документ уже пользуется в MRW-12, — удалением строки из базы до применения.
Защита от удаления у этой строки стоит **колонкой**, а не триггером (`0001_initial.sql:1614`,
`deletion_protection boolean`), то есть держится прикладным слоем и прямому удалению фикстурой
не препятствует; дочерние строки уходят с ней сами — внешний ключ ведомости эмитированного
объявлен с каскадным удалением (`0001_initial.sql:5354`). Схема при этом не допускает **лишь**
второй активной строки той же выдачи, а ноль строк допускает: частичный уникальный индекс
судит дубль, а не отсутствие.

**Дом MRW-12 несёт ПОРЯДОК, который диктует схема, а не второй факт мира.** Строку группы,
числящуюся субъектом выдачи, прямое удаление не берёт: триггер
`groups_subject_ref_before_delete_trg` (`0001_initial.sql:5171`) отвергает его кодом `23503`
через `principal_not_referenced_as_subject` (`:1302–1319`). Значит выдача снимается первой, и
дочерняя строка субъекта уходит с ней сама — внешний ключ `access_binding_subjects_scope_fk`
объявлен с `ON DELETE CASCADE` (`:5362`). Дельта против MRW-11 остаётся **одна** — объявленной
группы в базе нет; но следствие этого порядка наблюдаемо, и потому названо в «Тогда» MRW-12
отдельной строкой: приходит **и** находка подраздела выдач. Скрыть её было бы хуже, чем
назвать: проба, требующая ровно одной находки, покраснела бы на верном поведении.

**Дом MRW-23, MRW-04 и MRW-05 — ОДИН, и строится он СНЯТИЕМ СТРОКИ ГРУППЫ.** Три сценария
делят один мир и утверждают о нём разное: MRW-23 — пишущую ветвь группы (ось «строка есть /
строки нет», близнец MRW-02), MRW-04 и MRW-05 — порядок и доставку (ось «доставка есть /
доставки нет», близнецы друг другу). Так же устроены MRW-19 и MRW-20, делящие мир снятой
выдачи.

**Порядок внутри дома диктует схема, а не второй факт мира** — тот же довод, что у MRW-12.
Строку группы, числящуюся субъектом выдачи, прямое удаление не берёт: триггер
`groups_subject_ref_before_delete_trg` (`0001_initial.sql:5171`) отвергает его кодом `23503`
через `principal_not_referenced_as_subject` (`:1302–1319`). Значит выдача снимается первой,
дочерняя строка субъекта уходит с ней каскадом (`access_binding_subjects_scope_fk`, `:5362`), а
членства — **если они есть** — уходят каскадом внешнего ключа группы
(`group_members_group_fk … ON DELETE CASCADE`, `0001_initial.sql:5458`). В этом доме их **нет**:
доставки он не получает, а членства свода сняты миграцией (§1.3), — каскад здесь свойство схемы,
а не факт базы, и уносить ему нечего. Ни одно из снятий не является вторым фактом: это
единственный порядок, которым схема допускает первый.

**Триггеры журнала ресурса снятию не мешают, и это проверено чтением.** На `groups` и
`access_bindings` цепочка добавила триггеры `BEFORE DELETE`
(`20260914090000_resource_journal_serves_the_subscription.sql:314`, `:338`); их функция
`resource_journal_emit` только пишет строку журнала ресурса (`INSERT`, без `RAISE`,
`:192–227`), поэтому прямое удаление фикстурой она пропускает. Прежние редакции говорили «BEFORE
DELETE нет» только о своде; на полной цепочке они есть, и конструируемости это не меняет.

**Наблюдаемое следствие названо в «Тогда», а не скрыто.** В мире без доставки (MRW-05, MRW-23)
членов у группы после применения **ноль** — вступления приезжают доставкой, а её нет; это ровно
то, что MRW-05 и утверждает. Скрыть было бы хуже, чем назвать: проба, ждущая пяти членов,
покраснела бы на верном поведении.

**Почему этот дом ОБЯЗАТЕЛЕН, а не удобен.** На базе миграций дерева строка группы жива из свода
и снимающей её миграции нет ни одной (§2.10). Значит «Тогда», говорящее о **состоянии** группы,
на такой базе истинно независимо от применителя, а «Тогда» о **записи** — беспредметно. Дом со
снятой строкой — единственный, в котором обе стороны оси различимы.

**Дом MRW-22 строится ПРАВКОЙ, и правка выразима.** Назначение живой строки меняется прямым
`UPDATE kaname.groups SET description = …`: ограничение на колонке одно — длина не больше 256
(`groups_description_check`, `0001_initial.sql:1999`), запрещающего триггера нет, а тот, что
есть на обновлении, лишь пишет строку в журнал ресурса
(`20260914090000_resource_journal_serves_the_subscription.sql:311`). Применитель это состояние
не «чинит» по дороге: сверка прогоняется **после** применения, а применитель кладёт объявленное
назначение конфликтом `DO UPDATE SET description` — поэтому правка делается между применением и
сверкой, как и удаление строки в MRW-12.

**Дом MRW-21 обязан называть «выдачи в базе нет», и это НЕСУЩЕЕ.** Без этого факта «Тогда»
беспредметно: писатель объявляет конфликт `ON CONFLICT (id) DO NOTHING` и на живой строке
возвращает `RowsAffected()==0`, то есть **ни** ведомость эмитированного, **ни** журнал прав не
получают ничего (`internal/repo/kaname/pg/module_seed_writer.go:300–334`) — утверждать о форме
записанного субъекта было бы не о чем. Прежняя редакция называла в доме только вид получателя.

**Одно «Дано» требует оговорки.** MRW-03 просит живую строку, чей идентификатор выведен при
прежнем написании якоря. Она **не синтетика**: именно её заводит `0001_initial.sql:3196` на
**каждой** установке, включая чистую, а якорь переименовывается следом — тоже на каждой. То есть MRW-03 и MRW-01 описывают одну и ту же базу с разных сторон, и
различие между «чистой» и «живой» установкой здесь не в этой строке, а в том, применялся ли
посев прежде.

**Признак готовности S1:** сверка посева зелена, перепись **обоих** тронутых подразделов —
групп и выдач — печатает «с владельцем» не ноль; применение на базе с живыми строками свода
проходит без отказа; применение на базе, из которой строка **выдачи** удалена, печатает
«выдач записано 1» и кладёт субъекта **с сигилом членства**, а на служебной записи — **без**
него; применение на базе, из которой удалена строка **группы** (вместе с её выдачей — порядок
диктует схема), печатает «групп записано 1» и чеканит идентификатор, отличный от снятого, а на
той же базе без удаления — «групп записано 0» (обе половины оси, а не одна: строка группы жива
из свода на каждой установке, поэтому «есть ровно одна группа» истинно и при применителе,
который раздела `seed.groups` не читает, — §2.10); **проба** побайтового равенства встроенной
копии зелена, и правка `manifest.yaml` **без пересборки копии её роняет** (цель сборки этого
признака не исполняет — она копию восстанавливает, а не сверяет две); довод применителя посева
отличен от перечня доставки; ни одно из **шести** утверждений п. 8 в дереве не встречается;
держатель атрибуции `TestModuleManifestDeclaresTheSeedTheLiveBaseHolds` **PASS** в посадке
самостоятельного клона (Postgres) с переписью «группы … с владельцем **1** · выдачи … с
владельцем **1** · вступления … живых **0**», и его исполняет контейнерное задание конвейера —
отбор `run-integration.sh` называет `internal/moduleseedparity` и `internal/migrations`
(п. 9–10).

### S2а — вступления в снимаемую группу уходят из манифестов платформы (репозиторий `PRO-Robotech/kacho`)

Пять правок, по одной на манифест (§1.4, левый столбец), плюс шапки пяти манифестов, которые
после S1 утверждают неверное: группу заводит **служба**, а не платформа.

**Признак готовности S2а** (предикат исполнимый, по копии платформы):
`for m in compute nlb registry storage vpc; do git -C <копия платформы> show origin/main:services/$m/manifest.yaml | grep -c 'module-quota-readers'; done`
→ **0** во всех пяти; та же команда по `module-relation-writers` → **1** во всех пяти.

### S2б — строки снимаются миграцией службы (репозиторий `PRO-Robotech/kaname`)

Новая миграция **с обеими половинами**. Прямой ход снимает строку группы и её членства —
**сколько их записал применитель** (из свода после `20260909202745` их ноль, §1.3), — кладёт в
журнал прав строку снятия кортежа на каждое членство, запись аудита по группе и печатает
перепись числами. **Откатная половина (`Down`) — контракт, а не выбор исполнителя**, и он взят у
обоих прецедентов дома (`20260909202745:107–118`, `20260914091500:210–270`):

- `Down` возвращает **строку группы свода дословно** — идентификатор `grp1ed8897b56bb9106f`,
  аккаунт `acc1a18042d81fb438d6` (`system`), назначение и метки строки `0001_initial.sql:3488`.
  Идентификатор — тот же, а не отчеканенный заново: он стоит в записи аудита прямого хода и в
  `Down` соседней `20260914091500` (`:219`, `v_group`), и выданный заново отвязал бы откат от
  того, что снималось;
- `Down` **не возвращает членств** — ни свода (их сняла `20260909202745`, и её `Down` вернёт
  свои сам), ни применителя (они принадлежат доставке, и восстановит их следующий старт по
  `joins`, если доставка их ещё объявляет). Это тот же предел, который прецедент называет
  словом: «не восстановит строки, которые появились ПОСЛЕ прямого хода — их заводит
  применитель» (`20260909202745:115–118`);
- `Down` **не пишет ни в журнал прав, ни в аудит**: кортежей возвращать не с чего (членств нет),
  а запись аудита о снятии остаётся свидетельством состоявшегося снятия и не «отменяется»;
- **откатная цепочка сходится by construction:** `goose` откатывает версии от старшей к младшей,
  поэтому `Down` этой миграции возвращает группу **раньше**, чем `Down` `20260914091500`
  попробует вернуть ей выдачу `quota_reader`, — а тот на отсутствующей группе **выходит молча**
  (`IF NOT EXISTS … RAISE NOTICE … RETURN`, `:234–237`). Пустой `Down` здесь оставил бы откат
  соседа без предмета — второе основание, по которому он не может быть пустым (§14.2).

Сценарии `MRW-16`, `MRW-24`, `MRW-17`, `MRW-25`, `MRW-18`. Механизм «повторного применения» в
доме миграций один — откат до своей версии и накат снова (`goose.Down` в цикле, пока версия
базы не станет ниже своей, затем `goose.Up`; форма прецедента
`TestLimitReaderGrant_DownRestoresTheGrantAndTheReapplyConverges`,
`internal/migrations/limit_reader_grant_revoked_integration_test.go:137–184`, прогнан — §14.1:
PASS, «откат: миграций снято 2»). Отдельного «применить ту же версию ещё раз» у `goose` нет, и
прежняя формулировка MRW-17 этим механизмом не строилась (§14.1, ОП-3); мир «группы нет» строится
до прямого хода (§5).

**Признак готовности S2б:** в базе после применения нет ни группы, ни её членств; на каждое
снятое членство есть строка снятия в журнале — **позже** строки записи того же кортежа по
идентификатору очереди, — и прямого факта членства в проекции не осталось; запись аудита **одна
на группу** типа `iam.group.deleted` с арендатором, на членства — ни одной (Р6, решение о
следе); перепись печатает «членств N · группа 1» на базе с членствами от применителя (MRW-16),
«членств 0 · группа 1» на базе миграций без доставки (MRW-24) и «членств 0 · группа 0» на базе,
где группы нет к прямому ходу (MRW-17), — три исхода прямого хода, и отсутствие группы —
перепись, а не отказ; **откат и повторный накат сходятся** (MRW-25): после `Down` строка группы
на месте с тем же идентификатором и назначением, членств ноль, журнал и аудит без новых строк,
после `Up` снова — «членств 0 · группа 1». Пробы миграции живут в `internal/migrations` и
исполняются контейнерным заданием конвейера по отбору S1 п. 10.

**Предикат допуска S2б — ВНЕШНИЙ, и это сказано прямо.** Стадия не применяется, пока S2а не
выпущена платформой и не доехала доставкой до установок. Машинной проверки у этого условия
нет: миграция исполняется в init-контейнере и каталога доставки не читает by construction.
Держится это **порядком работ**, а не гейтом; признак для ведущего линию — S2а влита в ствол
платформы и попала в выпуск.

Эта работа его **сужает**, а не закрывает: из разряда уходят **две** строки — группа `module-relation-writers` и её выдача `fga_writer`, — потому что посылка соседа «нет модуля, чей манифест мог бы их объявить» истекает вместе с Р1 ровно для них. Между доставленными порядок **не решён**, и это состояние без предмета, а не отсрочка: доставленных манифестов, объявляющих группу, — **ноль из пяти**. ## §9 Чем это будет держаться

| требование | чем | почему не иначе |
|---|---|---|

## §10 Публичный репозиторий

Оба репозитория публичны. Документ называет **предмет**, **решение** и **следствие для
контракта** и не собирает в одном месте тройку «координата + условие, при котором защита не
действовала + следствие для постороннего».

Что названо и почему это безопасно: имена группы, отношения и якоря лежат в открытом своде и
в открытом каноне; состав получателей права работой **не меняется**; отказ, описанный в §2.2,
есть отказ **старта службы**, а не обход защиты — он закрывает установку, а не открывает её.
Идентификаторы строк (`grp…`, `acb…`) — идентификаторы **системных** строк, одинаковые на
каждой установке по построению свода, и адресовать ими снаружи нечего: обе строки защищены от
удаления и наружной поверхности не имеют.
