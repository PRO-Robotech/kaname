## Обзор

Живой код восстановления у личности один — тот, что в последнем поставленном ей письме (Ф5 Р8
п. 4), и годен он только для адреса, который принадлежит личности, когда код записан. Документ
утверждает это свойство в последовательном и в одновременном случае — для запросов одной
личности, разных личностей и запроса против исхода смены адреса — с положительными близнецами,
чтобы изменение `kaname#776` (и миграция, если её потребует решение) опиралось на одобренный
контракт.

## Что НЕ входит

- окно писем адресата и окно источника — Ф5-26, Ф5-27: сверхнормативный запрос код **не**
  вытесняет (Ф5 Р8 п. 4); здесь не переутверждается;
- предъявление кода, его срок, повтор и конкуренция предъявлений — Ф5-03…Ф5-05;
- последовательная смена адреса после запроса кода — EC-23 (опора);
- порядок захвата строк в уборке кодов (`kaname#774`) и в регистрации ключа против удаления
  личности (`kaname#775`) — внешнего контракта не меняют, ведутся задачей и TDD;
- выбор механизма (замок, ограничение схемы, повторное чтение) — решение реализации; приёмка
  утверждает исход.

## Решение (наблюдаемое)

**Р1.** После любого числа принятых запросов кода одной личности — последовательных или
одновременных — годен к предъявлению ровно один код: тот, что в последнем поставленном письме
`mail.recovery.send` этой личности (порядок очереди — возрастание `id` строки очереди). Прочие при
предъявлении получают отказ Ф5-04 побайтово (код, тело, текст Ф5 Р10 п. 2).

**Р2.** Упорядочивание — у **личности**: запросы разных личностей друг друга не вытесняют и
фиксации друг друга не ждут.

**Р3.** Каждый принятый запрос, чей адрес на момент записи принадлежит личности, **ставит
письмо** (`RecoveryRequestQueued`): проигрыш одновременному запросу той же личности не превращает
исход ни в `store-failed`, ни в иной исход без письма. Ответ вызывающему на всех путях — ответ
Ф5-01 (тело и код прежние); он исход не различает (Ф5 Р2) и в этом документе различающим
утверждением не служит.

**Р4.** Запрос судится адресом, который принадлежит личности **на момент записи кода**, а не на
момент первого чтения. Запрос, чья запись наступает после зафиксированной смены адреса личности с
`a` на `b`, кода и письма на `a` не выдаёт; его исход — `no-row` (адрес `a` на момент записи не
принадлежит никому; Д3). После исхода смены у личности нет годного кода, письмо с которым
поставлено на прежний адрес.

## Сценарий RCL-01: последовательный повтор запроса вытесняет прежний код · E · I

**ID:** RCL-01

**Given** личность `P` с подтверждённым адресом `a`, окно писем адресата `a` не меньше 2 (Ф5-26)
**And** запрос `POST /iam/v1/auth/recovery` с `email = a` принят, письмо `mail.recovery.send` с
кодом `c1` поставлено
**When** тот же запрос повторён и письмо с кодом `c2` поставлено
**Then** `POST /iam/v1/auth/recovery/complete` с `email = a`, `code = c1`,
`newPassword = "brand-new-password-pl"` — `UNAUTHENTICATED` / `401`, тело побайтово равно отказу
Ф5-04
**And** то же с `code = c2` — исход Ф5-03 (пароль записан, выдана сессия)
**And** сценарий — положительный контроль RCL-02: без него RCL-02 зеленел бы на полосе, не
выдающей кодов

## Сценарий RCL-02: одновременные запросы одной личности — писем N, живой код один · I

**ID:** RCL-02

**Given** личность `P` с подтверждённым адресом `a` и живым кодом `c0` (`seedWithLiveCode`), окно
писем адресата `a` не меньше `N + 1`, `N = 8` (Д2); диспетчер постановки синхронный (`SyncDispatcher`)
**And** однократная задержка на снятии кодов (`installOneShotHold` на `recovery_codes`, `DELETE`)
взведена с `want = N − 1`
**When** `N` запросов кода для `a` исполняются одновременно: первый, снявший коды, спит в
задержке, пока прочие `N − 1` не ждут замка (сцена построена — `requireHoldSceneBuilt` вернул
`N − 1`), затем задержка отпускается
**Then** наблюдатель запроса насчитал `RecoveryRequestQueued` = `N`, `RecoveryRequestStoreFailed` = 0
и ни одного иного исхода
**And** строк очереди `mail.recovery.send` личности `P` прибавилось ровно `N`, у каждой свой код
**And** неприменённых кодов `P` в хранилище — ровно **1**
**And** предъявление (`email = a`, `newPassword = "brand-new-password-pl"`) проходит ровно у
одного из `N` кодов — того, что в строке очереди с наибольшим `id`; прочие `N − 1` получают
отказ Ф5-04 побайтово; `c0` — тоже отказ Ф5-04
**And** проба обязана быть красной на свежей `origin/746` до правки (DoD п. 1)

## Сценарий RCL-03: одновременные запросы РАЗНЫХ личностей — каждый ставит письмо, не дожидаясь другого · I

**ID:** RCL-03 (положительный близнец RCL-02; отличающий факт один — у запросов разные личности)

**Given** личности `P1` и `P2` с подтверждёнными адресами `a1`, `a2`, окна не меньше 1
**And** однократная задержка на снятии кодов (`recovery_codes`, `DELETE`) **с явным отпуском**:
держит, пока проба её не отпустит, без счёта ждущих; общий срок — только страховка, исчерпание
которого — отказ фикстуры, а не вердикт. Такой фикстуры в линии нет (`armOneShotHold` требует
`want ≥ 1` и отпускает по сроку) — **заказ полосе `kaname#776`**
**And** держатель — транзакция запроса кода для `a1`: она спит в задержке, не зафиксировавшись
(`awaitSleepingBackend`)
**When** пока транзакция `P1` спит в задержке, исполняется запрос кода для `a2`
**Then** запрос `P2` вернулся, и наблюдатель насчитал `RecoveryRequestQueued` = 1, пока запрос `P1`
ещё не вернулся (канал исхода держателя пуст)
**And** в тот же момент чтение `recovery_codes` вне обеих транзакций видит неприменённых кодов у
`P2` — 1, у `P1` — 0: код `P1` не зафиксирован
**And** после отпускания задержки запрос `P1` возвращается с исходом `RecoveryRequestQueued`;
неприменённых кодов у `P1` — 1, у `P2` — 1; оба кода проходят предъявление (исход Ф5-03 у каждой)

## Сценарий RCL-04: запрос кода зафиксирован раньше исхода смены адреса · I

**ID:** RCL-04 (порядок фиксаций «запрос → смена»)

**Given** личность `P` с подтверждённым адресом `a`, живым кодом `c0` и ожидающей смены адреса на
`b` (`seedWithPendingChange`)
**And** однократная задержка на снятии кодов взведена; держатель — транзакция запроса кода для `a`
**When** пока запрос спит в задержке, приходит подтверждение смены адреса `P` (EC-02), затем
задержка отпускается (`runRecoveryOverlap`, держатель — запрос, второй — смена)
**Then** обе транзакции фиксируются, ни одна не получает `40P01`; исход запроса —
`RecoveryRequestQueued`, исход смены — успех EC-02
**And** после обеих неприменённых кодов `P` — **0**: код `c1` из письма на `a` снят исходом смены, `c0`
снят запросом
**And** `POST /iam/v1/auth/recovery/complete` с `email = b` и `code = c1`, и с `email = b` и
`code = c0` — отказ Ф5-04 побайтово, пароль прежний

## Сценарий RCL-05: исход смены адреса зафиксирован раньше записи запроса кода · I

**ID:** RCL-05 (порядок фиксаций «смена → запрос»; близнец RCL-04 — отличающий факт один: кто
держатель задержки)

**Given** личность `P` с подтверждённым адресом `a`, живым кодом `c0` и ожидающей смены адреса на
`b`; строк очереди `mail.recovery.send` с `to = a` у `P` — `k`
**And** однократная задержка на снятии кодов взведена; держатель — транзакция исхода смены
адреса (адрес строки уже `b`, транзакция не зафиксирована)
**When** пока смена спит в задержке, приходит запрос кода для `a` (его чтение адреса видит
зафиксированное состояние: личность `P` с адресом `a`; незафиксированную смену на `b` чтение не
видит), затем задержка отпускается
(`runRecoveryOverlap`, держатель — смена, второй — запрос)
**Then** обе транзакции фиксируются, ни одна не получает `40P01`; исход смены — успех EC-02
**And** исход запроса — `RecoveryRequestNoRow` (Р4, Д3), не `RecoveryRequestQueued`
**And** строк очереди `mail.recovery.send` с `to = a` у `P` — по-прежнему `k`: письма на прежний
адрес после смены нет
**And** неприменённых кодов `P` — **0**
**And** `POST /iam/v1/auth/recovery/complete` с `email = b` и `code = c0` — отказ Ф5-04 побайтово
**And** положительный контроль: затем запрос кода для `b` ставит письмо с кодом `c2` на `b`,
и предъявление `email = b`, `code = c2` — исход Ф5-03

## Допущения

- **Д1.** Годен код **последнего поставленного письма** — так же, как Ф5 Р8 п. 4. Письмо ставится
  каждому принятому запросу (Р3), поэтому правило «первый зафиксированный побеждает» означало бы
  годный код не в последнем письме и отвергается.
- **Д2.** `N = 8` — ширина конкуренции пробы; число контрактом не является.
- **Д3.** Исход запроса по Р4 — существующее значение `no-row` закрытого перечня
  (`RecoveryRequestOutcomes`): на момент записи адрес `a` не принадлежит никому, и это ровно тот
  случай, что у полосы чтения. Новое значение перечня не заводится; ответ вызывающему тот же
  (Ф5-01/Ф5-02 неразличимы по Ф5 Р2).
