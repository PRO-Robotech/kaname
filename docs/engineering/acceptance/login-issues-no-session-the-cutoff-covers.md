## §0. Перепись производителей — до сценариев

Каждое «Тогда» ниже опирается на производителя из этой переписи. Производитель, которого в
дереве ещё нет, помечен «заводит это изменение». Условие, которого схема не допускает, в
«Дано» не ставится. Посевы §0.10–§0.12 и §0.14 исполнены на стенде `newSessionLane` с базой в
контейнере временной пробой, которая не закоммичена.

### 0.1. Кто назначает момент аутентификации входа и когда

Момент назначается **после проверки пароля и до открытия транзакции выдачи**:

```sh
git grep -n 'now := uc.now().UTC()' -- internal/apps/kaname/api/humansession/login.go
# → :280   (после Verify, до второго фактора и выдачи)
git grep -n -E 'IssueSession\(ctx, w, IssueInput|At: +now,' -- internal/apps/kaname/api/humansession/login.go
# → :466, :469   (выдача получает тот же момент)
```

Операция выдачи пишет его в запись как момент аутентификации
(`internal/apps/kaname/api/humansession/issue.go:74-78`, `AuthenticatedAt: at`). Часы входа —
порт `LoginDeps.Now`, проба подаёт их своими. На посадке это часы процесса
(`cmd/kaname/loginlane.go:464`, `Now: time.Now`), и их показание несёт наносекунды. В каком
разрешении это значение доходит до края — §0.12.

### 0.2. Что транзакция выдачи входа берёт и чего не читает

Транзакция выдачи открывается писателем общего вида, строки личности она заранее не берёт:

```sh
git grep -n 'w, err := uc.store.Writer(ctx)' -- internal/apps/kaname/api/humansession/login.go
# → :399 (запись попытки), :450 (ВЫДАЧА), :528 (переписывание материала)
```

Отсечку она не читает вовсе:

```sh
git grep -c -E 'RevokedBefore|Cutoff|cutoff' -- internal/apps/kaname/api/humansession/login.go internal/apps/kaname/api/humansession/issue.go
# → пусто (0)
```

Единственный замок на строке личности, который она берёт, — ключевой (`FOR KEY SHARE`),
его ставит проверка внешнего ключа при вставке записи сессии. С замком писателя нескольких
сессий он совместим, и дерево говорит это о себе прямо:

```sh
git grep -n 'поэтому вход человека (вставка сессии), выдача кода и' -- internal/repo/kaname/pg/human_session_repo.go
# → :341   («…им не останавливаются»)
```

С кодом второго фактора транзакция выдачи берёт строку фактора **раньше** строки личности
(§0.11).

Уровень транзакции — `read committed` (`ceremonyWriterTx`,
`internal/repo/kaname/pg/oauth_ceremony_repo.go:465`; открытие —
`beginHumanSessionWriter`, `human_session_repo.go:182`). Своего предела ожидания замка она не
ставит: ожидание ограничивает потолок одного оператора пула (`statement_timeout`, 30 с), а
`lock_timeout` пул не ставит намеренно (`human_session_repo.go:614-621`).

### 0.3. Что делает принудительный выход и что видит его снятие

1. Момент выхода — текущее время процесса, взятое **до** открытия его транзакции:
   ```sh
   git grep -n -E 'now := time.Now\(\).UTC\(\)|RevokeBefore: *now' -- internal/apps/kaname/api/internal_iam/force_logout.go
   # → :345 · :349
   ```
2. Транзакция выхода открывается ключевым замком строки личности
   (`human_session_repo.go:643`, `lockUserForKeySQL`) и поднимает его до замка писателя
   нескольких сессий (`FOR NO KEY UPDATE`) на входе в снятие (`EndOtherSessions`,
   `human_session_repo.go:483-488` → `holdPersonForSessionSet`, `:360-375`).
3. Снятие — один оператор `endSessionsOfSQL` (`human_session_repo.go:469-472`) с условием
   `ended_at IS NULL`. На `read committed` он видит записи, зафиксированные к началу оператора.
   Запись, которую вход положил, но ещё не зафиксировал, в его снимок не входит.
4. Отсечка и событие — той же транзакцией, после снятия. Событие
   `iam.session.force_logout` несёт исход снятия, `sessions_ended` — число снятых
   (`force_logout.go:673-687`). Каждое ожидание замка ограничено `forceLogoutLockWait`, 2 с
   (`force_logout.go:531`); сверх него — частичный исход `#340` (отсечка стоит, распорядителю
   ответ «не выполнено»).

### 0.4. Кто читает отсечку для браузерной сессии

**Край, и только он.** Резолв сессии в службе отсечку не применяет и объявляет это о себе
(`internal/apps/kaname/api/humansession/resolve.go:9`; ветви резолва —
`human_session_repo.go:90-99`: снята · истекла · личность неактивна). Край спрашивает службу
дважды — `Resolve` о носителе и `SessionCutoffOf` о личности
(`internal/apps/kaname/api/session_revocations/session_cutoff.go:76`) — и судит пару сам:

- правило включающее: сессия годна ⟺ момент аутентификации **строго позже** отсечки
  (`PRO-Robotech/kacho:gateway/internal/middleware/auth_session_cutoff.go:232`,
  `authenticatedAt.After(cutoff)`; там же сказано, что граница включает свой момент ради
  принудительного выхода, совпавшего по метке со входом);
- оба значения пары край получает из хранилища и в его разрешении (§0.12);
- на отсечённой сессии край отвечает 401 и гасит носитель — на любом пути, включая глаголы
  формы (`PRO-Robotech/kacho:gateway/internal/middleware/auth_own_session.go:127-131`, Ф3-51).

Эту пару — ответ `Resolve` и ответ `SessionCutoffOf` — сценарии ниже называют **парой
края**. Проба читает её у службы; правило края цитируется и здесь не исполняется.

### 0.5. Что из этого следует — выведено чтением кода, прогоном не подтверждено

Порядок «вход назначил момент → принудительный выход зафиксирован → вход выдал» оставляет у
человека **живую** запись сессии, чей момент аутентификации **не позже** стоящей отсечки:

- снятие её не видело — к началу оператора снятия записи не было (п.0.3.3);
- выдача отсечку не читала (п.0.2);
- резолв службы отвечает «сессия есть» (п.0.4), край на первом же предъявлении отвечает 401 и
  гасит носитель (п.0.4).

То же даёт порядок «вход положил запись → снятие начато → вход зафиксирован»: ключевой замок
выдачи снятие не останавливает (п.0.2), и оператор снятия незафиксированной записи не видит.

Итог в обоих порядках: вход ответил «выдана», запись говорит «жива», край говорит «кончена»,
а событие выхода её не сосчитало. Прогоном это здесь не подтверждено; подтверждает красный
KN-OVL-02 и KN-OVL-03 на дереве до правки (§6 п.5).

### 0.9. Прецедент: выдача против снятия уже решена замком

Выдача кода авторизации в сессии столкнулась со снятием той же сессии, и решено это замком
`FOR SHARE` на строке сессии: он конфликтует с замком снятия (`FOR NO KEY UPDATE`), а
ключевой (`FOR KEY SHARE`) с ним совместим и снятия не держит
(`internal/repo/kaname/pg/oauth_ceremony_repo.go:215-221`, оператор — `:229-230`). Там же
записано правило порядка: родители внешних ключей берутся не позже строки сессии (`:178-179`).
У входа строки сессии до выдачи нет. Строка, на которой встречаются вход и снятие, — строка
личности: её снятие берёт первой (п.0.3.2).

### 0.10. Какую личность удаляет полоса удаления — посев

Личность, заведённую регистрацией полосой, полоса удаления не удаляет. Регистрация делает её
владельцем личного аккаунта и субъектом привязок. Удаление (`UsersW().Delete`,
`internal/repo/kaname/pg/user_repo.go:812-851`) отвергает такую строку охраной по привязкам и
строки не берёт; владельца аккаунта держит и внешний ключ `accounts_owner_fk`
(`ON DELETE RESTRICT`, `internal/migrations/0001_initial.sql:5402`). Удаляется не-владелец
без привязок и без членств. Посев; вывод дословно, без префикса строки, идентификатор опущен:

```
lane-registered P: users=1 accounts-owned=1 bindings-as-subject=4 group-memberships=0 sessions=1 live=1 login-method-rows=1 lookup-set-rows=0
delete lane-registered P: err=failed precondition: User … has active access bindings and cannot be deleted
```

`bindings-as-subject` — строки `access_bindings` и `access_binding_subjects` вместе. Q —

### 0.11. Выдача с кодом второго фактора берёт строки во встречном удалению порядке — посев

С кодом второго фактора транзакция выдачи сначала пишет строку фактора: берёт строку набора
замком `FOR UPDATE` (`login_method_repo.go:369-370`) и снимает элемент
(`uc.factor.settle`, `login.go:456-463`). Строки личности она касается позже — проверкой
внешнего ключа при вставке записи сессии (`:466` → `InsertSession`). Удаление берёт строку
личности (`FOR UPDATE`) и каскадом — строки фактора. Порядки встречные. Код по времени пишет
ту же строку способа (принятый шаг), и порядок у него тот же.

Посев: вход Q паролем и запасным кодом задержан на входе во вставку записи сессии (фактор уже
записан); удаление Q начато и видно стоящим на замке; задержка снята. Три раунда, в каждом
свежая Q. Вывод сокращён до несущих полей:

```
wrong-order round 0: delete-waited-on-lock=true … deadlocks+1 after: users=1 sessions=2 live=2 login-method-rows=3
wrong-order round 1: delete-waited-on-lock=true … deadlocks+1 after: users=1 sessions=2 live=2 login-method-rows=3
wrong-order round 2: delete-waited-on-lock=true … deadlocks+1 after: users=1 sessions=2 live=2 login-method-rows=3
```

Взаимная блокировка — три раунда из трёх, одна из двух транзакций откатывается. Контроль —
тот же вход, задержанный на фиксации выдачи: строку личности к этому моменту уже держит
ключевой замок вставки, и удаление ждёт её. Вывод сокращён так же:

```
09/1 round 0: delete-waited-on-lock=true login=nil delete=nil deadlocks+0 after: users=0 sessions=0 login-method-rows=0
09/1 round 1: delete-waited-on-lock=true login=nil delete=nil deadlocks+0 after: users=0 sessions=0 login-method-rows=0
09/1 round 2: delete-waited-on-lock=true login=nil delete=nil deadlocks+0 after: users=0 sessions=0 login-method-rows=0
```

Это класс `#382` — порядок захвата писателей строк сессии против удаления личности — на одном
его писателе, выдаче входа.

### 0.12. В каком разрешении край судит пару — посев

Край сравнивает значения, прочитанные из хранилища. Момент аутентификации приходит из записи
сессии неусечённым (`resolve.go:93-103`, «НЕ усечён»), отсечка — в разрешении хранилища
(`session_cutoff.go:95-103`). Хранилище держит оба до микросекунды. Вставка записи сессии
кладёт момент как есть (`InsertSession`, `human_session_repo.go:377-392`, момент не
нормируется), и доля ниже микросекунды при записи отбрасывается. Посев: выдача моментом
X + 500 нс, X — целая микросекунда, затем чтение `authenticated_at`:

```
clock=…:53.2972935Z stored=…:53.297293Z clock.After(X)=true stored.After(X)=false stored.Equal(X)=true
```

Показание позже X, записанное значение равно X. Разрешение хранилища дерево учитывает и у
соседей: завершение восстановления выдаёт на единицу разрешения позже своей отсечки
(`recovery_complete.go:264-269`), выход датирует отсечку на единицу разрешения раньше первой
аутентификации (`logout.go:117-140`).

### 0.13. Исход «хранилище не ответило» у транзакции выдачи уже есть

- Всякая ошибка транзакции выдачи → клетка `store-failed`, `ErrStoreUnavailable`
  (`login.go:329-332`). Транспорт: 503, `UNAVAILABLE`, текст
  `request not performed; try again later` (`handler.go:885-886`,
  `humansession/refusals.go:24`).
- Следа попытки этот путь не кладёт: попытку пишет только `refuseWith` (`login.go:397-419`).
- Транзакция при этом откатывается целиком (`defer w.Rollback`, `login.go:454`), и запись
  второго фактора, сделанная в ней, уходит вместе с ней.

### 0.14. Место захвата и что его держит — посев

Захвата в дереве нет, поэтому его место эмулировано. Обёртка писателя вызывает в транзакции
выдачи оператор замка строки личности писателя сессии (`EndOtherSessions` →
`holdPersonForSessionSet`, сила `FOR NO KEY UPDATE`). Мест три:

- **первым** — до записи фактора;
- **место А** — после записи фактора, до вставки записи сессии;
- **место Б** — после вставки.

Против `FOR UPDATE` удаления эта сила конфликтует так же, как `FOR SHARE`. Сцена — KN-OVL-09
на Q (§0.10). Вход идёт паролем и запасным кодом и останавливается в одной из двух точек: в З4
(половина 09/2) либо в З3, на входе в эмулированный захват (половина 09/3). Удаление —
`UsersW().Delete`. Проба ждёт первого из двух событий, «удаление стоит на замке» либо «удаление
зафиксировано», и снимает задержку. Каждая сцена прогнана три раза, каждый раз со свежей Q,
и все три прогона сцены дали один вывод. Вывод сокращён до несущих полей. `delete=aborted` — отказ
удаления `conflicting concurrent change`. Им продукт отвечает и на `40001`, и на `40P01`
(`internal/repo/kaname/pg/pgmaperr.go:247`), а что здесь это `40P01`, показывает счётчик
блокировок:

```
mode=none  stop=Z4 ×3: first=delete-waits-on-lock login=<nil> delete=aborted deadlocks+1 after: users=1 sessions=2
mode=first stop=Z4 ×3: first=delete-waits-on-lock login=<nil> delete=nil deadlocks+0 after: users=0 sessions=0
mode=first stop=Z3 ×3: first=delete-finished login=second factor temporarily unavailable delete=nil deadlocks+0 after: users=0 sessions=0
mode=A     stop=Z4 ×3: first=delete-waits-on-lock login=<nil> delete=nil deadlocks+0 after: users=0 sessions=0
mode=A     stop=Z3 ×3: first=delete-waits-on-lock login=<nil> delete=aborted deadlocks+1 after: users=1 sessions=2
mode=B     stop=Z4 ×3: first=delete-waits-on-lock login=<nil> delete=aborted deadlocks+1 after: users=1 sessions=2
mode=B     stop=Z3 ×3: first=delete-waits-on-lock login=<nil> delete=nil deadlocks+0 after: users=0 sessions=0
```

- **Захвата нет** (`none`) — это дерево сегодня. Строка повторяет §0.11 и показывает, что проба
  видит взаимную блокировку.
- **Первым.** В З4 удаление ждёт строку личности, и блокировок нет: так 09/2 выглядит после
  правки. В З3 удаление проходит раньше, чем снята задержка: это сцена 09/3. Отказ входа
  «второй фактор временно недоступен» — артефакт эмуляции. Исхода «строки нет» у неё нет, и
  вход доходит до чтения набора, которого уже нет. Исход 3 (Р4) посевом не показан, показана
  только сцена.
- **Место А.** 09/2 зелёная: удаление ждёт строку личности и до строк фактора не доходит.
  09/3 краснеет взаимной блокировкой. В З3 строка фактора уже взята, удаление берёт строку
  личности и ждёт строку фактора, а захват ждёт удаление.
- **Место Б.** 09/2 краснеет взаимной блокировкой: до З4 строку личности не держит никто, как
  сегодня. 09/3 краснеет без блокировки. Вставка уже держит строку личности ключевым замком, и
  удаление ждёт её. Захват поднимает уже взятый замок, не вставая в очередь. Вход выдаёт
  сессию (`login=<nil>`: исход «выдана», отказа `no-row` нет), а удаление проходит после
  фиксации.

Итог: свойство «строка личности взята до вставки записи сессии» держит 09/2, свойство «строка
личности взята до записи фактора» — 09/3. 09/3 краснеет и на месте Б, но другим фактом. Ни
одно неверное место не проходит обе половины сразу. Жертвой блокировки во всех раундах было
удаление. Жертву выбирает движок, и сценарии этого не утверждают. Вывод совпадает с посевом
круга 2 (запись ревью `c9a0c3c7…`, поле `seed_attempt`).

## §1. Предмет

### 1.1. Что меняется

Вход, чей момент аутентификации не позже стоящей отсечки личности, **сессии не выдаёт** и
отвечает тем же одним отказом, что на неверный пароль, не считая его попыткой. Момент судится
в разрешении хранилища — тем значением, которое легло бы в запись (Р1). Транзакция выдачи входа
первым делом берёт строку личности замком, несовместимым с замком снятия, и после этого читает
отсечку. Поэтому в любом порядке двух глаголов исход один: сессия, которую выход накрыл, либо
снята им, либо не выдана вовсе. Операция захвата, не ответившая, закрывает вход отказом
«не выполнено» и ничего не оставляет (Р4).

Ответ предъявителю, код и текст отказа не меняются. Меняется то, что вход больше не отвечает
«выдана» на сессию, которую край не примет, и что запись службы больше не называет живой
сессию, которую край считает кончённой.

Захват первой операцией заодно выравнивает порядок строк у выдачи с кодом второго фактора и у
удаления личности. Сегодня он встречный, и взаимная блокировка воспроизводится (§0.11). После
изменения порядок у обоих один — «личность, затем строки фактора». Держит это KN-OVL-09 двумя
половинами, у каждой своё место: «строка личности взята до записи фактора» — 09/3, «до
вставки записи сессии» — 09/2 (§0.14).

### 1.2. Почему сейчас

Предмет передан сюда приёмкой `#334` (§2 того документа) и держит закрытие волны `#366`:
под посадкой `own` и вход, и принудительный выход — пути службы, и граница между ними —
свойство службы. Исход у предъявителя сегодня безопасен: край отсечённую сессию не пускает
(§0.4). Предмет — правдивость записи и ответа входа, а не доступ.

## §3. Решения

### Р1. Граница — момент аутентификации против момента отсечки, включающе, в разрешении хранилища

Принудительный выход выводит всякую сессию, аутентифицированную не позже его момента. Так его
определяет Ф1: сессии личности разом гасит отсечка
(`login-session-and-credentials-are-our-contract.md`, §5.1). Так его исполняет край,
единственный читатель отсечки для браузерной сессии, сравнением «строго позже — годна»
(§0.4). Отсюда исход для входа внахлёст:

- **момент входа не позже момента выхода** — вход выходом накрыт, в каком бы порядке оба
  глагола ни дошли до базы. Живой сессии он не оставляет;
- **момент входа позже** — это новый вход. Принудительный выход удостоверений не отзывает и
  повторного входа не запрещает: после выхода человек входит снова (Ф1-67). Его сессия жива,
  если снятие её не застало. Застало — снята и сосчитана, как всякая запись, которую снятие
  видело.

Момент — тот, что назначен после проверки пароля (§0.1), а не момент фиксации выдачи. Это
момент предъявления удостоверения, и его же сравнивает край.

**Разрешение сравнения — разрешение хранилища.** Край сравнивает то, что прочитано из
хранилища, а хранилище держит оба момента до микросекунды (§0.12). Показание часов входа на
посадке несёт наносекунды (§0.1) и в `authenticated_at` ложится усечённым. Поэтому момент
входа, который судится, — **m: показание часов, усечённое до микросекунды**. Одно и то же m
вход сравнивает с отсечкой и отдаёт выдаче. Сравниваемое и записанное — одно значение, а не
два, которые совпадают лишь потому, что драйвер отбрасывает долю ниже микросекунды: уже
выровненному значению отбрасывать нечего. Итог: **вход накрыт ⟺ m ≤ T**.

Отвергнуто — сравнивать показание, как оно лежит в памяти. В пределах одной микросекунды
такой вход выдал бы сессию, чей записанный момент равен отсечке, и край отверг бы её на первом
предъявлении. Это рассинхронизация записи с краем, которую запрещает Р2 (KN-OVL-07/3).

### Р2. Запись согласна с краем

После обоих глаголов, в любом порядке их старта, у человека нет живой записи сессии, чей
момент аутентификации не позже стоящей отсечки. И вход отвечает «выдана» только на сессию,
которая либо годна краю, либо снята выходом и сосчитана в его событии.

Отвергнуто:

- **оставить как есть.** Запись называла бы живой сессию, которую край отвергает на первом
  предъявлении. Вход отвечал бы «выдана» с носителем, мёртвым с рождения. Событие выхода её
  не считало бы. Запись жила бы до абсолютного срока, и уборка сносила бы её как истёкшую, а
  не как снятую. Это та же рассинхронизация записи с краем, которую `#313` закрыл для
  принудительного выхода;
- **передвинуть момент входа за отсечку.** Сессия, чьё удостоверение предъявлено до выхода,
  ушла бы из-под выхода, а запись называла бы ложный момент аутентификации. Завершение
  восстановления поступает так законно (`recovery_complete.go:264-269`, «на единицу
  разрешения ПОЗЖЕ отсечки»): отсечку оно пишет само, моментом своего же действия. Вход
  отсечки не пишет, а стоящая отсечка у него чужая.

### Р3. Ответ входа — тот же один отказ, не попытка, своя клетка, ничего не записано

- Ответ — тот же, что на неверный пароль: 401, `UNAUTHENTICATED`, `authentication failed`,
  побайтово то же тело (KN-OVL-06). Причина отзыва — наш журнал, а не ответ предъявителю
  (Ф1-17). Отдельный ответ называл бы держателю пароля действие распорядителя.
- Попыткой не считается: удостоверение предъявлено верно, и следа неверного предъявления
  отказ не кладёт. Прецедент — исчерпание ёмкости (§0.8). Иначе принудительный выход
  приближал бы человека к отказу по частоте.
- Своя клетка счётчика исходов входа — **`before-cutoff`** (заводит это изменение). Причина
  различима только приёмником, как у прочих исходов входа.
- Транзакция выдачи откатывается целиком: ни записи сессии, ни события выдачи, ни сброса
  счёта, ни записи второго фактора (принятого шага, потреблённого запасного кода). Повторный
  вход тем же удостоверением — новый вход (Р1) и проходит (KN-OVL-08).
- Отказ уходит не раньше потолка огибающей, как всякий исход после ворот частоты (§0.8).

Почему не `503`: наша сторона ответила, и ответ определённый; «повторите позже» было бы
неправдой о хранилище. `503` — исход, когда захват **не** ответил (Р4, исход 4).

### Р4. Сериализация — строкой личности, первой операцией транзакции выдачи

- **Строка личности.** Строки сессии до выдачи нет, а строку личности снятие берёт первой
  (§0.3.2). Встретиться вход и снятие могут только на ней.
- **Сила — `FOR SHARE`.** Он конфликтует с замком снятия (`FOR NO KEY UPDATE`) и с удалением
  личности (`FOR UPDATE`). Совместим он с ключевым (`FOR KEY SHARE`: открытие транзакции
  выхода, проверки внешних ключей, выдача кода) и сам с собой: два входа одного человека
  друг друга не ждут. Сила та же, что у прецедента §0.9, и по той же причине.
- **Первой операцией транзакции.** Порядок «личность → дочерние строки» — правило §0.9.
  Транзакция выдачи с кодом второго фактора пишет и дочернюю строку личности (потреблённый
  элемент набора, принятый шаг). Сегодня она берёт её раньше строки личности, и порядок с
  удалением встречный (§0.11). Захват первым делает его одним. Держат это две половины
  KN-OVL-09, у каждой своё место (§0.14). «До записи фактора» держит 09/3: захват, поставленный
  после записи фактора, встречает удаление, которое уже взяло строку личности и ждёт строку
  фактора. «До вставки записи сессии» держит 09/2: захват после вставки оставляет строку
  личности до вставки ничьей, как сегодня.
- **Захват — отдельная операция писателя сессии**, и она отвечает стоящей отсечкой личности,
  прочитанной после захвата той же транзакцией. На `read committed` новый оператор видит
  выход, зафиксированный, пока вход ждал замка. «Отсечки нет» — отдельный ответ операции, а не
  нулевой момент. Отдельной операцией она нужна сценариям: на входе в неё (З3) KN-OVL-09/3
  задерживает транзакцию, а KN-OVL-10 отвечает ошибкой.
- **Сравнение — в варианте использования входа**, правилом края в разрешении хранилища:
  m ≤ отсечки ⇒ отказ Р3 (Р1). То же m уходит в выдачу.

**Исходы операции захвата — закрытый перечень, «прочего» нет:**

1. **Строка взята, отсечки у личности нет** — сравнивать не с чем, выдача идёт.
2. **Строка взята, отсечка T** — правило Р1: накрыт — отказ Р3; не накрыт — выдача.
3. **Строки нет** — личность удалена между чтением адреса и захватом. Вход поступает так же,
   как на адрес, у которого строки нет при чтении: исход `no-row` (§0.8) — тот же один отказ,
   попытка считается, клетка `no-row`. Транзакция выдачи откатывается. Клетка `no-row` так и
   значит одно на обоих местах: «личности по адресу нет». Держит KN-OVL-09/3.
4. **Операция не ответила** — ошибка хранилища, отмена, обрыв, ожидание замка сверх потолка
   оператора (§0.2), выбор жертвой взаимной блокировки. Вход закрыт: 503, `UNAVAILABLE`, текст
   `request not performed; try again later`, клетка `store-failed` — исход, который у
   транзакции выдачи уже есть на всякую её ошибку (§0.13). Транзакция откатывается целиком:
   нет записи сессии, события выдачи, следа попытки, записи второго фактора; клетка
   `before-cutoff` не растёт. Непрочитанная отсечка не считается ни отсутствующей, ни
   накрывающей. Держит KN-OVL-10.

Следствия, названные, чтобы их не открывали заново:

- вход ждёт транзакцию писателя нескольких сессий того же человека: принудительного выхода,
  смены пароля, снятия второго фактора, завершения восстановления. Эти транзакции коротки;
- неключевые правки строки личности (`UPDATE users`) сериализуются с выдачей. Цикла нет:
  они берут только строку личности;
- снятие ждёт открытую выдачу не дольше `forceLogoutLockWait`. Сверх — частичный исход `#340`
  (§2);
- комментарий писателя нескольких сессий о том, что вход его замком не останавливается
  (§0.2), становится ложным и правится тем же изменением (§6 п.4).

### Р5. Правило — про отсечку, кем бы она ни положена

Вход сравнивает свой момент со **стоящей отсечкой** личности, а не с признаком
принудительного выхода. Отсечки выхода и смены пароля датированы ниже первой аутентификации
личности (§2) и нового входа не встречают никогда. Отсечки моментом «сейчас» кладут
принудительный выход, завершение восстановления и сброс второго фактора распорядителем, и
правило для них одно. KN-OVL-07 держит это отсечкой, положенной дверью записи отсечки с
чужой причиной.

### Р6. Правится только вход

Операция выдачи (`IssueSession`) общая для трёх глаголов (§0.6). Проверка ставится в
транзакции выдачи входа, а не в общей операции. Иначе изменение меняло бы наблюдаемый исход
завершения восстановления, для которого решения здесь нет (§2).

## §4. Сценарии

**Общее для всех сценариев.**

- Посадка `own`. Личность P заведена **регистрацией полосой пароля** — писателем продукта:
  зеркало, способ входа, сессия одним исходом, как на посадке (форма — `newSessionLane`).
  Регистрация выдаёт P запись сессии S0, и «Дано» её учитывает. **KN-OVL-09 — исключение:**
  личность регистрации полосой удаления не удаляется (§0.10), и там действует личность Q
  (абзац сценария). S0 у Q нет.
- **Вход** — `POST /iam/v1/auth/login` транспортом полосы поверх `LoginUseCase.Execute` и
  `HumanSessionRepo`, как их собирает соседний стенд полосы. Тело — camelCase, закрытый набор
  полей (`handler.go:231-246`):
  - «вход паролем» — `{"email": "<адрес P>", "password": "<пароль P>", "csrfToken": "<признак>"}`;
  - «вход паролем и запасным кодом c» — то же плюс
    `"secondFactor": {"method": "lookup_secret", "code": "<c>"}`.

  Признак — ответ `GET /iam/v1/auth/csrf?form=login` в контексте формы, как у
  `sessionLane.login`. Код и тело ответа читаются на транспорте.
- Между вариантом использования и хранилищем стоит **обёртка хранилища входа**. Она
  встраивает порт `humansession.Store` и задерживает вход каналом в одной из четырёх точек.
  Порядок точек в транзакции выдачи — З1 → З3 → З4 → З2:
  - **З1** — открытие первой транзакции записи входа (`Store.Writer`): момент уже назначен,
    в базе от входа ещё ничего нет;
  - **З3** — вход в захват строки личности транзакцией выдачи (Р4): транзакция открыта,
    ничего не взято. Это верно, пока захват стоит первым. При захвате, поставленном позже
    (инъекции §6 п.10), в З3 уже взято то, что транзакция взяла до него, и на этом краснеет
    09/3. В KN-OVL-10 обёртка здесь отвечает ошибкой, не передавая вызова хранилищу, и считает
    вызовы;
  - **З4** — вход в запись сессии (`Writer.InsertSession`): запись второго фактора сделана,
    записи сессии нет. Точка есть и в дереве до правки;
  - **З2** — фиксация транзакции выдачи (`Writer.Commit`): запись сессии положена, замки
    транзакции держатся.

  Сна нет нигде, порядок задают каналы.
- **Часы входа** — порт `LoginDeps.Now`. По умолчанию это часы процесса, как на посадке
  (§0.1): показание с наносекундами. Проба оборачивает их и запоминает показание. Своими
  значениями часы подаёт только KN-OVL-07. Её значения отсчитаны от часов процесса: X —
  показание часов процесса, снятое пробой до старта входа и усечённое до микросекунды, сдвиг
  от него — меньше микросекунды или ровно одна. Срок записи `Resolve` судит по часам
  процесса (момент аутентификации плюс срок сессии). Значение вдали от них покрасило бы
  сценарий сроком, а не правилом. Огибающую порт не задевает: её отсчёт идёт по часам
  процесса (`login.go:230-233`).
- **m** — момент входа **в разрешении хранилища**: показание часов, усечённое до микросекунды
  (Р1). Это значение ложится в `authenticated_at`. Там, где сценарию важно само показание, оно
  так и названо.
- **Принудительный выход** — `kaname.cloud.iam.v1.InternalIAMService/ForceLogout` с телом
  `user_id` = идентификатор P, `reason` не задан. Обработчик собран, как его собирает корень на
  посадке `own`: снятие наших записей провязано. Вызывающий держит `system_admin` на
  `cluster`; страж не меняется, и сценарии его не утверждают. «Завершён» значит: операция
  `done = true`, `error` пуст.
- **T** — `revoke_before` у P после выхода, прочитанный `SessionCutoffOf`, в разрешении
  хранилища (§0.12).
- **Пара края** — §0.4.
- **Клетка** — значение счётчика исходов входа (`LoginOutcomes()`); «выросла на один» —
  разность снятий до и после.
- **«Входом ничего не записано»** — три наблюдения, каждое снимается до и после: число записей
  сессии у P не выросло; событий `iam.session.issued` с `user_id` = P не прибавилось; следов
  неверного предъявления по адресу P не прибавилось. KN-OVL-08 и KN-OVL-10/2 утверждают все
  три и добавляют четвёртое — код второго фактора не потреблён, что видно по повтору тем же
  кодом. В них три наблюдения снимаются до входа и после отказа, до повтора.

У каждого сценария назван производитель «Тогда». У отрицательного и различающего названа
дельта против близнеца, и она равна ровно одному факту.

### KN-OVL-01 · вход после принудительного выхода — новый вход: сессия жива и годна краю

> **Дано** личность P; принудительный выход для P завершён, его момент — T
> **Когда** P выполняет вход паролем без задержки; часы входа — часы процесса
> **Тогда** вход отвечает 200, ответ несёт сессию S1; клетка `issued` выросла на один
> **И** S1 жива (`ended_at` пуст), и `authenticated_at(S1)` = m > T
> **И** пара края говорит «годна»: `Resolve` находит S1; `SessionCutoffOf(P)` — отсечка
> найдена, её момент T строго раньше `authenticated_at(S1)`

Положительный близнец KN-OVL-02, KN-OVL-07/2 и KN-OVL-10/1. Без него отказы тех сценариев
зеленели бы и на реализации, отказывающей во входе всякой личности со стоящей отсечкой, без
сравнения моментов. Тогда после принудительного выхода человек не вошёл бы больше никогда, а
это противоречит Ф1-67. Между T и m лежат фиксация транзакции выхода и опрос операции, и
в одну микросекунду они не укладываются: m > T здесь — следствие сцены, а не удачи.

**Производители:** транзакция выдачи входа (`login.go:448-490`) — захват и чтение отсечки
заводит это изменение, здесь они отвечают «отсечка раньше момента»; `SessionCutoffOf`
(`session_cutoff.go:76`) и `HumanSessionRepo.Resolve` (`human_session_repo.go:64-114`) — без
изменений. **До правки:** зелёный.

### KN-OVL-02 · момент входа раньше выхода, выдача — после его фиксации: вход отказывает и ничего не пишет

> **Дано** личность P; P начал вход паролем, пароль сошёлся, момент m назначен, вход стоит в З1
> **Когда** распорядитель выполняет `ForceLogout` для P, выход завершён; затем задержка снята
> **Тогда** вход отвечает 401, `code` = `UNAUTHENTICATED`, текст `authentication failed`
> **И** m ≤ T
> **И** входом ничего не записано: у P одна запись сессии — S0, и она снята выходом
> (`ended_reason = 'admin-force-logout'`); событий `iam.session.issued` для P — ноль; следов
> неверного предъявления по адресу P — ноль
> **И** клетка `before-cutoff` выросла на один; `issued` и `mismatched` не изменились
> **И** событие `iam.session.force_logout` несёт `sessions_ended = 1`
> **И** ответ уходит не раньше потолка огибающей (унитарная половина: хранилище-подделка
> отвечает отсечкой не раньше m, потолок огибающей больше нуля)

**Дельта против KN-OVL-01 — один факт:** где стоит момент входа относительно момента выхода.
В обоих сценариях транзакция выдачи открывается после фиксации выхода.

**Производители:** захват строки личности и чтение отсечки в транзакции выдачи входа,
сравнение «m ≤ отсечки ⇒ отказ», отказ без записи попытки, клетка `before-cutoff` — всё
заводит это изменение. Без изменений: ответ одного отказа (`handler.go:858-859`), огибающая
(`login.go:233-236`), снятие S0 (`endSessionsOfSQL`, `human_session_repo.go:469-472`).

**Красный до правки:** вход отвечает 200 с сессией S1; S1 жива, её момент m не позже T;
`Resolve` находит её. Красный называет эти три факта.

### KN-OVL-03 · выход пришёл, когда выдача уже положила запись: выход дожидается выдачи и снимает выданное

> **Дано** личность P; вход P дошёл до фиксации выдачи: запись S1 положена и не
> зафиксирована, вход стоит в З2
> **Когда** распорядитель вызывает `ForceLogout` для P; проба дожидается, что транзакция
> выхода стоит на замке (состояние движка), и сразу снимает задержку
> **Тогда** вход отвечает 200 с сессией S1
> **И** выход завершён, и завершён он после фиксации выдачи
> **И** S1 снята: `ended_reason = 'admin-force-logout'`, `ended_at` = T
> **И** событие `iam.session.force_logout` несёт `sessions_ended = 2` (S0 и S1)
> **И** `Resolve` на носитель S1 отвечает «сессия снята»

**Дельта против KN-OVL-02 — один факт:** где стоит выход относительно выдачи. В KN-OVL-02
он зафиксирован до открытия транзакции выдачи, здесь приходит внутрь неё, когда запись уже
положена.

Задержка снимается сразу, как ожидание увидено. Транзакция выхода ждёт замка не дольше
`forceLogoutLockWait`, и дольше держать вход значило бы снимать частичный исход `#340` вместо
предмета.

**Производитель:** захват строки личности замком `FOR SHARE` первой операцией транзакции
выдачи (заводит это изменение). Снятие без изменений.

**Красный до правки:** выход замка не ждёт (§0.2) и завершается раньше, чем проба увидит
ожидание. Проба ждёт первого из двух событий — «выход стоит на замке» либо «выход завершён» —
и на дереве до правки получает второе. Дальше: `sessions_ended = 1`, S1 после фиксации жива, её
момент не позже T. Красный называет, какое событие пришло первым.

### KN-OVL-04 · вход завершён до выхода: выход снимает выданное (близнец KN-OVL-03)

> **Дано** личность P; вход P завершён, 200, сессия S1 жива
> **Когда** распорядитель выполняет `ForceLogout` для P, выход завершён
> **Тогда** S1 снята: `ended_reason = 'admin-force-logout'`, `ended_at` = T
> **И** событие `iam.session.force_logout` несёт `sessions_ended = 2`

**Дельта против KN-OVL-03 — один факт:** зафиксирована ли выдача к старту выхода.
Сценарий отделяет свойство «снятие снимает выданное входом» (есть сегодня) от свойства
«снятие дожидается открытой выдачи» (заводит это изменение). Красная KN-OVL-03 при зелёной
KN-OVL-04 называет производителем ровно замок.

**Производитель:** `endSessionsOfSQL`, без изменений. Сегодня его держит
`TestIntegration_ForceLogoutEndsOurOwnLoginSession` на записи, положенной писателем напрямую;
здесь запись производит сам вход. **До правки:** зелёный.

### KN-OVL-05 · спорный путь без порядка: в каждом раунде запись согласна с краем и с ответом входа

> **Дано** не меньше двадцати раундов, в каждом — свежая личность Pᵢ (регистрацией);
> задержек нет; часы входа — часы процесса; старт сведён на входе двух транзакций: вход — на
> открытии транзакции выдачи, выход — на открытии своей транзакции (`ForceLogoutWriter`)
> **Когда** вход Pᵢ паролем и `ForceLogout` для Pᵢ идут одновременно
> **Тогда** в каждом раунде выход завершён; вход отвечает либо 200, либо одним отказом
> `authentication failed` — ни `503`, ни взаимной блокировки
> **И** в каждом раунде живых записей у Pᵢ с `authenticated_at ≤ T` — ноль
> **И** в каждом раунде исход, который назвал вход, совпадает с записью: 200 ⟺ запись S1
> есть, и она либо снята выходом (`admin-force-logout`, `ended_at` = T, сосчитана в
> `sessions_ended`), либо жива с `authenticated_at` = m > T; отказ ⟺ записи от входа нет,
> m ≤ T (m — показание, запомненное обёрткой часов, в разрешении хранилища), клетка
> `before-cutoff` выросла на один
> **И** в каждом раунде `sessions_ended` равно числу записей Pᵢ, снятых выходом
> **И** проба печатает, сколько раундов дал каждый из трёх исходов: «отказ», «выдана и
> снята», «выдана после отсечки»

Сводный старт не упорядочивает моменты. Выход берёт свой момент до открытия транзакции
(§0.3.1), вход — до открытия своей (§0.1), поэтому m и T стоят в любом порядке, и законны все
три исхода. Число каждого печатается, а не требуется: исход гонки не детерминирован, и
требование «каждый исход хоть раз» краснело бы по жребию. Упорядоченные половины — KN-OVL-02,
03 и 01. Сравнение m с T в разрешении хранилища здесь несущее: раунды идут на часах процесса,
и сравнение показаний в памяти краснело бы по жребию на законной реализации.

**Производители:** те же, что в 02 и 03, под настоящей конкуренцией. **До правки:** красный
по жребию — в раундах, где оператор снятия не застал незафиксированную запись; в разводку
до правки не входит (§6 п.5).

### KN-OVL-09 · выдача с кодом второго фактора и удаление личности берут строки в одном порядке: взаимной блокировки нет

**Личность — Q, а не P** (§0.10): не-владелец без привязок и без членств в группах, в
аккаунте личности регистрации стенда. Строка личности — формой `seedAccountMember` соседа;
строка пароля — писателем продукта `LoginMethodRepo.Create`; второй фактор — глаголами Ф12
после входа Q полосой (`enrolledSecondFactor`). После посева у Q: владений аккаунтом — 0,
привязок субъектом — 0, членств — 0, одна живая сессия Sₑ (вход заведения), полный набор
запасных кодов (вывод §0.10). S0 у Q нет. Удаление — настоящим писателем полосы удаления
(`UsersW().Delete`) в своей транзакции, как у соседа. Вход несёт запасной код: транзакция
выдачи пишет строку фактора, и порядок «личность → строки фактора» несущий. «Удаление стоит
на замке» — `pg_stat_activity`, `wait_event_type = 'Lock'` у оператора удаления. Каждая
половина — не меньше шести раундов, в каждом свежая Q.

> **09/1. Дано** вход Q паролем и запасным кодом c дошёл до фиксации выдачи (З2): запись
> положена, код потреблён, транзакция держится
> **Когда** удаление Q начато, и проба видит его стоящим на замке; затем задержка снята
> **Тогда** взаимных блокировок ноль (`pg_stat_database.deadlocks` не вырос); вход отвечает
> 200; удаление зафиксировано; личности Q нет, записей сессии Q нет, строк способов входа Q нет

> **09/2. Дано** вход Q паролем и запасным кодом c стоит в З4: код потреблён, записи сессии
> нет, транзакция держится
> **Когда** удаление Q начато, и проба видит его стоящим на замке; затем задержка снята
> **Тогда** взаимных блокировок ноль; вход отвечает 200; удаление зафиксировано; личности Q
> нет, записей сессии Q нет, строк способов входа Q нет

> **09/3. Дано** вход Q паролем и запасным кодом c открыл транзакцию выдачи и стоит в З3 — на
> входе в захват строки личности
> **Когда** удаление Q начато; проба ждёт первого из двух событий — «удаление зафиксировано»
> либо «удаление стоит на замке» — и снимает задержку
> **Тогда** взаимных блокировок ноль; удаление зафиксировано; личности Q нет, записей сессии Q
> нет
> **И** вход отвечает тем же одним отказом: 401, `UNAUTHENTICATED`, `authentication failed`
> **И** клетка `no-row` выросла на один; `issued`, `before-cutoff` и `store-failed` не
> изменились; событий `iam.session.issued` для Q не прибавилось; следов неверного предъявления

**Дельта 09/2 против 09/1 — один факт:** где стоит вход, когда приходит удаление: до записи
сессии (З4) или после неё (З2). В 09/1 строку личности к этому моменту держит вход в обоих
деревьях — ключевым замком вставки, — и удаление ждёт её. В 09/2 сегодня строку личности не
держит никто: удаление ждёт строку фактора, а вставка затем ждёт удаление (§0.11).

вовсе не встретились.

**Производители:** захват строки личности первой операцией транзакции выдачи (Р4, заводит это
изменение). Его место держат обе половины, каждая своё (§0.14): «до вставки записи сессии» —

§0.14: три раунда из трёх); красный называет счётчик и откаченную транзакцию. 09/3 до правки
не исполнима: операции захвата нет, и точки З3 нет. Её способность упасть показывают две
инъекции места захвата (§5, §6 п.10).
