# Приёмка: выход, произведённый распорядителем, назван в записи сессии своей причиной

- **Статус:** DRAFT — редакция 2. Круг 1 вернул редакцию 1 (`CHANGES_REQUESTED`, одна
  блокирующая находка рода PRODUCER). Вердикта на редакцию 2 нет, санкции на код нет
  (ban #1). Вердикт выносит `acceptance-reviewer`
- **Статическая форма:** DRAFT. Слово выше вписано и не означает вердикта. Действующее
  одобрение выводится из записи ревью по отпечатку этой редакции и из внешнего события, на
  которое запись ссылается (`change-graph.md` §2 «Вердикт привязан к ОТПЕЧАТКУ, а не к
  документу»). Слово DRAFT после ревью не правится. Номер редакции в строке статуса
  правится тем же изменением, что и тело: иначе строка называла бы прочитанной не ту
  редакцию
- **История ревью:** только дописывается строками вида «дата · круг · вердикт · SHA-256
  редакции · путь записи»; прежние строки не правятся и не удаляются
  - 2026-09-23 · круг 1 · `CHANGES_REQUESTED` ·
    `eff62d6f7090bc171f384fa15979cdeacfdd310e3fcc6cfdb31d58870b80b3ef` ·
    `docs/specs/reviews/forced-exit-has-its-own-session-end-reason/eff62d6f7090bc171f384fa15979cdeacfdd310e3fcc6cfdb31d58870b80b3ef.yaml`
- **Журнал редакций:** только дописывается
  - **ред. 2 · 2026-09-23** — правка ПОСЛЕ вердикта круга 1, по его записи. B1: у KN-SER-05
    названы производители исхода «кто снял», независимые от строки (§0.6). Третья половина
    переписана на совпадение исхода, который называет выход, с записью в каждом раунде.
    Заведена четвёртая половина с принуждённым порядком. В §5 стоит таблица «снятый
    производитель → какая половина краснеет». §6 п.5 выводит третью половину из разводки

- **Дата:** 2026-09-23
- **Задача:** `PRO-Robotech/kaname#334`. Волна `#358`, эпик `#357`, цель линии —
  `PRO-Robotech/kacho#2564`. Тело задачи — источник признака и предиката снятия; здесь из

## §0. Перепись производителей — до сценариев

Каждое «Тогда» ниже опирается на производителя из этой переписи. Производитель, которого в
дереве ещё нет, помечен «заводит это изменение». Условие, которого схема не допускает, в
«Дано» не ставится.

### 0.1. Кто ПИШЕТ причину снятия записи сессии

Операторов записи **два**, в одном файле:

```sh
git grep -n 'ended_reason = \$' -- 'internal/**/*.go' ':!*_test.go'
# → internal/repo/kaname/pg/human_session_repo.go:278   (снятие одной записи)
# → internal/repo/kaname/pg/human_session_repo.go:306   (снятие записей личности, endSessionsOfSQL)
```

Оба оператора несут условие `ended_at IS NULL` (строки 279 и 307). Значит, запись снимается
один раз, и причину пишет тот, кто снял её первым. На этом стоит KN-SER-05. Какой из двух
актов снял запись, сама строка засвидетельствовать не может: второе снятие поверх первого
переписало бы ту же пару (`ended_at`, `ended_reason`). Свидетели вне строки перечислены в
§0.6.

Мест вызова, передающих причину, **пять** на вершине волны и **четыре** на базе:

```sh
git grep -n -E '\.(EndSession|EndOtherSessions|EndAllSessions)\(' -- '*.go' ':!*_test.go'
```

| место вызова | глагол | причина | на базе `cbbac984` |
|---|---|---|---|
| `humansession/logout.go:78` | собственный выход человека | `logout` | есть |
| `humansession/change_password.go:196` | смена пароля (гасит прочие) | `password-change` | есть |
| `humansession/recovery_complete.go:231` | завершение восстановления | `password-change` | есть |
| `humansession/sf_remove.go:123` | снятие второго фактора самим человеком | `second-factor-removed` | есть |
| `internal_iam/force_logout.go:422` | **принудительный выход распорядителем** | **`logout`** | **нет** |

Административный путь пишет в эту колонку **только на ветке волны**. На стволе принудительный
выход наших записей сессии не снимает вовсе:

```sh
git grep -c 'EndAllSessions' cbbac984 -- internal/apps/kaname/api/internal_iam/force_logout.go   # → пусто (0)
git grep -c 'EndAllSessions' -- internal/apps/kaname/api/internal_iam/force_logout.go             # → 2 (вызов и порт)
```

### 0.2. Кто ДЕРЖИТ словарь

Словарь держат два места, и сверки между ними сегодня нет.

**База.** Ограничение `human_sessions_ended_reason_check`. Определение стоит в трёх местах:
создание таблицы, накат второй миграции и её откат. Действует на голове второе:

```sh
git grep -n 'ADD CONSTRAINT human_sessions_ended_reason_check\|CONSTRAINT human_sessions_ended_reason_check CHECK' -- 'internal/migrations/*.sql'
# → 20260916190000_human_session_is_our_record.sql:89            logout · password-change
# → 20260917160000_second_factor_rows_carry_state_and_step.sql:100  + second-factor-removed   (накат)
# → 20260917160000_second_factor_rows_carry_state_and_step.sql:132  logout · password-change   (откат)
```

**Домен.** Константы `internal/domain/human_session.go:224-236`. Их **четыре**, и в словарь
снятия сессии входят только **три**. Четвёртая, `second-factor-reset`, — причина ОТСЕЧКИ.
Её пишет сброс второго фактора распорядителем, и ни одному снимающему методу она не
передаётся:

```sh
git grep -n 'RevokeReasonSecondFactorReset' -- '*.go' ':!*_test.go'
# → 4 строки: комментарий объявления (internal/domain/human_session.go:232), само объявление (:235),
#   internal/apps/kaname/api/user/reset_second_factor.go:185 (отсечка) и :197 (состав события); вызова End* нет
```

Эти константы служат сразу двум словарям: закрытому словарю снятия сессии и открытому полю
причины отсечки (`user_token_revocations_reason_check` — только длина ≤ 256). Поэтому
перечня «вот словарь снятия сессии» в домене сегодня нет. Его заводит KN-SER-07.

### 0.3. Кто ЧИТАЕТ причину

В продукте её не читает никто:

```sh
git grep -n 'ended_reason' -- '*.go' ':!*_test.go'
# → 5 строк: 3 комментария (force_logout.go:378, :414; human_session.go:230) и 2 оператора SET (§0.1).
#   Ни одного SELECT.
git grep -c -i -E 'ended_reason|endedReason' -- proto/   # → пусто (0): на проводе поля нет
```

Резолв сессии читает `ended_at`, а не причину (`resolveSQL`,
`internal/repo/kaname/pg/human_session_repo.go:49-57`; ветвь «снята» — строка 88-90). Уборка
тоже судит по `ended_at` (там же, строка 185). Отсюда два следствия. Новое значение не может
изменить ни ответ предъявителю, ни судьбу строки, и это держит KN-SER-04. А читатель у
колонки один — журнал службы, который читают при разборе.

### 0.4. Что отвергает база на этом входе

Значение вне словаря отвергается с именем ограничения
`human_sessions_ended_reason_check`. Проба-сосед —
`TestHumanSessionSchema_LevelAndMethodsAreHeldByTheBase`
(`internal/migrations/human_session_schema_integration_test.go:86-87`, значение `sneeze`).
Сегодня так отвергается и `admin-force-logout`: в миграциях значения нет.

```sh
git grep -c 'admin-force-logout' -- 'internal/migrations/*.sql'   # → пусто (0)
```

### 0.5. Где уже стоит это слово

Слово `admin-force-logout` в не-тестовом Go присвоено **одно**. Это умолчание СВОБОДНОЙ
причины отсечки, когда запрос причины не несёт:

```sh
git grep -n '"admin-force-logout"' -- 'internal/**/*.go' ':!*_test.go'
# → internal/apps/kaname/api/internal_iam/force_logout.go:276   reason = "admin-force-logout"
```

То же слово контракт называет умолчанием поля `reason` в `ForceLogoutRequest`
(`proto/kaname/cloud/iam/v1/internal_iam_service.proto:493-496`). Поле описано как «свободная
причина на записи отсечки и в событии». О записи сессии контракт не говорит ничего, и это
изменение этого не меняет (§2).

### 0.6. Кто СВИДЕТЕЛЬСТВУЕТ, какой акт снял запись, помимо самой строки

Перепись нужна KN-SER-05. Строка против себя самой не свидетель (§0.1), поэтому исход
читается из мест вне строки. У каждого названа координата.

1. **Сам глагол выхода.** `LogoutUseCase.Execute` возвращает `ended`, то есть была ли снята
   запись ЭТИМ вызовом (`humansession/logout.go:53-55`). `true` отдаётся одной строкой, после
   отсечки, события и фиксации. `false` после попытки снятия отдаёт ветвь, в которой
   оператор снятия строки не изменил (`logout.go:83-86`).
   ```sh
   git grep -n 'ended bool, err error\|if !ended\|return true, nil' -- internal/apps/kaname/api/humansession/logout.go
   # → :55 (сигнатура) · :83 (снял не этот вызов) · :114 (снял этот)
   ```
2. **Событие выхода.** Выход, снявший запись, кладёт `iam.session.logged_out`, и его состав
   несёт `session_id` (`logout.go:98-105`). Принудительный выход кладёт событие другого
   вида, `iam.session.force_logout` (`internal_iam/force_logout.go:78`), и идентификатора
   сессии в его составе нет (`hook_pool_adapters.go:195-199`). Значит, счёт событий выхода по
   `session_id` принудительного выхода не видит. Чтение очереди аудита по `session_id` в
   дереве уже есть (`loginlanehttp/step_up_journal_integration_test.go:99-102`).
   ```sh
   git grep -n 'AuditSessionLoggedOut\|"session_id":' -- internal/apps/kaname/api/humansession/logout.go
   # → :25, :26 (слово события) · :99 (вид) · :103 (идентификатор сессии в составе)
   ```
3. **Запись отсечки выхода по строке отсечки НЕ наблюдаема, и это измерено.** Оператор
   отсечки монотонен: момент берётся через `GREATEST`, причина и актор идут за принятым
   моментом, а отброшенный момент не переносит на запись ничего
   (`user_token_revocations_repo.go:35-39`, оператор `:49-59`). Момент отсечки выхода — на
   микросекунду раньше первой аутентификации и не позже момента сессии (`logout.go:117-140`).
   Момент принудительного выхода — его текущее время (`force_logout.go:282`). Первый всегда
   меньше второго. Значит, отсечка выхода, записанная после принудительной, строку отсечки
   не меняет, и отличить «выход её писал» от «не писал» строка не может. Поэтому запись
   отсечки выхода считается на порту: обёртка хранилища выхода (п.6) считает вызовы записи
   отсечки на писателе, выданном выходу.
   ```sh
   git grep -n 'GREATEST(user_token_revocations.revoke_before' -- internal/repo/kaname/pg/user_token_revocations_repo.go   # → :53
   git grep -n 'return first.Add(-time.Microsecond)' -- internal/apps/kaname/api/humansession/logout.go                   # → :140
   ```
4. **Момент принудительного выхода лежит в его отсечке.** Глагол пишет одно значение момента
   и в отсечку, и в снятие записей (`force_logout.go:282` и `:422`). Значит, `ended_at`
   строки, снятой принудительным выходом, равен `revoke_before` его отсечки. После обоих
   актов строка отсечки несёт момент принудительного выхода: он больше момента отсечки
   выхода (п.3).
   ```sh
   git grep -n 'RevokeBefore: now,\|EndAllSessions(ctx, marker.UserID, now' -- internal/apps/kaname/api/internal_iam/force_logout.go
   # → :282 · :422
   ```
5. **Момент выхода задают часы, которые передаёт проба.** `NewLogoutUseCase` принимает
   источник времени (`logout.go:37`), и снятие пишет его значение (`logout.go:59`, `:78`).
6. **Порядок задаёт обёртка хранилища выхода.** Выход берёт хранилище портом
   `humansession.Store` (`logout.go:30`, `:37`), и `HumanSessionRepo` этот порт исполняет
   (`human_session_repo.go:578`). Принудительный выход снимает записи своим экземпляром
   `HumanSessionRepo` (`force_logout_own_session_integration_test.go:68`). Поэтому обёртка на
   хранилище выхода задерживает только выход. Встраивание порта в обёртку пробы в дереве уже
   есть:
   ```sh
   git grep -n -A1 'type setJudgingStore' -- internal/handler/loginlanehttp/recovery_session_integration_test.go
   # → :239 (тип) · :240 (встроенный humansession.Store)
   ```
7. **Пробы, сводящей выход с принудительным выходом, в дереве нет, ни в каком порядке.**
   ```sh
   git grep -l 'NewLogoutUseCase' -- '*_test.go'
   # → 2 файла: internal/apps/kaname/api/humansession/usecase_test.go,
   #   internal/handler/loginlanehttp/session_lane_integration_harness_test.go
   git grep -c 'ForceLogout' -- internal/apps/kaname/api/humansession/usecase_test.go internal/handler/loginlanehttp/session_lane_integration_harness_test.go   # → пусто (0)
   ```

## §1. Предмет

### 1.1. Что меняется

На посадке `own` принудительный выход снимает наши записи сессии входа. Сегодня (на ветке
волны) он пишет в них причину `logout`, то есть ту же, что собственный выход человека. После
этого изменения он пишет **`admin-force-logout`** — четвёртое значение закрытого словаря
снятия сессии. Словарь при этом объявляется в домене одним перечнем, и база сверяется с ним в
обе стороны.

Ответ глагола не меняется, ответ предъявителю тоже. Меняется только то, что служба записывает
о снятой сессии в свой журнал. Норма та же, что уже стоит в Ф1 для отсечки: журнал обязан
отличать выход от смены пароля (Ф1-63), а причина отзыва — это наш журнал, а не ответ
предъявителю (Ф1-17, `login-session-and-credentials-are-our-contract.md` §3.3). Действующий
текст Ф1 одобрен: запись ревью круга 11 стоит на его отпечатке
(`docs/specs/reviews/login-session-and-credentials-are-our-contract/7bdef287….yaml`,
`APPROVED`, сверено `sha256sum` на вершине волны). Здесь то же правило применено к записи
сессии.

### 1.2. Почему — ссылкой, а не пересказом

Довод о следствии изложен в задаче и здесь не повторяется. Репозиторий публичен
(`security-disclosure.md` §«Публичные артефакты»), и приёмка — не место для этого разбора.
Предмет выражен сценариями: запись сессии называет того, кто её снял.

### 1.3. Почему сейчас, и чем это измерено

Значение **добавляется**. Обратного заполнения нет (KN-SER-08), и нет потому, что оно
не нужно. На стволе административный путь в эту колонку не пишет вовсе (§0.1, 0 на
`cbbac984`), значит ни одна строка, записанная стволом, не помечена неверно. Путь, пишущий
`logout`, живёт только в ветке эпика и вливается в `main` тем же запросом эпика, что и это
изменение (порядок вливания — тело `#357`, «Ветки»). Условие названо, потому что посылка на
нём держится: приди `#313` в ствол без этого изменения, строки ствола получили бы `logout` от
распорядителя. Решения о прошлом, верного для таких строк, нет.

## §2. Что НЕ входит

- **Состав и порядок события принудительного выхода.** Событие кладётся транзакцией отсечки
  до снятия и числа снятых записей не несёт. Это предмет `#340`, у него свой вопрос о
  частичном исходе.
- **Словарь причин отзыва семейства** (`token_families_revoked_reason_ck`) — предмет `#339`.
  Снятие сессии отзывает выданное в ней причиной семейства `session-ended`. Это изменение её
  не трогает.
- **Причина отсечки.** Поле остаётся свободным: причина из запроса распорядителя или умолчание
  (KN-SER-02). Ограничение `user_token_revocations_reason_check` не меняется.
- **Проводной контракт.** Ни `proto`, ни REST, ни ответ `ForceLogout`, ни текст отказа не
  меняются. Причину снятия сессии наружу не выводит ни одно чтение (§0.3), и вывод её в
  контракт этим изменением не заводится.
- **Посадка `external`.** Там полоса входа не поднимается, наших записей сессии нет, и снимает
  сессию внешний поставщик (`ProviderSessions`). Писать в колонку там нечему.
- **Вход внахлёст с принудительным выходом** того же человека — предмет `#385`. KN-SER-05
  сводит принудительный выход только с собственным выходом.
- **Прочие четыре писателя** (§0.1) — их значения не меняются. KN-SER-03 держит одного из них
  как близнеца.
- **Строки стендов**, которым ветка эпика уже записала `logout` от распорядителя. Они неотличимы
  от выхода человека по построению, и отличить их нечем. Изменение их не переписывает
  (KN-SER-08) и о них ничего не утверждает. Уборка снесёт их по сроку наравне с прочими
  снятыми (§0.3).

## §3. Решения

### Р1. Значение — `admin-force-logout`

Слово берётся из предиката снятия задачи дословно. Форма — строчные буквы через дефис, как у
трёх соседей словаря. Это же слово служба уже пишет умолчанием причины отсечки (§0.5), и
совпадение намеренное: предмет у обеих записей один — принудительный выход.

### Р2. Значение закрытого словаря не берётся из запроса

Причина в `ForceLogoutRequest.reason` — свободный текст распорядителя. Она по-прежнему идёт в
отсечку и в событие. В запись сессии она не идёт: запись сессии получает значение закрытого
словаря, и только его. Иначе всякая причина, отличная от слова словаря, стоила бы самого
выхода — база отвергла бы снятие, и глагол ответил бы отказом. Держит это KN-SER-02.

### Р3. Слово объявлено один раз

Домен объявляет значение один раз и объявляет перечень словаря снятия сессии. Умолчание
причины отсечки и причина снятия сессии ссылаются на это объявление, а не повторяют литерал.
Держит это KN-SER-10. Второе место — комментарий контракта (§0.5). Он описывает умолчание для
интегратора и остаётся как есть: слово не меняется, и контракт этим изменением не правится.
Держателя у пары «объявление домена — комментарий контракта» нет, и это сказано прямо. Смена
слова была бы изменением контракта со своей приёмкой, и правила бы оба места.

### Р4. Накат лежащих строк не трогает

Миграция только расширяет ограничение, операторов данных в накате нет (KN-SER-08). Довод —
§1.3.

### Р5. Откат переводит `admin-force-logout` в `logout`

Откат возвращает словарь из трёх значений и переводит строки с новым значением в `logout`.
Факт снятия и его момент (`ended_at`) откат не трогает. Форма та же, что у отката миграции
`20260917160000`: там `second-factor-removed` переводится в `password-change`, потому что
«сессии сняты, и остаются снятыми». Выбор значения не произвольный: `logout` — ровно то, что
код до этого изменения писал для того же акта. После отката база и код снова согласны.
Различение при этом теряется. Это свойство отката в словарь, где различения нет, и
восстановить его не взялся бы ни один способ. Отказ от отката был бы хуже: пока есть
снятые распорядителем строки, откат стал бы невыполнимым, а живут такие строки до уборки.
Держит это KN-SER-09.

## §4. Сценарии

Посадка во всех сценариях, кроме схемных (06–09) и сценария дерева (10), — `own`. Вызывающий
`InternalIAMService.ForceLogout` — субъект, у которого есть `system_admin` на `cluster`.
Страж и отказы стража не меняются, и сценарии их не утверждают. У каждого сценария назван
производитель «Тогда». У отрицательного и различающего сценария названа дельта против
близнеца, и она равна ровно одному факту.

### KN-SER-01 · принудительный выход без причины в запросе — запись сессии несёт `admin-force-logout`

> **Дано** личность P в состоянии `ACTIVE` и одна её живая запись сессии S. Запись положена
> тем же писателем, которым её кладёт полоса входа
> **Когда** вызывается `kaname.cloud.iam.v1.InternalIAMService/ForceLogout` с телом:
>   - `user_id` = идентификатор P
>   - `reason` не задан
>
> **Тогда** операция завершена: `done = true`, `error` пуст, `metadata` =
> `ForceLogoutMetadata{ userId: P }`, `response` = `ForceLogoutResult{ revokedCount: 1 }`, и
> `OperationService.Get(id)` отдаёт то же самое
> **И** у S стоят `ended_at` и `ended_reason = 'admin-force-logout'`
> **И** в журнале отсечек у P причина `admin-force-logout`, актор — вызывающий

Первый факт — положительный контроль: форма ответа не изменилась. Второй — сам предмет.
Третий фиксирует, что причина отсечки прежняя.

**Производители:** значение пишет вызов снятия в `internal_iam/force_logout.go`, аргументом
служит объявление домена (заводит это изменение). Принимает значение ограничение, которое
расширяет новая миграция (заводит это изменение). Оператор — `endSessionsOfSQL`
(`human_session_repo.go:305`). Ответ операции даёт `forceLogoutOperationPayload`
(`force_logout.go`), и держит его прежняя проба
`TestForceLogout_OperationIsPersistedAndCompletes`.

**Красный до правки:** проба `TestForceLogout_EndsOurOwnLoginSession` утверждает сегодня
`domain.RevokeReasonLogout`. Её утверждение меняется на новое значение и краснеет, пока
глагол пишет `logout`. Интеграционная половина читает `ended_reason` строки S из базы. На
дереве «код правлен, миграции нет» она краснеет отказом глагола: база отвергает значение, и
операция не завершается успехом.

### KN-SER-02 · свободная причина из запроса не доходит до закрытой колонки

> **Дано** то же, что в KN-SER-01
> **Когда** `ForceLogout` вызывается с телом:
>   - `user_id` = идентификатор P
>   - `reason` = `incident-4711`
>
> **Тогда** операция завершена: `done = true`, `error` пуст
> **И** у S `ended_reason = 'admin-force-logout'`
> **И** в журнале отсечек у P причина `incident-4711`

**Дельта против KN-SER-01 — один факт:** в запросе есть свободная причина. Сценарий отделяет
верную реализацию от той, что передаёт в снятие причину из запроса. На KN-SER-01 обе
зелены, потому что умолчание совпадает со словом словаря (Р1). Здесь вторая краснеет: база
отвергает `incident-4711`, снятие отказывает, и глагол отвечает `UNAVAILABLE`
`could not end the login session`.

**Производители:** значение сессии — то же, что в KN-SER-01. Причину отсечки пишет
`SessionRevocationsAdapter.RevokeAllUserTokensTx`
(`internal/repo/kaname/pg/hook_pool_adapters.go:170`), без изменений.

### KN-SER-03 · собственный выход человека по-прежнему пишет `logout` (близнец KN-SER-01)

> **Дано** личность Q в состоянии `ACTIVE` и одна её живая запись сессии T, на той же базе
> **Когда** Q выполняет собственный выход носителем T (глагол выхода полосы входа)
> **Тогда** у T стоят `ended_at` и `ended_reason = 'logout'`

**Дельта против KN-SER-01 — один факт:** кто выполнил выход. Без этого близнеца KN-SER-01
зеленел бы и у реализации, которая перевела на новое слово ОБА пути, и различения снова
не было бы.

**Производитель:** `humansession/logout.go:78` (`EndSession` с `domain.RevokeReasonLogout`),
без изменений. Сегодня ни одна проба не утверждает причину на СТРОКЕ после собственного
выхода. `TestLogout_F3_15_16_EndsOwnSessionWritesCutoffBeforeFirstAuthentication` утверждает
причину ОТСЕЧКИ (`cut.reason`), а не строки. Утверждение заводит это изменение, и читается
значение тем же чтением базы, что в KN-SER-01.

### KN-SER-04 · предъявитель разницы не видит (Ф1-17)

> **Дано** S снята как в KN-SER-01, T — как в KN-SER-03; носители обеих сохранены
> **Когда** каждый носитель предъявлен резолву сессии
> **Тогда** оба ответа одинаковы: «сессия снята» (`NoSessionEnded`). Ни один не отвечает
> «истекла», «личность неактивна» или «неизвестна»

Это положительный контроль нормы Ф1-17: причина снятия — журнал, а не ответ. Без него
сценарии 01 и 03 допускали бы реализацию, которая различила бы два выхода и в ответе
предъявителю.

**Производитель:** `HumanSessionRepo.Resolve` (`internal/repo/kaname/pg/human_session_repo.go:88-90`).
Он судит по `ended_at` и причину не выбирает (§0.3). Изменение его не трогает.

### KN-SER-05 · причину пишет тот, кто снял запись первым, и выход называет свой исход так же, как запись

Сценарий из четырёх половин, ниже 05/1…05/4. Общее у всех четырёх:

- выход — глагол выхода полосы входа (`LogoutUseCase.Execute`) поверх `HumanSessionRepo`
  через обёртку хранилища выхода (§0.6 п.6). Обёртка считает вызовы записи отсечки на
  писателе, выданном выходу. Её задержка взведена во всех половинах, кроме 05/3, и
  срабатывает, только когда резолв выхода нашёл запись живой: выход стоит между резолвом и
  открытием писателя, пока проба не снимет задержку. В 05/1 проба снимает её сразу, в 05/4 —
  после завершения принудительного выхода, а в 05/2 ей не на чем сработать. Значит, три
  упорядоченные половины различает одно: где стоит принудительный выход относительно шагов
  выхода — после выхода (05/1), до его резолва (05/2) или между резолвом и записью (05/4);
- **записи выхода** — это событие `iam.session.logged_out` с `session_id` этой записи в
  очереди аудита (§0.6 п.2) и вызов записи отсечки на писателе выхода по счёту обёртки
  (§0.6 п.3);
- **победителя проба узнаёт из `Execute`**, а не из строки: счёт по строке сравнивал бы
  запись с ней самой;
- **момент принудительного выхода** проба читает из его отсечки, то есть из `revoke_before`
  у личности (§0.6 п.4). В 05/1, 05/2 и 05/4 часы выхода задаёт проба (§0.6 п.5).

> **Дано** живая запись S личности P
> **Когда** P выполняет собственный выход носителем S, а затем распорядитель выполняет
> `ForceLogout` для P
> **Тогда** выход без ошибки, `Execute` вернул `ended = true`, и записей выхода по одной:
> событие для S и вызов записи отсечки
> **И** `ForceLogout` завершён успехом (снимать было нечего, и это законный исход)
> **И** у S `ended_reason = 'logout'`, а `ended_at` — момент часов выхода

> **Дано** живая запись S′ личности P′
> **Когда** распорядитель выполняет `ForceLogout` для P′ и операция завершена
> (`done = true`), а затем P′ выполняет собственный выход носителем S′
> **Тогда** выход отвечает тем же исходом, что на отсутствующую сессию (Ф3-18): без ошибки, и
> `Execute` вернул `ended = false`
> **И** записей выхода ноль: ни события для S′, ни вызова записи отсечки
> **И** у S′ `ended_reason = 'admin-force-logout'`, а `ended_at` равен моменту отсечки
> принудительного выхода

> **Дано** живая запись S″ личности P″; задержки в обёртке нет
> **Когда** собственный выход носителем S″ и `ForceLogout` для P″ идут одновременно; раунд
> повторяется на свежей записи не меньше двадцати раз
> **Тогда** в каждом раунде оба глагола отвечают успехом: выход без ошибки, `ForceLogout` —
> операцией с `done = true` и пустым `error`
> **И** в каждом раунде исход, который назвал выход, совпадает с записью:
> `ended_reason = 'logout'` ⟺ `Execute` вернул `ended = true` ⟺ записей выхода по одной
> (событие для S″ и вызов записи отсечки); `ended_reason = 'admin-force-logout'` ⟺
> `Execute` вернул `ended = false` ⟺ записей выхода ноль
> **И** проба печатает, сколько раундов выиграл каждый акт, по счёту `Execute`

> **Дано** живая запись S‴ личности P‴
> **Когда** P‴ начинает собственный выход носителем S‴, и резолв выхода находит запись
> живой. Пока выход задержан, распорядитель выполняет `ForceLogout` для P‴, и операция
> завершена (`done = true`). Затем задержка снимается, и выход доходит до своей записи
> **Тогда** выход отвечает тем же исходом, что на отсутствующую сессию (Ф3-18): без ошибки, и
> `Execute` вернул `ended = false`
> **И** записей выхода ноль: ни события для S‴, ни вызова записи отсечки
> **И** у S‴ `ended_reason = 'admin-force-logout'`, а `ended_at` равен моменту отсечки
> принудительного выхода

**Дельта 05/1 против 05/2 — один факт:** порядок двух актов. Журнал обязан называть акт,
который снял запись на самом деле. Второй акт причину не переписывает, иначе запись называла
бы того, кто пришёл позже. 05/1 — ещё и положительный близнец счёта записей выхода: без неё
«записей ноль» в 05/2 и 05/4 было бы неотличимо от счёта, который не читает ничего.

**Дельта 05/4 против 05/2 — один факт:** что увидел резолв выхода. В 05/2 принудительный
выход завершён до начала выхода, и резолв находит запись снятой. В 05/4 резолв находит её
живой, а принудительный выход завершается между резолвом и записью выхода. «Тогда» у двух
половин одно. В порядке 05/4 проигравший выход молчит условием снятия одной записи
(`human_session_repo.go:279`) и ветвью `logout.go:83-86`, а не ранним выходом
`logout.go:65-70`. Без 05/4 этот порядок оставался бы жребию раундов 05/3.

**05/3 — спорный путь без порядка.** Какой акт выиграет, она не утверждает: это решает база.
Она утверждает, что ни один глагол не отказывает и что в каждом раунде выход называет свой
исход так же, как запись. Число выигрышей печатается, а не требуется: исход гонки не
детерминирован, и требование «оба выиграли хоть раз» краснело бы по жребию. Держит только
она путь, где снятие выхода ждёт замка строки, взятого снятием принудительного выхода. В 05/4
снятие выхода приходит после фиксации и замка не ждёт.

**Производители:** условие `ended_at IS NULL` в обоих операторах
(`human_session_repo.go:279`, `:307`), ветвь «сессии нет» (`humansession/logout.go:65-70`) и
ветвь «снял не этот вызов» (`logout.go:83-86`). Все четыре без изменений. Независимые от
строки свидетели — `Execute`, событие выхода, счёт записи отсечки и момент отсечки
принудительного выхода (§0.6). Какая половина краснеет на снятии какого производителя —
таблица под §5. Одновременная пара «снятие одной записи против снятия записей личности» пробы
сегодня не имеет: `human_session_repo_integration_test.go` гоняет параллельно только первую
аутентификацию и замещение материала. Пробы, сводящей выход с принудительным выходом, нет
ни в каком порядке (§0.6 п.7). Пробу и обёртку заводит это изменение. Сценарий утверждает,
что новое значение этим свойством не обходится.

### KN-SER-06 · база принимает новое значение и по-прежнему отвергает чужое

> **Дано** база на голове миграций; пять живых записей
> **Когда** первая снимается с причиной `admin-force-logout`
> **Тогда** база принимает
> **Когда** вторая снимается с причиной `sneeze`
> **Тогда** база отвергает, ограничение — `human_sessions_ended_reason_check`
> **Когда** третья, четвёртая и пятая снимаются с `logout`, `password-change` и
> `second-factor-removed` соответственно
> **Тогда** база принимает все три

**Дельта между принятием и отказом — один факт:** значение причины. Записи разные, но
одинаковые по состоянию (живые, одной личности), и оператор с моментом у них один.

**Производитель:** новая миграция (заводит это изменение). Форма — соседа,
`TestHumanSessionSchema_LevelAndMethodsAreHeldByTheBase`: там уже стоит отказ на `sneeze`,
а принятия ни одного значения словаря нет.
**Красный до правки:** на голове без новой миграции первое снятие отвергается тем же
ограничением.

### KN-SER-07 · словарь объявлен в домене одним перечнем, и база совпадает с ним в обе стороны

> **Дано** база на голове миграций и перечень словаря снятия сессии, объявленный доменом
> **Тогда** каждое значение перечня есть в определении `human_sessions_ended_reason_check`
> **И** каждое значение в кавычках из определения есть в перечне
> **И** в перечне нет `second-factor-reset`: это причина отсечки, а не снятия сессии (§0.2)
> **И** проба печатает перепись: значений у домена N, в ограничении M. На голове N = M = 4

Форма — `TestHumanSessionMethodVocabularyAgreesWithTheRule` у соседней колонки той же
таблицы: словарь в ограничении сверяется с производителем, а не выписывается вторым местом.

**Способность упасть — в обе стороны, и обе исполнены.** Направление «домен шире базы» даёт
естественный красный: дерево с расширенным перечнем и без новой миграции. С этого красного
и начинается реализация (ban #12). Направление «база шире домена» подаётся определением
ограничения с лишним значением в кавычках. Проба обязана краснеть и назвать это значение.

**Производители:** перечень в `internal/domain/human_session.go` (заводит это изменение) и
новая миграция.

### KN-SER-08 · накат не переписывает лежащие строки

> **Дано** база, накатанная до версии, предшествующей новой миграции. На ней снятые записи
> с `logout`, `password-change`, `second-factor-removed` и одна живая
> **Когда** накат до новой версии
> **Тогда** версия базы после наката равна новой
> **И** у всех четырёх `ended_at` и `ended_reason` те же, что до наката, а живая остаётся
> живой

Решение Р4 здесь наблюдаемо. Без этого сценария «обратного заполнения нет» было бы только
словами документа. Первое «Тогда» несущее: без него сценарий зеленел бы и там, где новой
миграции нет вовсе. Накат до версии, которой в каталоге нет, проходит, ничего не применив:
мигратор в этом случае возвращает успех (`pressly/goose/v3` v3.27.3, `UpToContext`, ветвь «no
migrations to run», прочитано в кэше модулей). Строки тогда остаются нетронутыми по пустой
причине.

### KN-SER-09 · откат возвращает словарь из трёх; снятые распорядителем становятся `logout`; повторный накат сходится

> **Дано** база на голове. Запись A снята с `admin-force-logout`, запись B — с
> `password-change`, запись C живая
> **Когда** откат до версии, предшествующей новой миграции
> **Тогда** у A `ended_reason = 'logout'`, а `ended_at` прежний
> **И** у B `ended_reason = 'password-change'` и прежний `ended_at`; C живая
> **И** снятие с причиной `admin-force-logout` отвергается ограничением
> `human_sessions_ended_reason_check`
> **Когда** повторный накат
> **Тогда** снятие с причиной `admin-force-logout` снова принимается

**Дельта A против B — один факт:** значение причины до отката. B — положительный контроль, и
значение у него выбрано не `logout` намеренно. Откат, переводящий в `logout` ВСЕ снятые
строки, оставил бы строку с `logout` нетронутой, и контроль молчал бы. На `password-change`
такой откат краснеет. C отделяет перевод снятых строк от снятия живых.

**Производитель:** раздел отката новой миграции (заводит это изменение). Форма пробы —
`TestRecoveryCodeMigration_DownRestoresTheSingleKindAndTheReapplyConverges`: откат идёт до
своей версии, а не «на один шаг».

### KN-SER-10 · слово объявлено один раз

> **Дано** не-тестовое Go-дерево модуля службы
> **Тогда** узел строкового литерала со значением `admin-force-logout` в нём ровно один — это
> значение константы в объявлении домена (`internal/domain/human_session.go`)
> **И** `force_logout.go` ссылается на это объявление, а `domain.RevokeReasonLogout` в нём
> не встречается
> **И** проба печатает объём осмотренного: сколько файлов разобрано и сколько узлов литерала
> со словом найдено. На голове узел один

**Почему разбор узлов, а не текстовый поиск.** Текстовый поиск по модулю находит слово и в
комментарии сгенерированного контракта:

```sh
git grep -n '"admin-force-logout"' -- '*.go' ':!*_test.go'
# → internal/apps/kaname/api/internal_iam/force_logout.go:276   (литерал)
# → pkg/api/kaname/cloud/iam/v1/internal_iam_service.pb.go:808  (комментарий, не литерал)
```

Разбор ходит по узлам, и комментарий в счёт не идёт по построению. Форма — проба каталога
`internal/check/` `TestAssuranceMethodVocabularyIsDeclaredOnce` с парой инъекций
`TestMethodVocabularyGateRedsOnEveryListForm` и
`TestMethodVocabularyGateStaysSilentOnLegalTwins`. Имя константы проба берёт из найденного
объявления, а не выписывает у себя: иначе её собственная копия имени стала бы вторым
объявлением.

**Способность упасть — в обе стороны.** Второй литерал слова в файле вне домена — находка с
координатой. Селектор `domain.RevokeReasonLogout` в `force_logout.go` — находка. Одно
объявление домена — молчание. Пустой обход — отказ, а не зелёное. Естественный красный даёт
дерево §6 п.5: там слово уже объявлено доменом, а литерал `force_logout.go:276` ещё стоит.
Слепая зона названа: слово, собранное сложением строк, разбор не видит.

**Производитель:** объявление в `internal/domain/human_session.go` (заводит это изменение).
**Держатель — проба разбора дерева в `internal/check/`** (заводит это изменение). Предикаты
§6 п.3 и п.4 — проверка посадки, а не держатель: после вливания их никто не гоняет, и второго
литерала они не заметят.

## §6. Признак готовности (DoD)

Каждый пункт имеет объективное «пройдено / не пройдено».

1. **Миграция НОВАЯ** (ban #5). Ни одна применённая миграция не тронута:
   `git diff --name-status origin/358...HEAD -- 'internal/migrations/*.sql'` даёт ровно одну
   строку, и она с пометкой `A`. Версия старше всякой миграции волны на момент вливания —
   `TestNewMigrationOutranksEveryAppliedOne` зелёный. В файле стоят оба маркера мигратора,
   `-- +goose Up` и `-- +goose Down`. Шапка миграции ссылается на эту приёмку как на санкцию.
2. **Значение в схеме:**
   ```sh
   git grep -c 'admin-force-logout' -- 'internal/migrations/*.sql'   # ≥ 1 — ровно в новом файле
   ```

   Такой предикат выполнила бы одна проба, без единой миграции, поэтому здесь он сужен до
   `*.sql`.
3. **Код пишет новое значение, а не `logout`:**
   ```sh
   git grep -n 'RevokeReasonLogout' -- internal/apps/kaname/api/internal_iam/force_logout.go   # → 0 (сейчас 1, строка 423)
   ```


   заведён перечень домена и слово объявлено (иначе пробы не соберутся, а несобранная проба

   контроли 03, 04 и 05/1: контроль, красный до правки, судит не то, что ему приписано.
