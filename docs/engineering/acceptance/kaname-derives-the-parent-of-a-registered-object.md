## §0. Перепись производителей — до сценариев

### 0.1. Правило проксируемой записи сегодня — одно и не знает манифеста

```sh

# → internal/apps/kaname/api/internal_iam/handler.go:181   (1 вызов)

# → :80 hierarchicalRelations · :242 forbiddenHierarchySubjectTypes · :413 ValidateTuple
```

Правило (`corelib` `authz/proxytuple/policy.go:413-479`) принимает кортеж, если отношение — одно из
трёх `project`, `parent`, `owner`, субъект не класс (`system_class`), тип объекта — не из
запретного перечня и принадлежит модулю вызывающего. Чего правило НЕ спрашивает: объявил ли
манифест модуля это отношение для этого типа объекта, и того ли типа субъект, что объявлен у
указателя. Манифеста правило не знает вовсе; это свойство и есть предмет Р1. Отказ правила —
`PERMISSION_DENIED` `permission denied` без деталей (`handler.go:176-186`, держатель
`TestProxyTupleRefusalMapsToPermissionDenied`).

## §1. Предмет

Модуль регистрирует свои объекты в kaname. Две вещи, которые сегодня держит корректность
модуля, переходят к kaname:

1. **Закрытая политика записи.** Что модуль вправе записать на объект своего типа — тройка «тип
   объекта, отношение, тип субъекта» — объявляет манифест модуля: указатель типа (`parents`)
   и, сверх него, явный ключ `writes`. Регистрация вне политики отвергается `PERMISSION_DENIED`,
   ничего не записано.
2. **Вывод родителя.** Родителя объекта (проект, аккаунт, объект-контейнер) kaname выводит из
   своих данных: из опоры регистрации — проекта либо зарегистрированного контейнера — и своей
   иерархии. Сведения модуля о родителе, которые с выводом расходятся, отвергаются
   `FAILED_PRECONDITION` с машинной причиной, ничего не записано. Сведения, которые модуль
   опустил, kaname не дописывает.

Снятие регистрации и публикация для анонимного чтения не меняются.

## §2. Что НЕ входит

1. **Привязка объекта к проекту после снятия регистрации** — `#983` (своя одобренная приёмка).
   Здесь — только порядок двух отказов, когда приложимы оба (Р10)
2. **Проект НОВОГО объекта верхнего уровня при скомпрометированном модуле.** Опору реестра —
   проект — называет модуль; kaname проверяет, что проект существует и что остальные сведения с
   ним согласны, но знать, тот ли это проект, не может. По Д-A2 его держит метка пространства,
   которую пишет площадка (SRI-112 e приёмки svc-registry). Остаток, названный в `#983` §2 п.2,
   этой задачей не закрывается
3. **Личности и методы:** закрытый перечень методов на личность (SRI-110 a, b, f), привязка
   внутреннего `Check` к домену модуля (SRI-110 c), круг пересыльщиков (SRI-110 g), чужая
   личность (SRI-91). Это задачи kaname из §3а приёмки svc-registry, не эта
4. **Снятие регистрации** политикой не судится (Р11): снятие сужает доступ и обязано оставаться
   возможным для кортежа, записанного до политики; отказ в снятии был бы стоящей выдачей
5. **Публикация для анонимного чтения** (`user:*` / `system_class:anonymous` с `v_get`) судится
   прежним закрытым правилом (`proxytuple.PublicReadObjectTypes`, приёмка
   `anonymous-and-authenticated-are-subject-classes.md`), а не ключом `writes`
6. **Пустая цепь и опущенные звенья.** Контракт `parent_chain` (`internal_iam_service.proto:423-452`):
   пустая цепь — утверждение «предков нет», оно стирает рёбра объекта. Такая регистрация и
   регистрация с пропущенным звеном объект в чужую область не помещают, а сужают его область;
   сверка их принимает, поведение прежнее (Р7, вопрос В3)
7. **Контейнер, сменивший проект после регистрации ребёнка.** Вывод судит регистрацию в момент
   её записи. Перерегистрация уже зарегистрированных детей при переносе контейнера (для типов
   без привязки `#983`) — не здесь; модуль, переносящий контейнер, перерегистрирует детей сам
8. **Манифесты модулей `PRO-Robotech/kacho`** — не трогаются (порядок «сначала kaname»).
   Следствие для registry платформы названо в §7 строка 2
9. **Пределы числа регистраций** — у svc-registry (Р-В7)
10. **Край, консоль, сквозной набор newman.** Глаголы регистрации живут только на внутреннем
    слушателе без `google.api.http` (§0.2); край их не видит. Сквозную проверку держит потребитель:

## §3. Решения

### Решения владельца (не переоткрываются)

Переданы заданием диспетчера 2026-10-26 (те же формулировки, что у соседа
`object-keeps-its-project-after-unregistration.md` §3):

- **Р-В1.** Токены и кортежи пишет svc-registry. Kaname кортежей за модуль не дописывает и
  выведенных сведений в регистрацию модуля не вписывает (Р7): вывод только сверяет
- **Р-В3.** Kaname только авторизует. Политика и вывод — проверка входа регистрации, а не новая
  запись прав
- **Р-В7.** Лимиты — в svc-registry. Kaname не ограничивает число регистраций

### Решения диспетчера по кругу 1 (2026-10-26, спор приёмки решает диспетчер)

- **Место политики — use-case.** Политика (Р1) и вывод (Р4–Р6) исполняются в use-case `Register`,
  в транзакции регистрации — единая точка для любого входа. Обработчик отвергнут: его обходят
  внутренние вызывающие use-case (§0.2). Следствие — мир П6 переписывается (§0.6, §5.2, DoD п.7)
- **Вывод — в той же транзакции, до первой записи.** Порядок с отказом привязки `#983` — Р10,
  условие к коду — §7 строка 4
- **Окно «регистрация обгоняет удаление проекта»** названо, исход законен (Р12)
- **Опора записи из `writes` — выведенный родитель объекта**, а не первое звено цепи (Р4, DP-17)
- **Открытые вопросы В1–В4 — вариант (а)** (§8)

### Решения автора

**Р1. Политика записи типа.** Для типа объекта T из живой строки каталога:

```
политика(T) = { (T, p.name, p.type) : p — указатель T из parents }
            ∪ { (T, w.relation, s)  : w — запись T из writes, s ∈ w.subjects }
```

Регистрация кортежа `(субъект типа S, отношение r, объект типа T)` проходит политику, только
если `(T, r, S) ∈ политика(T)`. Политика СУЖАЕТ правило 0.1 и не расширяет его: кортеж обязан
пройти оба. Источник — живой каталог: строка, применённая из доставленного манифеста, либо
строка посева в паритете с манифестами (как `parent_types`, §0.4). Указатели не объявляются
вторично: регистрация по указателю и есть регистрация объекта, нужна она каждому типу, и
манифест её уже объявил. В1 решён диспетчером — вариант (а).

**Место.** Политику судит use-case `Register` в транзакции регистрации (`emit`), до первого
оператора записи, — для любого входа: обработчик и вызов use-case мимо обработчика судятся
одинаково (DP-06). Читается политика из той же строки каталога, которую транзакция уже читает
для перевода имени типа (§0.2). Снятие регистрации (`emit` с `write = false`) и публикация
(`isPureGrant`, `register_resource.go:387`) политикой не судятся (Р11).

**Р2. Ключ манифеста `writes`.** Ресурс объявляет отношения сверх указателя, которые модуль
пишет сам:

```yaml
  - name: registries
    objectType: registry_registry
    parents: [project]
    relations:
      - {name: owner, definition: '[user, service_account]', position: beforeTiers}
    writes:
      - relation: owner
        subjects: [user, service_account]
```

Значение выражается одним способом: ключ отсутствует (модуль пишет только указатель) либо
непустой список. Загрузка манифеста отвергает, ни одной строки каталога не применяя:
- `writes: []` — `manifest.ErrWritesEmpty`;
- `relation` — имя указателя ресурса — `manifest.ErrWriteIsPointer` (второй способ сказать то,
  что объявил `parents`);
- `relation` не объявлено в `relations` ресурса — `manifest.ErrWriteRelationUndeclared`;
- `relation` объявлено, но модуль его писать не вправе (не входит в отношения иерархии правила
  0.1, `proxytuple.HierarchicalRelations`) — `manifest.ErrWriteRelationNotWritable`: иначе ключ
  обещал бы запись, которую правило 0.1 отвергнет на каждой доставке;
- `subjects` пуст, называет тип вне `{user, service_account}` либо называет тип дважды —
  `manifest.ErrWriteSubjectsInvalid`. Перечень закрыт: сверх указателя модуль пишет создателя, а
  создатель — человек или учётка; класс или группа в отношении иерархии раздали бы доступ мимо
  выдачи (`corelib` `authz/proxytuple/policy.go:242`, `forbiddenHierarchySubjectTypes`);
- одна `relation` в двух записях — `manifest.ErrWriteDuplicate`.

Координата отказа — `resources[i].writes[j]` с полем. Признак переносится в строку каталога
(колонка — замысел) тем же путём, что `parent_types` и `publicReadToChildren`; гейт паритета
посева каталога (`internal/check/catalog_seed_parity.go`) знает новую колонку.

**Р3. Отказ политики.** `PERMISSION_DENIED`, `message` = `permission denied`, деталей нет —
побайтово тот же ответ, что у правила 0.1: какая оговорка отвергла, не наблюдаемо. Ничего не
записывается: ни строки зеркала, ни цепи, ни факта, ни события перерасчёта. Ответ одинаков,
пришёл ли запрос через обработчик или вызовом use-case мимо него (DP-06): текст отказа один, и
производитель у него один. Тип, у которого нет живой строки каталога, судится как сегодня
(`INVALID_ARGUMENT`, поле `object`, `register_resource.go:869-871`): ни политики, ни вывода у него
нет, оба шага его пропускают, и отказ по правам на вход, у которого вызывающему есть что чинить,
был бы худшей диагностикой.

**Р4. Опора регистрации.** Опора — объект, под которым регистрируемый объект живёт по манифесту
(у каждого типа модуля указатель один, §0.4):
- регистрация кортежем указателя (`project` у типов под проектом, `parent` у
  `registry_repository`) — опора есть субъект кортежа;
- регистрация отношением из `writes` — опора есть ВЫВЕДЕННЫЙ родитель объекта: субъект его факта
  указателя в kaname (`kaname.relation_fact`, отношение — имя указателя типа, чтение по префиксу
  ключа `relation_fact_pkey (object_type, object_id, relation)`, `0001_initial.sql:4257`). Факт
  указателя ложится только регистрацией указателем, а она после этой задачи проходит вывод.
  Цепь и поля строки зеркала опорой НЕ служат: регистрация вправе опустить звенья и поля (§2 п.6),
  и объект с цепью `[account:…]` либо с пустой цепью опору всё равно имеет (DP-17 a, c). Факта
  указателя нет — опоры нет (Р8, DP-15 b). Фактов указателя несколько (перенос под другой
  контейнер того же проекта, ND-09, когда прежний указатель ещё не снят) — сведения сверяются с H
  каждого и проходят, если согласны хотя бы с одной: каждый такой субъект — родитель, уже
  выведенный kaname (DP-17 e, f).

**Р5. Иерархия kaname от опоры** — H(a):
- `a = project:P` — P есть строка `kaname.projects`; `H = [project:P, account:A]`, A — её
  `account_id`;
- `a = K` (объект модуля) — у K есть строка зеркала; проект K — её `parent_project_id`, при
  пустом — звено `project` цепи K; `H = [K, project:P_K, account:A_K]`, A_K — аккаунт P_K по
  `kaname.projects`. Если проект K ни из строки, ни из цепи не выводится, `H = [K]` — иерархия
  без проекта и аккаунта. Здесь читается ЗАПИСАННАЯ область контейнера, а не его факт указателя:
  ребёнок не бывает в области шире, чем записана у его контейнера (DP-14);
- иначе иерархии нет: проекта в kaname нет либо K не зарегистрирован.

**Р6. Сверка.** Регистрация проходит, только если H выведена и каждое сведение модуля с ней
согласно:
- `parentProjectId` пуст либо равен проекту H (у H без проекта — только пуст);
- `parentAccountId` пуст либо равен аккаунту H (у H без аккаунта — только пуст);
- `parentChain` — подпоследовательность H: каждое звено есть звено H дословно (`<type>:<id>`),
  порядок звеньев H сохранён, звена вне H и повтора нет.

Расхождение любого одного — отказ Р8. Это и есть «проект объекта совпадает с проектами звеньев
цепи»: проект в поле, проект в звене цепи и проект контейнера, названного в цепи, равны проекту
опоры.

**Р7. Вывод сверяет, а не дописывает.** Опущенное поле остаётся пустым, опущенное звено в цепь не
вставляется (Р-В1): `parent_project_id` строки зеркала равен присланному. Прежнее дозаполнение
пустого аккаунта по проекту (`register_resource.go:847-855`) сохраняется: оно берёт аккаунт из
`kaname.projects` и с Р5 совпадает by construction. Пустая цепь и пропущенное звено — §2 п.6.

**Р8. Отказ вывода.** `FAILED_PRECONDITION`, `message` = `<object> parent scope does not match`,
где `<object>` — значение поля `object` запроса дословно. Ровно одна деталь `ErrorInfo`:
`reason = "PARENT_SCOPE_MISMATCH"`, `domain = refusaldomain.For("iam")` (тот же, что у
`REFERENCE_*`, `internal/apps/kaname/shared/reference_refusal.go:68-76`),
`metadata = {"resource_type":"<модельный тип>","resource_id":"<id>"}`. Ни `message`, ни
`metadata` не называют выведенного проекта, аккаунта или контейнера и того, какое сведение
разошлось. Ответ одинаков, нет ли опоры или разошлось сведение. Ничего не записывается. Повтор
того же запроса — тот же отказ. Отказ не терминален для потребителя: ребёнок, пришедший раньше
своего контейнера, проходит повтором после регистрации контейнера.

**Р9. Порядок отказов.** Ворота личности → правило 0.1 и политика (Р3, `PERMISSION_DENIED`) →
вывод (Р8, `FAILED_PRECONDITION`). Политика стоит раньше вывода (DP-16): модуль не узнаёт ничего
об иерархии kaname записью, на которую не вправе. Политика и вывод — в той же транзакции, что
пишет регистрацию, до её первого оператора записи; отказ любого из двух откатывает транзакцию,
и ничего не записано. Прежние отказы формы (`INVALID_ARGUMENT` полей кортежа и меток) не
меняются; их место относительно политики эта приёмка не утверждает. Порядок с отказом привязки
`#983` — Р10.

**Р10. Соседство с `#983`.** Когда к регистрации приложимы оба отказа — Р8 этой приёмки и отказ
привязки `OBJECT_BOUND_TO_OTHER_PROJECT` (`#983` Р4), — возвращается отказ привязки. Так
одобренная редакция `#983` остаётся верной без правки: её PB-24 a–d (поле и звено цепи расходятся
между собой у привязанного объекта) ждут отказа привязки, а не Р8. До посадки `#983` привязок нет,
и такие запросы получают Р8. Держатель порядка — PB-24 a–d `#983` (§5.4). В2 решён диспетчером —
вариант (а).

Порядок сам не получается: вывод стоит до первой записи (Р9), а сверка привязки по одобренной
`#983` живёт на уровне записи зеркала и цепи — оператором либо триггером транзакции `UpsertTx`, не
в `emit` (`#983` Р9, строка PB-01 её §5). Без условия к коду PB-24 a–d получили бы Р8, в том
числе PB-24 c, где привязку заводит этот же запрос. Условие ложится на реализацию `#983`, которая
идёт после этой задачи, и названо в §7 строке 4.

**Р11. Снятие регистрации и публикация** — §2 п.4, п.5. Ни политика, ни вывод их не судят.

**Р12. Чтение в транзакции записи.** Вывод читает строку проекта, строку зеркала и рёбра
контейнера в той же транзакции, что пишет регистрацию. Нового межстрочного инварианта сверх
момента записи нет: смена контейнера после регистрации ребёнка — §2 п.7, и любой порядок двух
коммитов даёт состояние, достижимое последовательным порядком. Поэтому конкурентного сценария
с CAS здесь нет.

Вывод судит иерархию **на момент чтения в той же транзакции**, а не на момент коммита. Строка
`kaname.projects` читается без блокировки, и у зеркала ключа на проект нет. Отсюда окно
«регистрация обгоняет удаление проекта»: транзакция регистрации прочла проект, удаление проекта
закоммитилось раньше неё, регистрация коммитится, и строка зеркала называет проект, которого уже
нет. Окно остаётся, и его исход законен: он объявлен приёмкой
`non-empty-project-is-not-deleted.md` §7.4 (отпечаток
`db46a803c1f4fbeeb7597bd51f72e220b7e0735ac103ef086c4cadbaafac1cc6`, в линии `origin/955`) и
закреплён её сценарием IAM-PNE-1-13 (`internal/repo/kaname/pg/project_delete_nonempty_integration_test.go:170`
`TestProjectDelete_PNE_1_13`, проба
пишет через `UpsertTx` напрямую, эта задача её не трогает). Эта приёмка окна не закрывает и
пробы сериализации регистрации с удалением проекта не заводит: такая проба мерцала бы, а
законный исход уже имеет держателя.

**Р13. Контракт.** `.proto`: комментарий `RegisterResource` (`internal_iam_service.proto:167-184`)
называет оба отказа (код, причина, когда); комментарии `parent_project_id`, `parent_account_id`,
`parent_chain` (`:404-411`, `:423-452`) — что kaname сверяет их со своей иерархией и не
дописывает. Новых полей и номеров нет; `buf breaking` зелёный.

### Критерии продукта (ban #18)

- **Производительность.** Цена на регистрацию: политика — 0 обращений сверх чтения строки
  каталога, которое транзакция `emit` уже делает (`catalog_type.go:98`, вызов
  `register_resource.go:832`); у имени типа, пришедшего уже в словаре каталога (с точкой), перевод
  базу не спрашивает, и там политике нужен 1 поиск строки каталога по ключу. Вывод от проекта —
  1 поиск по первичному ключу `kaname.projects` (сегодня он делается только при пустом аккаунте);
  вывод от контейнера — 1 поиск по первичному ключу строки зеркала, ≤ 4 строки рёбер (предел
  глубины `resource_parent_edge_depth_bounded`) и 1 поиск проекта; запись из `writes` — сверх
  этого 1 чтение фактов указателя по префиксу первичного ключа `relation_fact_pkey`. Все чтения — в
  той же транзакции, нового обращения вне её нет. Замер — DoD п.8;
- **Безопасность.** Поверхность сужается: новых методов, слушателей и полей нет. Закрывается
  запись модулем отношения, которого он не объявил (`owner` у svc-registry — SRI-110 d), субъекта
  не того типа в указателе, и регистрация под проектом, аккаунтом или контейнером, с которыми
  иерархия kaname не согласна на момент чтения в той же транзакции (SRI-110 e). Окно «регистрация
  обгоняет удаление проекта» остаётся, его исход законен и объявлен (Р12). Закрытие держит
  use-case для любого входа, а не обработчик (Р1, DP-06). Новый наблюдаемый признак — «проекта с таким id в
  kaname нет» — получает только личность модуля на внутреннем слушателе, и он неотличим от
  расхождения (Р8). Остаток назван и закрытием не объявлен: проект нового объекта верхнего
  уровня (§2 п.2);
- **Инновационность.** Модуль объявляет данными манифеста, ЧТО он пишет, и kaname выводит
  иерархию сам, а не верит модулю;
- **Узнаваемость относительно рынка.** Аналога «объявленная форма записываемого отношения на
  тип объекта, сверяемая службой доступа с её собственной иерархией» нет: обычно модулю
  выдают право писать отношения целиком. Наш вариант лучше тем, что неверная регистрация
  отвергается на входе, а не обнаруживается выдачей;
- **Перспективность.** Аддитивно: ключ отсутствует — модуль пишет только указатель; внешне
  адресуемая координата (id) не меняется; откат — снятие проверки без миграции данных арендатора;
- **Благо продукта и производственность.** Режимов «только для стенда» нет.

  `(тип объекта, отношение, тип субъекта)` для модельного типа, порядок не значим.

Каждый сценарий исполняется на своём мире ДР; примеры одного сценария — на одном мире, в порядке
таблицы, если «Дано» не говорит иного.

**Тело отказа политики** («ПД-отказ»): `PERMISSION_DENIED`, `message` = `permission denied`,
деталей нет — побайтово как у правила 0.1.

**Тело отказа вывода** («Р8-отказ(obj)»): `FAILED_PRECONDITION`; `message` =
`<obj> parent scope does not match`; ровно одна деталь `ErrorInfo` с `reason =
"PARENT_SCOPE_MISMATCH"`, `domain = refusaldomain.For("iam")`,
`metadata = {"resource_type":"<модельный тип>","resource_id":"<id>"}`; ни `message`, ни `metadata`
не содержат id проекта, аккаунта или контейнера, кроме самого объекта.

## §8. Открытые вопросы

Все четыре вопроса решены диспетчером 2026-10-26 — вариант (а). Варианты и цены оставлены как
основание решения.

**В1. Как модуль получает право писать отношение сверх указателя.** Решено (а): Р1, Р2.
- (а) явный ключ `writes`. Цена — ключ, шесть отказов загрузчика, колонка; registry платформы
  теряет запись `owner` до правки своего манифеста (§7 строка 2);
- (б) только указатели, сверх них — ничего ни у кого. Цена — у registry платформы пути вернуть
  `owner` нет вовсе, пока он не заменён svc-registry; DP-03, DP-15, DP-16, DP-20 снимаются;
- (в) право выводится из авторского отношения `owner` в `relations`. Цена — SRI-110 d
  невыполним, пока svc-registry держит `owner` в модели ради вывода действий; политика снова
  шире нужного — ровно признак `#982`.
**Рекомендация — (а).**

**В2. Порядок отказа вывода и отказа привязки `#983`.** Решено (а): Р10, условие к коду — §7
строка 4.
- (а) отказ привязки раньше. Цена — условие реализации `#983` (§7 строка 4); одобренная `#983`
  не правится;
- (б) отказ вывода раньше. Цена — PB-24 a–d `#983` ждут другого кода: новая редакция `#983` и
  новый круг её ревью.
**Рекомендация — (а).**

**В3. Пустая цепь и пропущенное звено.** Решено (а): принимаются (§2 п.6, Р7; запись из
`writes` у такого объекта — DP-17 a, c).
- (а) принимать, как сегодня. Цена — объект с пустой цепью выпадает из области (сужение, не
  расширение доступа);
- (б) отвергать у регистрации указателем. Цена — меняет контракт `parent_chain`
  (`internal_iam_service.proto:438-449`), ломает форму PB-25 d `#983` и до 29 файлов проб.
**Рекомендация — (а).**

**В4. Проект опоры, которого нет в kaname.** Решено (а): отказ Р8 (DP-10 g); окно гонки с
удалением проекта — Р12.
- (а) отказ. Цена — регистрация под удалённым или выдуманным проектом не проходит; часть проб
  §0.6 переписывается;
- (б) принимать, как сегодня. Цена — модуль кладёт объект под проект, которого kaname не знает,
  и охрана удаления проекта такой объект не видит.
**Рекомендация — (а).**
