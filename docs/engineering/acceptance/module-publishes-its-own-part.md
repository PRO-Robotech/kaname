## Обзор

Сегодня части модели доступа модулей приезжают в kaname каталогом файлов и читаются один раз при
старте; поправить часть можно только перезапуском всех реплик, снять модуль нельзя, а сам модуль
опубликовать свою часть не может. Эта приёмка делает базу kaname единственным источником частей:
модуль своей учёткой деплоя вызывает `Publish` на внутреннем слушателе, ревизия части неизменяема
и только растёт, модель собирается и допускается целиком при публикации, реплики переходят на
новую ревизию модели без перезапуска, а ревизия модели видна в каждом решении. Сужение, оставляющее
выдачи арендаторов без опоры, проводит только человек с усиленным входом. Чтение каталога на старте
снимается этим же изменением.

## Что НЕ входит

1. **Правка платформы** (пять манифестов `services/*/manifest.yaml` получают `revision`, Job
   публикации подключается к чартам модулей, маршруты края на изменённые глаголы) — делается при
   перепине kacho, вне этой приёмки (основание порядка выше). Цена названа в §8.
2. **Сквозные пробы края (newman)** для человеческой полосы (`Plan`/`Apply`/`Withdraw` через край)
   — их дом край платформы, и они садятся с перепином. В kaname эти глаголы судятся integration-пробой
   с идентичностью края (`testing-newman.md#edge-internal-consequence`: следствие внутреннего
   слушателя, краем пока не маршрутизируемое). Публикация модулем (`Publish`) краем не
   маршрутизируется вовсе — её уровень integration по построению.
3. **Перечень выдач посева, который вправе объявить часть**, — предмет `kaname#979`; здесь только
   утверждается, что `Publish` зовёт тот же полный судья посева, что и загрузка, — доказано
   существующим отказом якоря (981-24, Д9). Проба судьи перечня вызовом `Publish` — пункт DoD
   `kaname#979`; порядка посадки между задачами нет. **Правило MOD-MF-24 для валидатора связности
   не меняется**: вступление своей личностью в группу, которую посев не заводит, законно
   (`module-manifest-seed-contract.md` §5.7); `Publish` поверх него сужает **множество групп**
   вступления до групп встроенной части kaname (Р4е, 981-19, Д10).
4. **Чарт registry-operator** (вне наших стволов) — шаблон Job публикации лежит в чарте kaname
   (Д3) и подключается модулем у себя.
5. **Подписка на изменения модели** (поток событий ревизий) — не заводится: реплики узнают о новой
   ревизии сигналом базы и опросом-страховкой (§2.8); `ListSubjects` и `WhoAmI` ревизию модели не
   несут (§2.9).
6. **Сторонние модули без выпуска kaname** — по решению задачи закрыто (§2.4, Д4; пересмотр — при
   первом стороннем модуле).
7. **Замер p50/p95 сборки и допуска** — заказ O-2 разбора; его отчёт есть пункт DoD (§9 п. 9), а не
   сценарий.

### §0.3. Что ОПРОВЕРГНУТО перемером

1. **«Манифест registry пока не несёт ревизии»** (тело задачи, «Зависимости» п. 1) — уже, чем
   дерево: ревизии не несёт **ни один** из пяти манифестов платформы. По файлам
   `git -C <kacho> show 41d7edad9b:services/<m>/manifest.yaml | grep -c '^revision:'` → 0 у
   compute, nlb, registry, storage, vpc; знаменатель — `git -C <kacho> ls-tree -r --name-only
   41d7edad9b | grep -c '^services/[^/]*/manifest.yaml$'` → 5. И встроенная часть kaname ревизии
   не несёт (П20).
2. **«Расширение модуль публикует сам»** при нынешнем каноне неисполнимо: 20 из 33 типов канона —
   типы модулей (П9), а норма композиции требует их побайтного равенства канону (П10). Решение — §2.4.
3. **«Пространство имён модуля»** из имени модуля не выводится: модуль `loadbalancer` объявляет
   типы `nlb_*` (`git show 41d7edad9b:services/nlb/manifest.yaml | grep -E '^module:|objectType:'`).
   Решение — данными (§2.4).

## §1. Предмет

Три наблюдаемых свойства, каждое — с держателем:

1. **Модуль публикует новую ревизию своей части без перезапуска kaname**, и не позже окна `W` после
   `done` все реплики решают по модели не старше этой публикации либо отвечают закрытым отказом
   одного вида (981-01, 981-60, 981-61).
2. **Граница публикации**: чужой модуль, выход за своё пространство имён, сужение не человеком,
   откат ревизии — отвергаются; у каждого отказа положительный близнец (§6).
3. **Второго способа читать части нет**: чтения каталога на старте нет, Job импорта публикует тем же
   глаголом (981-80, 981-83, 981-88).

только наблюдаемое поведение, которого им не хватало.

### §2.1. Поверхность: две полосы, одна служба, один конвейер

- **Полоса модуля** — новый сервис `InternalModulePublishService` с глаголами `Publish` и `Plan`.
  Только внутренний слушатель (ban #6), прямой вызов учёткой деплоя модуля; в перечень
  гейт-фронтируемых **не входит** (зовёт не край). Право — `module_publisher` на объекте
  `module:<module из запроса>`; ступень `required_acr_min = "1"` объявлена явно.
- **Полоса человека** — `InternalModuleService` (П1): `Plan`, `Apply`, новый `Withdraw`, `Get`,
  `List`. Право — `system_admin` на `cluster`; `Apply` и `Withdraw` — `required_acr_min = "2"`; все
  члены перечня гейт-фронтируемых (зовёт только край).
- **Один конвейер**: разбор → суждение формы и пространства имён → суждение ревизии → классификация
  дельты → сборка модели из частей всех модулей → допуск модели → перепись выдач без опоры →
  запись. `Plan` любой полосы — тот же конвейер с откатом транзакции; полосы различаются только
  допуском классов (§2.5). Второй реализации сравнения не заводится.
- **Мутации возвращают терминальную `Operation`** (форма службы, П1): `done = true` приходит в
  ответе, отказы — синхронной ошибкой gRPC. `done` означает «ревизия части, строки каталога и
  ревизия модели закоммичены» — и только; переход реплик в `done` не входит (`api-operation-done`).
- **Имя модуля — неизменяемый идентификатор** модуля (ключ каталога; после снятия не
  переиспользуется, §2.7), а не косметическая метка: адресация `module:<имя>` не нарушает ban #15.

### §2.2. Вход `Publish` и `Plan` полосы модуля

```
PublishModuleRequest { string module = 1; bytes document = 2; }
PlanPublishRequest   { string module = 1; bytes document = 2; }
```

- **Р2а. Порядок проверок** (наблюдаемый): проверенный SAN → политика вызывающего (любой
  проверенный модуль, без ветки «вне боевой посадки — пропуск») → форма поля `module` (непусто,
  грамматика имени модуля `domain.IsWellFormedModuleName`; объект права из неё не строится, и отказ
  формы о правах не говорит ничего) → `Check(module_publisher, module:<module>)` → потолок размера
  `document` → разбор → `document.module == module` → остальное. Тело от вызывающего без права не
  разбирается (981-13).
- **Р2б. Отпечаток** считает только сервер, тем же производителем, что загрузчик (П4); клиент его
  не присылает.
- **Р2в. Ревизия обязательна**: документ без `revision` — `INVALID_ARGUMENT`, поле
  `document.revision`; подстановки ревизии нет ни у `Publish`, ни у Job импорта. Это и есть стадия
  S2 `kaname#906`, внесённая в `Publish` (Д1).
- **Р2г. Семантика CAS одна**: новая ревизия больше живой; равная с равным отпечатком — успешный
  повтор без записи (`unchanged = true`); равная с иным — конфликт; меньшая — отказ «старше».
  Тексты отказов — производитель П2, дословно. Откат выражается новой большей ревизией с прежним
  содержимым.

### §2.3. Ответ

```
PublishModuleResponse { module; revision; digest; model_revision; classification; unchanged }
PlanPublishResponse   { module; live_revision; declared_revision; classification;
                        revision_outcome; orphaned_counts (по популяциям §2.5); model_revision_base }
```

`PlanPublishResponse` полосы модуля несёт **только числа** по популяциям, без идентификаторов
выдач и субъектов: перечень субъектов арендаторов — данные арендатора, и учётке деплоя он не
нужен (§3, У11). Перечни — у человеческого `Plan` (§2.6).

### §2.4. Модуль, его пространство имён и канон

- **Р4а (RA1, Д2). Канон сужается до своих типов kaname** (13 нынешних плюс новый `module`); 20
  типов модулей платформы уходят из канона и приходят только опубликованными частями. Норма
  «блок типа канона равен канону» продолжает действовать — для типов kaname (981-21).
- **Р4б (RA2). Пространство имён — данные встроенной части kaname**, закрытым перечнем:

  | модуль | префикс типов | учётка деплоя (аккаунт `kacho-system`) |
  |---|---|---|
  | `vpc` | `vpc_` | `kacho-vpc-publisher` |
  | `compute` | `compute_` | `kacho-compute-publisher` |
  | `loadbalancer` | `nlb_` | `kacho-nlb-publisher` |
  | `registry` | `registry_` | `kacho-registry-publisher` |
  | `storage` | `storage_` | `kacho-storage-publisher` |

  Часть модуля вправе объявить только типы со своим префиксом; родителем типа — свой тип либо
  контейнер kaname из закрытого перечня `{project, cluster}` (перепись П24: иных родителей у
  частей нет); правила ролей части называют только ресурсы своего модуля. **Точек расширения в
  типах kaname нет**: часть не дописывает отношений ни в один тип kaname, ссылка на контейнер
  родителем — не расширение. Перечень и префиксы читаются из данных, а не выводятся из имени
  модуля (§0.3 п. 3).
- **Р4в (RA11). Перечень модулей закрыт в бинарнике kaname**: выдачи `module_publisher`
  объявляет только встроенная часть, и меняются они только выпуском kaname; единственное
  исключение — переходная учётка Job импорта, чьи выдачи есть подмножество той же таблицы (§2.11),
  то есть перечня не расширяют. Подключение модуля,
  которого нет в таблице, требует выпуска kaname. Это **сужает** решение «набор модулей разомкнут»
  (`internal/manifest/moduleset.go`): сегодня сторонний модуль объявлялся доставкой без пересборки
  образа, после изменения — нет. Сказано прямо; решение — Д4 (пересмотр при первом стороннем модуле).
- **Р4г. Отношение `module_publisher`** объявлено как `[service_account]` и только так: без
  подстановки, без класса, без членства группы (единственный неизменный получатель на модуль —
  исключение `grant-to-group` по его же предикату). Допуск модели канон по подстановке не судит
  (`TestAdmitCanonWildcardIsNotJudged`), а допуск вида получателя подстановку объявления не
  засчитывает (П28), поэтому у отношения своя проба — на самом объявлении в допущенной модели
  (981-16 (а)). Выдача `module_publisher` выражается **только строкой таблицы Р4б** (учётка
  деплоя — служебная запись по имени, другого вида получателя строка не несёт); выдачей посева
  (`seed.accessBindings`) она невыразима ни одной частью, встроенной в том числе: якорь посева —
  только кластер (П27), а у типа `cluster` отношения `module_publisher` нет (981-16 (б)).
- **Р4д. Рабочая учётка модуля** (лист, которым модуль ходит в kaname; у registry-operator —
  `kacho-registry`) права публикации не имеет (981-12).
- **Р4е (Д10). Группа вступления — только группа, объявленная встроенной частью kaname**
  (`seed.groups` встроенной части; сегодня ровно одна — `module-relation-writers`, П30), по паре
  (аккаунт, имя) в написании встроенной части. Множество закрыто в бинарнике так же, как таблица
  Р4б, и меняется только выпуском kaname. Правило MOD-MF-24 при этом верно как было: группа
  вступления не обязана быть заведена посевом самой части; сужается лишь множество, из которого
  она берётся, — группы другой части и группы арендаторов в него не входят. Живых вступлений вне
  множества нет: 5 из 5 частей платформы вступают в `module-relation-writers` (П30). Вступление
  вне множества — `INVALID_ARGUMENT`, поле `document.seed.joins[i].group`, текст называет пару
  группы и группы встроенной части (981-19 (б)).
- **Р4ж. `Publish` зовёт полный судья посева загрузчика**, а не его часть: связность выдач и
  вступлений (П25), якорь (П27), вид субъекта и выдачу отношением (П28) — плюс сужение Р4е. Выдача
  отношением в `Publish` судится против канона kaname всегда (перепись связности: выдач
  отношением суждено = прочитано): якорь посева — кластер, тип `cluster` — тип kaname, а
  отношений в типы kaname часть не дописывает (Р4б), поэтому ответ канона авторитетен до сборки
  модели. Судья перечня `kaname#979` встаёт в тот же вход (§3 У15).

### §2.5. Опора выдачи и классификация дельты (RA6)

**Выдача** — запись, дающая право и называющая элемент части модуля. Популяций четыре, перечень
закрыт:

| № | популяция | производитель сегодня |
|---|---|---|
| В1 | ссылки правил ролей на ресурс или глагол модуля | П21 (переселение, ведомость сирот) |
| В2 | глаголы ролей, выведенные из глагола модуля | П21 |
| В3 | элементы селекторов правил, называющие тип модуля | П21 (вырезание) |
| В4 | факты отношений и привязки доступа на объектах типа модуля либо по отношению, объявленному частью | записи `RegisterResource` и `AccessBindingService.Create` |

**Опора выдачи** — живость в применяемой ревизии каждого элемента, который выдача называет (тип,
ресурс, глагол, отношение). **Без опоры** выдача остаётся, если применяемая ревизия снимает или
сужает хотя бы один такой элемент. Выдачи без опоры считаются **в транзакции записи**, а не
переносятся из плана.

**Классов дельты пять, набор закрыт:**

| класс | определение | полоса модуля | полоса человека |
|---|---|---|---|
| `UNCHANGED` | равная ревизия, равный отпечаток | принимается без записи | принимается без записи |
| `EXTENSION` | ни один элемент прежней части, несущий право, не снят и не сужен (только добавления; правка прозы `notes`/`description` — сюда) | принимается | принимается |
| `NARROWING_WITHOUT_ORPHANS` | снят или сужен элемент, но выдач без опоры ноль по всем В1…В4 | принимается | принимается |
| `NARROWING_WITH_ORPHANS` | выдач без опоры больше нуля хотя бы в одной популяции, **либо** дельта нераспознаваема: смена `parents` или `objectType` у существующего ресурса (структурная правка путей разрешения) | **отвергается** `FAILED_PRECONDITION` | принимается при подтверждении и потолках |
| `WITHDRAWAL` | снятие модуля целиком | **невыразим**: пустая часть — `INVALID_ARGUMENT` (981-29), `Withdraw` модулю не дан (981-54) | только `Withdraw` |

Переименование типа или ресурса — снятие плюс добавление и классифицируется по выдачам; правка,
не выразимая ни добавлением, ни снятием, — худший класс.

### §2.6. Человеческая полоса: `Plan`/`Apply` переоснованы (RA4)

- **Вход меняется**: каталог доставки снят (Р9), поэтому `PlanModuleRequest` и
  `ApplyModuleRequest` получают поле `bytes document` (новый номер); перечитывание каталога
  уходит. Шапка `internal_module_service.proto` «вход — имя модуля, никогда тело» правится тем же
  изменением: оба её довода сняты (второго пути доставки нет; опора стража паритета переезжает на
  живые ревизии базы).
- **`Plan` становится `POST …/{module}:plan`** (тело в `GET` невозможно). Ответ несёт перечни по
  В1…В4 (с усечением, как сегодня), класс дельты и `expected_state`, который `Apply` подтверждает.
- **Поля, потерявшие предмет** — вердикт `MODULE_PLAN_VERDICT_WOULD_BE_REFUSED_BEYOND_ANCHOR` и
  поля `beyond_anchor_extra`, `beyond_anchor_missing`: опоры доставки больше нет, производителя у
  них нет. Снимаются с `reserved` номера и имени, ломающее изменение объявляется в коммите
  (`api-outcome-remove`).
- **Цена**: маршруты края платформы на `Plan` (сейчас `GET`) и отсутствующий маршрут `Withdraw`
  расходятся с контрактом до перепина kacho; до перепина человеческая полоса через край
  недостижима (§8).

### §2.7. Надгробия, снятие модуля, неопубликованный модуль (RA9, RA10)

- **Снятие типа** — правкой части с классом сужения; тип получает **надгробие**: имя занято
  навсегда, повторное объявление в любой ревизии — `FAILED_PRECONDITION` «тип <имя> снят и не
  переиспользуется». Выдачи на объекты снятого типа остаются строками (каскада нет).
- **Снятие модуля** — глагол `InternalModuleService.Withdraw(module, expected_state, потолки)` →
  терминальная `Operation`; только человеческая полоса, `system_admin`, ступень 2; `Plan` снятия —
  `PlanModuleRequest` с признаком снятия вместо документа (одно из двух, `oneof`). Пустой документ
  и документ без ресурсов снятием **не являются** — `INVALID_ARGUMENT` (981-29).
- **Снятый модуль**: `Get` — `NOT_FOUND` «Module <имя> is withdrawn»; публикация — `FAILED_PRECONDITION`
  «модуль <имя> снят и не переиспользуется». **Никогда не публиковавшийся модуль**: `Get` —
  `NOT_FOUND` «Module <имя> not found» (форма П1). Три состояния различимы: не опубликован · живая
  ревизия N · надгробие.
- **Решение по типу**: для типа модуля без опубликованной ревизии — `allowed = false`, причина
  `module_unpublished: <модуль>`; для типа под надгробием — `allowed = false`, причина
  `type_retired: <тип>`. Это отказ определённый (права нет), а не «повтори» — поэтому `allowed =
  false`, а не `UNAVAILABLE`. У `ExpandRelations` (интроспекция, не решение) те же состояния —
  `FAILED_PRECONDITION` с тем же текстом причины.

### §2.8. Живая модель на репликах (RA3)

- Собранный и допущенный текст модели хранится ревизией модели (целое, растёт на 1 при каждой
  записи части, кроме `UNCHANGED`) с отпечатком. Реплика не пересобирает, а загружает по ревизии,
  сверяет отпечаток и подменяет снимок **целиком**: модель, факты каталога модулей и системные
  роли частей одной ревизии.
- **Подтверждение**: реплика считает себя текущей, если не дольше `W` назад прочла из базы
  головную ревизию модели и держит именно её. Сигнал базы ускоряет, опрос с периодом `P < W`
  страхует.
- **Закрытый отказ**: реплика без подтверждения в окне `W` на всякое решение (`Check`,
  `BatchCheck`, `InternalIAMService.Check`, `ExpandRelations`) отвечает `UNAVAILABLE` с
  фиксированным текстом «authorization model is not confirmed current» — одним видом, не `allowed
  = false`: «не знаю текущей модели» и «прав нет» различимы, и потребитель не кеширует отрицание.
- **Наблюдаемая гарантия**: пусть `Publish` вернул `done` с `model_revision = M` в момент `t0`.
  В любой момент `t ≥ t0 + W` каждое решение каждой реплики либо несёт `model_revision ≥ M`, либо
  `UNAVAILABLE`. Время фактического схождения (p50/p95) — замер (§9 п. 9), а не контракт.
- **Ручки без умолчания** (отказ старта при незаданной, `P < W`): `model.stale-after`
  (`KANAME_MODEL__STALE_AFTER`) и `model.poll-interval` (`KANAME_MODEL__POLL_INTERVAL`); значения
  чарта — 30 с и 5 с (Д6).
- **Готовность**: реплика не объявляет себя готовой, пока не загрузила и не подтвердила головную
  ревизию (981-65). Недоступная база дольше `W` даёт `UNAVAILABLE` — сегодня решения при
  недоступной базе тоже недоступны (П23), новой потери доступности нет.

### §2.9. Ревизия модели в решении (RA12)

Новое поле — **новый номер и новое имя**; номера и имена из П14 не переиспользуются:

| ответ | поле | номер | JSON |
|---|---|---|---|
| `AuthorizeCheckResponse` (`Check` и каждый элемент `BatchCheck`) | `int64 model_revision` | 5 | `modelRevision` |
| `ExpandRelationsResponse` | `int64 model_revision` | 5 | `modelRevision` |
| `CheckResponse` (`InternalIAMService.Check`) | `int64 model_revision` | 3 | `modelRevision` |

Заполняется на **каждом** решении — разрешении и отказе — из того снимка, по которому решение
принято; один снимок на запрос (у `BatchCheck` — один на всю пачку, значение у всех элементов
равно). `ListSubjects` и `WhoAmI` поля не несут: это перечисления, не решения; вопрос о
согласованности страниц между ревизиями — вне объёма (Что НЕ входит п. 5).

### §2.10. Аудит и пределы (RA7, RA8)

- **Аудит**: каждая **записанная** публикация (не `UNCHANGED`) пишет ровно одну запись аудита в той
  же транзакции: актор — из проверенной личности вызова, полоса (`module` · `import` · `operator` ·
  `embedded`), модуль, ревизия, отпечаток, класс дельты, ревизия модели. Без проверенной личности —
  отказ до транзакции.
- **Отвергнутые публикации** записи аудита **не пишут** (отказ откатывает транзакцию; запись на
  пути отказа была бы усилителем нагрузки на базу) — их учитывает счётчик
  `kaname_module_publish_refusals_total{reason}` с закрытым набором причин: `permission`,
  `module_mismatch`, `namespace`, `revision_missing`, `revision_stale`, `revision_conflict`,
  `size`, `rate`, `narrowing_requires_operator`, `withdrawn`, `form`, `seed` (посев части отвергнут
  полным судьёй посева Р4ж — связность П25, якорь П27, вид и отношение П28, сужение групп Р4е;
  после посадки `kaname#979` — и судьёй перечня выдач). Плюс структурная строка
  журнала с актором и причиной. «Ноль отказов за жизнь» наблюдаем счётчиком с нулём.
- **Потолок размера**: ручка `module-publish.max-document-bytes`
  (`KANAME_MODULE_PUBLISH__MAX_DOCUMENT_BYTES`) без умолчания; значение чарта 262 144 Б — 3,3 ×
  наибольшей части (П20, 78 375 Б). Превышение — `INVALID_ARGUMENT`, поле `document`, текст
  называет потолок; транспортный предел внутреннего слушателя задаётся явно не ниже потолка (П19).
- **Предел частоты**: не больше 3 **новых** ревизий одного модуля за 60 с, общий на все реплики и
  держимый базой в транзакции записи (образец П16), а не счётчиком процесса. `UNCHANGED` и отказы
  в счёт не идут: предел бережёт смену модели на всех репликах, а смену дают только записи.
  Превышение — `RESOURCE_EXHAUSTED`, текст называет окно и предел. Ручки
  `module-publish.window` и `module-publish.max-revisions-per-window` без умолчания (Д5).

### §2.11. Переход: старт, встроенная часть, Job импорта, шаблон Job публикации

- **Чтение каталога на старте снимается** (Р9): оба прод-вызова читателя доставки (П7) и все
  четыре ручки раздела `manifests` (П8). Заданная ручка — отказ старта с текстом «manifests.* сняты:
  части модулей публикуются глаголом Publish» (не молчаливое игнорирование).
- **Встроенная часть kaname** (`module: iam`) получает `revision: 1` (П20) и публикуется самим
  процессом при старте тем же конвейером, полоса `embedded`, если её ревизия больше живой. На
  пустой базе модель = канон + часть `iam`.
- **Обновление существующей базы**: строки каталога, применённые прежним путём, при старте не
  трогаются; частей у модулей платформы нет, решения по их типам — `module_unpublished`, пока модуль
  не опубликует ревизию. Публикация ревизии 1 с прежним содержимым — класс `EXTENSION` либо
  `UNCHANGED` по строкам, выдачи без опоры не появляются, права не переселяются (981-82).
- **Job импорта** (чарт kaname, переходный клиент `kaname#964`): читает ConfigMap, перечисленные в
  values, и вызывает `Publish` своей учёткой `kaname-manifest-import`, полоса `import`. Учётку
  объявляет встроенная часть, а выдачи `module_publisher` ей процесс пишет при старте по ручке
  `module-publish.import-modules` (`KANAME_MODULE_PUBLISH__IMPORT_MODULES`, перечень имён): ровно
  пересечение перечня с таблицей Р4б, прочие выдачи этой учётки снимаются тем же шагом. Ручка без
  умолчания; пустой перечень значит «импорт выключен, выдач нет» — сужение до нуля, а не «не
  сужаем»; имя вне таблицы Р4б — отказ старта. Чарт выводит перечень из тех же values, что
  монтируют ConfigMap (Д7). Ревизию Job не подставляет; на отказе содержимого завершается неуспехом
  без повтора; на `UNAVAILABLE` повторяет в объявленном бюджете. **Предикат снятия
  переходности**: все модули таблицы Р4б публикуют свою часть своим Job публикации на стенде — тогда
  Job импорта, ручка и учётка снимаются из чарта и встроенной части одним изменением.
- **Шаблон Job публикации** — в чарте kaname (Д3), для подключения модулем: объявляет ПАРУ —
  адрес внутреннего слушателя kaname и удостоверение учётки деплоя; половина пары — отказ рендера;
  хук `pre-install,pre-upgrade` (публикация до подъёма кода модуля).

## §3. Модель угроз (высокоуровнево)

Описаны классы угроз и чем они закрыты; механика эксплуатации не приводится (репозиторий публичен).

**Активы**: модель доступа (кто что может у всех арендаторов) · части модулей и история ревизий ·
выдачи арендаторов · аудит.

**Действующие лица**: учётка деплоя модуля (законный издатель) · рабочая учётка пода модуля ·
учётка деплоя ДРУГОГО модуля · Job импорта · край и человек-оператор · реплика kaname · вызывающий
без проверенного сертификата.

| № | угроза | чем закрыта | сценарии |
|---|---|---|---|
| У1 | Публикация от имени чужого модуля | право на `module:<module запроса>`; `document.module` обязан совпасть; модуль учётки определяет только выдача, не SAN | 981-10, 981-11 |
| У2 | Захват рабочей учётки пода ведёт к публикации | право только у отдельной учётки деплоя | 981-12 |

**Остаточные риски, названные, а не скрытые** (`ban18-q-security`):

1. Захват учётки деплоя модуля позволяет **расширить** права на типах своего модуля — так решено
   задачей («расширение модуль публикует сам»). Ограничители: только своё пространство имён (У3),
   аудит каждой записи (У13), предел частоты (У9), раздельные учётки деплоя и пода (У2).
2. **Вступление в группу, которую часть не заводит**, законно по одобренной MOD-MF-24 (Д8):
   членство заявляет вступающий, владелец группы его не перечисляет. Вступившая личность получает
   всё, что выдано группе, и перечень выдач `kaname#979` это членство не судит — он судит выдачи
   посева, а не выдачи группы. С публикацией модулем заявление членства переходит от доставки
   чартом к учётке деплоя модуля. **Множество групп сужено** (Р4е, Д10): группа вступления — только
   группа встроенной части kaname, закрытая в бинарнике; группы арендаторов и других частей в него
   не входят, и захваченная учётка деплоя не впишет свою личность в группу арендатора. Остаётся:
   вступившая личность получает выдачи группы встроенной части (сегодня — `fga_writer` на
   кластере, П26), то есть всё, что выпуск kaname этой группе выдал. Ограничители: вступает
   только своя личность модуля (MOD-MF-23), только в группу встроенной части (981-19), у
   вступления обязательна причина (MOD-MF-25), каждое новое вступление — записанная публикация с
   аудитом (У13).

Поверхность расширяется на: один внутренний сервис (`Publish`, `Plan`), один тип и одно отношение
модели, одну учётку деплоя на модуль и одну учётку импорта.

`project`); `D(vpc, N)` — для `module: vpc`, ресурс `networks` (`vpc_network`, родитель
`project`). Посев каждого `D(<m>, N)` — форма манифеста платформы (П26): `seed.serviceAccounts`
заводит рабочую учётку модуля (`kacho-registry` у `registry`), а `seed.joins` вступает ею в группу
`module-relation-writers` встроенной части (аккаунт и имя — как объявлены встроенной частью) с
причиной `why` — это вступление в **чужую** группу, законное по MOD-MF-24. Так `kacho-registry`
пишет факты владения через `InternalIAMService.RegisterResource`.
`M0` — ревизия модели до сценария. Ручки пробы: `W = 30 с`, `P = 5 с`, потолок 262 144 Б, предел 3
за 60 с (часы пробы управляемые).

## §6. Сценарии

### A. Публикация модулем — положительный путь

#### 981-01 Первая публикация части

**Given** kaname запущен на пустой базе со встроенной частью; части `registry` нет
**And** вызывающий — учётка `kacho-registry-publisher` с проверенным SAN
**When** `InternalModulePublishService.Publish` с `{module: "registry", document: D(registry, 1)}`
**Then** `Operation.done = true`, `error` пуст; ответ `PublishModuleResponse`:
`module = "registry"`, `revision = 1`, `digest` вида `sha256:<64 hex>` (равен отпечатку
загрузчика над тем же документом), `modelRevision = M0 + 1`, `classification = EXTENSION`,
`unchanged = false`
**And** `InternalModuleService.Get{module: "registry"}` отдаёт ресурсы `registries`, `repositories`
и живую ревизию 1 с тем же отпечатком
**And** после `RegisterResource` объекта `registry_registry:reg-01` с владельцем `usr-a`
(вызывающий — `kacho-registry`) `InternalIAMService.Check{subject: usr-a, get, registry_registry:reg-01}`
отвечает `allowed = true`, `modelRevision = M0 + 1`
**And** ровно одна запись аудита: полоса `module`, актор `kacho-registry-publisher`, ревизия 1

#### 981-02 Новая ревизия — расширение

**Given** живая часть `registry` ревизии 1
**When** `Publish{module: "registry", document: D'(registry, 2)}`
**Then** `done = true`, `revision = 2`, `classification = EXTENSION`, `modelRevision` больше на 1
**And** роль с правилом на глагол `purge` ресурса `repositories` (`RoleService`) и её привязка
субъекту `usr-a` (`AccessBindingService`) создаются — правило проходит проверку каталога, хотя до
публикации тот же запрос отвергался бы как неизвестный глагол
**And** привязка — на проекте `project:prj-01`; объект `registry_repository:repo-01` (родитель
`registry_registry:reg-01`, его родитель `project:prj-01`) записан `RegisterResource` от
`kacho-registry`; `InternalIAMService.Check{subject: usr-a, purge, registry_repository:repo-01}`
отвечает `allowed = true` с новой `modelRevision` — без перезапуска процесса

#### 981-03 Повтор той же ревизии — успех без записи

**Given** живая ревизия 2 с отпечатком X
**When** `Publish` того же `D'(registry, 2)` (отпечаток X)

**And** записей аудита не прибавилось; счёт предела частоты не прибавился

#### 981-04 Сужение без выдач без опоры — модулем

**Given** живая ревизия 2 (`D'(registry, 2)`); ни одна выдача не называет глагол `purge`
**When** `Publish` `D(registry, 3)` (= `D(registry, 1)` с `revision: 3`, глагол `purge` снят)
**Then** `done = true`, `classification = NARROWING_WITHOUT_ORPHANS`, `revision = 3`
**And** близнец по одному факту — 981-40 (там выдача на снимаемый глагол есть)

#### 981-05 `Plan` полосы модуля равен исходу `Publish`

**Given** живая ревизия 3
**When** `InternalModulePublishService.Plan` с `D'(registry, 4)`, затем `Publish` того же документа

**And** ответ `Plan` не несёт идентификаторов выдач и субъектов — только числа
**And** последующий `Publish` даёт тот же `classification` и `revision = 4`

#### 981-16 Отношение издателя не выполнимо подстановкой, классом, группой

Свойство Р4г живёт на объявлении отношения, поэтому держатель — само объявление (а); посевный
путь (б) показывает, что выдать отношение посевом нельзя вовсе. Варианты `user:*` и
`system_class:authenticated` выдачей посева не строятся: их отвергает судья вида субъекта П28
(`ErrSubjectNotSeeded`) раньше канона, и объявления отношения такой отказ не судит — поэтому они
держатся в (а), а не выдачей.

(а) **Given** процесс стартовал на пустой базе со встроенной частью (Given 981-81); модель
допущена
**When** проба спрашивает владельца модели об объявлении отношения `module_publisher` у типа
`module` в допущенной модели процесса
**Then** отношение прямое; перечень прямых получателей в написании канона — ровно
`[service_account]`: подстановки (`user:*`, `group:*`), класса (`system_class`) и членства группы
(`group#member`) нет; вид `serviceAccount` принимается, вид `group` — нет
**And** контроль зрения пробы: тот же вопрос об отношении `fga_writer` у типа `cluster` той же
модели даёт `[service_account, group#member]` (П29) — проба различает объявления, а не отвечает
одним «нет»
**And** близнец по одному факту — инъекция DoD п. 3: объявление `module_publisher`, дополненное
одним получателем (по одному на прогон: `user:*`, `system_class:authenticated`, `group#member`),
→ проба красная; откат → зелёная

(б) **Given** учётка `kacho-registry-publisher`; живая часть `registry` ревизии 1
**When** `Publish` `D(registry, 2)`, чей посев дополнен выдачей своей рабочей учётке
`kacho-registry` (вид `serviceAccount`, заведена этим посевом) отношения
`grantedRelation: module_publisher` на якоре `scopeType: iam.cluster`, `scopeId: cluster_root`,
`target: allInScope`
**Then** `INVALID_ARGUMENT`, нарушение поля `document.seed.accessBindings[0].grantedRelation`,
текст — вид `ErrRelationNotDeclared` П28 дословной формы: называет отношение `module_publisher`,
тип `cluster` и объявленные у типа отношения; ни ревизии, ни записи аудита; счётчик
`reason="seed"` +1
**And** близнец по одному факту: та же выдача с `grantedRelation: system_viewer` (форма живой
выдачи П29) → принято, класс `EXTENSION`

#### 981-19 Вступление в группу — своей личностью и только в группу встроенной части

**Given** учётка `kacho-registry-publisher`; части `registry` нет
**When** `Publish{module: "registry", document: D(registry, 1)}`, где изменён один факт вступления
`seed.joins[0]`, по одному на прогон:
(а) в `serviceAccount` вместо `kacho-registry` стоит `kacho-vpc` (форма пары годна, но
`seed.serviceAccounts` этой части такой записи не заводит); группа та же —
`module-relation-writers` встроенной части;
(б) в `group` вместо `module-relation-writers` стоит `registry-tenant-writers` в том же аккаунте —
группа, которую встроенная часть не объявляет; вступает `kacho-registry`, заведённая этим посевом
**Then** (а) `INVALID_ARGUMENT`, нарушение поля `document.seed.joins[0].serviceAccount`, текст —
вид `ErrJoinServiceAccountNotSeeded` П25 дословной формы «вступает запись (account <аккаунт>, name
kacho-vpc), которой не заводит seed.serviceAccounts; заведены: <аккаунт>/kacho-registry. Вступает СВОЯ
личность модуля — чужую он вписать не вправе»
(б) `INVALID_ARGUMENT`, нарушение поля `document.seed.joins[0].group`, текст называет пару группы
(аккаунт, `registry-tenant-writers`) и группы встроенной части (`module-relation-writers`)
**And** в обоих: ни ревизии, ни записи аудита; счётчик `reason="seed"` +1
**And** близнец обоих по одному факту — 981-01: вступает `kacho-registry`, заведённая этим
посевом, в `module-relation-writers` встроенной части → принято без отказа; правило «субъект
заведён этим посевом» к группе вступления не применяется (MOD-MF-24) — группа не заведена посевом
части и принята; после публикации `kacho-registry` пишет факты владения (981-01,
`RegisterResource`)
