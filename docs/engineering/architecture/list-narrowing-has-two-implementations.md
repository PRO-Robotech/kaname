# Сужение списков: почему у iam своя реализация

**Решение принято 2026-08-22 по задаче `PRO-Robotech/kacho#723`.** Записано с
обеих сторон: здесь и в шапке `pkg/listnarrow/doc.go`, где до этого стояло
«ЕДИНСТВЕННАЯ реализация».

## Предмет

Фундамент `pkg/listnarrow` несут шесть служб (vpc, nlb, compute, storage,
registry — плюс geo, у которой предмета нет и это записано осью дескриптора).
iam сужает свои списки собственным пакетом `internal/authzfilter`.

Две реализации одного предмета — обычно находка: правка нормы доезжает до одной
из двух, а различить «выровнено» и «разошлось» можно только чтением обоих
пакетов подряд, то есть **помня**, что второй существует.

## Почему здесь это НЕ дубликат

Вопросы разные, и различие не стилистическое.

| | фундамент | iam |
|---|---|---|
| предикат видимости строки | **одно** действие (`IDs(…, action string, …)`) | **набор** отношений (`RelationsFor(objectType)`) |
| как спрашивается | один раунд | по очереди: следующее отношение — **только** для тех, кому отказало предыдущее |
| чем является порядок | нет порядка | решение о **стоимости**, никогда о корректности |

У iam тип объекта определяет свой предикат членства в странице: у роли это
`viewer` **или** `v_list`, у большинства прочих — `v_get`. Тип без записи берёт
умолчание, и оно **узкое**: пропуск не может молча расширить страницу.

Позвать фундамент по разу на каждое отношение технически можно — и это умножит
обращения к модели на размер набора. Стоимость страницы и есть то, ради чего
фундамент написан, поэтому такой перевод ухудшил бы ровно измеряемое свойство.

## Что остаётся общим — и это важнее различия

**Форма вопроса.** Обе реализации спрашивают **пообъектно по странице** и ни одна
не перечисляет разрешённое. Перечисление имеет жёсткий серверный предел без
продолжения, и на нём собственный ресурс арендатора становился невидим навсегда
при живых правах. Это свойство у обеих зафиксировано пробами.

## Предикат истечения решения

Причина держать вторую реализацию — **невыразимость составного предиката
фундаментом**. Она отпадает в один шаг: как только `pkg/listnarrow` начнёт
принимать **набор** действий (сигнатура `IDs`/`Page` перестанет быть одиночным
`action string`), различия не останется, и iam переводится туда, а
`internal/authzfilter` снимается вместе со своими пробами.

Держит это **гейт дерева**, а не память: `internal/repohygiene`
`TestListNarrowSecondImplementationKeepsItsReason` падает, когда фундамент
научился набору, а вторая реализация всё ещё стоит.
