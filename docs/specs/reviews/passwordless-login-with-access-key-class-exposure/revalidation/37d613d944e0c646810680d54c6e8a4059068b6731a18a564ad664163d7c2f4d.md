## Три смещённых условия — закрыты в use-case входа, не в примитивах Ф7

Измерено на `kaname@ae1338ba` — Ф7 уже посадил примитивы с семантикой «из сессии», и замысел эту
семантику **не наследует**.

### D3 — рукоятка

- **Измерение основания:** `finish_assertion.go:140` — `case len(in.UserHandle) > 0 && !bytes.Equal(in.UserHandle, key.UserHandle):` — сверка **под охраной присутствия**; строка `:138` — `case key.UserID != in.UserID:` (связывание из сессии). Колонка `user_access_keys.user_handle` — `bytea`, nullable, `CHECK (… IS NULL OR длина 1..64)`, комментарий «Читатель — полоса входа Ф13» (миграция `…access_keys_are_our_record.sql:81,95,105`).
- **Закрытие в замысле (§2.1):** `userHandle` — обязательное поле формы (нет/пусто → 400 до сверки); сравнение **безусловное**; охрана присутствия `len>0` **НЕ наследуется**; строка `:138` в полосе входа **заменяется** (человек **находится** из `key.UserID`, не сверяется с вызывающим); `key.UserHandle == NULL` → «совпасть не может» → единый отказ, никогда «пропустить».
- **Вердикт:** закрыто в **use-case входа**, не в `webauthnverify`. Класс `code-authoring §1.3` (sentinel «не задано»/значение), `§5.3` (перечень входных поверхностей), `§6.1` (узость Ф7 — контракт, который вход не обязан наследовать) — отображён верно.

### D12 — сверка одна на дерево

- **Измерение основания:** `webauthnverify.VerifyAssertion` — **одно** объявление (`verify.go:409`); **один** нетестовый вызывающий (`finish_assertion.go:128`). Прочие совпадения — комментарий у объявления и цитата в приёмке.
- **Закрытие в замысле (§2.3):** use-case входа — **второй ВЫЗЫВАЮЩИЙ**, не второе объявление; две добавки Ф13 (испытание по контексту, рукоятка со строкой) живут в use-case, не в проверяющем — иначе изменили бы from-session поведение Ф7; приманка времени — забота вызывающего, вход её повторяет.
- **Вердикт:** отображён верно. `architecture §«Параллельные полосы одного механизма обязаны сверяться МЕЖДУ СОБОЙ»` — две сверки одного утверждения не заводятся, единый проверяющий держит паритет; гейт дерева Ф13-31 (адресат — автор кода, `gate-authoring §6`).

### D2 — анти-replay

- **Измерение основания:** `access_key_repo.go:241` — `ConsumeChallenge(ctx, challenge, userID, purpose, now)`; `:178` — `Challenge(ctx, challenge, userID, …)` — оба ключуют по **`userID`**. У входа `userID` нет by construction. Токен контекста формы существует (`humansession/form_token.go`).
- **Закрытие в замысле (§2.2):** ключ хранилища — **токен контекста формы** (`kaname_form`), не `UserID`; **своя таблица в БД** (не в памяти — kaname масштабируется > 1 реплики, однократность держится **cross-replica**); годность+сгорание — **одна атомарная операция** (`UPDATE … WHERE … consumed_at IS NULL AND expires_at>$now`, исход по `RowsAffected()==1`), не «проверил→пометил» (ban #10); «одно живое на контекст» — замещением; срок — тот же литерал Ф7 (§7 инв.5), нового значения не заводится.
- **Вердикт:** отображён верно. Класс `code-authoring §2.1` (спросить и списать раздельно — запрещено), `security-surface S7.3` (одноразовое состояние в памяти процесса, а домен параллелизма — весь флот) — закрыт своей таблицей и атомарным оператором.

## D10 — вердикт по кандидату в новый пункт

**Что вносит замысел (§2.4):** одно **опциональное** поле `AccessKeyID` в `IssueInput` (Go-структура,
внутренняя); sentinel: пусто = не задано; идентификаторы ключей `ak-…`, пустыми не бывают. Пишется в
**payload события** `iam.session.issued` ключом `access_key_id` **только когда непусто**. Запись сессии
`domain.HumanSession` **не трогается**.

**Измерение:** на `ae1338ba` `IssueInput` несёт `Presented []assurance.Presentation` и `EmitAudit bool`,
но **не** `AccessKeyID` (`issue.go:35–46`). То есть поле — реальная дельта замысла, а не существующее.

**Оценка по трём осям задания:**

1. **Новый пункт перечня?** — **ДА**: это новое sentinel-значение, введённое замыслом; по
   `change-graph.md §4` новый sentinel — новый пункт, требующий отображения и пересверки. Первичный
   разбор его не нёс by construction (поле изобретено замыслом, чтобы исполнить Р10 без расширения записи).
2. **Меняет ли внешнюю/наблюдаемую поверхность?** — **узко**: один **аддитивный** ключ в payload
   **существующего** события; вид события неизменен, нового эмитента нет, нового асинхронного пути нет
   (тот же outbox Ф1, §6 подтверждён замером — оба шва внутрипроцессные). Значение `ak-…` — адрес (Ф7 Р10),
   не PII; покрыто гейтом `audit_payload_pii`.
3. **Держится ли инвариант «состав записи сессии не расширяется»?** — **да**: поле идёт в **событие**, не
   в `domain.HumanSession` (§7 инв.11); ни `access_key_id`, ни флаги в запись не пишутся.

**Sentinel чист (`code-authoring §1.3`, ХОРОШИЙ случай):** пусто как «не задано» **не пересекается** с
областью значений `AccessKeyID` (`ak-…` никогда не пусты). Отсутствие представимо отдельно от значения —
коллизии нет.

**Требует ли ОТДЕЛЬНОЙ пересверки?** — **НЕТ.** Новый пункт отображён в §2.4 и **пересверен ЗДЕСЬ**;
поскольку (а) sentinel чист, (б) нет нового внешнего вызова / асинхронного пути / runtime-ребра, (в)
запись сессии не расширяется и PII-гейт покрывает поле — пункт **покрыт** экспозиционными классами D4
(«состав записи не расширяется») и D10 («`access_key_id` в событии»). Отдельная строка перечня и
отдельный круг пересверки не нужны. **Условие снятия покрытия:** если реализация положит `AccessKeyID`
в **запись** сессии, ЛИБО заведёт под него второй эмитент/новый вид события, ЛИБО `ak-…` станет пустым в
каком-либо пути — это **новый пункт и новая пересверка**.

## Форма порта — подтверждение: ССЫЛОЧНАЯ АДАПТАЦИЯ, без вендоринга

Решение диспетчера (задание) и директива владельца: реализация **портирует форму** оркестрации
passwordless из ory/kratos, **существо сверки — наше Ф7**. Подтверждено по замыслу и по дереву.

- **По замыслу:** §3 карта — из kratos берётся **только форма потока** (два глагола, пустой
  `allowCredentials`, резолв по удостоверению+рукоятке); существо (сверка Ф7, выдача Ф1, уровень Ф11,
  единый отказ Ф3/Ф7) — **наше, из kratos не берётся**. §3 явно: «порт ≠ копия файла kratos (ban #20)»,
  «порт ≠ новое runtime-ребро и ≠ новая зависимость». §7 q1 и §6 — вендоринг был бы **новым пунктом и
  новой пересверкой**.
- **По дереву (`kaname@ae1338ba`):** модуля `github.com/ory/kratos` нет в `go.mod`/`go.sum` и ни в одном
  импорте `*.go` (предикат `git grep -rnE 'github.com/ory'` → пусто). 63 нетестовых упоминания «kratos» —
  **комментарии** о **пред-существующей** внешней интеграции с Ory Kratos/Hydra как поставщиком личности
  (вебхуки провизии/восстановления), **не** вендоренный исходник и **не** код потока Ф13.
- **Вывод:** форма порта — ссылочная адаптация; вендоринга в дереве нет, замысел его не вносит и явно
  относит к триггеру новой пересверки. Подтверждено.
