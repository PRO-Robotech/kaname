## Порядок, который держит весь замысел: сначала сузить модель, потом снять отказ края

Норма — `security-hardening.md` `hard-narrow-before-removing`. Здесь она становится условием на
**порядок посадок**, проверяемым командой:

1. **Тип.** В модели появляется `type system_class`; `SubjectType` получает
   `SUBJECT_TYPE_SYSTEM_CLASS` (L1, L2).
2. **Условный вывод.** Множество говорящего в `relverdict` строится одним производителем по
   признаку говорящего: `user`/`service_account` → оба класса; `system_class:anonymous` → только
   `anonymous`; группа → ни одного (CE-01). Безусловная подстановка `'user:*'` снята (L2+L3).
3. **Переезд фактов** (L3, один пакет с L2, CE-03).
4. **Только после этого** край перестаёт отказывать в `phaseSubject` на строках с признаком
   (L4). Предусловие старта L4 — на ревизии kaname, до которой поднят пин в `kacho/go.mod`:
   - `git grep -c "SELECT 'user:\*'" -- internal/repo/kaname/pg/relverdict` → 0 (сегодня 3);
   - `git grep -c -E '^type system_class' -- internal/authzmodel/fga_model.fga` → 1 (сегодня 0).

   Внутри L4 признак каталога (`AdmitsAnonymous`, CE-11) и отказ загрузки SC-35 садятся тем же
   изменением, что пропуск слоя аутентификации, или раньше. Пропуск без признака не открывает
   ничего, а признак без пропуска не меняет поведения: обратного окна нет.

Если L4 сядет раньше шага 2, аноним получит всё, что выдано `user:*`: 9 строк каталога
`cluster#viewer` (разбор JSON каталога @`2ec6e1e3d`). Это K1 в боевом виде.

## Новые пункты

### CE-19 · D12 · выдача классу на кластере недостижима ни одной ролью

Класс — `code-authoring` §«Решение и его следствие разнесены». Правило «на кластере выдать
классу всю область можно» объявлено, но его следствие в дереве перекрыто тремя воротами.

Порядок Create (`create.go`): форма области → `Validate` → право выдавать
(`requireGrantAuthority`) → структурные ворота (`validateStructuralGates`) → правило кластера
(`validateGlobalAllSelector`). Измерено:

- ворота 2 (`IsRoleAssignable`, `role_scope.go`): на `cluster` назначаема **только системная**
  роль. Своя роль отвергается: `FAILED_PRECONDITION`, текст
  `role <id> (definitionTier …) is not assignable on iam.cluster:cluster_root; …`;
- `RoleService.Create` ставит `IsSystem = false`: «system roles are seeded via migration, not
  API» (`role/create.go`). Значит `rol-read-named` из посева П1 («существующими фикстурами
  создания … роли») — своя роль и на кластере неназначаема;
- системных ролей в посеве 48; с `resource_names` или `match_labels` — 0. Правило без имён и
  меток — якорное, и `validateGlobalAllSelector` отвергает его для всех ролей, кроме роли
  кластерного администратора. У той роли пишущие глаголы, и класс её не получит (SC-21).

Итог: на дереве `@797031968` выдача классу на кластере через `Create` невозможна ни при какой
роли. Близнец SC-28 (`usr-K` → `done=true`) и второй близнец SC-19 недостижимы. «Отрицание
правила ствола» с `rol-read` упрётся в ворота 2 (`FAILED_PRECONDITION`) раньше ожидаемого
`INVALID_ARGUMENT` `GLOBAL scope requires names or labels selector…`. Это Given, которых схема
не допускает, — раздел «Вернуть в приёмку».

Условия на код (при любом решении приёмки):

- (а) ворота класса (Р4 — роль только чтения, Р5 — вид цели) стоят **после**
  `requireGrantAuthority`. Отказ SC-28 от `usr-A` остаётся `PERMISSION_DENIED` и ничего не
  говорит о роли;
- (б) ворота класса не обходят ворота 2 и `validateGlobalAllSelector`. Ветки «класс на кластере —
  разрешить своей роли» нет;
- (в) единственная классовая выдача на кластере — системная выдача отношения (Р8). Её не создаёт
  `Create`, её производит миграция.

Чем держится: красный `TestSystemClass_SC28_…` после выравнивания под решение приёмки (заказ
автору проб). Сегодня проба берёт системную якорную роль `rolfe683216e63311d3f`, и её
«контроль: выдача человеку на кластере» краснеет не по предмету: правило кластера отвергает
якорную роль.

### CE-21 · D14 · якорь кластера — переменная установки, а не литерал

Класс — `code-authoring` §«Контракт, который нельзя выразить» (обратное заполнение);
`code-authoring` §«Умолчание, которое становится утверждением».

Якорь переписывается переписчиком `kaname.rename_cluster_anchor` и читается по факту
(`kaname.cluster_anchor()`): так устроены миграции `20260906085136_…` и `20260906214500_…`. В
базовой миграции системная выдача посеяна на `cluster_kacho_root` (`0001_initial.sql:3161`,
`:3175`, `:3195`), в коде — `ClusterSingletonID = "cluster_root"`. Миграция переезда, которая
ищет выдачу по литералу якоря, на установке с другим написанием перепишет 0 строк и пройдёт
молча. Переезд при этом не случится.

Условия на код:

- (а) миграция переезда находит системную выдачу по id `acbc5d32d66fc8dc4952` и субъекту
  `user/*`, а факты — по субъекту `user:*`. Литерала якоря в предикатах выборки нет. Где объект
  нужен, он строится из `kaname.cluster_anchor()`;
- (б) нулевая выборка при живой системной выдаче `user/*` — отказ миграции, а не тишина. Тот же
  исход «третий — отказ», что у миграции якоря;
- (в) номер новой миграции старше всех применённых. Держит `TestNewMigrationOutranksEveryAppliedOne`.

Чем держится: красные `SC40_…`, `SC43_…`, `SC44_…` на П2. Проба на установке с переписанным
якорем — заказ L3; близнец — П2 как есть.

### CE-22 · D15 · субъект без дома: перечни выдач по классу

Класс — `code-authoring` §«Умолчание, которое становится утверждением»; `security.md`
`sec-page-then-check`.

У класса нет аккаунта-дома. Сегодня `ListBySubject` для вида вне `user | service_account |
group` отказывает `PERMISSION_DENIED` в `resolveSubjectHome` (ветка `default`), даже
кластерному администратору: разрешение дома идёт раньше полосы администратора
(`subject_read_authority.go`). SC-17 требует ответа. Первая очевидная правка — ветка класса в
`callerIsSubject` («каждый вошедший — член `authenticated`») — даёт полосу «сам» любому
вошедшему, и он видит выдачи классу **всех арендаторов**: роли, области, id объектов чужого
аккаунта. Невидимость системной выдачи у арендатора (SC-53) держится областью: консоль читает
`listAccessBindingsByAccount` (`AccessBindingsPage.tsx:97`), а системная выдача стоит на
кластере, без аккаунта. Флаг `system` её не прячет.

Условия на код:

- (а) `callerIsSubject` для `system_class` возвращает `false`: принадлежность классу — не «сам»;
- (б) у класса нет дома. Полосы две: кластерный администратор — без сужения; прочие — сужение
  страницы построчно (`visibleOnNarrowedPage`) по праву на область выдачи. Ветки «нет дома —
  значит можно» нет;
- (в) невидимость SC-53 держится областью и правом на неё, а не фильтром по `is_system` в
  консоли или в службе.

Чем держится: красный `SC17_…`. Отрицательного близнеца «чужой арендатор» в приёмке нет —
раздел «Вернуть в приёмку».

## Чего измерить нельзя

- **Окно между посадками L4 и L6 на стенде** — свойство расписания выкатки, а не дерева.

  отказа, а не числа.

     одного объекта. Это расширение поверхности (`ban18-q-security`);
   - (в) разрешить свою роль на кластере. Это ломка правила назначаемости ствола — отвергается.
