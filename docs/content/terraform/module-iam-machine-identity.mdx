# Модуль `iam-machine-identity`

Модуль описывает машинную личность целиком: служебную учётку и ключи, которыми она входит.

Зачем одним объявлением: учётка и ключ — два разных ресурса края, и заведённая отдельно
учётка выглядит готовой, будучи личностью, которой нечем войти. Она есть в списках, ей
выдают права, а войти ею нельзя. Модуль не даёт получить такое состояние по
невнимательности — карта `keys` не может быть пустой.

## Использование

```hcl
module "ci" {
  source = "github.com/PRO-Robotech/kacho//terraform/modules/iam-machine-identity"

  account_id         = var.account_id
  name               = "ci-deployer"
  description        = "учётка конвейера выкатки"
  created_by_user_id = var.my_user_id

  labels = { origin = "terraform" }

  keys = {
    default = {}
    rotate  = { description = "второй ключ на время смены" }
  }
}
```

Права этой учётке выдаются отдельно — [модулем `iam-access`](module-iam-access) по её
идентификатору из выхода `service_account_id`.

## Главное, что надо знать до `apply`

:::danger Закрытый ключ лежит в файле состояния ОТКРЫТЫМ
Край отдаёт материал ключа **один раз** — в ответе на выпуск — и повторно не выдаёт
никому, поэтому Terraform обязан сохранить его у себя, иначе ресурс был бы бесполезен.
Пометка `sensitive` на выходе скрывает значение в выводе команд и **не шифрует состояние**.

Отсюда три следствия, и они не про аккуратность, а про то, кто может войти как эта машина:

1. состояние проекта, применяющего модуль, хранится там же, где хранят секреты, —
   зашифрованный backend с ограниченным доступом;
2. в репозиторий состояние не коммитится никогда, как и его локальные выгрузки;
3. кто может прочитать состояние — тот и есть эта машина, со всеми её правами.
:::

:::warning `apply` под служебной учёткой ВОЗМОЖЕН — не называйте ответственного
Прежняя редакция этой врезки утверждала обратное: «модуль объявляет `created_by_user_id` и
всегда его шлёт, значит `apply` под машиной край отклонит `INVALID_ARGUMENT`». Это было
верно и **починено**: умолчание переменной — `null`, и модуль пробрасывает его как есть.
Страница пережила свой предмет и отговаривала от пути, который работает.

Как есть сегодня:

- **служебная учётка** — `created_by_user_id` не называйте вовсе (`null`, умолчание модуля).
  Ответственного край проставит сам — владельцем аккаунта целевой учётки, потому что сама
  служебная учётка строкой пользователей не является. Порог повышенной аутентификации
  (`required_acr_min=2`) машине не мешает: она от него освобождена, иначе выпуск был бы
  недостижим для машин навсегда, ничего при этом не защитив. Остаётся одно условие —
  выданный этой учётке `v_update` на целевой;
- **человек** — либо тоже не называйте, либо назовите **себя**: чужой идентификатор край
  отвергает как подлог. Уровень аутентификации при этом нужен второй, а базовый токен
  доступа даёт первый, и поднять его на той полосе нечем — нужна интерактивная сессия.

Пустая строка не годится ни там, ни там: на проводе она неотличима от отсутствия, а в
состоянии осталась бы утверждать пустоту про ключ, у которого ответственный есть. Поэтому
модуль отвергает её на `plan`.

Разбор по обоим ресурсам провайдера — на его [странице](provider).
:::

## Что модуль решает за вас

### Карта ключей, а не один ключ

Смена ключа требует **двух живых ключей одновременно**: новый выпускается, потребители
переходят на него, старый отзывается. С единственным ключом смена — это перерыв в
обслуживании, поэтому её откладывают до последнего, то есть до истечения срока.

Умолчание — один ключ `default`. Имя ключа собирается как имя учётки с суффиксом — ключом
своей записи (`ci-deployer-default`, `ci-deployer-rotate`).

:::warning Правка записи ПЕРЕСОЗДАЁТ ключ
Изменяющей операции у выпущенного ключа не существует, поэтому смена описания, срока или
назначения — это отзыв старого ключа и выпуск нового материала. Правьте запись, только если
готовы сменить то, чем машина входит; смена ключа без перерыва делается добавлением
**второй** записи, а не правкой первой.
:::

### Метки — тоже пересоздающее поле у ключа

На учётке метка правится на месте, на ключе — нет: край помечает метки ключа как
пересоздающие. Поэтому добавленная задним числом метка **отзывает каждый ключ учётки** и
выпускает новый материал, и всё, что ходило прежним ключом, перестаёт входить.

Метки задаются вместе с учёткой; правка их на живой машинной личности — это смена ключей, а
не разметка.

### Срок ключа задан модулем ЯВНО

Умолчание модуля — `7776000` секунд (90 дней). Явно, а не оставлено краю, потому что
`ttl_seconds = 0` у края означает **не «бессрочно», а «взять умолчание установки»**:
величина конечна и настраивается (`KACHO_IAM_SAKEY_DEFAULT_TTL`; чарт платформы ставит те же
90 дней — `2160h`). То есть без явного значения срок ключа решает настройка той установки,
куда пришёл `apply`, а конфигурация об этом молчит. Бессрочный ключ получается ровно в одном
случае — на установке, где умолчание не настроено вовсе, — и это тот исход, о котором никто
не узнает.

Зачем срок вообще нужен: бессрочный ключ перестаёт работать только когда его отзовут
вручную, а отзывать забывают. Человек, заводивший конвейер, уходит; сам конвейер
переезжает; выгрузка состояния остаётся на чьём-то ноутбуке. Утёкший бессрочный ключ не
закрывается никогда сам по себе, и знать об утечке при этом неоткуда. Срочный ключ
закрывается в известный день, и этот день видно в выходе `key_expires_at` — то есть смена
ключа становится наблюдаемой задачей, а не воспоминанием.

`0` остаётся доступным и означает «отдать срок умолчанию установки», но задаётся только
**явно**: такое решение принимают, а не получают по невнимательности.

### Потолок здесь — год, а не два

Модуль отвергает `ttl_seconds` больше `31536000` (год). Столько включительно допускает
развёрнутый край (`KACHO_IAM_SAKEY_MAX_TTL`; чарт платформы — `8760h`), отвергая запрос
сверх него ещё до регистрации клиента. Контракт объявляет вдвое больше (`63072000`), и
проверять по контракту здесь бессмысленно: отказ пришёл бы на `apply` — после того как
учётка уже создана, — а проверка стоит ровно ради того, чтобы он пришёл на `plan`.

Установка, поднявшая свой потолок, получит отказ раньше края. Перекос намеренно в сторону
более короткого машинного удостоверения.

### Порядок несущий с обеих сторон

Ключ ссылается на учётку по идентификатору, и ссылка строит граф.

На создании: ключ не выпускается раньше, чем учётка существует, — адрес выпуска строится из
идентификатора владельца. На сносе: обратный порядок, ключи раньше учётки. Без ссылки
Terraform волен снести учётку первой, и тогда отзыв ключа уйдёт по адресу владельца,
которого уже нет: отзыв, о котором Terraform отчитается как о выполненном, на деле не будет
выполнен им.

## Переменные

| Имя | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `account_id` | `string` | — | Аккаунт-владелец учётки. Сменить нельзя. |
| `name` | `string` | — | Имя учётки в аккаунте; оно же основа имён ключей. |
| `description` | `string` | `""` | Описание учётки. |
| `labels` | `map(string)` | `{}` | Метки учётки и **всех** её ключей. |
| `created_by_user_id` | `string` | `null` | Кого записать ответственным за выпуск. `null` — не называть: край подставит сам (человеку вызывающего, служебной учётке — владельца аккаунта). Человек вправе назвать только себя. |
| `key_ttl_seconds` | `number` | `7776000` | Умолчание срока для ключей модуля. |
| `keys` | `map(object)` | `{ default = {} }` | Ключи: ключ карты — суффикс имени. |

### Запись ключа

| Поле | Назначение |
|---|---|
| `description` | Описание ключа. |
| `ttl_seconds` | `null` — взять умолчание **модуля**; число — свой срок. |
| `audience` | `null` — взять умолчание **края**. Кому предназначен токен по этому ключу, и одновременно **сужение**: названный список — единственные адресаты, которые по этому ключу выдаются. |

Два `null` означают разное намеренно. У срока модуль подставляет своё умолчание, потому что
краевой ноль — это настройка чужой установки, и молча наследовать её значило бы отдавать
решение о сроке тому, кто его не принимал. У назначения токена наоборот: это предметное
решение владельца ключа, и подставлять за него что-то своё модуль не вправе.

## Проверки входа

На `plan`, до обращения к краю:

- пустое `name` — имя единственный способ найти уже созданную учётку, если ответ на
  создание потерялся; без него повтор завёл бы вторую машинную личность с теми же правами,
  о существовании которой никто не знает;
- пустая строка в `created_by_user_id` (а `null` — законный вход: «не называть»);
- пустая карта `keys`;
- `key_ttl_seconds` и `ttl_seconds` записи: дробное, отрицательное или больше `31536000`.

Существование пользователя и годность его идентификатора модуль **не** проверяет:
проверяется непустота, а не префикс. Словарь префиксов принадлежит iam, и сверка чужого
идентификатора по своей копии словаря отвергла бы законный ввод в тот день, когда владелец
сменит форму.

## Выходы

| Имя | Что это |
|---|---|
| `service_account_id` | Идентификатор учётки — им она называется в выдачах прав и в членстве в группах. |
| `key_ids` | Идентификаторы ключей по ключам входной карты. **Ими ключ отзывается.** |
| `client_ids` | Идентификатор клиента OAuth2 каждого ключа — им ключ представляется при обмене на токен. |
| `public_key_pems` | Открытые ключи в PEM. Секрета не несут. |
| `key_expires_at` | Когда истекает каждый ключ. |
| `private_key_pems` | Закрытые ключи в PEM. Помечен `sensitive`. |

Право выдаётся на `service_account_id`, а не на имя: имя косметическое и может меняться, а
выдача обязана пережить переименование.

`key_ids` и `client_ids` — **разные** значения одного ключа, и путать их нельзя:
идентификатор подписи для отзыва не годится, а одного закрытого ключа для входа мало —
отсутствие второй половины обнаруживается уже в конвейере.

`key_expires_at` — единственное место, где видно, что смена ключа просрочена; ради него срок
и задаётся. Пусто здесь бывает только у ключа без срока, а такой получается в одном случае:
`ttl_seconds = 0` встретил установку, где умолчание срока не настроено.

Прочитать материал осознанно: `tofu output -json private_key_pems`. Печатать его в лог
конвейера не нужно — лог переживает и ключ, и того, кто его выпускал.

## Ключ не импортируется

У провайдера нет импорта ключа, и это не пропуск: перечитать материал нечем, и импорт дал бы
состояние, которое выглядит рабочим и не работает. Существующий ключ отзывается и
выпускается заново.

## Чем проверяется сам модуль

У модуля есть пробы: `tests/wiring.tftest.hcl`, гоняются командой `tofu test` из каталога
модуля. Провайдер в них подменён (`mock_provider`), то есть край не участвует — падение
означает ошибку в модуле, а не состояние стенда.

Проб **14**, из них **7** отрицательных. Положительные закрепляют **связывание**: учётка и
ключ приезжают вместе, ключ ссылается на учётку по идентификатору, срок по умолчанию
конечен, значения записи доезжают до ресурса без подмены, метки достают до учётки и до
каждого ключа, а срок ровно на потолке края принимается. Отрицательные закрепляют
**отвержение**: учётка без ключа, пустое имя, пустой выпускающий, срок сверх потолка,
отрицательный и дробный срок, тот же перебор потолка в записи ключа.

Пара «ровно на потолке принимается» и «на единицу выше отвергается» стоит намеренно: без
положительной половины проверка границы зеленела бы и на модуле, отвергающем всё подряд.

Конвейер требует пробы от КАЖДОГО модуля и падает на модуле без них.
