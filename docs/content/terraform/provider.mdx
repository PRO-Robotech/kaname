# Провайдер Terraform: ресурсы IAM

Провайдер `kacho` один на всю платформу — установка и настройка описаны на
странице «Провайдер Terraform» в документации VPC. Здесь только то,
что относится к IAM.

## Ресурсы

| Ресурс | Что описывает | Область |
|---|---|---|
| `kacho_iam_account` | Аккаунт — корень тенантности | — |
| `kacho_iam_project` | Проект — область, внутри которой живут ресурсы платформы | аккаунт |
| `kacho_iam_group` | Группа субъектов | аккаунт |
| `kacho_iam_service_account` | Служебная учётка — принципал машинного доступа | аккаунт |
| `kacho_iam_role` | Пользовательская роль — набор прав | аккаунт или проект |
| `kacho_iam_access_binding` | Привязка: кому, какая роль, где и на что | кластер, аккаунт или проект |
| `kacho_iam_user_invitation` | Приглашение человека в аккаунт и его строка членства | аккаунт |
| `kacho_iam_user_token` | Личный токен пользователя | пользователь |
| `kacho_iam_service_account_key` | Ключ служебной учётки | служебная учётка |

Проект, группа и служебная учётка — **аккаунтные**: они принимают `account_id`, а не
`project_id`. Служебная учётка тоже: сузить её до проекта можно только выдачей прав, а не
местом заведения.

Типовые связки описывают модули: [`iam-project`](module-iam-project) — проект с группами и
учётками, [`iam-access`](module-iam-access) — роли и выдачи,
[`iam-machine-identity`](module-iam-machine-identity) — служебная учётка вместе с ключами.

## Права выдаются группе, а не перечислением людей

Право, которое получает больше одного принципала **или** чей состав получателей может
измениться, выдаётся **группе**; люди и служебные учётки в неё добавляются. Причина —
цена изменения состава: снять одного из группы это одна запись членства, снять одного из
перечисления — снятие прав по всем объектам роли.

Перечисление субъектов законно ровно для одного случая: получатель один и меняться не
будет (служебная учётка модуля, чья личность и есть предмет выдачи).

:::warning Состав группы провайдером НЕ управляется
Ресурса членства в группе у провайдера нет, и `kacho_iam_group` состава не принимает: у
него есть только аккаунт, имя, описание и метки. Группу Terraform заводит, права ей
выдаёт — а кто в ней состоит, задаётся вне Terraform.

Это стоит учесть при планировании: описав группу и выдачу в конфигурации, вы получите
работающую выдачу, которая никому ничего не даёт, пока в группу не добавят людей.
:::

## Основы: имя, «не найдено», асинхронность

### Имя обязательно, хотя платформа его не требует

`name` — единственный способ найти уже созданный ресурс, если ответ на создание не дошёл.
Без имени повтор создал бы дубль, поэтому провайдер требует имя строже, чем край.

### Ответ «не найдено» не означает «удалено»

Край отвечает на запрос к недоступному ресурсу дословно так же, как на запрос к
несуществующему. Провайдер не снимает ресурс из состояния по одному такому ответу: он
подтверждает отсутствие отдельным запросом к списку и **останавливается**, если подтвердить
нечем. Полная таблица исходов — на
странице «Провайдер Terraform» в документации VPC.

У привязки прав подтверждение устроено иначе, чем у остальных ресурсов, и это не мелочь:
имени у неё нет вовсе, а грамматика её списочного запроса закрыта ключами субъекта, роли и
якоря. Поэтому отсутствие подтверждается **обходом выдач якоря страницами**; если у якоря
не видно ни одной выдачи, различить «удалена» и «доступ отозван» нечем — провайдер
останавливается и оставляет решение оператору.

### Мутации асинхронны

Каждое изменение возвращает операцию, и провайдер ждёт её завершения. Идентификатор
созданного ресурса он читает **только** после проверки, что операция не завершилась
отказом: идентификатор присутствует в метаданных даже у неудачной операции, и прочитанный
без проверки указывал бы на несуществующий ресурс.

## Проект, группа, служебная учётка

```hcl
resource "kacho_iam_project" "prod" {
  account_id  = var.account_id
  name        = "production"
  description = "боевой контур"
  labels      = { env = "prod" }
}

resource "kacho_iam_group" "admins" {
  account_id = var.account_id
  name       = "prod-admins"
}

resource "kacho_iam_service_account" "ci" {
  account_id = var.account_id
  name       = "ci-deployer"
}
```

У всех трёх изменяемы имя, описание и метки; `account_id` пересоздаёт ресурс.

## `kacho_iam_account`

Аккаунт — корень тенантности: под ним лежат все проекты и вся выданная в них поверхность.
Обычная работа идёт в существующем аккаунте, а не заводит новый на каждую задачу.

`owner_user_id` — **вычисляемый** атрибут, а не вход: в конфигурации он не задаётся, край
выводит владельца из применившего и присланное значение отвергает. Владелец — **структурный**
источник прав на свой аккаунт: он создаёт и сносит его сам, не дожидаясь выдачи.

## `kacho_iam_role`

```hcl
resource "kacho_iam_role" "vpc_operator" {
  definition_tier = {
    tier_type = "iam.project"
    tier_id   = kacho_iam_project.prod.id
  }

  name        = "vpc-operator"
  description = "правка сетей контура"

  rules = [
    {
      module    = "vpc"
      resources = ["vpc.network", "vpc.subnet"]
      verbs     = ["get", "list", "create", "update"]
    },
  ]
}
```

Роль сама по себе доступа не даёт: она описывает, **что** можно делать, а привязка —
**кому** и **где**.

### Уровень определения задаётся одним способом

`definition_tier` — единственный вход: `iam.account` или `iam.project` плюс идентификатор
якоря. Контракт принимает ещё и пару `accountId`/`projectId` как прежнюю форму, но при
заданном уровне не читает её вовсе, поэтому в ресурсе эта пара оставлена **только на
чтение** — как проекция ответа края. Два написания одного и того же однажды разошлись бы
между настройкой и состоянием.

`iam.cluster` здесь недопустим: роли этого уровня платформа сеет миграциями.
Смена уровня **пересоздаёт** роль — перенести определение с одного якоря на другой край
не умеет.

### Правила — поле роли, а не отдельные ресурсы

У правила нет собственного идентификатора, адресовать его извне нечем, и край принимает
правила только целым набором в том же запросе. Отсюда список, а не набор: порядок край
сохраняет, и два правила одного модуля, различающиеся только сужением, законны — набор
потребовал бы от них отличаться друг от друга ещё чем-то.

Одно правило — однородная выдача: перечисленные глаголы над перечисленными типами **ровно
одного** модуля. Роль на несколько модулей — это несколько правил.

Сужение необязательно и задаётся **либо** перечнем идентификаторов (`resource_names`),
**либо** отбором по меткам (`match_labels`). Отсутствие сужения выражается **опусканием**
поля: край не отличает пустой перечень от отсутствующего и вернёт его отсутствующим —
`resource_names = []` дало бы расхождение плана на совершенно законной настройке, и
провайдер отвергает такую запись заранее.

### Что провайдер проверяет сам, а что оставляет краю

Проверяются **структурные** условия, нарушение которых отвергается всегда: недопустимый
уровень определения, пустая политика, двойное сужение, пустое сужение, заданное явно,
подстановка `*` в модуле или типе (она разрешена только системным ролям), `*` среди
глаголов не единственным элементом, `*` вместо идентификатора, подстановка вместе с
сужением.

Не проверяются **перечни** — модулей, типов ресурсов, верхние границы количества. Они
принадлежат краю и меняются вместе с платформой; своя копия начала бы отвергать законную
настройку ровно в тот день, когда появится новый модуль, — и виноватым выглядел бы край.

Написание типов неоднородно (`compute.instance`, `iam.serviceAccount`, но
`storage.volumes`, `registry.registries`), а модуль балансировщика называется
`loadbalancer`, а не `nlb`. Сверяйтесь с каталогом прав `GET /iam/v1/permissionCatalog`.

### Смотрите на `effective_verbs`, а не на написанное в `rules`

`authored_verbs` — что роль выдаёт по букве правил (`*` раскрыт). `effective_verbs` — что
она выдаёт фактически: платформа доматериализует часть глаголов, например редактирующая
роль удаляет то, что редактирует. `verb_notes` поясняет, почему глагол попал в расширенный
набор. Все три считает край.

### Меток версии, автора и времени правки в ресурсе нет

Контракт роли их объявляет, но ответ края их не несёт. Показать такое поле значило бы
выдать пустую строку за факт о роли — «автора нет», «не изменялась никогда». Версия тем
более не украшение: на ней держалась бы защита от одновременной правки, и всегда пустое
поле объявляло бы включённой защиту, которая не срабатывает ни разу.

Защита при этом есть и работает без вашего участия: край читает версию строки в начале
операции и применяет изменение сверкой с ней, поэтому чужая правка, успевшая вклиниться,
роняет вашу. На такой отказ провайдер отвечает подсказкой повторить `apply` — он перечитает
роль и построит изменение от её нового состояния.

:::warning Роль освобождает УДАЛЕНИЕ привязки, а не её отзыв
Ссылку на роль держит сама строка привязки, и отозванная строка её не отпускает — она
продолжает существовать. Отозвав выдачи и получив тот же отказ, легко пойти искать причину
не там.
:::

Системные роли этим ресурсом не управляются: край отказывает в их изменении и удалении, а
имя, совпадающее с системной ролью, отвергает как занятое. Втянув системную роль импортом,
вы получите ресурс с `is_system = true`, у которого не работает ни `apply`, ни `destroy`.

## `kacho_iam_access_binding`

```hcl
resource "kacho_iam_access_binding" "prod_admins" {
  role_id = kacho_iam_role.vpc_operator.id

  scope_type = "iam.project"
  scope_id   = kacho_iam_project.prod.id

  subjects = [
    { type = "SUBJECT_TYPE_GROUP", id = kacho_iam_group.admins.id },
  ]

  target = { all_in_scope = true }
}
```

Привязка — сама выдача: **кому** (`subjects`), **какая роль** (`role_id`), **где**
(`scope_type` + `scope_id`) и **на что** под этим якорем (`target`).

### Изменяемы ровно два поля

`deletion_protection` и `labels`. Всё остальное край в маске изменения не принимает,
поэтому провайдер помечает такие поля пересоздающими явно: «сменить роль» или «добавить
получателя» означает снять выдачу и выдать заново — и лучше, чтобы это было видно в плане
как замена, чем чтобы правка молча не применилась.

### Цель обязательна и умолчания не имеет

Ровно одна ветвь: `all_in_scope = true` (право действует на **все** объекты под якорем,
включая ещё не созданные) либо `resources` — закрытый набор объектов, до 256. Широчайшая
выдача берётся только явным словом, чтобы её нельзя было получить по невнимательности;
`all_in_scope = false` не выражает ничего и отвергается — ветвь выбирается **опусканием**
поля. Подстановочный знак `*` в пообъектном перечне тоже не принимается.

### `destroy` УДАЛЯЕТ привязку, а не отзывает её

У края два разных действия. `Delete` сносит строку — после него `Get` отвечает «не
найдено». Отзыв строку **сохраняет** со статусом `REVOKED` ради аудиторского следа.
Доступ снимается одинаково обоими, поэтому выбор не про безопасность, а про то, что значит
«ресурса нет». Провайдер зовёт `Delete`: у Terraform нет глагола между «есть» и «нет»,
которым выразить мягкий отзыв.

Отозванную вне Terraform привязку провайдер считает **отсутствующей**: строка у края есть,
доступа она не даёт, и держать её в состоянии значило бы показывать план без изменений на
выдаче, которой больше нет. Провайдер предупреждает и убирает ресурс из состояния —
следующий план предложит выдать право заново, новой строкой. Отозванная строка при этом
останется у края: это её назначение.

### Защита от удаления мешает и ЗАМЕНЕ

Пока `deletion_protection = true`, край отвергает удаление синхронно. Замена начинается с
удаления, поэтому правка `role_id`, `subjects`, `target` или `scope_*` упрётся в тот же
флаг. Снимите его отдельным `apply`, затем меняйте остальное. Провайдер флаг **не снимает**
сам: тихо обойдённая защита от удаления бессмысленна.

### `expires_at` — абсолютный момент, а не длительность

RFC 3339, не меньше пяти минут вперёд: доступ материализуется асинхронно, и более короткий
срок мог бы истечь раньше, чем право заработает, — край такое значение отвергает. Записанный
в конфигурацию момент однажды окажется в прошлом, и следующий `apply` упрётся в тот же
отказ.

### `materialized_at` отличает окно распространения от ошибки

Пусто здесь означает «ещё не материализовалось» **либо** «этой привязке нечего
материализовать пообъектно» (выдача на уровне кластера) — но никогда «выдача не работает».
Пока поле пусто, отказ доступа у получателя может быть временным.

## `kacho_iam_user_invitation`

```hcl
resource "kacho_iam_user_invitation" "alice" {
  account_id   = var.account_id
  email        = "alice@example.com"
  display_name = "Алиса"
  labels       = { team = "platform" }
}
```

Пользователь у Kachō заводится **приглашением**, а не созданием: вызова создания
пользователя в контракте нет вовсе. Ресурс заводит строку членства в состоянии `PENDING`,
а `ACTIVE` она становится сама, когда приглашённый войдёт через провайдера личности. Ждать
этого Terraform не будет — `apply` завершается на отправленном приглашении.

Отсюда и имя ресурса: он управляет приглашением и его строкой членства, а не человеком —
личность принадлежит провайдеру входа, и облако ею не распоряжается.

:::warning В состоянии Terraform лежат персональные данные
Почта и отображаемое имя приглашённого попадают в файл состояния в открытом виде.
:::

:::danger `destroy` снимает ЧЕЛОВЕКА с аккаунта
Удаляется строка членства: непринятое приглашение отзывается, а вошедший человек теряет
участие в аккаунте вместе с выпущенными на эту строку токенами. Личность в других аккаунтах
не затрагивается. Пересоздание означает то же самое, только с последующим новым
приглашением — вошедший человек снова окажется `PENDING`.
:::

### Изменяемы метки и запрет входа, остальное — затравки

`account_id`, `email`, `display_name`, `project_id`, `role_id` пересоздают ресурс:
изменяющей операции для них у края нет.

`display_name` — именно **затравка**: край подставляет её при заведении и перезаписывает
при первом входе данными провайдера личности. Поэтому значение в конфигурации остаётся
вашим, а фактическое имя видно в `effective_display_name`, и совпадать они не обязаны.

`blocked` у края не поле, а два **действия**. Провайдер отправляет действие только при
расхождении желаемого с прочитанным: край принимает повтор молча, но пишет запись в журнал
аудита на каждый принятый вызов. Непринятое приглашение заблокировать нельзя — внешней
личности у него ещё нет. Уже выданные токены блокировка не отзывает, она прекращает выдачу
новых.

Приглашение по паре «аккаунт + почта» **идемпотентно**: повторное приглашение подберёт
существующую строку, а не заведёт вторую. Почта ищется без учёта регистра, и написание
сохраняется за вами, пока речь об одном адресе.

### Стартовая выдача создаётся, но НЕ управляется

`project_id` + `role_id` создают привязку прав одной транзакцией с приглашением —
приглашённый входит уже с доступом. Прочитать её обратно или снять этот ресурс не может:
край не возвращает её идентификатор, а удаление строки членства привязку не убирает. Если
выдаче нужен жизненный цикл — заводите её отдельным `kacho_iam_access_binding`, а эти два
поля не задавайте.

Практическое следствие: приглашение со стартовой выдачей по умолчанию **не уничтожается**,
пока привязку не снять отдельно.

### Импорт частичен

Затравки (`display_name`, `project_id`, `role_id`) край обратно не отдаёт, поэтому после
импорта они пусты. Если в конфигурации они заданы, первый же план увидит расхождение по
пересоздающему полю и предложит снять человека с аккаунта и пригласить заново. Импортируя
существующее членство, эти три поля не задавайте — управляйте метками и запретом входа.

## `kacho_iam_user_token` и `kacho_iam_service_account_key`

Личный токен — то, чем человек ходит в платформу неинтерактивно. Ключ учётки — то, чем
входит машина. Устроены они одинаково в том, что важно.

```hcl
resource "kacho_iam_service_account_key" "ci" {
  service_account_id = kacho_iam_service_account.ci.id
  created_by_user_id = var.my_user_id
  name               = "ci-deployer-default"
  ttl_seconds        = 7776000
}
```

:::danger Закрытый ключ попадает в состояние Terraform
Край отдаёт закрытый ключ **один раз** — в ответе на выпуск — и повторно не выдаёт никому.
Значит единственный экземпляр материала лежит в файле состояния в открытом виде. Состояние
такого проекта обязано храниться там, где хранят секреты; в репозиторий оно не коммитится
никогда. То же касается вывода `terraform show` и артефактов конвейера, куда попадает
состояние.
:::

### Правка ЛЮБОГО поля пересоздаёт секрет

Изменяющей операции у выпущенного токена и ключа не существует: сменить срок, имя или
назначение можно только выпуском нового. Помечено это явно на каждом поле, а не умолчанием
— умолчание означало бы тихую подмену материала под тем же адресом ресурса.

### Импорта нет, и это не пропуск

Импортировать можно то, что читается. Материал край повторно не отдаёт, поэтому импорт дал
бы ресурс с пустым секретом — состояние, которое выглядит рабочим и не работает.
Существующий ключ отзывается и выпускается заново.

### Обратное чтение подтверждает существование и НЕ трогает материал

Перечитать секрет нечем. Обычное «прочитать ресурс и разложить в состояние» затёрло бы
закрытый ключ пустотой — то есть уничтожило бы единственный экземпляр руками того, кто
просто сделал `refresh`.

:::warning Истёкший токен Terraform НЕ заменит сам
По истечении срока край перестаёт принимать подпись, но **строку токена не удаляет**:
обратное чтение по-прежнему её видит, расхождения с настройкой нет, и `plan` честно скажет
«изменений нет» — про мёртвые учётные данные. Ротация — действие оператора:
`terraform apply -replace=<адрес ресурса>` либо срок жизни, выраженный отдельным
ресурсом-таймером, от которого зависит этот.
:::

### Кто вправе выпустить — решает модель прав, а не второй фактор

Выпуск и отзыв удостоверения несут порог повышенной аутентификации (`required_acr_min=2`),
и **служебная учётка от этого порога освобождена**: интерактивной церемонии у машины нет,
поэтому порог не защитил бы RPC, а сделал бы его недостижимым для машин навсегда. Правило
одно на обе точки контроля — край и cluster-internal слушатель, — и освобождение в нём
узкое: ровно тип принципала `service_account`; `user`, `system`, отсутствующий и незнакомый
тип не освобождены (fail-closed).

Освобождение снимает **только** порог уверенности и не выдаёт ни одного права: per-RPC Check
выполняется независимо. Поэтому «сможет ли конвейер применить этот ресурс» решается
контрактом и отношением, а не вторым фактором:

  <thead><tr><th>Ресурс</th><th>Что спрашивает край</th><th>Конвейер под служебной учёткой</th></tr></thead>

Базовый токен доступа даёт уровень аутентификации `1`, а порог выпуска — `2`, и церемонии,
поднимающей уровень, у этой полосы нет. Человеку, применяющему такой проект, нужна
интерактивная сессия со вторым фактором.
:::

### Ответственного за выдачу подставляет край, и на каждой полосе — своего

`created_by_user_id` — поле аудита, и назвать в нём кого-либо вправе **только человек и
только самого себя**. Поэтому у обоих ресурсов оно объявлено **необязательным**: конвейер,
ходящий служебной учёткой, назвать ответственного не вправе вовсе, а требование поля делало
бы ресурс неисполнимым у машины при любом входе — непустое значение край отвергает
синхронно, а пустого требование не допускает.

Кого край подставит, когда поле не прислано, зависит от полосы, и одной фразой на обе это
не описывается:

| Ресурс | Вызывающий — человек | Вызывающий — служебная учётка |
|---|---|---|
| `kacho_iam_user_token` | вызывающего | **целевого пользователя** — тот самый `user_id`, что назван запросом |
| `kacho_iam_service_account_key` | вызывающего | владельца аккаунта целевой учётки |

Служебная учётка ответственным не бывает ни на одной полосе: её идентификатор строкой
пользователей не является, и запись такого ответственного отвергла бы сама база.

Присланное непустое значение принимается, только если совпадает с тем, что край запишет, —
и лишь там, где край это значение **знает**. У токена он знает его всегда (`user_id` назван
тем же запросом), поэтому совпавшее значение применяется. У ключа ответственный резолвится
глубже, из владельца аккаунта учётки, и на крае его нет ни в каком виде — сверять нечем,
поэтому от служебной учётки отвергается **любое** непустое значение. Чужой идентификатор
отвергается как подлог на обеих полосах.

### Нуль в `ttl_seconds` значит у ключа и у токена РАЗНОЕ

Это единственное место, где два ресурса расходятся, и расхождение не косметическое.

**У токена `0` — действительно «бессрочно»**: срок ставится, только когда значение больше
нуля, ни умолчания, ни потолка на стороне установки у него нет. Верхняя граница одна —
контрактная, `63072000` (два года).

**У ключа `0` — «взять умолчание установки»**: величина конечна, настраивается
(`KACHO_IAM_SAKEY_DEFAULT_TTL`, чарт платформы ставит 90 дней) и в конфигурации не видна.
Бессрочный ключ получается ровно на установке, где умолчание не настроено вовсе, — и это тот
исход, о котором никто не узнает. Сверх контрактной границы у ключа есть ещё и **потолок
установки** (`KACHO_IAM_SAKEY_MAX_TTL`, чарт платформы — год): запрос выше него край
отвергает до регистрации клиента.

В обоих случаях задавайте срок явно.

### У ключа два идентификатора, и путать их нельзя

`id` — то, чем ключ **отзывается**; `key_id` — идентификатор подписи (`kid`), для отзыва он
не годится. У токена эти два значения совпадают — так подписанное утверждение само называет
свой ключ.

## Что мешает удалению

Край отказывается удалять ресурс, на который ещё ссылаются. Провайдер называет причину
заранее, в самом отказе, — иначе она выясняется перебором:

| Ресурс | Что удерживает |
|---|---|
| Аккаунт | Проекты аккаунта |
| Проект | Пользовательская роль, определённая в этом проекте: ссылка защищена на уровне хранилища |
| Группа | Действующие выдачи прав на группу. Члены удалению **не** мешают — членство снимается вместе с ней |
| Служебная учётка | Действующие выдачи прав и членство в группах. Ключи учётки **не** мешают |
| Роль | Привязки, ссылающиеся на неё. Их надо **удалить**: отзыв оставляет привязку на месте |
| Привязка | `deletion_protection` |
| Приглашение | Живые ссылки на пользователя: привязки, где он субъект (в том числе стартовая выдача), членство в группах, аккаунт в его владении, ключи и токены, выпущенные от его имени другим. Токены самой этой строки членства **не** мешают |
