# Модуль `iam-access`

Модуль описывает доступ на одном якоре целиком: роли, которые на нём определены, и выдачи
этих ролей. Это типовая единица — роль без выдачи не даёт ничего, а выдача без роли не
существует.

## Использование

```hcl
module "prod_access" {
  source = "github.com/PRO-Robotech/kacho//terraform/modules/iam-access"

  scope = {
    type = "iam.project"
    id   = kacho_iam_project.prod.id
  }

  labels = { origin = "terraform" }

  roles = {
    "vpc-operator" = {
      description = "правка сетей контура"
      rules = [
        {
          module    = "vpc"
          resources = ["vpc.network", "vpc.subnet"]
          verbs     = ["get", "list", "create", "update"]
        },
      ]
    }
  }

  group_grants = {
    "prod-admins" = {
      group_id = kacho_iam_group.admins.id
      role     = "vpc-operator"
      target   = { all_in_scope = true }
    }
  }

  subject_grants = {
    "ci-deployer" = {
      subject       = { type = "SUBJECT_TYPE_SERVICE_ACCOUNT", id = module.ci.service_account_id }
      justification = "учётка конвейера выкатки; получатель один и не изменится"
      role_id       = var.system_editor_role_id
      target        = { resources = [{ type = "vpc.network", id = module.vpc.network_id }] }
    }
  }
}
```

## Что модуль решает за вас

### Якорь один на роли и на выдачи

Роль, определённая на проекте, выдаётся только на своём проекте. Две переменные позволили
бы задать расхождение, которое обнаружится только на `apply`, — поэтому переменная одна.

Сужение выдачи внутри якоря делается **целью**, а не вторым якорем. Роль, определённая выше
(аккаунтная) или системная, выдаётся на этот якорь по идентификатору — полем `role_id`, и
определять её здесь не требуется.

`iam.cluster` недопустим: роли такого уровня край не создаёт вовсе, а выдача на кластер —
это супер-доступ, который принимают отдельным решением, а не получают модулем удобства.

### Групповая выдача — основной вход, именная — отдельный

`group_grants` и `subject_grants` — **разные** переменные и разные ресурсы, а не одна карта
с полем «вид получателя». Так перечень исключений установки виден одним адресом и в плане, и
в состоянии, а обзор «кому у нас выдано лично» не требует разбирать содержимое каждой
записи.

У `subject_grants` форма входа сделана под единственный законный случай и только под него:

- получатель **ровно один** — перечислить нескольких здесь нечем, и «добавить второго»
  означает завести группу, а не дописать строку;
- `justification` обязателен и непуст — в нём пишут, почему состав получателей не
  изменится. Все обоснования видны разом в выходе `subject_grant_justifications`;
- группа сюда не кладётся — для неё есть основной вход.

Вид принципала у групповой выдачи проставляет **модуль**: у этого входа он один по
построению, и поле для него означало бы, что здесь же можно выдать право лично — то есть
обойти осознанный шаг, ради которого заведён отдельный вход.

### Роль называется ровно одним способом

`role` — имя роли **из этого модуля** (ключ в `roles`); `role_id` — готовая роль, системная
или определённая выше. Ровно одно из двух: два написания одного и того же разошлись бы.

Имя резолвится в идентификатор внутри модуля, поэтому привязка ссылается на роль **по
идентификатору** — ссылка строит граф, и снос идёт в обратном порядке: выдачи раньше роли,
которую они держат. Порядок здесь несущий, край его подкрепляет: роль, на которую ссылается
живая выдача, он удалять не станет.

### Идентификатор группы — поле, а не ключ карты

Ключи `for_each` обязаны быть известны на плане, а идентификатор приезжает от края. Ключ,
взятый из идентификатора, сделал бы невозможным план на ещё не заведённой группе.

## Переменные

| Имя | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `scope` | `object` | — | Якорь: `type` (`iam.account` или `iam.project`) и `id`. |
| `roles` | `map(object)` | `{}` | Роли модуля: ключ — имя, значение — описание и политика. |
| `group_grants` | `map(object)` | `{}` | Групповые выдачи: ключ — имя группы, значение — её идентификатор, роль и цель. |
| `subject_grants` | `map(object)` | `{}` | Именные выдачи: получатель, обоснование, роль и цель. |
| `labels` | `map(string)` | `{}` | Метки на все ресурсы модуля — и на роли, и на выдачи. |

### Поля выдачи

| Поле | Обязательно | Назначение |
|---|---|---|
| `group_id` / `subject` | да | Получатель. У именной выдачи `subject.type` — `SUBJECT_TYPE_USER` или `SUBJECT_TYPE_SERVICE_ACCOUNT`. |
| `justification` | да, у именной | Почему получатель один и не изменится. |
| `role` / `role_id` | ровно одно | Роль модуля по имени либо готовая роль по идентификатору. |
| `target` | да | Ровно одна ветвь: `all_in_scope = true` либо непустой `resources`. |
| `expires_at` | нет | Абсолютный момент RFC 3339. Опущен — выдача **бессрочна**. |
| `deletion_protection` | нет, по умолчанию `false` | Защита от удаления. |

### Умолчания названы явно, а не оставлены краю

**Цели умолчания нет вовсе**: широчайшая выдача берётся только явным `all_in_scope = true`.
`all_in_scope = false` не выражает ничего и отвергается — ветвь выбирается опусканием поля.

**Опущенный `expires_at` означает бессрочную выдачу.** Это умолчание края, и оно названо
здесь, а не оставлено читателю: право, задуманное «на время», иначе остаётся навсегда и
молча. Общего срока модуль не подставляет намеренно — момент абсолютный, и один на всех он
в один день истёк бы у каждой выдачи сразу. Право снимается **снятием выдачи**, а не
ожиданием срока; заданный срок — дополнение к этому, а не замена.

**Защита от удаления выключена по умолчанию, и это сказано явно.** Здесь ресурсами
управляет Terraform, а включённая защита отвергает не только `destroy`, но и **замену** —
а заменой у привязки является правка роли, получателя, цели или якоря: край не принимает
эти поля в маске изменения. Включив её, снимайте отдельным `apply` прежде, чем менять
остальное.

## Проверки входа

На `plan`, до обращения к краю:

- `scope.type` вне `iam.account` / `iam.project` (в том числе короткое `account` и
  `iam.cluster`);
- роль без единого правила;
- правило, суженное дважды (`resource_names` и `match_labels` вместе);
- выдача, где задано не ровно одно из `role` и `role_id`;
- цель без ветви или с двумя ветвями сразу;
- `target.all_in_scope = false`;
- группа в `subject_grants`;
- пустое `justification`.

Имя роли, которого нет среди ролей модуля, ловится предусловием у самой привязки — оно
срабатывает позже проверок входа, но всё ещё до края.

Перечни модулей, типов ресурсов и глаголов модуль **не** проверяет: они принадлежат краю и
меняются вместе с платформой. Своя копия начала бы отвергать законную настройку в тот день,
когда платформа заведёт новый тип, и виноватым выглядел бы край.

:::note Проверки двух карт выдач повторены дословно — так и задумано
Проверка переменной не видит ни `locals`, ни соседних переменных, поэтому общего места для
них в модуле нет. Правя одну, правьте обе — иначе исключение станет мягче основного входа.
:::

## Выходы

| Имя | Что это |
|---|---|
| `role_ids` | Идентификаторы ролей модуля по именам. |
| `group_binding_ids` · `subject_binding_ids` | Идентификаторы выдач по ключам их записей. |
| `subject_grant_justifications` | Обоснования именных выдач — все исключения установки одним списком. |
| `binding_status` | Состояние каждой выдачи: `PENDING` или `ACTIVE`. Ключи размечены `group/…` и `subject/…`. |

`binding_status` выведен наружу потому, что `PENDING` отличает окно распространения от
ошибки в самой выдаче: пока доступ не материализовался, отказ у получателя может быть
временным.

Третьего значения контракта — `REVOKED` — здесь не бывает, и обещать его значило бы обещать
поведение, которого у ресурса нет: отозванную привязку провайдер считает отсутствующей и при
первом же чтении убирает из состояния, после чего план предлагает выдать право заново.

## Чего модуль не делает

**Состав групп он не ведёт.** Ресурса членства в группе у провайдера нет вовсе, поэтому
выдача группе, у которой никого нет, применится успешно и никому ничего не даст. Членство
задаётся вне Terraform.

**Группы он не создаёт** — принимает их идентификаторы. Заводит группы
[модуль `iam-project`](module-iam-project).

## Чем проверяется сам модуль

У модуля есть пробы: `tests/wiring.tftest.hcl`, гоняются командой `tofu test` из каталога
модуля. Провайдер в них подменён (`mock_provider`), то есть край не участвует — падение
означает ошибку в модуле, а не состояние стенда.

Проб **23**, из них **14** отрицательных. Положительные закрепляют **связывание**: роль и
выдача берут один якорь, выдача ссылается на роль по идентификатору, групповая выдача
называет получателя группой, правила роли и обе ветви цели доезжают до ресурса без подмены,
готовая роль берётся по идентификатору, защита от удаления по умолчанию выключена, а
заданное значение доезжает, именная выдача называет ровно одного принципала, метки достают
до каждого ресурса. Отрицательные закрепляют **отвержение** — все условия из раздела выше.

Второе не менее важно первого: без отрицаний положительные пробы зеленели бы и на модуле,
принимающем что угодно.

Конвейер требует пробы от КАЖДОГО модуля и падает на модуле без них.
