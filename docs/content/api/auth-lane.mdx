# Полоса входа — регистрация, вход, сессия, восстановление, второй фактор, свои сессии

**Полоса входа** — HTTP-слушатель службы, на который консоль платформы отправляет формы
человека: регистрацию, вход, выход, смену пароля, восстановление доступа, второй фактор и
перечень своих сессий с выходом из выбранной или из всех, кроме текущей.
Это **единственный** вход человека в продукт: посадка личности у службы одна, внешнего
поставщика удостоверений нет (устройство — [Идентичность и токены](/architecture/identity)).

Путей у полосы **двадцать три**, и объявлены они одним перечнем — `loginlanehttp.Paths()`
(`internal/handler/loginlanehttp/handler.go`); перечень ниже сверяется с ним пробой, а не
выписан.

## Положение подтверждения — дальше экрана подтверждения нельзя {#verification-position}

Сессия человека, чей текущий адрес почты **не подтверждён**, находится в **положении
подтверждения**; подтверждён — в обычном. Положение не хранится в сессии: его читает каждый,
кто решает, из отметки в строке человека — на **каждом** запросе, поэтому снятие отметки и
подтверждение действуют на следующем же запросе. Ответ входа и регистрации несёт его полем
`session.emailVerified`.

В положении подтверждения доступны вход и регистрация, выход, признак формы, запрос письма,
предъявление кода, «кто я» края и восстановление доступа. Смена пароля, заведение пароля,
второй фактор, церемония повышения, смена адреса и свои сессии (перечень и оба выхода) отвечают **отказом положения**: `403`, код `7`,
`email address is not verified: confirm it with the code from the letter (POST /iam/v1/auth/verify-email/confirm)`,
`ErrorInfo.reason` — `EMAIL_NOT_VERIFIED`; печенья не трогаются, сессия остаётся живой. Текст
называет шаг, который снимает отказ: предъявить код из письма регистрации (или из письма,
поставленного запросом ниже) глаголом подтверждения — этот путь доступен в положении
подтверждения. Клиент решает по `reason`, а не по тексту. Тот же отказ тем же значением дают методы обоих
gRPC-слушателей службы, права человека не действуют, токены ему не выдаются, а выданные
раньше на предъявлении недействительны до подтверждения. Каждый путь полосы объявлен одной из
двух строк — `loginlanehttp.PathPositions()`, — и путь без объявления есть находка гейта.

### Подтверждение адреса — два обращения под сессией

`POST /iam/v1/auth/verify-email` с `{ "csrfToken" }` ставит письмо с **кодом** — десять знаков,
вводятся руками; адрес берётся из строки человека, а не из формы (поле `email` в теле —
`Illegal argument email: unknown field`). Успех — `200 {}` без печений; `Retry-After`
называет промежуток до следующего разрешённого письма. Письмо регистрации ставится той же
транзакцией, что заводит человека.

`POST /iam/v1/auth/verify-email/confirm` с `{ "code", "csrfToken" }`: верный код в срок ставит
отметку, выдаёт **новый** носитель той же сессии, снимает прочие сессии человека и, если
строка человека — приглашение, активирует его. Ответ — `{"session": {…, "emailVerified": true}}`.
Регистр, пробелы и дефисы кода не значимы. Код однократен, жив последний выданный, у кода свой
срок и предел неподошедших попыток; писем одному человеку — не чаще промежутка и не больше
предела за окно, письмо регистрации в счёт.

### Смена адреса почты — два обращения под сессией {#email-change}

Адрес меняет только **второе** обращение, и только кодом, пришедшим на **новый** адрес. Оба
пути — правка своих данных: в положении подтверждения они отвечают отказом положения, без
сессии — `401` `authentication failed`.

`POST /iam/v1/auth/email-change` с `{ "newEmail", "csrfToken" }` требует **свежей** сессии
(момент последнего предъявления не старше окна правки своих данных; ровно окно — свежая), иначе
`403` `SESSION_NOT_FRESH` — следующий шаг `POST /iam/v1/auth/step-up`. Адрес приводится так же,
как при регистрации: пусто — `Illegal argument newEmail: required`, форма не годится —
`Illegal argument newEmail: invalid format`, совпал с текущим —
`Illegal argument newEmail: must differ from the current address`; лишнее поле (например,
`email`) — `Illegal argument email: unknown field`. Успех — `200 {}` без печений, `Retry-After`
— секунды до следующего разрешённого запроса. На новый адрес уходит письмо с кодом — десять
знаков, вводятся руками; ссылки-предъявителя в письме нет. До предъявления кода действует
**прежний** адрес: им входят, на него идёт восстановление, его отдаёт `GET /iam/v1/users/{userId}`.

Ответ на адрес, **занятый** другой учётной записью, побайтово тот же, что на свободный: запрос
записывается и расходует темп одинаково, но письма с кодом нет, и подходящего кода не
существует. Экран говорит «письмо отправлено, если адрес может быть использован». Темп — те же
пять величин, что у подтверждения адреса: между двумя принятыми запросами смены — не меньше
промежутка, за окно — не больше предела; на один адрес из многих учётных записей — не больше
окна писем адресата. Сверх любого предела — `429` `TOO_MANY_ATTEMPTS` с `Retry-After`; запрос
не записан, прежний код жив. Новый принятый запрос вытесняет прежний неприменённый код.

`POST /iam/v1/auth/email-change/confirm` с `{ "code", "csrfToken" }` свежести не требует —
владение ящиком доказывает код. Верный код в срок одним исходом: адрес — новый, отметка
подтверждения — момент предъявления, **новый** носитель той же сессии (прежний больше не
годен), все **прочие** сессии человека завершены, живые коды восстановления сняты, на
**прежний** адрес уходит уведомление без нового адреса. Ответ — `{"session": {…, "emailVerified":
true}}`. Неподошедший код — неверный, истёкший, вытесненный, применённый, истраченный пределом
попыток, выданный другому человеку — один отказ `401` `authentication failed`; пустой `code` —
`Illegal argument code: required`. Адрес, занятый между запросом и предъявлением, — `409`,
код `6`, `email address is already in use`, `EMAIL_IN_USE`: исход откатывается целиком, код
остаётся неприменённым. Смена отсечки не пишет: короткие токены доступа завершённых сессий
живут до своего срока.

Совпадение путей **точное**: параметры запроса к пути не относятся, а `/iam/v1/auth/` —
не приставка, под которой всякий новый маршрут получал бы те же свойства. «Кто я»
(`GET /iam/v1/auth/me`, `GET /iam/v1/me`) — маршруты **края**, а не полосы: на слушателе их
нет.

## Кто вправе звать — ровно край, и это судится до тела запроса

Слушатель поднимается по адресу `api-server.login-lane-endpoint`
(`KANAME_API_SERVER__LOGIN_LANE_ENDPOINT`; умолчания нет, в поставляемом профиле
`tcp://0.0.0.0:9100`) под **взаимным TLS** (`KANAME_LOGINLANE_SERVER_MTLS_*`, режим `mutual`).
Множество допущенных вызывающих равно **краю платформы**: короткое имя службы, разобранное из
SAN проверенного клиентского сертификата под доменом доверия установки, обязано равняться имени
края (`api-gateway`). Пир с иным именем получает `403` с кодом `7` и текстом
`permission denied` — тело не читается, заголовки в счёт не попадают.

Отсюда три следствия, которые надо знать до установки:

- **браузер ходит на адрес консоли**, а не на слушатель: он отправляет `POST /iam/v1/auth/login`
  на origin консоли, и край ретранслирует тело службе, приложив один адрес источника в
  `X-Forwarded-For`. Заголовков переданной личности, которыми платформа переносит субъекта
  между своими компонентами, полоса не читает вовсе: субъект берётся из печенья
  `kaname_session`;
- **полоса поднимается на каждом старте**: в боевом режиме необъявленный адрес слушателя —
  отказ старта с именем ручки, а не старт без входа человека;
- **поставка без края платформы дверь входа человека не открывает.** Слушатель впускает только
  предъявителя сертификата с именем края под вашим доменом доверия; собственные REST-фронты
  службы (`:9098`, `:9099`) этих путей не обслуживают. На такой установке человеку вход
  недоступен, а машине доступен обмен ключа на токен (`POST /iam/v1/token`). Сквозной прогон полосы в репозитории службы идёт на стенде, где
  место края занимает прогонщик набора: клиентский лист на имя края ему выписывает
  внутренний удостоверяющий центр стенда (`.github/scripts/stand-chart.sh`).

:::note Что из двадцати трёх путей ретранслирует край — свойство версии края
Служба обслуживает все двадцать три (`loginlanehttp.Paths()`). Край платформы ретранслирует
перечень, объявленный у него (`gateway/internal/middleware/login_lane_paths.go` в
`PRO-Robotech/kacho`), и перечень этот — свойство ревизии края, которую вы ставите. Путь,
которого край не ретранслирует, отвечает с адреса консоли отказом края, а не службы.
Предикат: `git show <ревизия края>:gateway/internal/middleware/login_lane_paths.go`.
:::

## Признак формы — против подделки запроса

Каждый `POST` несёт поле `csrfToken`, полученное `GET /iam/v1/auth/csrf?form=<вид>` **с тем же**
печеньем `kaname_form`. Признак — свёртка HMAC-SHA256 над видом формы с ключом-контекстом:
признак вида `logout` форме `password` не подходит, чужой контекст не подходит тоже, и оба
случая отвечают **одним** отказом. Виды: `login`, `logout`, `password`, `register`,
`recovery`, `recovery-complete`, `second-factor`, `step-up`, `verify-email`,
`verify-email-confirm`, `access-key-begin`, `access-key-login`, `password-enroll`,
`email-change`, `email-change-confirm`, `session-end`.

<CodeBlock language="bash">
  {dedent`
    curl -c jar -b jar 'https://console.example/iam/v1/auth/csrf?form=login'
    # → {"csrfToken":"…"}; в jar легло kaname_form
  `}
</CodeBlock>

Неизвестный вид — `400` с кодом `3`:
`Illegal argument form: must be one of [login logout password register recovery recovery-complete second-factor step-up verify-email verify-email-confirm access-key-begin access-key-login password-enroll email-change email-change-confirm session-end]`.

## Форма запроса и ответа — по глаголу

Тело — JSON с **закрытым** набором полей: лишнее поле не глотается, а называется (`Illegal
argument <поле>: unknown field`, у вложенного — `secondFactor.<поле>`); потолок тела — 16 КиБ.
Незаполненное обязательное поле называется до глагола: `Illegal argument email: required`,
`Illegal argument csrfToken: required` — такой отказ в счёт частоты не идёт.

### Вход — `POST /iam/v1/auth/login`

<CodeBlock language="json">
  {dedent`
    { "email": "dev@acme.example", "password": "…", "csrfToken": "…",
      "secondFactor": { "method": "totp", "code": "123456" } }
  `}
</CodeBlock>

`secondFactor` необязателен: без него сессия получает уровень `1`, даже если фактор заведён;
с ним (`method` — `totp` либо `lookup_secret`, `code` — шесть цифр либо десять знаков
запасного кода) — уровень `2`. Форма кода судится **до** пароля: негодный код — отказ формы с
именем поля (`Illegal argument secondFactor.code: must be 6 digits`), не попытка. Всё
остальное о коде — не сошёлся, повторён, потреблён, **фактор не заведён** — отвечает тем же
`401`, что неверный пароль **с тем же полем**, и считается попыткой: по ответу на вход нельзя
узнать ни состояние фактора, ни то, совпал ли пароль.

Отказ входа **с полем** `secondFactor` — один на все причины этой формы (адреса нет, пароль не
тот, личность заблокирована, код не тот, повторён или потреблён, фактора нет) — и называет шаг:
`authentication failed; check the email, the password and the code, and send secondFactor only if a second factor is enrolled`. Вход **без** поля отвечает прежним `authentication failed`. Это не оракул:
форму запроса знает сам вызывающий, и текст различает присланное, а не найденное. Если фактор
не заведён, войдите без `secondFactor` и прочитайте его состояние
[`GET /iam/v1/auth/second-factor`](#second-factor). Попытка с кодом при незаведённом факторе
окно частоты тратит так же, как неверный пароль: иначе темп окна выдавал бы, совпал ли пароль.

Успех — `200`, печенья `kaname_session` и **новое** `kaname_form`:

<CodeBlock language="json">
  {dedent`
    {
      "user":    { "id": "usrbr69ze0ftz3jf7396", "email": "dev@acme.example", "displayName": "dev" },
      "session": { "expiresAt": "2026-09-18T10:00:00Z", "assuranceLevel": "1",
                   "emailVerified": false }
    }
  `}
</CodeBlock>

Тот же ответ и те же печенья отдают регистрация и завершение восстановления.

### Регистрация — `POST /iam/v1/auth/register`

<CodeBlock language="json">
  {dedent`
    { "email": "dev@acme.example", "password": "…", "csrfToken": "…" }
  `}
</CodeBlock>

Четыре следствия одним исходом: строка личности (у адреса живого приглашения — строка самого
приглашения: способ входа и сессия ложатся на неё, второй строки не заводится, а приглашение
остаётся `PENDING` до подтверждения адреса), требование подтверждения адреса
(`emailVerified: false`), сессия и **личный аккаунт** с проектом `default`, которым
зарегистрировавшийся владеет. Личный аккаунт — один на человека: у адреса живого приглашения его
заводит не регистрация, а подтверждение адреса, и аккаунт пригласившего личным для приглашённого
не становится. Имя личного аккаунта — `personal-cloud-<хвост>`; причиной отказа регистрации оно
не бывает, а префикс `personal-cloud-` зарезервирован за личными аккаунтами
([Аккаунт](/api/account)). Отображаемое имя сюда не принимается — оно выводится из
адреса, и глагола его правки в публичном API нет: `displayName` у пользователя только для
чтения, а `UpdateUser` с ним в `updateMask` отвечает `INVALID_ARGUMENT`
([Пользователь](/api/user)).

Правило пароля судится **до** транзакции и называет поле: `Illegal argument password: shorter
than the declared minimum length` (`authn.login.password-min-length`) ·
`… must not resemble the e-mail address` · `… appears in a known breach corpus` (при включённой
проверке утечек).

### Выход — `POST /iam/v1/auth/logout`

Тело — только `csrfToken`. Исходов два, и печенье гасится только в первом:

- **выход выполнен** — `200 {}` и погашенное печенье; сюда же относится «сессии нет» (носителя
  нет, он истёк или уже погашен), и его причина видна только в счётчиках;
- **выход не выполнен** — хранилище не ответило: `503`, `logout not performed; try again later`.
  Печенье не тронуто, сессия жива, повторить можно. Отказ признака формы либо тела тоже
  печенья не трогает и сессию не завершает.

Считать сессию закрытой можно только по `200`.

### Смена пароля — `POST /iam/v1/auth/password`

<CodeBlock language="json">
  {dedent`
    { "currentPassword": "…", "newPassword": "…", "csrfToken": "…" }
  `}
</CodeBlock>

Требует печенья сессии. Успех — `200 {"session": {…}}` и **новое** `kaname_session`: сессия
перевыпускается, все **прочие** сессии человека завершаются. Неподошедший текущий пароль и
отсутствующая сессия отвечают одним `401`.

### Заведение первого пароля — `POST /iam/v1/auth/password/enroll` {#password-enroll}

Человек, у которого пароля нет (он входит ключом доступа), заводит его из **своей свежей**
сессии: `{ "newPassword", "csrfToken" }`, признак вида `password-enroll`. Текущего пароля здесь
нет by construction — его и нет. Сессия должна быть свежей (момент последнего предъявления не
старше окна правки своих данных; ровно окно — свежая), иначе `403` `SESSION_NOT_FRESH` —
предъявите способ входа ещё раз. Без подтверждённого адреса — отказ положения подтверждения
(`403` `EMAIL_NOT_VERIFIED`). Новый пароль судится тем же правилом, что при смене.

Успех — `200` с `{"session": {...}}` той же формы, что у входа, **без** `Set-Cookie`: прочие
сессии живут, носитель не перевыпускается, уровень сессии не меняется. Если пароль у человека
уже есть — `409` `ALREADY_EXISTS`, `PASSWORD_ALREADY_SET`, `password is already set; change it
with the current password`: пароль меняют через `POST /iam/v1/auth/password` с текущим. Глагол
секрета не предъявляет и в счёт неверных предъявлений не идёт.

### Восстановление доступа — два обращения

`POST /iam/v1/auth/recovery` с `{ "email", "csrfToken" }` отвечает **`200` одним телом при
любом исходе**, без печений и не дожидаясь постановки письма:

<CodeBlock language="json">
  {dedent`
    { "nextStep": "a letter with a recovery code is sent if this address can recover access; if no letter arrives, request again later, sign in and confirm the address, or ask an administrator to reset your sign-in methods" }
  `}
</CodeBlock>

Адреса нет · адрес не подтверждён у личности со способом входа (код не выдаётся) · код выдан и
письмо в очереди — снаружи неразличимы, исход виден только счётчиком
`kaname_recovery_request_outcomes_total`. Текст `a letter with a recovery code is sent if this address can recover access; if no letter arrives, request again later, sign in and confirm the address, or ask an administrator to reset your sign-in methods`
называет шаг условием, которое знает сам человек: письмо пришло — завершение; не пришло —
повторить позже, войти и подтвердить адрес либо обратиться к администратору. Что письмо
**отправлено**, он не утверждает. Поле `nextStep` стоит всегда; клиент на его значение не
ключуется — оно для человека. Заблокированная личность код получает и встречает отказ на
предъявлении. Срок кода — `authn.login.recovery-code-ttl`; новый запрос вытесняет прежние коды.

`POST /iam/v1/auth/recovery/complete` с `{ "email", "code", "newPassword", "csrfToken" }` —
текущего пароля здесь нет by construction, код и есть доказательство. Правило нового пароля
судится **до** применения кода (негодный пароль код не тратит). Успех отвечает как вход: тело
Ф3, `kaname_session`, новый `kaname_form`; все прежние сессии человека завершены. У
заблокированной личности код применяется и пароль записывается, но сессия не выдаётся. Отказ
завершения — `401` / `16` без печений, **один** текст на все причины (код не тот, истёк,
применён; адреса нет; личность заблокирована): `access not restored; request a new recovery code, and if a new code does not restore access, ask an administrator`.
Он свой у глагола, а не текст отказа входа, и называет шаг для каждой причины: новый код лечит
неверный, истёкший и применённый, а если и новый не помог — нужен администратор.
Если пароля у человека не было вовсе (он входил только ключом доступа), завершение его
**заводит** — исход тот же, что у человека с паролем: так возвращается доступ при утрате
единственного ключа.

:::note Восстановление для неподтверждённого адреса
Код восстановления выдаётся на подтверждённый адрес, а также на неподтверждённый адрес личности `ACTIVE`, у которой нет способа входа (Ф5 Р9): предъявление такого кода подтверждает адрес и заводит первый пароль одной транзакцией. Для прочих неподтверждённых адресов запрос кода **не выдаёт** (исход
`unverified`): сперва адрес подтверждается кодом из письма
([подтверждение адреса](#verification-position)).
:::

### Второй фактор {#second-factor}

`GET /iam/v1/auth/second-factor` (без признака, с сессией) — три формы тела:

<CodeBlock language="json">
  {dedent`
    { "totp": { "enrolled": false } }
    { "totp": { "enrolled": false, "pendingUntil": "2026-09-17T10:15:00Z" } }
    { "totp": { "enrolled": true, "confirmedAt": "2026-09-17T10:00:00Z" },
      "backupCodes": { "remaining": 8, "total": 10 } }
  `}
</CodeBlock>

`POST …/enroll` (`{ "csrfToken" }`) отвечает `{ "secret", "otpauthUri", "expiresAt" }` — секрет
в Base32 показывается **один раз**; печений нет. Требует **свежего** предъявления: последнее
предъявление пароля или кода не старше `authn.self-service-freshness`, иначе `403`
`SESSION_NOT_FRESH`; тем же окном ограничен срок неподтверждённого заведения (`pendingUntil`).
Заведённый фактор — `409` `SECOND_FACTOR_ALREADY_ENROLLED`.

`POST …/confirm` (`{ "code", "csrfToken" }`) — первым кодом с приложения; ответ
`{ "backupCodes": [десять кодов], "session", "assurance" }` и **новый** `kaname_session`:
подтверждение — предъявление, сессия получает уровень `2`. Запасные коды показываются один раз.
Требует **свежего** предъявления, как и заведение: иначе `403` `SESSION_NOT_FRESH`, и при
истёкших обоих окнах — свежести и заведения — первой отвечает свежесть. Без начатого либо
истёкшего заведения — `400` `ENROLLMENT_NOT_PENDING`; неверный код — `401`.

`POST …/remove` и `POST …/backup-codes` подтверждаются кодом — `{ "method", "code",
"csrfToken" }` (`method`: `totp` либо `lookup_secret`), как смена пароля подтверждается текущим.
Ответ — `200 { "session", "assurance" }` и новый носитель. У перечеканки к нему добавлен
`backupCodes` (новый набор). Снятие несёт ещё `backupCodesRemaining: 0` — **всегда** и любым годным
кодом, а не только потребившим запасной. Поле означает «второй фактор снят, резервных кодов не
осталось»: снятие убирает фактор, набора запасных кодов после него нет. Успешность снятия
подтверждают через `GET …/second-factor` по `totp.enrolled: false`, **а не** по счётчику остатка.
Поле `backupCodesRemaining` в ответе снятия (плоское, всегда `0`) — это **не** то же, что
`backupCodes.remaining` из `GET` заведённого фактора (вложенное, «сколько кодов ещё у живого
фактора»): два разных нуля — у снятия `0` значит «фактора больше нет», у живого фактора
`backupCodes.remaining: 0` значит «фактор жив, но коды исчерпаны». Без заведённого фактора —
`400` `SECOND_FACTOR_NOT_ENROLLED`.

Утративший и приложение, и запасные коды сам фактор не снимет: за него это делает надзор облака
глаголом [`UserService.ResetSecondFactor`](/api/user#reset-second-factor).

### Церемония повышения — `POST /iam/v1/auth/step-up`

<CodeBlock language="json">
  {dedent`
    { "method": "totp", "code": "123456", "csrfToken": "…" }
    { "method": "password", "password": "…", "csrfToken": "…" }
  `}
</CodeBlock>

Способ называет клиент: `password`, `totp`, `lookup_secret`; поле, не относящееся к способу,
отвергается по имени. Успешное предъявление кладёт способ в множество предъявленных, уровень
пересчитывается правилом (монотонно — понижения нет), носитель перевыпускается. Неудачное
предъявление сессию не гасит и не понижает. Ответ — `{ "session", "assurance" }`:

<CodeBlock language="json">
  {dedent`
    { "session": { "expiresAt": "…", "assuranceLevel": "2", "emailVerified": true },
      "assurance": { "level": "2", "level2Reachable": true, "missingForLevel2": [] } }
  `}
</CodeBlock>

`level2Reachable` — есть ли среди заведённых у человека способов такой, что даст `2`;
`missingForLevel2` — какие способы (`totp`, `lookup_secret`) его предъявление в этой сессии
выполнит; пуст, когда `2` достигнут либо недостижим. Пароль вместе с кодом по времени или
запасным кодом — `2`; один пароль либо код восстановления — `1`.

### Вход ключом доступа — `POST /iam/v1/auth/access-key/{begin,login}` {#access-key-login}

Ключ доступа — **первичный** способ входа, а не добавка к паролю: человек без пароля входит им и
получает ту же сессию, что вошедший паролем. Обращений два, и у каждого **свой** вид признака
формы — `access-key-begin` у испытания и `access-key-login` у предъявления; контекст формы
(`kaname_form`) при этом один. Церемония входа поэтому стоит **двух** обращений к
`GET /iam/v1/auth/csrf` — по признаку на каждый вид: признак испытания предъявлению не годится,
и наоборот (`403`, `form token rejected`).

**Первое — испытание.** Тело — одно поле `csrfToken`; запрос не называет человека вовсе. Ответ —
параметры предъявления для браузерного интерфейса: `allowCredentials` — **пустой массив
словом** (браузер сам предлагает подходящее обнаруживаемое удостоверение, служба не подсказывает,
у кого оно есть); `timeout` — срок испытания в миллисекундах; `rpId` и `userVerification`
(`preferred`) — величины привязки службы.

<CodeBlock language="json">
  {dedent`
    POST /iam/v1/auth/access-key/begin
    {"csrfToken": "…"}

    200
    {"publicKey": {
      "challenge": "…", "rpId": "console.example", "timeout": 300000,
      "userVerification": "preferred", "allowCredentials": []
    }}
  `}
</CodeBlock>

Испытание живёт при **контексте формы**, а не при человеке, и оно **одно** на контекст: повторное
обращение замещает прежнее. Предъявление гасит испытание при любом исходе, поэтому второе
предъявление с тем же испытанием не проходит никогда — утверждение собирают заново с нового
`begin`. Каждое `begin` считается попыткой по источнику: частые испытания с одного адреса
упираются в тот же `429` `TOO_MANY_ATTEMPTS`, что и неверные пароли.

**Второе — предъявление.** Тело несёт ответ браузера. Поля — base64url **без дополнения**; все
перечисленные ниже обязательны, `userHandle` в том числе: по нему служба сверяет, чей это ключ.

<CodeBlock language="json">
  {dedent`
    POST /iam/v1/auth/access-key/login
    {"csrfToken": "…", "credential": {
      "id": "…", "rawId": "…", "type": "public-key",
      "response": {"clientDataJSON": "…", "authenticatorData": "…",
                   "signature": "…", "userHandle": "…"}
    }}
  `}
</CodeBlock>

Поле вне этого перечня отвергается `400` с его именем, а не глотается. Стандартная сериализация
браузера (`PublicKeyCredential.toJSON()`) несёт ещё `clientExtensionResults` и
`authenticatorAttachment` — **снимите их** перед отправкой, иначе первый же вызов получит `400`.
Поля `secondFactor` у этой формы тоже нет: второй фактор вход ключом не требует и не принимает.

Ответ успеха — **та же форма, что у входа паролем**: `user`, `session`, печенье `kaname_session`
и новый `kaname_form` (оба признака прежнего контекста после выдачи негодны). Уровень сессии
выводится из флагов **этого** утверждения: ключ, выполнивший проверку пользователя и не
допускающий резервного копирования, даёт `3`; всякое другое утверждение ключа — `2`.

Отказ входа ключом — **тот же один отказ**, что у входа паролем: `401`, код `16`,
`authentication failed`, без печенья. Что именно не сошлось — испытание, удостоверение,
рукоятка, подпись, блокировка, — ответ не говорит; различает причины только оператор службы по
её счётчикам. Отказ **формы** (поле не прислано, лишнее поле, чужой вид признака) остаётся
отличимым: он про запрос, а не про личность. Пароль полоса ключа не читает и не требует —
полосы входа независимы, и человек с паролем и ключом входит любой.

Утраченный единственный ключ у человека без пароля возвращается **восстановлением по
подтверждённому адресу** (`POST /iam/v1/auth/recovery`, затем `…/recovery/complete` с новым
паролем); после входа паролем человек заводит новый ключ и снимает утраченный.

### Ключи доступа (WebAuthn) — `AccessKeyService`

Ключ доступа — **свой ресурс** человека (не строка способа входа): своя таблица, свой `id`
формы `ak-…`, свои шесть глаголов. Ходят они **не полосой форм**, а обычным REST-фронтом
службы (тем же, что `UserService`), и поднимаются вместе с полосой входа на каждом старте. Церемонию ведёт браузер (`navigator.credentials.create` /
`get`); служба выдаёт испытание, судит результат и хранит открытый ключ. Аттестация ключа не
требуется, не проверяется и не хранится; модель устройства продукт не судит.

Испытание регистрации несёт литералы контракта, одинаковые у всех установок: имя доверяющей
стороны показывается как `Kacho Cloud`, проверка пользователя `preferred` (на обеих
церемониях), обнаруживаемое удостоверение `required`, аттестация `none`, расширение
`credProps` запрошено; `user.id` — рукоятка человека: 64 случайных байта, одни у всех его
ключей и не выводимые ни из его `id`, ни из адреса, ни из имени. Рукоятка уходит в
аутентификатор и обратно приходит полем `userHandle` утверждения. Срок испытания —
**5 минут**, одноразовое, привязано к вызывающему и к церемонии: результат над чужим,
повторённым, просроченным или невыданным испытанием отвергается.

<CodeBlock language="json">
  {dedent`
    { "challenge": "…", "rp": { "id": "access.example.invalid", "name": "Kacho Cloud" },
      "user": { "id": "…", "name": "alice@example.invalid", "displayName": "Alice" },
      "pubKeyCredParams": [ { "type": "public-key", "alg": -7 }, { "type": "public-key", "alg": -8 }, { "type": "public-key", "alg": -257 } ],
      "authenticatorSelection": { "residentKey": "required", "requireResidentKey": true, "userVerification": "preferred" },
      "attestation": "none", "extensions": { "credProps": true }, "expiresAt": "…" }
  `}
</CodeBlock>

Результат церемонии — `{ "name", "description", "credential": { "id", "clientDataJson",
"attestationObject", "discoverable" } }`: `name` — той же формы, что имя всякого ресурса
(пустое заменяется `id`), `description` — до 256 знаков, `discoverable` — значение
`credProps.rk`, если браузер его сообщил (сообщённое `false` отвергается: ключ обязан быть
обнаруживаемым). Форма имени и описания судится **до** результата церемонии и испытание не
гасит. Утверждение — `{ "credential": { "id", "clientDataJson", "authenticatorData",
"signature", "userHandle" } }`; ответ — `{ "userId", "accessKeyId", "flags": { "userPresent",
"userVerified", "backupEligible", "backupState" } }`, и `userId` всегда равен вызывающему.

Число ключей человека ограничено потолком `own-ceilings.access-keys-per-user` (ноль — «ключей
не заводить»); последний способ входа человека снять нельзя. Привязку — имя доверяющей стороны,
перечень происхождений консоли, перечень алгоритмов (`-7` ES256, `-8` EdDSA, `-257` RS256) —
объявляет посадка ручками `authn.access-keys.*`; их смена делает существующие ключи негодными.

Отказы полосы регистрации и снятия различимы по `reason`: `SESSION_NOT_FRESH` (403),
`CHALLENGE_NOT_ISSUED` · `CHALLENGE_ALREADY_PRESENTED` · `CHALLENGE_EXPIRED` ·
`ORIGIN_NOT_ALLOWED` · `RP_ID_MISMATCH` · `USER_NOT_PRESENT` · `ALGORITHM_NOT_ALLOWED` ·
`CREDENTIAL_NOT_DISCOVERABLE` (400 на приёме результата), `LAST_SIGN_IN_METHOD` (400 на
снятии), `AlreadyExists` на удостоверении, уже принятом, отказ потолка с действующей величиной
и следующим шагом. Отказ **утверждения** — один на все причины и без подробностей:
`400` `access key assertion is not accepted`; какая именно — видно только оператору по
счётчикам. Малформный `accessKeyId` — `400` `invalid access key id '…'` первым стейтментом;
чужой и несуществующий ключ на снятии — одинаковое `404`.

### Свои сессии — `GET /iam/v1/auth/sessions`, `POST …/sessions/{end,end-others}` {#own-sessions}

Человек видит свои живые сессии и выходит из любой, кроме той, в которой сидит, — например,
забытой на чужом компьютере или на потерянном устройстве. Субъект всех трёх глаголов —
владелец сессии носителя `kaname_session`: ни путь, ни тело, ни параметры человека не называют,
и чужих сессий глаголы не видят и не снимают. Ответ синхронный: снятая сессия перестаёт
действовать на следующем же запросе её носителем — опрашивать нечего.

`GET /iam/v1/auth/sessions` (без признака, с сессией) — страница живых сессий (не снятых, срок не
вышел) в порядке выдачи: по моменту создания записи, при равенстве — по `id`, от старой к новой.

<CodeBlock language="json">
  {dedent`
    {
      "sessions": [
        {
          "id": "hss-0123456789abcdefg",
          "current": true,
          "authenticatedAt": "2026-10-07T09:00:00Z",
          "lastPresentedAt": "2026-10-07T09:00:00Z",
          "expiresAt": "2026-10-08T09:00:00Z",
          "userAgent": "Mozilla/5.0 (X11; Linux x86_64)"
        }
      ],
      "nextPageToken": ""
    }
  `}
</CodeBlock>

- `current` — `true` ровно у сессии, носителем которой сделан запрос; на странице, где её нет,
  `true` нет ни у одной.
- `userAgent` — описание клиента, каким его назвал запрос, **выдавший** сессию (вход паролем,
  вход ключом, регистрация, завершение восстановления): заголовок `User-Agent` как есть. Служба
  его не разбирает и ничего из него не выводит. Каждый байт вне допустимой последовательности
  UTF-8 заменён руной U+FFFD, затем значение урезано до **512 рун** (кодовых точек, а не байт);
  выдачу это не роняет. Клиент не назвался либо сессия выдана до появления поля — ключа
  `userAgent` **нет** (не пустая строка). Перевыпуск носителя (смена пароля, повышение) поле не
  трогает.
- `lastPresentedAt` — момент последнего **предъявления способа входа** в этой сессии (пароль,
  код, ключ), а не последнего запроса: запись на каждый запрос служба не ведёт.
- Моменты — RFC 3339, до секунды. Других ключей у элемента нет.
- Страница: `pageSize` — целое `0…1000`, `0` и отсутствие — 50; `pageToken` — курсор из
  `nextPageToken` предыдущей страницы; пустой `nextPageToken` — страница последняя. Иных
  параметров нет: `Illegal argument <параметр>: unknown field`. Негодные значения — `400` код `3`,
  `details` пуст: `Illegal argument pageSize: must be in [0..1000] (0 means default)`,
  `Illegal argument pageSize: must be an integer`, `Illegal argument pageToken: malformed`.
  Параметры проверяются до чтения хранилища.

`POST /iam/v1/auth/sessions/end` — `{ "sessionId", "csrfToken" }`, признак вида `session-end`.
Успех — `200 {"ended": true}`, **без** `Set-Cookie`: сессия снята вместе со всем, что в ней
выдано, носитель текущей не перевыпускается. `sessionId`, который не есть живая сессия самого
человека — чужая, неизвестная, снятая, истёкшая, — **один** отказ: `404`, код `5`,
`session not found`, `SESSION_NOT_FOUND`; тело у всех случаев побайтово одно и идентификатора не
повторяет — по ответу нельзя узнать, существует ли чужая сессия. Названа текущая сессия — `400`,
код `9`, `the current session ends by logout`, `SESSION_IS_CURRENT`: из текущей выходят
выходом `POST /iam/v1/auth/logout`, который гасит печенье. Форма поля — до хранилища:
`Illegal argument sessionId: required`,
`Illegal argument sessionId: must match ^hss-[crockford-base32]{17}$`.

`POST /iam/v1/auth/sessions/end-others` — `{ "csrfToken" }`, тот же вид признака. Успех —
`200 {"ended": N}`, `N` — сколько сессий снято (`0`, если прочих живых нет); текущая жива,
`Set-Cookie` нет. Сессия, выданная **после** ответа, жива: снятие действует назад. Два таких
запроса наперегонки из двух сессий одного человека оставляют живой ровно одну из двух: запрос из
сессии, снятой встречным, получает `401` `authentication failed` и не снимает ничего.

Оба выхода требуют **свежей** сессии: момент последнего предъявления не старше
`authn.self-service-freshness` (ровно окно — свежая), иначе `403` `SESSION_NOT_FRESH` —
повышение `POST /iam/v1/auth/step-up` освежает сессию, после него выход проходит.
Довод: носитель, оказавшийся у постороннего, без свежести давал бы ему выгнать владельца со всех
прочих устройств. Перечень свежести не требует. Отсечки эти глаголы не пишут, и в счёт неверных
предъявлений не идут. Каждое снятие пишет событие аудита `iam.session.ended_by_person`
(`user_id`, `session_id` — откуда сняли, `ended_session_ids` — что снято); снято ноль — события нет.

одной причины.

## Что видит оператор

Исходы, которых клиент не видит в ответе, служба отдаёт счётчиками: входа, регистрации, запроса
и завершения восстановления, отказов формы, второго фактора, ключей доступа, подтверждения и
смены адреса —
[Наблюдаемость](/advanced/observability).
Величины полосы — срок сессии, домен печенья, окна частоты, правило пароля, стоимость хеша,
срок кода восстановления, окно свежести, ключи обёртки секретов фактора и пять величин
подтверждения адреса (`authn.login.verification-code-ttl`, `verification-code-attempts`,
`verification-resend-interval`, `verification-resend-limit`, `verification-resend-window`) —
обязательны и названы в [Конфигурации](/install/configuration#login-lane) и
`INSTALL.md` §3.
