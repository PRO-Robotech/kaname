# Вход по коду авторизации

Клиент платформы — консоль, утилита командной строки — получает токен **за человека** церемонией
OAuth 2.1 `authorization_code`: человек входит нашим входом, эндпоинт авторизации выдаёт клиенту
одноразовый код, клиент обменивает его на подписанный платформой предъявитель и дальше продлевает
доступ обновляющим удостоверением.

Церемония существует на посадке со своим входом человека (`authn.identity-provider=own`). Клиент —
**конфиденциальный** интерактивный клиент (`ic-…`), зарегистрированный администратором облака; все
такие клиенты первопартийны, поэтому экрана согласия нет — код выдаётся сразу после входа.

:::note Два разных «authorize»
`GET /iam/v1/authorize` на поверхности выдачи — это эндпоинт авторизации **этой** церемонии.
REST-действия проверки доступа `/iam/v1/authorize:<действие>` — другой предмет, они описаны на
странице [Авторизация и каталог](/api/authorize) и обслуживаются краем.
:::

## Координаты

| путь | метод | что делает |
|---|---|---|
| `/iam/v1/authorize` | `GET` | эндпоинт авторизации: выдаёт код перенаправлением |
| `/iam/v1/token` | `POST` | токен-эндпоинт: `grant_type=authorization_code` и `grant_type=refresh_token` |
| `/.well-known/oauth-authorization-server` | `GET` | метаданные обнаружения (RFC 8414), без аутентификации |

Иной метод на любом из путей — `405` с заголовком `Allow`.

## Шаг 1. Запрос авторизации

Браузер человека переходит по адресу:

```text
GET /iam/v1/authorize?response_type=code
    &client_id=ic-…
    &redirect_uri=https://console.example/auth/callback
    &scope=openid
    &state=<не короче 22 знаков>
    &code_challenge=<BASE64URL(SHA256(code_verifier))>
    &code_challenge_method=S256
```

| параметр | правило |
|---|---|
| `client_id` | идентификатор интерактивного клиента в состоянии `ACTIVE` |
| `redirect_uri` | **обязателен** и совпадает с одной из зарегистрированных целей клиента **точно**, как строка: хвостовой слэш, регистр процентного кодирования, порт по умолчанию не приводятся |
| `response_type` | только `code` |
| `state` | **обязателен**, не короче **22 знаков** алфавита VSCHAR (`%x20-7E`). 22 — запись BASE64URL от 16 случайных байтов, то есть самая короткая форма 128-битного значения |
| `code_challenge`, `code_challenge_method` | **обязательны**; метод — только `S256`. PKCE обязателен вдобавок к секрету клиента, а не вместо него |
| `scope` | необязателен; токены области через одиночный пробел |
| `acr_values` | необязателен; уровни `1`…`3` через пробел — запрос удовлетворяет любой из них |

Каждый параметр — не более одного раза. Неизвестные параметры не читаются.

### Ответы

| исход | ответ |
|---|---|
| код выдан | `302` на `redirect_uri` с `code` и `state` — `state` ровно тот, что прислан |
| клиента нет, клиент снят, цель не зарегистрирована, `client_id`/`redirect_uri` не прислан или повторён | `400` `{"error":"invalid_request"}` **без перенаправления** — ответ одинаков для всех этих причин |
| иной неверный запрос (`state`, PKCE, `response_type`, `scope`, `acr_values`, повтор параметра) | `302` на `redirect_uri` **ровно с `error`**: `invalid_request`, `unsupported_response_type` либо `invalid_scope` |
| сессии нашего входа нет | `401` `{"error":"login_required"}` |
| сессия ниже запрошенного `acr_values` | `401` `{"error":"insufficient_user_authentication","acr_values":"<уровень>"}` — поднимите уровень церемонией повышения входа и повторите запрос |
| наш источник не ответил | `302` с `error=temporarily_unavailable`, а до сверки цели — `503` |

:::warning `state` в перенаправлении с ошибкой не возвращается
Перенаправляемый отказ несёт **только** `error` — ни `state`, ни описания: строка запроса
перенаправления уходит в историю браузера и в заголовок источника перехода. Библиотека, ожидающая
эха `state` в ответе с ошибкой, должна сопоставлять такой ответ со своим незавершённым запросом по
иному признаку.
:::

Собственная строка запроса зарегистрированной цели сохраняется: параметры ответа добавляются к ней.

Код живёт **одну минуту** и принимается один раз. Ответ не кэшируется (`Cache-Control: no-store`).

## Шаг 2. Обмен кода

Клиент аутентифицируется **базовой аутентификацией** секретом (RFC 6749 §2.3.1: идентификатор и
секрет кодируются формой, затем base64). Секрет в теле запроса и подписанное утверждение на этих
полосах не принимаются.

```text
POST /iam/v1/token
Authorization: Basic <base64(urlencode(ic-…):urlencode(секрет))>
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=<код>&redirect_uri=<та же цель>&code_verifier=<verifier>
```

Ответ `200`:

```json
{
  "access_token": "<JWT>",
  "token_type": "Bearer",
  "expires_in": 900,
  "refresh_token": "<удостоверение>",
  "scope": "openid"
}
```

Предъявитель подписан платформой и несёт субъекта (`sub = usr-…`), вид принципала `user`, уровень
входа `acr` и момент аутентификации `auth_time` **той сессии**, которой выдан код. Эти значения
назначает выдача кода: присланные в запросе обмена поля с такими именами не читаются. Адресат
предъявителя назначает платформа; параметр `audience` на этой полосе не читается.

## Шаг 3. Продление

```text
POST /iam/v1/token
Authorization: Basic <…>

grant_type=refresh_token&refresh_token=<удостоверение>
```

Каждое продление **ротирует**: ответ несёт новый предъявитель и новое обновляющее удостоверение,
прежнее недействительно. Необязательный `scope` сужает область нового предъявителя в пределах
выданной. Обновляющее удостоверение не переживает сессию входа, которой выдано: после выхода
человека либо истечения его сессии продление отвергается.

:::danger Повтор отзывает всё семейство
Предъявление **уже использованного** кода либо **уже ротированного** обновляющего удостоверения
отзывает все токены этой авторизации — выданные предъявители перестают приниматься, текущее
обновляющее удостоверение больше не продлевается. Храните обновляющее удостоверение так, чтобы одно
значение предъявлялось один раз, и не повторяйте обмен кода при обрыве соединения: начните церемонию
заново. Другие авторизации того же человека не затрагиваются.
:::

## Отказы токен-эндпоинта

| причина | ответ |
|---|---|
| повторённый либо недостающий параметр | `400` `invalid_request` |
| клиент не аутентифицирован: нет заголовка, неверный секрет, клиента нет или он снят | `401` `invalid_client` с `WWW-Authenticate: Basic` |
| код неизвестен, истёк, уже использован, не тот `code_verifier`, код другого клиента, не та цель; обновляющее удостоверение неизвестно, отозвано, ротировано, сессия закончена | `400` `invalid_grant` — **один и тот же ответ** на все эти причины |
| `scope` шире выданной области | `400` `invalid_scope` |
| временная недоступность проверки секрета или хранилища | `503` `temporarily_unavailable` |

Отказы до того, как запрос назвал код, различимы; после — нет. Оператор различает их по ряду
`kaname_authorization_ceremony_outcomes_total` ([Наблюдаемость](/advanced/observability)).

## Метаданные обнаружения

`GET /.well-known/oauth-authorization-server` без аутентификации отдаёт координаты церемонии:

```json
{
  "issuer": "<издатель>",
  "authorization_endpoint": "<издатель>/iam/v1/authorize",
  "token_endpoint": "<издатель>/iam/v1/token",
  "response_types_supported": ["code"],
  "response_modes_supported": ["query"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "code_challenge_methods_supported": ["S256"]
}
```

Способ аутентификации клиента не перечислен намеренно: по RFC 8414 его отсутствие означает базовую
аутентификацию секретом — ровно то, что принимают полосы церемонии.
