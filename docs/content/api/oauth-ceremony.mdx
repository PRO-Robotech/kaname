# Вход приложения — `authorization_code` с PKCE

Под посадкой личности `own` служба сама проводит интерактивную церемонию OAuth 2.1: человек
входит **нашим** входом ([Полоса входа](/api/auth-lane)), а приложение получает **наш**
подписанный токен доступа по коду авторизации. Под `external` церемонию держит внешний поставщик
удостоверений, и пути этой страницы на поверхности выдачи не отвечают.

Приложение — **интерактивный клиент**: у него зарегистрированы адреса возврата, получатели
выдаваемого токена и секрет. Все интерактивные клиенты первопартийны (консоль, CLI), поэтому
экрана согласия нет: код выдаётся сразу.

| Метод и путь | Что делает |
|---|---|
| `GET /iam/v1/authorize` | выдаёт код авторизации перенаправлением на адрес возврата клиента |
| `POST /iam/v1/token` | обменивает код на токен доступа и токен обновления; оборачивает токен обновления |
| `GET /.well-known/oauth-authorization-server` | метаданные обнаружения (RFC 8414), публичное чтение |

Все три пути стоят на внешней поверхности выдачи рядом с остальными видами выдачи токен-эндпоинта
и больше нигде.

## Запрос авторизации

Браузер человека открывает адрес авторизации с параметрами строки запроса:

| Параметр | Обязателен | Что значит |
|---|---|---|
| `response_type` | да | только `code` |
| `client_id` | да | идентификатор интерактивного клиента |
| `redirect_uri` | да | адрес возврата — **точно** один из зарегистрированных у клиента: без нормализации регистра, хвостового слэша и порядка параметров |
| `scope` | да | `openid` |
| `state` | да | непрозрачная строка приложения **не короче 22 знаков** — запись BASE64URL от 16 случайных байтов; возвращается дословно |
| `code_challenge` | да | `BASE64URL(SHA256(code_verifier))`, 43 знака |
| `code_challenge_method` | да | только `S256` |
| `acr_values` | нет | уровни входа, из которых приложению подходит любой (`1`, `2`, `3`) |

Субъекта, уровень, момент входа и получателя токена запрос не называет: их назначает выдача —
субъект, уровень и момент берутся у сессии человека, получатель — у регистрации клиента. Такие
параметры, если присланы, не читаются.

### Ответы

| Исход | Ответ |
|---|---|
| код выдан | `302` на адрес возврата с `code` и `state` (и `scope`); собственные параметры адреса возврата сохраняются |
| клиент неизвестен или снимается, адрес возврата не зарегистрирован, клиент либо адрес не названы | `400` — одна и та же страница **без перенаправления**: доверенной цели ещё нет |
| `state` не прислан либо короче 22 знаков, нет PKCE либо метод не `S256`, `response_type` не `code`, область вне перечня | `302` на адрес возврата с параметром **только** `error` (`invalid_request`, `unsupported_response_type`, `invalid_scope`) — без `state` и без описания отказа |
| нет сессии человека | `401 {"error":"login_required"}` — приложение ведёт человека на вход |
| уровень сессии ниже запрошенного `acr_values` | `401 {"error":"insufficient_user_authentication","acr_values":"…"}` — человек проходит шаг вверх и повторяет запрос |

## Обмен кода

Приложение обменивает код на токены **в течение 60 секунд** после выдачи:

```http
POST /iam/v1/token
Authorization: Basic base64(urlencode(client_id) ":" urlencode(client_secret))
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=…&redirect_uri=…&code_verifier=…
```

Секрет клиента принимается и телом запроса (`client_id` и `client_secret` полями формы), но не
двумя способами сразу. `redirect_uri` обязан совпасть с адресом, с которым код выдан.

Ответ `200` — стандартная форма:

```json
{"access_token": "…", "token_type": "Bearer", "expires_in": 900, "refresh_token": "…", "scope": "openid"}
```

Код одноразовый: его гасит первое же предъявление, в том числе с неверным `code_verifier`.
Повторное предъявление отвергается **и отзывает всё выданное по этому коду** — токен доступа
перестаёт приниматься везде, где его предъявляют, раньше своего срока.

## Токен обновления

```http
POST /iam/v1/token
Authorization: Basic …

grant_type=refresh_token&refresh_token=…
```

Каждое предъявление **оборачивает** токен обновления: ответ несёт новую пару, прежний токен
обновления больше не принимается. Предъявление уже обёрнутого токена — повтор: отвергается и
отзывает всё семейство выданного по исходному коду. Семейство живёт не дольше сессии человека, в
которой выдан код.

## Отказы токен-эндпоинта

| Ответ | Когда |
|---|---|
| `400 {"error":"invalid_grant"}` | всякий отказ после того, как назван код или токен обновления: неизвестен, истёк, уже использован, неверный `code_verifier`, код другого клиента, другой `redirect_uri`. Ответ побайтово один и тот же |
| `401 {"error":"invalid_client"}` | клиент не доказал себя: нет секрета, секрет неверен, клиента нет |
| `400 {"error":"invalid_request"}` | неразборчивая форма, параметр назван дважды, два способа доказать клиента |
| `503 {"error":"temporarily_unavailable"}` | служба временно не может сверить секрет клиента; повторите запрос |
| `405` | метод, отличный от `POST` |

## Токен доступа

Токен подписан нашим ключом и проверяется по нашему публикуемому набору. Он несёт субъекта
(`sub`), вид и идентификатор принципала (`kaname_principal_type` = `user`,
`kaname_principal_id`), клиента (`client_id`), выданную область (`scope`), получателя из
регистрации клиента (`aud`), уровень входа (`acr`) и момент входа (`auth_time`) — ровно той сессии,
в которой выдан код. Решение о доступе принимает модель прав, как для всякого нашего токена:
область прав не добавляет.

## Метаданные обнаружения

`GET /.well-known/oauth-authorization-server` отдаёт издателя, адреса точки авторизации и
токен-эндпоинта, виды ответа (`code`), способы доставки (`query`), виды выдачи токен-эндпоинта,
методы PKCE (`S256`) и области. Только публичный материал; метод — только `GET`.
