# User

**User** — человек-субъект платформы: сотрудник, которому выдаётся доступ. В модели Kachō User —
это **глобальная личность**: **одна строка на человека** на всю платформу, независимо от того, в
скольких аккаунтах он состоит. Пользователь — это то, к чему привязываются роли; сам вход
(пароль / passkey) живёт в провайдере аутентификации, а IAM хранит снимок личности и её
состояние.

Принадлежность человека аккаунтам выражает **отдельный ресурс** — [Membership](/api/membership),
и их у одного человека может быть несколько. Ресурс User про принадлежность не отвечает: поля
`accountId` у него нет (снято с контракта, см. врезку ниже).

Пользователи заводятся не через `Create`, а через **приглашение** (`Invite`) по email: backend
создаёт строку личности (если её ещё нет) и членство в аккаунте, которое становится `ACTIVE`
при первом входе с совпадением email.

:::info Чем ключевать человека во внешнем справочнике
Стабильный ключ человека — **`id`** (префикс `usr`). Он присваивается один раз и неизменен на
всю жизнь личности; второй аккаунт его не меняет и не заводит второго. Кадровый контур, каталог
и синхронизатор состояния ключуются на него.

Чем ключевать **нельзя**: `email` (меняется), `displayName` (снимок из провайдера),
`externalId` (пуст, пока человек ни разу не входил) и уж тем более идентификатор членства —
членство есть пара «человек × аккаунт», и у одного человека их несколько.
:::

:::note Аккаунта у пользователя нет — и это не пропуск в таблице

Поле `accountId` снято с ресурса. Оно объявляло, что у человека ровно один аккаунт, —
так было, пока человек был строкой **в** аккаунте. Теперь пользователь есть идентичность
платформы: одна строка на человека, а принадлежность аккаунтам выражается **членствами**,
которых у него может быть несколько. Одно значение из этого множества, отданное в ответе,
читалось бы как факт о человеке и лгало бы, не признаваясь в этом.

Номер поля и его имя зарезервированы в контракте: следующее поле не займёт их, и клиент
прежней версии не прочитает чужое значение как аккаунт.

Вопрос «кто состоит в этом аккаунте» отвечает список пользователей, суженный аккаунтом
(`GET /iam/v1/users?accountId=…`) — он читает членства, а не снятое поле.

:::

### Значения inviteStatus

<table>
  <thead><tr><th>Значение</th><th>Смысл</th></tr></thead>
  <tbody>
    <tr><td><code>PENDING</code></td><td>Приглашён, ещё ни разу не входил (<code>externalId</code> пуст)</td></tr>
    <tr><td><code>ACTIVE</code></td><td>Вошёл через Kratos, <code>externalId</code> заполнен</td></tr>
    <tr><td><code>BLOCKED</code></td><td>Вход на платформу запрещён администратором облака — во всех аккаунтах человека сразу</td></tr>
  </tbody>
</table>

:::warning `inviteStatus` — состояние ЛИЧНОСТИ, а не ответ на «принял ли он моё приглашение»
Состояний два, они про разное, и путать их дорого:

| вопрос | где ответ |
|---|---|
| входил ли человек на платформу хоть раз | `User.inviteStatus` — `PENDING` / `ACTIVE` / `BLOCKED` |
| принял ли он приглашение **в мой аккаунт** | [`Membership.state`](/api/membership) — `PENDING` / `ACTIVE` |

Человек, уже работающий в чужом аккаунте, имеет `inviteStatus = ACTIVE` **с момента своего
первого входа где угодно**. Пригласив его к себе, вы увидите `ACTIVE` в ответе `User` — и это
не значит, что он принял ваше приглашение. Про ваше приглашение отвечает членство: пока он не
вошёл после него, его `Membership.state` в вашем аккаунте — `PENDING`.

Обратное тоже верно: первый вход переводит в `ACTIVE` **все** членства человека разом, потому
что состояние личности одно.
:::

## Методы

`UserService` — чтение (`Get`/`List`), приглашение (`Invite`), исключение из аккаунта
(`RemoveFromAccount`), обновление меток (`Update`), запрет и разрешение входа
(`Block`/`Unblock`), удаление личности (`Delete`) и журнал операций. Классического `Create`
нет — пользователи появляются только через `Invite`.

:::info Что чьё

Человек — **глобальная личность**: одна строка на все его аккаунты. Отсюда разные адресаты
у похожих на вид действий:

| действие | чьё | что затрагивает |
|---|---|---|
| `Invite` / `RemoveFromAccount` | **аккаунта** (`editor` / `member_remover`) | участие человека в **этом** аккаунте |
| `Update` (метки) | **облака** (`record_writer`) | запись личности — во всех её аккаунтах |
| `Block` / `Unblock` | **облака** (`identity_suspender`) | вход на платформу целиком |
| `Delete` | **самого человека либо облака** (`identity_remover`) | личность целиком, необратимо |

Распорядителю аккаунта остаётся то, что названо первой строкой, плюс выдача и отзыв прав
(`AccessBinding`). Вывести человека **у себя** — это `RemoveFromAccount`, а не `Block` и не
`Delete`.

:::

### Get — получить пользователя

<ApiOperation method="GET" endpoint="/iam/v1/users/{user_id}">

Возвращает пользователя по идентификатору. Требует `v_get`.

<CodeBlock language="json">
  {dedent`
    {
      "id": "usrbr69ze0ftz3jf7396",
      "externalId": "ory:kratos:9f2c…",
      "email": "dev@acme.example",
      "displayName": "Dev One",
      "inviteStatus": "ACTIVE",
      "createdAt": "2026-06-24T10:00:00Z"
    }
  `}
</CodeBlock>

</ApiOperation>

### List — список пользователей аккаунта

<ApiOperation method="GET" endpoint="/iam/v1/users">

Возвращает пользователей аккаунта, **видимых вызывающему** (default-deny через scope-filter,
не 403): handler оставляет только пользователей аккаунтов, где вызывающий — участник. Обычному
пользователю `accountId` обязателен; поддерживает `filter` по `email` / `externalId` /
`inviteStatus`.

<CodeBlock language="bash">
  {dedent`
    curl 'http://localhost:18080/iam/v1/users?accountId=acc2bkd71802av7dywa8&pageSize=50' \\
      -H 'Authorization: Bearer <JWT>'
  `}
</CodeBlock>

:::note Пользователь всегда видит себя
Вызывающий всегда присутствует в результате `List` своего аккаунта (self-floor) даже без явной
роли — иначе он не смог бы найти собственную запись.
:::

</ApiOperation>

### Invite — пригласить пользователя {#invite}

<ApiOperation method="POST" endpoint="/iam/v1/users:invite" async>

Приглашает пользователя по email: создаётся `PENDING`-строка. Идемпотентно — повторное
приглашение уже приглашённого возвращает `Operation` без дублирования. Опционально — сразу
выдать роль на проекте (`projectId` + `roleId`), тогда AccessBinding создаётся атомарно.
Требует `editor` на аккаунте. Асинхронно (`response: User`).

<CodeBlock language="bash">
  {dedent`
    curl -X POST 'http://localhost:18080/iam/v1/users:invite' \\
      -H 'Authorization: Bearer <JWT>' \\
      -H 'Content-Type: application/json' \\
      -d '{
            "accountId": "acc2bkd71802av7dywa8",
            "email": "dev@acme.example",
            "displayName": "Dev One"
          }'
  `}
</CodeBlock>

`Operation.metadata` (`InviteUserMetadata`) несёт `magicLinkUrl` — recovery/magic-link Kratos,
который админ передаёт приглашённому вручную (автоотправка email не интегрирована). Для
повторного приглашения уже активного пользователя ссылка пустая.

</ApiOperation>

### Update — изменить метки пользователя

<ApiOperation method="PATCH" endpoint="/iam/v1/users/{user_id}" async>

Единственное mutable-поле — `labels` (делает пользователя label-selectable наравне с
account/project). Identity-поля (`externalId` и прочие, проецируемые из IdP) hard-immutable: их
наличие в `updateMask` → `INVALID_ARGUMENT` (`"<field> is immutable after User.Create"`).
Требует **`record_writer`** на записи личности. Асинхронно.

:::note Отношение сменилось: `v_update` → `record_writer`, и это решение
Прежде правка меток спрашивала глагольное `v_update`, у которого источники есть на уровне
аккаунта, — то есть распорядитель аккаунта мог размечать своих людей. Строка человека
**глобальна**, одна на все его аккаунты, поэтому метка, поставленная из одного аккаунта, была
бы фактом о нём во всех остальных: по ней матчились бы меточные выдачи чужих арендаторов.

Отношение `record_writer` источников уровня аккаунта не имеет ни одного — писать метки
человека вправе только надзор облака. Роль, спроектированная под прежнее отношение, выдастся
без ошибки и **откажет на каждом вызове**: выдача проходит, отказывает употребление.

Пер-аккаунтная разметка людей — отдельный предмет: у неё нет носителя, пока чтение меток не
принимает аргумент аккаунта.

**Чтение записи** остаётся делом аккаунта: `Get` требует `v_get`, `List` сужается видимостью.
:::

<CodeBlock language="bash">
  {dedent`
    curl -X PATCH 'http://localhost:18080/iam/v1/users/usrbr69ze0ftz3jf7396' \\
      -H 'Authorization: Bearer <JWT>' \\
      -H 'Content-Type: application/json' \\
      -d '{ "updateMask": "labels", "labels": { "team": "platform" } }'
  `}
</CodeBlock>

</ApiOperation>

### RemoveFromAccount — исключить человека из аккаунта {#remove-from-account}

<ApiOperation method="POST" endpoint="/iam/v1/users/{user_id}:removeFromAccount" async>

Снимает **участие** человека в названном аккаунте. Личность не затрагивается: в остальных
своих аккаунтах человек продолжает работать с той же записью — тот же `id`, та же почта, то
же состояние, те же метки.

Требует `member_remover` на **аккаунте** — по определению тот же круг, что у `Invite`.
Тело обязано называть `accountId`: членство есть пара, и вывести вторую половину из первой
нельзя. Асинхронно.

Идемпотентно: исключение того, кого в аккаунте нет, проходит.

**Сперва снимите права.** Пока у человека в этом аккаунте есть действующая привязка,
исключение отвергается `FAILED_PRECONDITION` — это ограничение базы, а не порядок вызовов.

</ApiOperation>

### Block / Unblock — запретить и разрешить вход

<ApiOperation method="POST" endpoint="/iam/v1/users/{user_id}:block" async>

Переводит `inviteStatus` в `BLOCKED`.

:::danger Радиус — ВСЯ ПЛАТФОРМА, а не ваш аккаунт
`Block` выключает человека **везде, где он состоит**: строка личности одна на все его
аккаунты, поэтому запрет действует и в тех аккаунтах, к которым вызывающий отношения не имеет.
Снимая доступ уволенному подрядчику этим глаголом, вы выключаете его и у остальных.

**Что нужно вместо, если предмет — ваш аккаунт:** снять участие человека в нём —
[`RemoveFromAccount`](#remove-from-account) выше. Личность при
этом не затрагивается.
:::

Требует `identity_suspender` — это надзор облака. У распорядителя аккаунта такого отношения
нет **by construction**, и у самого человека тоже: снять с себя запрет невозможно. Асинхронно.

Идемпотентно: аргумент — **состояние**, а не переход, поэтому повторный запрет уже
запрещённого проходит успехом. Безопасное направление контроля не должно отказывать на
повторе.

Приглашённого, ни разу не входившего (`PENDING`), запретить нельзя: внешней личности у него
ещё нет — `FAILED_PRECONDITION`. Чтобы такой человек никогда не появился в вашем аккаунте,
снимите членство, заведённое приглашением (`RemoveFromAccount`); первый вход его не вернёт.

**Уже выданные токены этим вызовом не отзываются** — они истекают по своему сроку.
Немедленно прекращается выдача **новых**: чеканка, обновление и разрешение субъекта на краю.

</ApiOperation>

<ApiOperation method="POST" endpoint="/iam/v1/users/{user_id}:unblock" async>

Возвращает `inviteStatus` из `BLOCKED` в `ACTIVE`. Тот же радиус, то же отношение
`identity_suspender`, та же идемпотентность. Асинхронно.

</ApiOperation>

### Delete — удалить личность

<ApiOperation method="DELETE" endpoint="/iam/v1/users/{user_id}" async>

Стирает **строку личности**, а значит человека во всех его аккаунтах сразу. Требует
`identity_remover`: это сам человек (самоудаление) либо администратор облака. Распорядителю
аккаунта здесь приходит `PERMISSION_DENIED` — ему служит `RemoveFromAccount` выше.
Асинхронно.

</ApiOperation>

### ListOperations — операции над пользователем

<ApiOperation method="GET" endpoint="/iam/v1/users/{user_id}/operations">

Возвращает операции над пользователем. Sync, курсорная пагинация. Требует `v_list`.

</ApiOperation>
