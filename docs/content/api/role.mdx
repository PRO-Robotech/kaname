# Role

**Role** — именованный набор прав: *что можно делать*. Роль описывает разрешённые действия
(«глаголы») над типами ресурсов («ресурсы»), опционально суженные до конкретных экземпляров.
Роль сама по себе никому доступ не даёт — она становится действующей, только когда её привязывают
к субъекту через [AccessBinding](/api/access-binding). Разделение «роль (что) ↔ привязка (кому и
где)» — основа модели: одну роль переиспользуют для многих субъектов и на разных уровнях иерархии.

Роли двух видов:

- **system-роли** (`isSystem=true`) — базовый каталог (`viewer` / `editor` / `admin` и т.п.),
  seed'ятся миграциями, привязаны к кластеру (`cluster_root`), **read-only** через
  публичный API (Update/Delete → `FAILED_PRECONDITION`);
- **custom-роли** (`isSystem=false`) — создаются тенантом; ровно один из `accountId` /
  `projectId` задан (взаимоисключающе, XOR): роль либо account-scoped, либо project-scoped.

## Модель правил

Политика роли задаётся полем **`rules[]`** (1–64 правила). Каждое `Rule` — однородный грант ровно
**одного модуля**:

<table>
  <thead><tr><th>Поле Rule</th><th>Тип</th><th>Описание</th></tr></thead>
  <tbody>
    <tr><td><code>module</code></td><td>string</td><td>Ровно один domain-модуль из закрытого набора платформы: <code>iam</code> / <code>vpc</code> / <code>compute</code> / <code>loadbalancer</code> / <code>registry</code> / <code>storage</code></td></tr>
    <tr><td><code>resources</code></td><td>string[]</td><td>Типы ресурсов модуля (1–16), lowercase (<code>networks</code>, <code>subnets</code>, ...)</td></tr>
    <tr><td><code>verbs</code></td><td>string[]</td><td>Глаголы (1–16): <code>get</code> / <code>list</code> / <code>create</code> / <code>update</code> / <code>delete</code></td></tr>
    <tr><td><code>resourceNames</code></td><td>string[]</td><td>Опц. пин по id (≤256). Взаимоисключающе с <code>matchLabels</code></td></tr>
    <tr><td><code>matchLabels</code></td><td>map</td><td>Опц. отбор по меткам (AND-equality, ≤16). Взаимоисключающе с <code>resourceNames</code></td></tr>
  </tbody>
</table>

:::note Модулей шесть, и перечень читается вызовом
Набор закрыт и совпадает с набором доменов платформы: `iam`, `vpc`, `compute`, `loadbalancer`,
`registry`, `storage`. Неизвестный модуль отвергается синхронно (`INVALID_ARGUMENT`).

Тонко выдать доступ к **хранилищу** и **реестру** можно так же, как к сетям, — системная роль на
весь уровень для этого не нужна. Какие `resources` и `verbs` каждый модуль принимает,
возвращает `GET /iam/v1/permissionCatalog` ([Authorize](/api/authorize#permissioncatalog)):
это источник таксономии, а не эта страница.

Имя модуля балансировщика — `loadbalancer`, не `nlb`. Домена `geo` в наборе нет: справочник
размещения читается всяким аутентифицированным и правами не выдаётся.
:::

Форма правила задаёт «прицел» (anchor):

- **без селекторов** — грант на *все* экземпляры `{module} × resources` в пределах scope привязки;
- **`resourceNames`** — пин на конкретные id (любой тип можно пиновать по id);
- **`matchLabels`** — отбор по меткам (только для label-selectable типов; иначе
  `INVALID_ARGUMENT`).

Роль, покрывающая несколько модулей, выражается несколькими правилами (по одному на модуль).
`rules[]` — источник истины и публичная поверхность роли; клиенты рендерят роль именно из него.
Грантабельную таксономию (какие модули/ресурсы/глаголы допустимы) отдаёт
[PermissionCatalog](/api/authorize#permissioncatalog).

:::note Wildcard `"*"` — по полю, а не по роли
Ярусом роли ограничена подстановка в `module` и `resources`: в custom-роли она вернёт
`INVALID_ARGUMENT`, в system-роли законна. Подстановка в `verbs` — **не** ограничена: глагол-`*`
означает «все глаголы типа» и грантабелен в custom-роли тоже; единственное условие — он идёт
единственным элементом (`["*", "get"]` → `INVALID_ARGUMENT`).
:::

## Методы

`RoleService` — CRUD (`Create`/`Update`/`Delete` async; `Get`/`List` sync) + журнал операций.
Мутации применимы только к custom-ролям.

### Get — получить роль

<ApiOperation method="GET" endpoint="/iam/v1/roles/{role_id}">

Возвращает роль по идентификатору. Каталог ролей — tenant-wide reference: чтение доступно любому
аутентифицированному вызывающему (без per-role scope).

Ответ несёт **все** поля ресурса, в том числе пустые: пустое значение — часть стабильного
контракта, а не пропуск. Поэтому `purpose` приходит как `""`, а `labels`, `verbNotes` и
`permissions` — как `{}` / `[]`.

## Когда роль перестаёт давать то, что обещает

Роль называет типы и глаголы платформы. Ссылка может потерять свой предмет — если
модуль сняли с обслуживания либо тип объявлен, но платформа его не знает. Роль при
этом **никуда не девается и не сужается молча**: она продолжает существовать, её
`rules[]` остаются теми же, что при выдаче, — но выдавать она начинает меньше.

Узнать это можно из ответа `Get` и `List` **одинаково**: оба несут `health` и пару
счётчиков, и оба считают их одним и тем же способом.

```json
{
  "id": "rol...",
  "health": "ROLE_HEALTH_DEGRADED",
  "declaredSegments": 12,
  "unresolvedSegments": 3,
  "withdrawnGrants": [
    {
      "objectType": "compute.instances",
      "verb": "start",
      "source": "WITHDRAWN_GRANT_SOURCE_GRANT",
      "reason": "не объявлен манифестом модуля compute",
      "withdrawnAt": "2026-09-03T13:15:44Z"
    }
  ]
}
```

Читается так: роль объявляет двенадцать пар «ресурс × глагол», три из них не дают
ничего. `EMPTY` означает, что не даёт ничего ни одна, — роль выглядит действующей и
не действует.

Счётчики говорят **сколько**, `withdrawnGrants` — **что именно и почему**. Без него
«право отобрали» со стороны читающего неотличимо от «права не было»: свою роль вы не
меняли, а действовать она перестала. `reason` — причина платформы, `withdrawnAt` —
момент; у всего, что отобрано одним изменением каталога, момент совпадает, поэтому по
нему собирается разом всё, что унесло одно снятие.

**Список пуст не всегда потому, что ничего не отбирали.** Он наполняется только тем,
что платформа сняла с обслуживания. У третьего пути потери — тип объявлен, а платформа
его не знает — отбирать было нечего, и список пуст при `health` не `HEALTHY`. Судить
по нему о здоровье роли поэтому нельзя: он объясняет счётчики, а не заменяет их.

**Порядок элементов не значим** — это набор. Сверяйте его по составу, а не по номеру
элемента.

### Что вырезано из правил: `prunedSelectorTypes`

`withdrawnGrants` отвечает про то, что адресуется парой «тип + глагол». Но правило
называет и **типы ресурсов** — без глагола, — и когда платформа снимает тип с
обслуживания, он вырезается оттуда же. Это второе поле, потому что событие второе:

```json
{
  "prunedSelectorTypes": [
    {
      "objectType": "compute.instances",
      "outcome": "SELECTOR_PRUNE_OUTCOME_SHORTENED",
      "reason": "не объявлен манифестом модуля compute",
      "prunedAt": "2026-09-03T13:15:44Z"
    }
  ]
}
```

`outcome` различает два исхода, и различие существенное: `SHORTENED` — правило
продолжает действовать, но на меньшем наборе типов; `DROPPED` — обслуживаемых типов
у правила не осталось, и оно не даёт **ничего**. Сложенные в одну величину, эти два
случая неразличимы, а решения по ним разные.

**Один тип может встретиться дважды с разными исходами** — если его называли два
ваших правила и одно из них лишилось последнего типа, а другое нет. А вот записи,
которые различались бы только тем, из какого правила вырезано, приходят **одной**:
какое именно из ваших правил это было, поле не сообщает, и повторять один и тот же
факт дважды оно не станет.

**Ваши правила при этом не менялись.** `rules[]` в ответе остаются ровно теми, что вы
записали: вырезание касается того, что платформа по ним обслуживает, а не вашего
объявления. Поэтому «правило перестало работать» и «правило исправлено» — разные
вещи, и вернуть тип в обслуживание правкой роли нельзя.

**Отбор по этому полю не поддерживается**, и синтаксиса для него нет: разбор
выражения `filter` знает равенство и вхождение, а «не равно» — не знает.

### Какое правило пострадало и почему: `ruleStates`

Счётчики роли говорят **сколько** сегментов перестало действовать. Два поля выше
говорят, **что именно** снято. Остаётся вопрос, на который не отвечает ни одно:
**какое из ваших правил** это задело — и по какой из двух причин.

Причин ровно две, и счётчики у них выглядят **одинаково**:

- **платформа сняла** то, на что правило ссылалось, — и записала это;
- **правило не разрешилось**: оно называет то, чего платформа не знает, и снимать
  было нечего, поэтому в `withdrawnGrants` о нём нет ни строки.

Без слова второе неотличимо от первого: список пуст, счётчик ненулевой, и «право
отобрали» читается ровно так же, как «права не было никогда».

```json
{
  "rules": [
    { "module": "vpc", "resources": ["network"], "verbs": ["get"] },
    { "module": "vpc", "resources": ["gateway"], "verbs": ["delete"] },
    { "module": "probe", "resources": ["thing"], "verbs": ["delete"] }
  ],
  "ruleStates": [
    { "ruleIndex": 0, "state": "RULE_LIFECYCLE_ACTIVE",
      "segments": 1, "lostSegments": 0, "explainedSegments": 0 },
    { "ruleIndex": 1, "state": "RULE_LIFECYCLE_WITHDRAWN",
      "segments": 1, "lostSegments": 1, "explainedSegments": 1 },
    { "ruleIndex": 2, "state": "RULE_LIFECYCLE_UNRESOLVED",
      "segments": 1, "lostSegments": 1, "explainedSegments": 0 }
  ]
}
```

Правило 1 — право у вас **отобрали**, и `withdrawnGrants` рядом называет чем и
почему. Правило 2 — оно ссылается на то, чего в платформе нет, и объяснения не
будет: разбирать надо **его**.

**Ключ — `ruleIndex`, номер правила в `rules`.** Порядок самих записей не значим:
это набор, сверяйте по ключу, а не по позиции. Записей всегда столько же, сколько
правил, — включая правила, которым терять нечего.

**Правило, у которого одна потеря объяснена, а другая нет, читается
`UNRESOLVED`** — слово называет то состояние, которое требует разбора. Состав при
этом виден: необъяснённых у него `lostSegments − explainedSegments`, и обе
величины стоят рядом со словом.

**Величины правила и счётчики роли — РАЗНЫЕ единицы, и потому названы по-разному.**
`declaredSegments` роли считает сегмент, названный двумя вашими правилами, **один
раз**; `segments` каждого правила — своё. Поэтому суммы совпадают не всегда, и
расходятся они ровно на таком сегменте — как в примере выше, где его нет и суммы
равны. Складывать их не надо: они отвечают на разные вопросы.

**Правило без адресуемых сегментов — `ACTIVE`.** Правило с `*` в модуле или в
ресурсе не называет имён, поэтому терять ему нечего, и его `segments` равен нулю.

**Пустой список означает два разных факта, и различает их `rules`.** У роли без
правил (унаследованной, заданной через `permissions`) он пуст потому, что
состояние есть свойство правила. У ответа `Create`/`Update` — потому, что не
вычислялся. Смотрите на `rules`, а не на длину этого списка.

**`ruleIndex` действителен в пределах одного ответа.** `Update` перестраивает
`rules` целиком, поэтому сохранять индекс между вызовами нельзя: адресуется роль
своим `id`, а правило — своим содержанием.

**Ревизии и автора у `WITHDRAWN` здесь нет.** Причина снятия и его момент
приезжают в `withdrawnGrants`, адресуемом той же парой «тип + глагол».

**`health` и `effectiveVerbs` отвечают на разные вопросы, и расходятся намеренно.**
`effectiveVerbs` говорит, что роль **обещает** по написанному; `health` — что по ней
**выдаётся на самом деле**. После снятия модуля первое не меняется, второе меняется;
у типа, которого платформа не знает, первое покажет весь словарь глаголов, а второе
будет `EMPTY`. Сложение их в одно утверждение даст неверный ответ в обе стороны.

<CodeBlock language="json">
  {dedent`
    {
      "id": "rolkw55v2z363gpqath1",
      "accountId": "acc2bkd71802av7dywa8",
      "name": "vpc-viewer",
      "description": "Read-only VPC networks",
      "permissions": [],
      "isSystem": false,
      "createdAt": "2026-06-24T10:15:00Z",
      "clusterId": "",
      "projectId": "",
      "rules": [
        { "module": "vpc", "resources": ["networks"], "verbs": ["get", "list"] }
      ],
      "resourceVersion": "8821",
      "createdByUserId": "usrb3n8q1x7wzk52pfeq",
      "updatedAt": "2026-06-24T10:15:00Z",
      "labels": {},
      "definitionTier": { "tierType": "iam.account", "tierId": "acc2bkd71802av7dywa8" },
      "authoredVerbs": ["get", "list"],
      "effectiveVerbs": ["get", "list"],
      "verbNotes": {},
      "displayName": "vpc-viewer",
      "purpose": "",
      "health": "ROLE_HEALTH_HEALTHY",
      "declaredSegments": 2,
      "unresolvedSegments": 0,
      "withdrawnGrants": [],
      "prunedSelectorTypes": [],
      "ruleStates": [
        {
          "ruleIndex": 0,
          "state": "RULE_LIFECYCLE_ACTIVE",
          "segments": 2,
          "lostSegments": 0,
          "explainedSegments": 0
        }
      ],
      "lifecycle": { "state": "ROLE_LIFECYCLE_STATE_DECLARED" }
    }
  `}
</CodeBlock>

Последние семь полей — **разбор**, и здесь он показывает здоровую роль: единственное
правило называет два сегмента (`vpc.networks` × `get` и × `list`), не потерян ни один,
отбирать и вырезать было нечего, модуль роль объявляет. Приходят они **всегда**, а не
«при беде»: пустые ведомости и нули — такое же утверждение, как непустые, и именно на
них опирается вызывающий, решая, что чинить нечего. У снятой роли `lifecycle` несёт
рядом `retiredAt`, `retiredReason` и `retiredBy`; у объявленной их нет.

У этой роли два набора глаголов совпадают — она ничего не редактирует. Расходятся они у
роли-редактора, и читать нужно `effectiveVerbs`: исполняется он. Роль `compute-operator`
из примера `Create` ниже несёт `update` и не несёт `delete` — значит она редактор, и к её
действующему набору добавлен производный `delete*`:

<CodeBlock language="json">
  {dedent`
    {
      "name": "compute-operator",
      "rules": [
        { "module": "compute", "resources": ["instances"], "verbs": ["get", "list", "update"] }
      ],
      "authoredVerbs": ["get", "list", "update"],
      "effectiveVerbs": ["get", "list", "update", "delete*"],
      "verbNotes": {
        "delete*": "co-materialized on in-scope leaf objects, NOT on the account/project anchor itself"
      }
    }
  `}
</CodeBlock>

Читается это так: оператор вправе удалить те машины, которые редактирует, но не сам аккаунт
или проект, в котором они лежат. Права на удаление ему никто не выписывал — оно следует из
права на изменение, и `verbNotes` называет, откуда взялось расхождение.

</ApiOperation>

### List — каталог ролей

<ApiOperation method="GET" endpoint="/iam/v1/roles">

Возвращает каталог ролей. Поддерживает `filter` (`is_system` / `name`) и `accountId`: при
заданном `accountId` ответ содержит system-роли (видны всегда) плюс custom-роли этого аккаунта.

<CodeBlock language="bash">
  {dedent`
    # только system-роли
    curl 'http://localhost:18080/iam/v1/roles?filter=is_system%3Dtrue' \\
      -H 'Authorization: Bearer <JWT>'
  `}
</CodeBlock>

</ApiOperation>

### Create — создать custom-роль

<ApiOperation method="POST" endpoint="/iam/v1/roles" async>

Создаёт custom-роль. Ровно один из `accountId` / `projectId` (XOR) — иначе `INVALID_ARGUMENT`.
Политика задаётся `rules[]`. Имя, совпадающее с system-ролью, → `ALREADY_EXISTS`. Требует
`editor` на аккаунте роли. Асинхронно (`response: Role`).

<CodeBlock language="bash">
  {dedent`
    curl -X POST 'http://localhost:18080/iam/v1/roles' \\
      -H 'Authorization: Bearer <JWT>' \\
      -H 'Content-Type: application/json' \\
      -d '{
            "accountId": "acc2bkd71802av7dywa8",
            "name": "compute-operator",
            "description": "Manage compute instances in prod project",
            "rules": [
              { "module": "compute", "resources": ["instances"], "verbs": ["get","list","update"] }
            ]
          }'
  `}
</CodeBlock>

</ApiOperation>

### Update — изменить custom-роль

<ApiOperation method="PATCH" endpoint="/iam/v1/roles/{role_id}" async>

Меняет `name` / `description` / `rules` / `labels` по `updateMask`. При изменении `rules`
обязателен `resourceVersion` (OCC под конкуренцией; mismatch → `FAILED_PRECONDITION`). Поля
`isSystem` / `accountId` / `projectId` / `clusterId` immutable. **System-роль → `FAILED_PRECONDITION`**.
Требует `v_update`. Асинхронно.

<CodeBlock language="bash">
  {dedent`
    curl -X PATCH 'http://localhost:18080/iam/v1/roles/rolkw55v2z363gpqath1' \\
      -H 'Authorization: Bearer <JWT>' \\
      -H 'Content-Type: application/json' \\
      -d '{
            "updateMask": "rules",
            "resourceVersion": "8821",
            "rules": [
              { "module": "vpc", "resources": ["networks","subnets"], "verbs": ["get","list"] }
            ]
          }'
  `}
</CodeBlock>

</ApiOperation>

### Delete — удалить custom-роль

<ApiOperation method="DELETE" endpoint="/iam/v1/roles/{role_id}" async>

Удаляет custom-роль. **System-роль → `FAILED_PRECONDITION`**. Custom-роль с активными
привязками → `FAILED_PRECONDITION` (сначала снять привязки). Требует `v_delete`. Асинхронно.

</ApiOperation>

### ListOperations — операции над ролью

<ApiOperation method="GET" endpoint="/iam/v1/roles/{role_id}/operations">

Возвращает операции над ролью. Sync. Требует `v_list`.

</ApiOperation>
