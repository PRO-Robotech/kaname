# Авторизация и каталог

Эта страница — **публичная проекция слоя авторизации**. Пока остальные ресурсы IAM управляют
*описанием* прав (роли, привязки), `AuthorizeService` отвечает на прямые вопросы *решения*: «может
ли этот субъект сделать X над Y?». Это policy decision point (PDP), которым пользуются UI (превью
доступности кнопок), SDK и admin-инструменты — не для гейтинга RPC (это делает внутренний
`InternalIAMService.Check`), а для явных tenant-facing запросов.

Рядом — `PermissionCatalogService`: грантабельная таксономия для редактора ролей.

:::info Subject-binding и защита от подглядывания
Обычный аутентифицированный вызов принимает субъект в форме `user:<usr…>` /
`service_account:<sva…>` / `group:<grp…>#member`. Обработчик проверяет право спрашивать
о **себе** либо о других субъектах как cluster-admin или администратор указанного
ресурса. Для запроса без удостоверения существует только описанная ниже
анонимная форма одиночного `Check`.
:::

## AuthorizeService

Все методы, кроме `WhoAmI`, — POST на `/iam/v1/authorize:*` и синхронны (это read-запросы к
решению доступа). Политика публичного слушателя проверяет вызывающего, а точное
per-subject/per-resource решение принимает обработчик.

### Check — одиночная проверка

<ApiOperation method="POST" endpoint="/iam/v1/authorize:check">

Возвращает `allowed=true`, если FGA-модель резолвит отношение между `subject` и `resource` **и**
все условия по пути резолюции истинны. Доводы о своей аутентификации из `context` не читаются —
их служба выводит сама (уровень — от края, способы и момент — из записи сессии вопроса; см.
«Условия на кортежах» в архитектуре прав). При отказе — `denyReasons` с коротким
упорядоченным списком (`["mfa_fresh: acr=2 (need 3)"]` или `["no path"]`).

<CodeBlock language="bash">
  {dedent`
    curl -X POST 'http://localhost:18080/iam/v1/authorize:check' \\
      -H 'Authorization: Bearer <JWT>' \\
      -H 'Content-Type: application/json' \\
      -d '{
            "subject": "user:usrbr69ze0ftz3jf7396",
            "resource": { "type": "vpc_network", "id": "net4h7q2xk9v0m3n5rst" },
            "action": "vpc.networks.get"
          }'
  `}
</CodeBlock>

<CodeBlock language="json">
  {dedent`
    {
      "allowed": true,
      "denyReasons": [],
      "checkedAt": "2026-06-24T10:30:00Z"
    }
  `}
</CodeBlock>

:::note Здесь стояло поле `authorizationModelId` — оно снято с контракта
Пример ответа показывал его, а разбор снятия стоял на этой же странице **84 строками ниже**.
Клиент читает пример как образец и пишет по нему разбор — разбор, который ждал бы поля, не
приходящего никогда. Противоречие в пределах одного документа обнаруживается только сплошным
чтением, то есть не обнаруживается.

Что снято и почему — [ниже](#retired-fields). В примере запроса тем же заходом исправлен
префикс идентификатора сети: там стоял `enp…`, а это префикс **операции** VPC, не сети.
:::

`action` — строка `<domain>.<resource>.<verb>`. Названное `requiredRelation` спрашивается
дословно. Без него сервер выводит отношение из каталога модуля: действие разрешается в
глагольное отношение `v_<глагол>` типа объекта (`resource.type`). Действие обязано относиться к
этому типу: имя ресурса, совпавшее с ключом каталога (`registry.repositories`), называет ровно
этот тип, а токен права (`vpc.networks`) принадлежит модулю, объявившему тип. Тип обязан
объявлять глагол; иначе ответ — отказ. Ответ поэтому не шире выданного: выданный `get` не
отвечает «да» на вопрос о `list`. Опциональный
`context` (`google.protobuf.Struct`) несёт атрибуты самого запроса для вычисления условий на
кортежах. Ключи, описывающие аутентификацию, соединение или время, — `acr_value`, `amr_claims`,
`mfa_at`, `client_ip`, `source_ip`, `device_attestation`, `valid_until`, `current_time` — из
`context` **не читаются**: присланное вызывающим значение отбрасывается, служба подставляет то,
что выводит сама (время — свои часы, уровень — от края, способы и момент — из записи сессии
вопроса). Чего служба вывести не может, остаётся отсутствующим, и зависящее от него условие
ложно (см. [Условия на кортежах](/architecture/authz#условия-на-кортежах)).

</ApiOperation>

### Анонимная проверка своего доступа

На прямом публичном REST-входе `POST /iam/v1/authorize:check` запрос без заголовка
`Authorization` может передать только `resource` и `action`, не задавая `subject`,
`context` и `requiredRelation`. Сервер сам выбирает `system_class:anonymous` и
передаёт вопрос обычному решателю прав. Например:

```json
{"resource":{"type":"registry_repository","id":"<registryId>/app"},"action":"registry.repositories.get"}
```

Отношение вопроса сервер выводит из каталога модуля так же, как любому вопросу без
`requiredRelation` (см. выше): глагольное отношение `v_<глагол>` типа объекта; глагол,
не объявленный типом, — отказ.

Такой вызов не создаёт выдач прав и не изменяет ресурс. `allowed` зависит от
существующих выдач для анонимного субъекта; отсутствующая выдача остаётся отказом.
Назвать другого субъекта или перечислить его права этим способом нельзя.
Любой предъявленный заголовок `Authorization`, включая пустой, негодный,
истёкший или отозванный, исключает переход на анонимную полосу. Обычный
аутентифицированный запрос по-прежнему называет своего субъекта явно.
Это исключение относится только к одиночному `Check`, не к `BatchCheck`,
перечислению субъектов, потокам или мутациям.

### BatchCheck — пакет проверок

<ApiOperation method="POST" endpoint="/iam/v1/authorize:batchCheck">

До 100 проверок в одном RPC (иначе `INVALID_ARGUMENT`). Сервер разворачивает их конкурентно;
порядок результатов совпадает с порядком `checks`. Пофайловая ошибка (например, malformed subject)
даёт `allowed=false` с per-item `denyReasons`, но не валит весь пакет. Удобно для UI, оценивающего
доступность многих действий разом.

</ApiOperation>

### ListObjects — СНЯТ с контракта

Глагол `ListObjects` и его маршрут `/iam/v1/authorize:listObjects` **сняты**. Номер и имя в
контракте зарезервированы; вызов маршрута возвращает `404`.

Он существовал ради перечисления объектов внешним движком отношений и наследовал две его границы,
о которых приходилось предупреждать вызывающего: **продолжения не было вовсе** (курсора у
перечисления в движке нет, поэтому непустой `pageToken` отвергался, а `nextPageToken` всегда
приходил пустым), а серверный потолок движка лежал ниже любого `maxResults` и снять его было
нельзя — то есть объект сверх потолка становился невидим при живых правах.

Ни движка, ни этих границ больше нет. Перечисление доступного — **внутренний путь списочных
обработчиков**: каждый `List` ресурса отдаёт страницу, отфильтрованную по видимости, курсором и с
работающим `nextPageToken` (см. [Модель авторизации](/architecture/authz)).
Отдельного публичного глагола для этого не требуется.

### ListSubjects — кто имеет доступ к ресурсу

<ApiOperation method="POST" endpoint="/iam/v1/authorize:listSubjects">

Возвращает всех субъектов с `action` на данном ресурсе (виджет «кто имеет доступ»).
Размер страницы — по правилу платформы: `pageSize` в `[0..1000]`, `0` — умолчание 50;
значение вне диапазона отвергается `INVALID_ARGUMENT` с нарушением поля `page_size` (раньше
проверки прав вызывающего). Опциональный `subjectTypeFilter`.

</ApiOperation>

### ExpandRelations — из чего складывается право

<ApiOperation method="POST" endpoint="/iam/v1/authorize:expandRelations">

Возвращает субъектов, у которых разрешается `relation` на данном ресурсе, — то есть **основания**
права. Используется инструментами аудита, чтобы объяснить решение «почему разрешено» или «почему
отказано».

**Ответ одноуровневый: перечень, а не дерево.** Основание права в Kaname — плоская запись: прямой
факт, выдача роли на область, выдача по меткам либо членство в группе. У плоской записи не бывает
глубины, поэтому спускаться не во что и ограничивать нечего.

```json
{
  "resource": { "type": "project", "id": "prj7mfpj2my52k5a06kg" },
  "relation": "viewer",
  "tree": {
    "leaves": ["user:usrbr69ze0ftz3jf7396", "group:grpq3v8z1w6k0dn2yfhs#member"],
    "truncated": false
  }
}
```

`truncated` — единственный сигнал «перечень обрезан серверным пределом»; вызывающий, который его
игнорирует, примет префикс за полный набор.

### Что снято с контракта {#retired-fields}

:::note Что снято с контракта и почему это не урезание
Это **свойство источника**, а не понижение возможностей:

- **графовые рёбра** (`computed`, `tuple_to_userset`) описывали спуск в под-множества графа
  отношений. Заполнить их нечем — записи, из которой такое ребро выводилось бы, не существует.
  Номера и имена зарезервированы;
- **`maxDepth`** ограничивал глубину спуска, пока ответ был деревом. Для одноуровневого ответа
  глубина не определена, и поле не читал бы никто. Принять число, на которое сервер не смотрит,
  значило бы обещать ручку, которой нет, — поэтому оно снято, а не игнорируется молча;
- **`authorizationModelId`** нёс версию модели, которую чеканил внешний движок для копии в своём
  хранилище. Движка нет, чеканить некому, и поле отвечало бы всем постоянной пустой строкой.
  **Сама модель прав никуда не делась** — она остаётся источником, из которого выводится проверка;
  не стало версии хранилища, которого нет.

Имя типа `UsersetTree` осталось историческим: менять его значило бы ломать форму на проводе ради
названия. Форма — перечень.
:::

</ApiOperation>

### WhoAmI — кто я и что вижу

<ApiOperation method="GET" endpoint="/iam/v1/me">

Возвращает личность вызывающего и снимок прав: `subject`, `userId`, `email`, `displayName`,
флаги `systemAdmin` / `clusterViewer` и `accounts[]` (членство в аккаунтах с грубой ролью). Любой
аутентифицированный принципал вызывает WhoAmI на себя (субъект берётся из auth-контекста, не из
тела). Ответ per-request свежий (без кэша), намеренно грубый — полный per-RPC гейтинг всё равно
делает middleware. Анонимный вызов → `UNAUTHENTICATED`.

<CodeBlock language="json">
  {dedent`
    {
      "subject": "user:usrbr69ze0ftz3jf7396",
      "userId": "usrbr69ze0ftz3jf7396",
      "email": "dev@acme.example",
      "displayName": "Dev One",
      "systemAdmin": false,
      "clusterViewer": true,
      "accounts": [
        { "accountId": "acc2bkd71802av7dywa8", "accountName": "acme", "roles": ["editor"] }
      ],
      "checkedAt": "2026-06-24T10:30:00Z"
    }
  `}
</CodeBlock>

`accounts[]` отвечает на вопрос **«что мне доступно»** и объединяет три источника — членство,
владение, привязку с областью на аккаунт — в одну строку на аккаунт. Владение в ней видно:
у аккаунта, которым вы владеете (личного, который завела регистрация, и заведённых вами
`Create`), роли содержат `owner`; у аккаунта, куда вас позвали, — нет. Следа приглашения — **кто** и
**когда** — здесь нет: он читается на своём списке членств,
[`MembershipService.ListMine`](/api/membership#list-mine).

</ApiOperation>

## PermissionCatalog

`PermissionCatalogService` отдаёт **грантабельную таксономию** для редактора правил роли: какие
`(module, resource)`-токены можно грантить, каков закрытый набор глаголов и wildcard-политика.
Каталог зеркалит ground-truth backend'а — «не больше и не меньше», поэтому редактор ролей строится
на нём, а не на захардкоженной копии.

### ListPermissionCatalog

<ApiOperation method="GET" endpoint="/iam/v1/permissionCatalog">

Возвращает всю таксономию одним sync-чтением (без параметров: каталог — одна платформенная
таксономия, растёт только с релизом backend'а). Доступен любому аутентифицированному вызывающему.

<CodeBlock language="json">
  {dedent`
    {
      "modules": [
        {
          "module": "iam",
          "resources": [
            { "resource": "role", "hasVerbRelations": true, "hasListEndpoint": true, "labelSelectable": true,
              "verbs": ["list", "update", "delete"] },
            { "resource": "user", "hasVerbRelations": true, "hasListEndpoint": true, "labelSelectable": true,
              "verbs": ["get", "list"] }
          ]
        },
        {
          "module": "vpc",
          "resources": [
            { "resource": "network", "hasVerbRelations": true, "hasListEndpoint": true, "labelSelectable": true,
              "verbs": ["get", "list", "update", "delete"] },
            { "resource": "securityGroup", "hasVerbRelations": true, "hasListEndpoint": true, "labelSelectable": true,
              "verbs": ["get", "list", "update", "delete"] }
          ]
        }
      ],
      "closedVerbs": ["list"],
      "wildcardPolicy": {
        "verbWildcardAllowedCustom": true,
        "moduleResourceWildcardSystemOnly": true
      },
      "retiredResources": [
        { "resource": "compute.disk", "supersededBy": "storage.volumes" },
        { "resource": "compute.image", "supersededBy": "storage.images" },
        { "resource": "compute.snapshot", "supersededBy": "storage.snapshots" }
      ]
    }
  `}
</CodeBlock>

Каждый `CatalogResource` несёт editor-флаги: `hasVerbRelations` (verb-bearing leaf vs
tier-only ancestor), `hasListEndpoint` (есть ли публичный filtered `List` — тогда пикер id
рендерит Select видимых экземпляров, иначе — free-text), `labelSelectable` (можно ли применять
`matchLabels`) — и **`verbs`: глаголы, которые правило роли вправе назвать на ЭТОМ ресурсе.**

`verbs` — это источник выпадающего списка глаголов, а не `closedVerbs`. Набор глаголов
принадлежит ТИПУ: `loadbalancer.targetGroups` несёт сверх обычного `addTargets` и
`removeTargets`, `registry.registries` — `create`, а у `iam.user` сняты оба
распоряжающихся глагола, `update` и `delete`: правку записи, запрет и снятие самой строки
личности спрашивают отдельные отношения, и выдать их нельзя — они вычисляемые. На этом
ресурсе правило вправе назвать только `get` и `list`. У `iam.role` нет `get`: прочесть роль
по идентификатору позволяет то же право, что и её перечень, — `list`. `closedVerbs` —
ПЕРЕСЕЧЕНИЕ наборов всех типов: оно отвечает на вопрос «что даёт любой ресурс» и по мере
расхождения наборов сужается (в примере выше — до `list`), поэтому строить из него список
нельзя ни в одну сторону. Правило, назвавшее
глагол вне набора своего типа, не даёт на нём ничего — материализация сверяется с тем же
набором.

### `retiredResources` — что платформа сняла и что назвать вместо

Правило роли, назвавшее снятый ресурс, отвергается синхронно:

```
INVALID_ARGUMENT
type compute.disk is retired (no resource of this type exists;
retired resources and their successors are published by GET /iam/v1/permissionCatalog)
```

Отказ называет тип и говорит, где узнать замену, но **саму замену не называет** — и это
не упущение: отказ приходит из прерванной транзакции, в которой чтения нет. Замену
отдаёт этот же каталог, тем единственным вызовом, на который отказ и указывает.

`retiredResources` — **не перечень грантуемого**. Взяв имя оттуда, правило вы не создадите:
отказ будет тем же. Перечень отвечает ровно на один вопрос — «что назвать вместо».

- `resource` — точечное имя снятого, в той же форме, какой его называет отказ;
- `supersededBy` — точечное имя **живого** ресурса взамен. Оно всегда есть в `modules[]`
  **этого же ответа**, поэтому набор глаголов замены спрашивайте там;
- `supersededBy` **пусто** — значит замена не назначена: ресурс снят, а преемника у него
  нет. Это не то же самое, что отсутствие записи: записи нет у ресурса, которого платформа
  не знала никогда.

Догадываться по имени не следует: написания намеренно не единообразны
(`compute.instance` в единственном числе, `storage.volumes` во множественном), поэтому
догадка ошибается ровно там, где нужна.

</ApiOperation>

## Латентность и коды

- Бюджет `Check` — ≤ 30 ms p95; `BatchCheck` линеен по размеру пакета.
- Недоступность базы IAM на пути запроса → `UNAVAILABLE` (fail-closed).
- Cross-tenant запрос про чужого субъекта → `PERMISSION_DENIED` (gateway) либо отфильтрован в
  handler'е.

:::tip Check ≠ гейтинг RPC
`AuthorizeService.Check` — для UI-превью и SDK-хелперов. Реальный per-RPC гейтинг сервисов делает
внутренний `InternalIAMService.Check` (порт :9091, mTLS) — см. [Авторизация](/architecture/authz).
:::
